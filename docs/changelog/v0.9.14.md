## Summary

_In development._ Engine QA continuation — follow-up branch to the v0.9.13 QA pass; continues working through the §10 task matrix in `docs/research/0.9.13-QA-improvements.md`.

## Changes

### Engine QA Pass — FPS Console Commands Relocation [CHANGED]

- **`connect`, `disconnect`, `demo`, `demolist`, `demoplay`, `netsim` commands moved to fps submodule** - the six fps-coupled commands that used to live in `src/engine/console/commands/` and import from `src/games/fps/*` now live inside the fps submodule at `src/games/fps/console/commands/`. The engine repo's console-commands directory no longer has any imports from the fps submodule.
- **New `registerFpsCommands()` hook** - mirrors the engine's `registerEngineCommands()` (Vite glob over `*Command.ts` with eager registration on `CommandRegistry`). Exported from the fps submodule's top-level `index.ts`.
- **`src/main.ts` wiring** - after `registerEngineCommands()`, the app now dynamically imports the fps module and calls `registerFpsCommands()` so the six commands join the shared `CommandRegistry`.
- **Headless intentionally unchanged** - `src/cli/headless-game.ts` doesn't currently exercise the moved commands, so it stays free of the fps coupling. A future headless workflow can opt in by calling `registerFpsCommands()` the same way `main.ts` does.

### Engine QA Pass — Type And Lint Cleanup [FIXED]

- **`noImplicitAnyLet` finished in non-jewel files** - typed the 17 remaining lazy-import lets across 11 console-command files. Each gets a type-only `import type` (erased at compile time, preserves the dynamic-import semantics that support headless mode) plus an explicit annotation. Special case in `JoinCommand`: four lets including `let FPSController: typeof FPSController` (self-referential shadow) — resolved by aliasing the type imports (`FPSControllerClass`/`FreeflyControllerClass`). `PK3Command` also picked up a `TS7006` once the surrounding implicit-any was fixed, annotated explicitly. Biome errors **39 → 22 (-44%)**.

### Engine QA Pass — Test Surface [ADDED]

- **`SpawnValidator` smoke coverage (CI guard for downstream submodules)** - `SpawnValidator` has zero in-repo callers but is a public engine API consumed by downstream SHAG game submodules (e.g. the isometric building project). Adds `src/engine/__tests__/SpawnValidator.test.ts` with 22 tests across 6 groups: singleton + defaults, register/unregister routing, validate() global ordering + short-circuit + named-validator dispatch + missing-id warning, disable/enable collision check, the built-in `CollisionValidator` (allow when empty, deny on prefab overlap, skip non-prefab/trigger meshes), and the example `ResourceCostValidator` + `MaxCountValidator`. No Babylon scene is constructed — tests use a minimal mock cast through `unknown` to `Scene`.

- **`FPSPickup` static-registry tests relocated to the fps submodule** - the 16 tests originally added in v0.9.13 lived at `src/engine/__tests__/Pickup.test.ts` and used a `FPSPickup as Pickup` import. Now that the engine-generic / FPS-specific split has settled, the tests follow the class to `src/games/fps/world/__tests__/FPSPickup.test.ts`. The outer `npm test` already discovers tests under `src/games/fps/**`, so the test count is unchanged; the file just moved.

### Engine QA Pass — ConnectingOverlay Decoupling [CHANGED]

- **`ConnectingOverlay` no longer imports `Game`** - the engine-shipped lobby overlay used to reach directly into the fps submodule's `Game.getInstance()` to start a network connection. It now consults a registered `NetworkConnector` interface and falls through to a clear "NO NETWORK ADAPTER" error state if none is registered.
- **New `NetworkConnector` interface + single-slot registry** - `src/engine/ui/components/NetworkConnector.ts` exports a two-method `NetworkConnector` interface (`isConnected`, `connect`) and a tiny registry (`registerNetworkConnector` / `getNetworkConnector` / `clearNetworkConnector`).
- **FPS adapter implementation** - the fps submodule provides `FpsNetworkConnector` (in `src/games/fps/client/FpsNetworkConnector.ts`) wrapping `Game.getInstance()`; `src/main.ts` registers it at boot after `registerFpsCommands()`.

### Engine QA Pass — LobbyPanel Relocation [CHANGED]

- **`LobbyPanel.ts` (1327 LOC) and its two stylesheets moved to the fps submodule** - the engine-positioned lobby panel imported four fps modules directly (`DemoService`, `DemoViewer`, `DurationPickerModal`, `FPSSettingsView`) and its only outer-repo caller (`src/main.ts`) is already fully fps-aware. Cleaner to move the whole panel than introduce four DI seams just to keep the file nominally in engine — the panel's design genuinely is FPS-shaped (MATCHMAKING / LEADERBOARD / MY PROFILE tabs for the FPS gametype). The companion CSS files (`LobbyPanel.css`, `DemoTab.css`) followed.
- **`src/main.ts` import path** updated from `./engine/ui/panels/LobbyPanel` to `./games/fps/client/LobbyPanel`.
- **`src/engine/ui/panels/` still contains** the engine-generic `GamePanel.ts` (the base class that both `LobbyPanel` and the fps `FPSPauseMenu` extend).

### Engine QA Pass — ServiceLocator Audit [FIXED]

- **`ServiceLocator.dispose()` is now resilient** - each individual `service.dispose()` call is wrapped in a try/catch with a `console.warn`. A throwing service can no longer block the rest of the reverse-order tear-down loop.
- **`EngineScene.dispose()` now sweeps via `ServiceLocator.dispose()`** at the end (just before `scene.dispose()`). The existing explicit manual disposes (`PostProcessingManager`, `SkyLightSystem`, `StreetLampSystem`) stay first — they're idempotent (each uses `?.dispose()` + null-out) — but the sweep now picks up the services the manual list missed (`ProceduralTextureGenerator`, `ModelLoader`, `SpriteBuildingManager`, the proper `WorldIndicatorSystem.dispose()` instead of `clearAll()`, etc.). Also replaces the in-method dynamic-import of `ServiceLocator` with a top-level static import.
