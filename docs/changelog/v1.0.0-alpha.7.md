# v1.0.0-alpha.7

**Release Date:** unreleased — living changelog

## Changes

- Rendering: on WebGPU, the first seconds after a map appears no longer
  stutter. Each material's render pipeline was built the first time it came
  into view, and the browser compiled it before the frame could finish: on
  washoi_dm5 about 105 pipelines in the first seconds of play, frames of up to
  2.4 s and 5–7 fps for two seconds. The loading screen now draws the whole map
  once and waits for the GPU, which adds 0.8–2.8 s to loading on the tested
  maps; play opens at 62–74 fps. Babylon also gave every material a second
  pipeline once a player outline had been drawn over a transparent surface,
  because a stencil mask that nothing reads stayed in its pipeline key. The
  mask is now reset when stencil is off. WebGL2 is unchanged.

- Rendering: additive map sprites (halos, coronas, glows) that share a texture
  draw as one mesh with one vertex upload a frame, instead of one each.
  washoi_dm2's 62 sprites draw from 4 meshes, washoi_dm5's 76 from 42. Frames
  aimed at sprites match before and after on WebGL2 and WebGPU. Alpha-blended
  sprites, whose look depends on draw order, keep a mesh each.

- Rendering: the first-person weapon camera no longer evaluates every mesh in
  the scene to draw the handful of weapon meshes it can see. The layer filter
  that did this, on by default only in Firefox, is now on in every browser and
  on WebGPU: on washoi_dm5 the weapon camera's mesh selection fell from about
  1.0 ms to 0.15 ms a frame on WebGL2 and from about 0.55 ms to 0.09 ms on
  WebGPU, with identical pixels. `r_weapon_candidates 0` turns it off for
  diagnostics.

- Rendering: WebGPU now submits frames through render bundles (Babylon's
  non-compatibility mode) by default instead of only with `?ncm=1`. When the
  CPU is the limit, frames were 9–14% faster than before in throttled tests
  on washoi_dm5, with matching pictures. Water skips its occlusion query in
  this mode. `?ncm=0` turns it off for a session.

- Fix (WebGPU): after a few map changes the world could stop drawing, every
  frame rejected with "buffer binding is too small", or a draw threw on a
  missing light texture. Frozen world surfaces were re-checked when their
  lights changed, but not when only the lights' order changed, and Babylon
  re-sorts every surface's lights whenever any light is added, even a model's
  own. A surface then bound one light's data where its shader expected
  another's. The check now follows each world surface's lights in order. The
  dm5 → dm2 → amphi1 → dm11 sequence that failed now runs without errors.
