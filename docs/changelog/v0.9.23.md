# v0.9.23

**Release Date:** unreleased — living changelog

## Summary

v0.9.23 makes BSP geometry move. `func_plat` and vertical `func_door` are
simulated, collided, predicted, heard, and will crush whoever blocks them —
brought in as one fixed-step system shared by the server, client prediction and
single-player, so a rider is carried by the same code everywhere.

Reaching for that exposed a larger one underneath: hit registration had never
been lag-compensated. `LagCompensation` had existed since v0.9.0 but was wired
only into a CLI harness, so every shot on the live server resolved against the
present. It now rewinds to the view the shooter actually had — using a tick the
client was already reporting and the server was already throwing away.

Both halves needed instruments that did not exist. `npm run test:lifts` walks
every lift on every installed map and fails if one cannot be called; that found
four dead lifts on wctf6. `npm run net:viewlag` holds frames in both directions
over a real socket and reports the lag the server observes; that found the
interpolation assumption double-counting on its first run. Ping, which had read
0 for every player since the field was introduced, is measured as well.

## Changes

### Lifts and movers

Moving BSP geometry — `func_plat` and vertical `func_door` (`angle` `-1`/`-2`) — is
now simulated, collided, predicted and heard.

- **Moving brush collision.** Lift brushes and faces are pulled out of the static
  world and traced as inline models at their live offset, so there is no ghost
  collision left behind at the authored stop. `pointContents` moves with them.
- **Shared simulation.** One fixed-step `LiftSystem` (`src/shared/bsp/LiftSystem.ts`)
  runs on the server, in client prediction and in single-player, so a rider is
  carried by the same code everywhere. No wall-clock timers.
- **Riders.** Bodies standing on a lift are carried; a jumping player detaches; a
  blocked move rolls back the whole step rather than crushing. Corpses and dropped
  weapons ride too, but cannot call a lift or hold one open.
- **Callers.** `trigger_multiple`, `trigger_once` and `func_button` all activate a
  targeted lift, and caller bounds honour the caller's own `origin`.
- **Sound.** Movers play their authored `noise_start`/`noise_stop` (falling back to
  the stock door/elevator one-shots) positionally, driven off shared state — so a
  lift another player called is heard when it departs and when it arrives.
- **Networking.** Full mover state ships in every snapshot as `lift_state`, binary
  encoded, and is restored before reconciliation.
- **Crush damage.** A mover blocked by a body deals its authored `dmg` (default 2)
  and reverses, exactly as Q3's `Blocked_Door` did — unless the CRUSHER spawnflag is
  set, in which case it keeps pushing. Damage is held at Q3's 20 Hz cadence so
  lethality does not scale with our tick rate. Corpses and items block but are not
  hurt.

### Lag-compensated hit registration

Hitscan resolved against the present on the live server — no rewind of any kind — so
a moving target got harder to hit the worse your connection was. `LagCompensation`
had existed since v0.9.0 (2026-01-31) but was never instantiated outside
`src/cli/server-game.ts`; `GameServer` never touched it.

Rewind is keyed off the **view tick the client already reports**, not a ping:

- Every usercmd already carried `tick` — the last snapshot the client had processed
  (`Game.ts` sets it from `NetworkGameHost.currentTick`). It was encoded, sent and
  decoded, and then dropped by `sanitizeCommand` before reaching the simulation. It
  now flows through to the input component as `viewTick`.
- This needs no protocol change, makes no assumption that a connection is equally
  slow in both directions, and is checkable: a client claiming a tick beyond the
  server's own is clamped on arrival, and a claim reaching further back than the
  compensation budget gets the budget's edge and no more.
- The earlier plan — have the client report its RTT — was dropped as strictly worse
  on all three counts.
- **Ping is now measured, and the scoreboard works.** It read 0 for every player
  because `connection.latency` was declared `= 0` on both transports and assigned
  nowhere; the server answered `Ping` but timed nothing. The server now times its
  own snapshot against the ack that comes back for it, smoothed, entirely from its
  own clock — no client-reported number. Measured at 0.3ms on loopback and 216ms
  against an injected 200ms round trip. It reads slightly above pure network RTT
  because it is the game loop's round trip, including the client's snapshot
  processing, which is the number that actually governs how the game feels.
- `GameServer` now owns a `LagCompensation` with a **100ms** maximum rewind, and
  records history right after the simulation step.
- The client renders remote players *behind* its newest snapshot, so that lag comes
  off the rewind too. The server **assumes** that interval rather than being told
  it: `cl_interp` is a client cvar, and a value the client chooses is a value a
  cheater inflates to be judged ever deeper in the past.
- **A latency harness, because none of this is observable at 0ms.** Frames are now
  held in both directions over a real socket, so the rewind can be measured instead
  of reasoned about (`npm run net:viewlag`, plus a regression suite). It found the
  interpolation assumption immediately: the server already sees **~32ms of view lag
  at zero network latency** from snapshot quantisation and queueing, and
  `SnapshotBuffer` settles on `avg + stddev` of arrival intervals — *one* interval
  plus jitter, not two. Assuming two double-counted it and handed a LAN player ~65ms
  of rewind, shooting people well after they reached cover. Corrected to one.
- Collapsed the three rewind presets (`CASUAL`/`COMPETITIVE`/`TOURNAMENT`) into one
  `LAG_COMPENSATION`. Nothing selected between them at runtime — two call sites each
  hardcoded a different one — and `allowAbilityOverride` was a config flag no code
  had ever read. Rewind budget is a fairness decision that should be the same
  everywhere, not a per-match knob.
- `WeaponSystem` resolves each trigger pull against where the shooter actually saw
  the world: target positions *and* mover geometry are rewound together, so a plat
  that has since risen cannot retroactively block a shot that was clear.
- History is compact by design — player positions and mover offsets per tick, not a
  deep `WorldState` clone, which would have meant cloning every entity 125×/second.
- Existing hit math is untouched. With no history wired (unit tests, headless), the
  trace behaves exactly as before.

Fixed along the way:

- Reconciliation was being skipped for every map containing a lift. `lift_state` is
  present in *every* snapshot on such a map, so the guard added for movers silently
  disabled the ledge-grab and wall-jump reconcile-skip almost everywhere. Mover state
  now restores ahead of the guard, and the guard is back to its original condition.
- Caller volumes ignored the caller entity's `origin`, so a trigger built around an
  origin brush was placed wrong.

### Gameplay

- **An empty gun says so, and then gets out of your way.** Pulling the trigger with
  no ammo used to fall through every branch and do nothing — the only feedback was
  a HUD banner you have to read mid-fight. Now the first pull plays the empty click
  (`sounds/weapons/weapon_noammo.ogg`, shipped but never referenced until now), and
  a *second* pull — or simply holding the trigger for ~200ms — swaps to the next
  owned weapon that can actually fire, wrapping in slot order with the starter
  weapon as the backstop.

  The two-stage shape is the point: swapping on the first pull would tear you off
  your rocket launcher for one mistimed tap. First pull reports, second pull (or a
  held trigger) acts.

  The click is played client-side from the same ammo derivation that already drives
  the out-of-ammo crosshair, so it lands on the press instead of a round trip later.
  It claims nothing happened, unlike a muzzle flash, so a mispredicted one costs
  nothing. The swap itself stays server-authoritative.

### Fixes

- **Quad survived death.** Powerups were cleared in `respawnPlayer`, not on the
  kill, so a corpse kept the carrier glow for the whole death screen — and every
  other player went on seeing the quad as live on the body. Now cleared the moment
  the kill lands, which is also what Q3's `player_die` does. The first-person
  weapon outline was already correct (the `death` event drops the local timers);
  it was the server-sent powerup mask, which drives the body glow, that went stale.
  Side effect, and the Q3 behaviour: a rocket fired before dying that lands after
  no longer gets the multiplier, since it reads the attacker's powerups at damage
  time.

## Technical Notes

- Lift state is clamped and validated on restore — a packet can move a known mover,
  never invent one.
- `lift_state` is a fixed binary record (count, then per lift: `uint16` model index,
  `float32` offset, `uint8` phase, `float32` remaining, cooldown list). This replaces
  a JSON blob that cost ~377 B/snapshot on a four-lift map (~11 KB/s per client at
  30 Hz).
- Phase indices are positional on the wire — append only.
- Fire-once callers are modelled as a large finite cooldown rather than extra state,
  so they survive serialization unchanged.
- Movers are parented to the map's world mesh, so map unload disposes their meshes,
  materials and render observers.
- `LiftSystem.step` returns the bodies it squashed rather than dealing damage
  itself; the shared simulation core stays out of the business of hurting anyone,
  and client prediction simply discards the result.
- Rewind history is pruned on a tick window and dropped wholesale if the tick count
  ever moves backwards, so a match restart cannot strand old entries.

## Known Unverified Items

- Nothing here has been exercised in a real browser session yet. Headless coverage
  only: mover audio mix levels, how a ridden lift feels under real latency, and how
  lag-compensated hit registration feels to both shooter and target all need play
  testing. Rewind is the change most likely to need tuning — `maxCompensationMs`
  is 100ms, and it is now a single number for every server rather than a preset.
- **The interpolation assumption is measured at the server, not the client.** One
  snapshot interval matches `SnapshotBuffer`'s steady state, but that buffer adapts
  up to 150ms under jitter, and the server cannot see a given client's actual value.
  A jittery connection therefore gets slightly under-compensated — deliberate, since
  erring high punishes the player who took cover. Confirming this needs the client's
  real `interpDelay` reported as **telemetry only**, never fed back into the rewind.
- Only hitscan is rewound. Projectiles still spawn against the present.
- A client that reports a stale view tick is clamped to the 100ms budget, so the
  most a dishonest one can buy is the same rewind a genuinely lagged player gets.
- `func_button` is activated by touch. Shootable buttons (`health` key) are not wired,
  and the button brush itself does not visually depress.
- Crush damage is applied server-side only; single-player local mode (`MovementSystem`)
  discards the crush events since that path has no combat system.
- Other mover classes — `func_train`, `func_bobbing`, rotating and horizontal doors —
  are still unhandled; horizontal `func_door` continues through the existing handler.
- The physics probe warning in `npm run test:physics` ("Y position changed
  significantly") is pre-existing and unrelated: verified identical on a clean
  pre-lift baseline. It is a naive heuristic in the CLI that expects a falling probe
  to hold its height.
