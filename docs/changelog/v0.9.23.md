# v0.9.23

**Release Date:** unreleased — living changelog

## Summary

v0.9.23 makes BSP geometry move. `func_plat` and vertical `func_door` are
simulated, collided, predicted, heard, and will crush whoever blocks them —
brought in as one fixed-step system shared by the server, client prediction and
single-player, so a rider is carried by the same code everywhere.

Reaching for that exposed a larger one underneath: hit registration had never
been lag-compensated. `LagCompensation` had existed since v0.9.0 but was wired
only into a CLI harness, so every shot on the live server resolved against the
present. It now rewinds to the view the shooter actually had — using a tick the
client was already reporting and the server was already throwing away.

Both halves needed instruments that did not exist. `npm run test:lifts` walks
every lift on every installed map and fails if one cannot be called; that found
four dead lifts on wctf6. `npm run net:viewlag` holds frames in both directions
over a real socket and reports the lag the server observes; that found the
interpolation assumption double-counting on its first run. Ping, which had read
0 for every player since the field was introduced, is measured as well.

Alongside that, a round of feel work: an empty gun now clicks and trades itself
for one that fires, field of view is a setting rather than a constant, and the
quad stops glowing on a corpse.

A playtest with seven bots then turned into a bug hunt, tracked in
`docs/research/v0.9.23-bughunt.md` and worked item by item. It turned out to be
mostly about other players: they were the only bodies in the map exempt from
culling, they were dead-reckoned through walls whenever a packet arrived late,
they shared a single skeleton between them, and the trail on the rocket you
fired at them collapsed to a flat sliver in the one case that matters — shooting
along the axis you are looking down.

The renderer then got its own pass, nearly all of it about drawing less: the
world is culled by its compiled PVS, players are culled and quieted along with
it, and autosprites stop rewriting vertices nothing moved. The one experiment
that did not survive contact with a browser was spatial batching — it cuts
triangles by a third to a half and costs about 20% more frame time, so
`r_bsp_cellsize` stays off with 36 captures behind the decision instead of
caution.

One thing was added rather than trimmed. Every impact in the game drew a fading
triangle and a point light — the same for a machinegun round as for a rail slug,
on every surface. Shots spark on contact now, tiered so that what fires on every
shot stays quiet and the flourish is kept for weapons that hit once and hard.

Networking then got the same treatment the renderer had: an audit rather than a
feature. Snapshots turned out never to say which state they were deltaed
against, so a dropped datagram — or merely an ACK still in flight, with nothing
dropped at all — could leave a component silently wrong until it changed again.
That is fixed at the protocol level, along with a set of replay bugs that shared
one shape: something that should have been a function of *which* simulation step
this is was instead counted per call, and reconciliation counts the same steps
more than once. The leading theory going in — that reconciliation fails to
restore hidden movement state — first looked refuted, until a review measured
every step instead of the last one. And knockback drag, which the client was
believed to predict, turned out never to run on a live client at all.

## Changes

### Lifts and movers

Moving BSP geometry — `func_plat` and vertical `func_door` (`angle` `-1`/`-2`) — is
now simulated, collided, predicted and heard.

- **Moving brush collision.** Lift brushes and faces are pulled out of the static
  world and traced as inline models at their live offset, so there is no ghost
  collision left behind at the authored stop. `pointContents` moves with them.
- **Shared simulation.** One fixed-step `LiftSystem` (`src/shared/bsp/LiftSystem.ts`)
  runs on the server, in client prediction and in single-player, so a rider is
  carried by the same code everywhere. No wall-clock timers.
- **Riders.** Bodies standing on a lift are carried; a jumping player detaches; a
  blocked move rolls back the whole step rather than crushing. Corpses and dropped
  weapons ride too, but cannot call a lift or hold one open.
- **Callers.** `trigger_multiple`, `trigger_once` and `func_button` all activate a
  targeted lift, and caller bounds honour the caller's own `origin`.
- **Sound.** Movers play their authored `noise_start`/`noise_stop` (falling back to
  the stock door/elevator one-shots) positionally, driven off shared state — so a
  lift another player called is heard when it departs and when it arrives.
- **Networking.** Full mover state ships in every snapshot as `lift_state`, binary
  encoded, and is restored before reconciliation.
- **Crush damage.** A mover blocked by a body deals its authored `dmg` (default 2)
  and reverses, exactly as Q3's `Blocked_Door` did — unless the CRUSHER spawnflag is
  set, in which case it keeps pushing. Damage is held at Q3's 20 Hz cadence so
  lethality does not scale with our tick rate. Corpses and items block but are not
  hurt.

### Lag-compensated hit registration

Hitscan resolved against the present on the live server — no rewind of any kind — so
a moving target got harder to hit the worse your connection was. `LagCompensation`
had existed since v0.9.0 (2026-01-31) but was never instantiated outside
`src/cli/server-game.ts`; `GameServer` never touched it.

Rewind is keyed off the **view tick the client already reports**, not a ping:

- Every usercmd already carried `tick` — the last snapshot the client had processed
  (`Game.ts` sets it from `NetworkGameHost.currentTick`). It was encoded, sent and
  decoded, and then dropped by `sanitizeCommand` before reaching the simulation. It
  now flows through to the input component as `viewTick`.
- This needs no protocol change, makes no assumption that a connection is equally
  slow in both directions, and is checkable: a client claiming a tick beyond the
  server's own is clamped on arrival, and a claim reaching further back than the
  compensation budget gets the budget's edge and no more.
- The earlier plan — have the client report its RTT — was dropped as strictly worse
  on all three counts.
- **Ping is now measured, and the scoreboard works.** It read 0 for every player
  because `connection.latency` was declared `= 0` on both transports and assigned
  nowhere; the server answered `Ping` but timed nothing. The server now times its
  own snapshot against the ack that comes back for it, smoothed, entirely from its
  own clock — no client-reported number. Measured at 0.3ms on loopback and 216ms
  against an injected 200ms round trip. It reads slightly above pure network RTT
  because it is the game loop's round trip, including the client's snapshot
  processing, which is the number that actually governs how the game feels.
- `GameServer` now owns a `LagCompensation` with a **100ms** maximum rewind, and
  records history right after the simulation step.
- The client renders remote players *behind* its newest snapshot, so that lag comes
  off the rewind too. The server **assumes** that interval rather than being told
  it: `cl_interp` is a client cvar, and a value the client chooses is a value a
  cheater inflates to be judged ever deeper in the past.
- **A latency harness, because none of this is observable at 0ms.** Frames are now
  held in both directions over a real socket, so the rewind can be measured instead
  of reasoned about (`npm run net:viewlag`, plus a regression suite). It found the
  interpolation assumption immediately: the server already sees **~32ms of view lag
  at zero network latency** from snapshot quantisation and queueing, and
  `SnapshotBuffer` settles on `avg + stddev` of arrival intervals — *one* interval
  plus jitter, not two. Assuming two double-counted it and handed a LAN player ~65ms
  of rewind, shooting people well after they reached cover. Corrected to one.
- Collapsed the three rewind presets (`CASUAL`/`COMPETITIVE`/`TOURNAMENT`) into one
  `LAG_COMPENSATION`. Nothing selected between them at runtime — two call sites each
  hardcoded a different one — and `allowAbilityOverride` was a config flag no code
  had ever read. Rewind budget is a fairness decision that should be the same
  everywhere, not a per-match knob.
- `WeaponSystem` resolves each trigger pull against where the shooter actually saw
  the world: target positions *and* mover geometry are rewound together, so a plat
  that has since risen cannot retroactively block a shot that was clear.
- History is compact by design — player positions and mover offsets per tick, not a
  deep `WorldState` clone, which would have meant cloning every entity 125×/second.
- Existing hit math is untouched. With no history wired (unit tests, headless), the
  trace behaves exactly as before.

Fixed along the way:

- Reconciliation was being skipped for every map containing a lift. `lift_state` is
  present in *every* snapshot on such a map, so the guard added for movers silently
  disabled the ledge-grab and wall-jump reconcile-skip almost everywhere. Mover state
  now restores ahead of the guard, and the guard is back to its original condition.
- Caller volumes ignored the caller entity's `origin`, so a trigger built around an
  origin brush was placed wrong.

### Rendering

- **The world is culled by its compiled PVS.** Every material batch used to be
  drawn every frame regardless of where the camera stood. Membership now comes
  from BSP leaf-face references rather than sampled bounds — a batch carries the
  union of its faces' clusters — so a surface is hidden only when the compiled
  data says it cannot be seen, and anything with unassigned or invalid membership
  stays visible. Enabled automatically once a playable load finishes spawning.

  Only annotated world surfaces register, so brush entities that move on their
  own — lifts included — stay outside static culling.

  Updates are cached: a stationary frame costs no BSP lookup and no mesh scan,
  movement inside a cluster checks only the source leaf, and any cluster
  transition reevaluates however small the step.

  Headless on `wdm2`, across six authored spawn origins, hides 19.3–40.1% of
  meshes. On `wbomb6` (286,736 triangles, 21 spawns) mean retained triangles fall
  22.2% at a 1024 cell size. Hidden-mesh counts are not GPU savings by themselves,
  which is why `npm run audit:pvs -- wdm2` reports retained triangles and a geometry hash
  as well.

- **`r_bsp_cellsize`** optionally splits large opaque batches spatially at the
  next map build. **It stays default off, now on evidence rather than caution.**

  36 warmed `wbomb6` captures on an RTX 4070 SUPER (WebGL2, 1280x720, zero
  shader compiles during capture) say the trade does not pay: splitting cuts
  active-index triangles by a third to a half and raises draw calls by around a
  third, and median frame p95 got **worse in every sampled view** — 16.3–28.5%
  at 1024, 10.6–17.8% at 2048. The headless triangle win was real and
  irrelevant; submissions cost more than the geometry saved.

  Recorded honestly: three short repetitions, not confidence intervals, and the
  baseline's own spread overlaps some split results in the noisier views. It is
  one map on one device, with no full gameplay traversal.

- **Skyboxes render again.** Most maps had no sky, for three unrelated reasons.
  wbomb6 ships a 1x1 grey `_dn` stub beside five 512x512 faces — authors stub the
  face you cannot see from inside the map — and the loader took the first face's
  size for all six, reading four bytes as 512x512 and losing the sky entirely.
  Faces are now scaled to the largest present, so a 1x1 becomes the solid fill it
  describes.

  wdm2 failed differently. Its shader uses Warsow's `skyparmssides`, which points
  several sides at one image, so the map ships `env/36sky.ktx` and nothing else
  but `_up` — no six-file set to find. A missing face now falls back to the
  unsuffixed base image, which is what such a shader is asking for. That file is
  also ETC1, a mobile format desktop WebGL will not accept; cube faces now reuse
  the software decode the ordinary texture path already had, rather than treating
  291 ETC1 textures in the pk3s as unreadable.

  Verified in the browser on both maps. It cannot be verified anywhere else:
  `NullEngine` cannot construct a `RawCubeTexture` at all, so `bsp sky apply` can
  report six faces assembled at the right size and then fail on a missing GL
  constant. Only the face-scaling maths is unit-tested.

- **Players are culled too, and quieted at a distance.** A player carries no
  compiled cluster — vis membership is baked per face at map build, and players
  move — so no body in the map was ever eligible for static culling and every
  one was submitted every frame. Each is now resolved to its leaf cluster and
  tested against the visible set the camera already computed, which costs one
  leaf descent rather than a fresh PVS solve.

  It **fails open** on every uncertainty: PVS off, no vis data, a camera not yet
  placed, a position that will not resolve. A wrongly hidden player is an
  invisible enemy; a wrongly drawn one costs a draw call. Five of the six tests
  pin that direction and the sixth proves culling still happens, so failing open
  cannot quietly become never culling.

  Hiding a mesh only saves the draw call — `AnimationGroup`s run at the scene
  level and go on evaluating bones for a model nobody can see — so skeletons are
  paused separately. On a bot-heavy map that is expected to be the larger half,
  though neither has been measured. Paused instances keep their pose, so a
  player who walks back into view resumes mid-stride instead of snapping.

  Distant players stop animating on **projected screen height**, not a distance
  in units: one distance constant means a different apparent size at every FOV
  and resolution — 2500 units is 1946 at 73° and 3394 at 1440p.

- **Every player gets their own skeleton.** The model was loaded into the live
  scene and cloned per player, but `Skeleton.clone()` keeps the *source*
  transform-node links, so cloned bones drove the template's nodes and bodies
  shared a pose. Loading also destroyed animation groups already in the scene,
  and the teleport ghost pool runs a second loader — so a teleport could freeze
  every live player into a T-pose.

  Models now load into an isolated `AssetContainer` and instantiate through
  Babylon's own retargeting, and instance creation asserts what used to fail
  silently: every bone and every animation target must belong to that instance.
  Equal channel counts alone never proved ownership, which is how the shared
  skeleton went unnoticed.

  Exports that ship one skin per submesh are handled rather than rejected —
  vanguard.glb carries three over one 65-joint rig, byte-identical down to the
  inverse bind matrices. The duplicates are collapsed onto one skeleton, but
  only after proving they are driven by the same nodes. Dropping them is worth
  doing anyway: each surviving skeleton is evaluated every frame over bones
  another skeleton has already computed.

- **Shots make contact now.** Every impact in the game produced a fading
  triangle (`CreateDisc` at `tessellation: 3`) and a pooled point light, and
  nothing else — no weapon, on any surface, threw anything. A comment in
  `firePellets` had said "impact sparks for ALL pellets" since it was written;
  the line under it only ever spawned a wall mark.

  Impacts are now tiered, because they fire on every shot and the default has to
  stay quiet: a scatter of embers on any contact, plus a posterized hit star
  reserved for weapons that hit once and hard (bolt and rail). That is the same
  restraint `CartoonHitEffect` already applies by gating its sprite on damage.

  Each ember is its own thin instance carrying a launch velocity; the vertex
  shader integrates the ballistic arc, so the whole system is one draw call with
  no per-frame CPU work however many are alive. A burst billboard would have
  been cheaper still and wrong — an arena is seen from every angle, and looking
  along a wall would collapse a flat burst into a line.

  Sparks mirror the shot about the surface, leaned back toward the normal, and
  every ember is then lifted to keep a minimum component along it. The scatter
  cone is wide enough that a grazing hit would otherwise throw part of the burst
  *into* the wall: a shot arriving 2° off a floor produces a scatter axis 59°
  from the normal against a ±35° cone.

- **Autosprites upload only when they have to.** Billboard vertex positions were
  rewritten every frame regardless of whether the camera had moved relative to
  them, and for meshes the culler had already hidden. Uploads are now skipped
  when the camera has not moved and while a sprite is invisible, re-uploading
  before the first visible draw. Billboarding is also confined to world cameras,
  so the weapon-only camera stops overwriting the world's sprite orientation.

### Networking: snapshot baselines, freshness and replay

A QA pass over the active multiplayer path — input generation, transport,
authoritative simulation, snapshots, reconciliation, clocks and lifecycle —
found eleven issues and reproduced nine of them as executable counterexamples
against production code. Six are fixed here; the ledger and its probes are in
[`docs/research/v0.9.23-QA.md`](../research/v0.9.23-QA.md).

**A snapshot now says what it was built from.** It carried its own tick but never
the identity of the baseline it was deltaed against. The sender deltaed against
the last state it *sent* — recording that state before the send could even fail
— and the receiver decoded against whatever it last *received*. One dropped
datagram left a component silently stale until it changed again. Worse, an ACK
still in flight was enough to pick a baseline the client had already moved past,
with **zero packets dropped**.

- The envelope carries a full/delta flag and the baseline tick, under a new
  message type so an old peer cannot misread the header. The raw
  `BinaryProtocol` frame is unchanged, so recorded demos still decode.
- Each client keeps a bounded history of the snapshots actually sent to it, and
  the encoder deltas only against the one that client has acknowledged. History
  advances *after* the send, so a throw cannot promote a packet that never left.
- A full snapshot every 64 emissions bounds recovery when an entry is evicted.
- `SnapshotReceiver` is now the shared acceptance path for the browser, bots and
  headless CLIs. It never ACKs state it could not reconstruct — which is what
  breaks the cycle, since a snapshot the client could not rebuild can no longer
  become the server's next baseline.
- Per-client history preserves PVS correctness for free: the retained baseline
  *is* the filtered state that was sent, so an entity entering or leaving
  visibility deltas against what the client actually saw.

**Arrival order is not server chronology.** A reordered or duplicate snapshot
rewound client state by however far the two ticks were apart. Stale ticks are
now refused at three layers — the host's receiver, the reconciler, and the
interpolation buffer — and a reconnect clears presentation state that only means
something inside one session — projectile timelines included, which a backward
demo seek now resets as well.

**The movement effect clock counts ticks, not commands.** The server repeats the
last command when a client starves it and drops old ones when it floods, so
deriving effect time from the command sequence meant a starved player kept
falling while their wall-jump window, slide, ladder cooldown and water jump
stopped expiring. Over 19 starved ticks the effect clock advanced 0ms instead of
152ms; a sequence gap did the reverse and jumped it 3992ms ahead of the physics.

**Knockback drag is replicated, and now actually runs on the client.** Drag
starts 50 steps after an impulse and ramps over 75 more, so replaying unacked
commands needs to know how far into that window the body is — which velocity
alone cannot say. The client's only source for it was an impulse API nothing in
the game ever called, so on a live client drag never ran during prediction or
replay while the server applied it every tick. Measured against the real server
subsystem, predicted velocity was up to 102 u/s wrong through the drag phase.
The server now sends each player their own drag age every snapshot,
reconciliation adopts it alongside position and velocity, and both sides step it
through one shared function: the same measurement is now exactly zero. The
client still does not predict an impulse itself — it arrives as snapshot
velocity — and the unwired impulse API is gone, along with the replay anchors
that only ever served it.

**Reconciliation can no longer be suppressed forever.** The skip that protects
wall jumps and ledge grabs from jitter re-armed its window on every eligible
snapshot and returned *before* measuring anything, so it could not tell a
sub-unit trace disagreement from a teleport. It now measures first and gives up
past 400 units of divergence or 500ms of continuous suppression. This bounds the
workaround rather than removing it — the underlying replay disagreement is not
resolved, and a control test asserts small corrections are still smoothed.

**A hitch no longer loses your weapon switch, or your position.** Two bugs with
the same shape: a bounded queue discarding things it should not. The server
buffers six commands per entity and drops the oldest, which is what stops a
flooding client banking physics time — but a weapon switch rides only the first
command of a catch-up burst, so the cap threw it away and the player kept firing
the old gun. The request now rides the oldest surviving command instead, so no
extra physics step is granted and the processed sequences are unchanged.

On the client, exceeding the 32-command replay budget replayed the newest 32
from a server state that precedes *all* of the unacked ones — resuming at a
position the client's own history never passed through. At the boundary that
showed as free fall *gaining* 2.624 units of height with authority in perfect
agreement. A suffix cannot be made correct, because the state it needs was never
kept, so the budget now triggers an explicit resynchronisation: adopt authority,
discard what can no longer be honoured, predict forward. You lose input in that
window, which is visible and honest, rather than ending up somewhere neither
side simulated.

**What the hidden-state investigation found.** The leading theory was that
reconciliation restores position, velocity and grounded and nothing else. A
differential harness over real collision geometry — hand the client a snapshot
that is *exactly* what authority computed, so reconciling must be a no-op —
first appeared to refute it, because it checked only the final position. A
review measured every step instead: a replay from before a predicted wall jump
kept that jump's *future* cooldown and refused to repeat it, putting the player
105 units off until later snapshots quietly corrected the endpoint. Cooldowns are
now a bounded history that a replay rewinds, and every parity scenario asserts
position and velocity at every step. Resetting slide state is caught at 9.24
units, which turns a load-bearing code comment into an assertion with evidence
behind it.

### Gameplay

- **An empty gun says so, and then gets out of your way.** Pulling the trigger with
  no ammo used to fall through every branch and do nothing — the only feedback was
  a HUD banner you have to read mid-fight. Now the first pull plays the empty click
  (`sounds/weapons/weapon_noammo.ogg`, shipped but never referenced until now), and
  a *second* pull — or simply holding the trigger for ~200ms — swaps to the next
  owned weapon that can actually fire, wrapping in slot order with the starter
  weapon as the backstop.

  The two-stage shape is the point: swapping on the first pull would tear you off
  your rocket launcher for one mistimed tap. First pull reports, second pull (or a
  held trigger) acts.

  The click is played client-side from the same ammo derivation that already drives
  the out-of-ammo crosshair, so it lands on the press instead of a round trip later.
  It claims nothing happened, unlike a muzzle flash, so a mispredicted one costs
  nothing. The swap itself stays server-authoritative.

  A weapon raised on your behalf now holds fire until its switch animation has
  played (~264ms, matching `WeaponSwitchAnim`'s drop plus raise). There was no
  server-side raise gate at all, so a swapped-in weapon was legal to fire the
  instant it was equipped — the same trigger pull that traded the gun also shot it,
  out of a hand that still looked empty. Firing straight out of a *manual* switch
  is untouched: that is a technique, not a bug.

- **`cl_fov`, in the units players actually think in.** Field of view is now a
  setting — 80 to 110, defaulting to 90 — stated as horizontal degrees at 16:9,
  the Quake-family convention, and surfaced as a slider under Settings → Graphics →
  Display. Babylon's camera wants *vertical radians*, so the conversion lives in
  one place (`FovSettings`) rather than being open-coded per call site.

  It needed no work to cooperate with ADS or speed FOV: the viewport pipeline
  already composes every effect as a multiplier over a single base FOV, so
  `cl_fov` sets the base and ADS zoom, speed widening and the wall-jump squeeze
  all scale with the player's choice without knowing it exists. The weapon
  viewmodel has its own camera and `cg_weaponfov`, so the gun does not warp.

  The camera keeps Babylon's vertical-fixed mode deliberately: holding the
  vertical angle and letting horizontal follow the viewport means an ultrawide
  player gains peripheral vision instead of having it cropped, and nothing has to
  recompute on resize.

  Fixed alongside it: `camera fov <degrees>` wrote `camera.fov` directly, which the
  next frame's viewport effects overwrote — it appeared to work for one frame and
  then reverted. It now drives `cl_fov`, so there is one source of truth.

### Ladders

Ladders were never implemented. Four of the thirty-nine installed maps —
`wbomb3`, `wbomb4`, `wbomb5` and `wbomb6` — bolt `textures/common/ladder`
brushes to their walls, and every one of them was scenery you walked into.

- **Climbing.** A body overlapping a `SURF_LADDER` volume climbs: gravity off,
  forward following the *pitched* view so looking up and holding forward goes
  up and looking down descends, crouch as an explicit descend for anyone facing
  along a corridor, and sideways input scaled well down so shuffling between
  rungs never becomes a way to travel. Jump lets go.
- **Shared, like every other movement branch.** The climb lives in the same
  `MovementProfile` the server, client prediction and single-player all run, so
  a climber is simulated by one piece of code. Attachment is re-derived from
  geometry every step rather than accumulated, which is what lets a
  reconciliation replay recompute it instead of inheriting a state the
  corrected position does not support.
- **Detection is a hull test, and had to be.** Ladder brushes sit flush against
  their wall and reach roughly 16 units into the room — exactly a player's hull
  radius. A body pressed against the ladder therefore has its *origin tangent
  to the brush's outer face*, never inside it, so the obvious `pointContents`
  probe that liquids use would have made climbing a coin flip on floating-point
  noise. The test expands each brush plane by the hull's reach along that
  plane's normal, which is Q3's own box-in-brush offset.
- **Against planes, not boxes.** Several shipped ladder brushes have angled
  faces (`wbomb4`, `wbomb5`), so an AABB approximation would have been wrong on
  exactly the maps that use ladders most.
- **Ladder brushes are collected once at load and scanned directly** rather than
  found through the BSP tree. A leaf lookup from the player's origin finds the
  open-air leaf and misses the brush at precisely the position where climbing
  has to work. Shipped maps carry at most ten, so the scan costs nothing.
- **Contact is not the same as climbing.** These brushes run all the way to the
  floor, so attaching on overlap alone would turn the foot of every ladder into
  mud for anyone walking past. Off the ground, contact is enough; a grounded
  player has to actually ask to go up.
- **Letting go.** Jump leaps straight up — a ladder is a volume, not a face, so
  there is no normal to push away from — and a short cooldown stops the next
  step from reattaching while the body is still inside the brush.
- **Animation.** The climb clip's playback is driven by vertical velocity, so
  going up plays it forward, coming down plays the same clip backwards, and
  pausing on a rung freezes it mid-reach. Tying it to displacement rather than
  wall-clock means prediction and reconciliation cannot drift the hands off the
  ladder. Same idiom the jump clip already used.
- **The weapon stows.** Climbing takes both hands, so the viewmodel slides down
  and rolls away, and comes back up on release. It reuses the weapon-switch
  animation's visual language but not its state machine: a switch is a fixed
  down/load/up round trip, while a holster stays down for an unbounded climb and
  can be reversed halfway. The mesh is only disabled once it has finished
  travelling, so the slide always gets to play.
- **Sound, with no new asset.** Rungs reuse the metal footstep bank already
  preloaded on every map, on a vertical-distance accumulator rather than a
  timer — the same distance-drives-cadence rule footsteps follow.

### Collision: facet bevels

Players got stuck in handrails. Reported on wbomb6's, next to the ladder, and
suspected on other complex geometry.

Patch (bezier) and triangle-soup surfaces were swept as raw triangles against
**only each triangle's own face plane**. That is the Minkowski sum of a box and
a triangle computed for its faces and nothing else: the sum also has a plane per
(triangle edge × box axis) and six axial planes, and without them a hull walks
straight through near any edge. Once inside, the trace reported `startSolid`
carrying the facet's flat face normal — which on a horizontal rail is vertical,
and therefore orthogonal to every horizontal escape. Clipping removed nothing,
the trace returned fraction 0 in all directions, and the body was welded.

Each collision triangle is now expanded at load into a closed convex facet —
face, back, three borders, six axial bevels and the surviving edge bevels — and
swept with the **same enter/leave solve brush collision already used**
(`CM_AddFacetBevels`, cm_patch.c). Triangles consequently inherit the
least-penetrated-plane normal that brushes have always had on `startSolid`,
which is the plane that actually pushes a trapped body out.

Measured on wbomb6 around the ladders, by `npm run audit:stuck`:

| | before | after |
| --- | --- | --- |
| penetrations | 1357 | 8 |
| sites with 1–2 of 9 escape directions | 38 | 0 |
| worst site | 1 of 9 | 8 of 9 |
| patch / soup split | 1341 / 16 | 5 / 3 |

That patch-to-soup ratio is the diagnosis in one number: tessellation makes a
bezier surface almost entirely edge, so patches took 98.8% of the penetrations
despite sharing the sweep with soup.

- **`npm run audit:stuck` — new.** Walks a hull along and into map surfaces and
  reports where it can penetrate, how many directions it can escape, and the
  coordinates to teleport to. Getting stuck on a rail is not reproducible by
  hand, so without it there is no way to tell whether a fix generalised or to
  find the rails nobody happened to walk into. `--ladders` narrows the scan,
  `--at x y z` dumps every surface a trace reports from one spot.
- Brush collision is untouched, and verified so: the same spawn probe returns
  byte-for-byte identical fractions, normals and textures either side of the
  change.
- Facet planes are packed into `Float32Array`/`Int32Array` rather than held as
  objects. wbomb6 carries 1.13M planes across 92k collision triangles; as
  `{normal: [], dist}` that is upwards of 100MB of heap for one map, against
  **17.7MB** packed (wdm2: 2.3MB). Backend init grows roughly 150ms on wbomb6.

### Fixes

- **Quad survived death.** Powerups were cleared in `respawnPlayer`, not on the
  kill, so a corpse kept the carrier glow for the whole death screen — and every
  other player went on seeing the quad as live on the body. Now cleared the moment
  the kill lands, which is also what Q3's `player_die` does. The first-person
  weapon outline was already correct (the `death` event drops the local timers);
  it was the server-sent powerup mask, which drives the body glow, that went stale.
  Side effect, and the Q3 behaviour: a rocket fired before dying that lands after
  no longer gets the multiplier, since it reads the attacker's powerups at damage
  time.

- **Remote players were dead-reckoned through walls.** Warping, bodies drifting
  inside walls, players floating above floors and sinking into them were all
  reported as separate intermittent oddities. They are one mechanism.

  When the snapshot buffer runs dry — a late or dropped packet putting
  `renderTime` past the newest snapshot — remote entities are extrapolated from
  their last known velocity, and that extrapolation is collision-blind. The cap
  was 200ms: 64 units at run speed, 180 off a rocket jump, against a player hull
  32 units across. So it permitted two full player widths of travel through
  solid geometry before the authoritative position arrived and snapped the body
  back. The snap is the warp; the interval before it is the body in the wall.

  The vertical branch explains the rest: airborne entities have gravity applied
  while extrapolating, so a bot caught mid-jump projects upward and one caught
  falling projects downward. Grounded entities hold their Y, which is why nobody
  standing still was ever affected. The cap is now 60ms.

- **Projectile trails collapsed to a flat sliver.** The trail is a camera-facing
  ribbon whose half-width runs along `Cross(tangent, toCamera)`. That degenerates
  in the one case that matters most — players shoot where they are looking, so
  tangent and `toCamera` go antiparallel, the cross product falls under the
  degeneracy guard, and the fallback produced a world-*horizontal* ribbon. (The
  report said "flat level triangles"; *level*, not merely flat, is what
  identified it.) A billboard viewed down its own axis has no valid orientation,
  so the fix is a second blade crossing the first at 90° rather than a better
  fallback.

- **Free-for-all showed a team scoreboard, and the result screen showed
  nothing.** Team-ness could not be inferred from `teamScores`, which ships with
  both sides present in every gametype, so it is now stated by the server. And a
  match ends by flagging everyone spectating and despawning their entities —
  which were the only source of score and deaths, so the board fell through to
  an empty spectator list at the moment the result mattered most. Final
  standings now come from the match's own tally and outlive the entities they
  describe. Both rosters are cleared on reset, so a new match cannot open
  showing the last one's names.

- **Jumppads are audible.** They launched you in silence; Warsow's own
  `trigger_push` sound already shipped in the pk3s. The movement profile reports
  the launch on every step the player overlaps the pad — velocity replacement is
  idempotent and has to stay that way for replay — so the one-shot fires on the
  rising edge rather than while the flag is held.

- **The remote-player hitbox wireframe flickered.** `cl_remotehitbox` treated an
  absent cvar as undefined rather than off, so the debug box appeared on enemies
  unasked.

- **A dropped weapon could half-initialise.** The pickup-proximity check cached
  the camera module before awaiting the inventory module, so a snapshot landing
  between the two sequential imports found one cached and the other still null.
  Both are now published together, behind an in-flight guard.

- **Your own corpse was a T-pose in the death camera.** The local body is the
  only one built and physicalised in the same tick — there is no third-person
  model of yourself, so one is created at the moment of death and handed
  straight to the ragdoll. `play()` schedules an animatable rather than
  evaluating it, so the skeleton still held its bind pose, and the ragdoll lays
  its bone bodies out from whatever pose it finds. A T-pose there is frozen in
  permanently. A remote corpse is detached after seconds of rendering, so it
  always had a real pose — which is why only your own body showed it.

  The death path had not changed since July. The source model used to be posed
  by accident: it loaded into the live scene under the glTF plugin's default
  start mode, so frames elapsed with its embedded clip running and every clone
  inherited a posed skeleton. Loading into an out-of-scene container with
  animations off is correct, and makes settling the pose an explicit step.

- **Any death froze every other player where they stood.** The ragdoll stopped
  every animation group in the scene before taking over the body, though its own
  comment said it was stopping the ones targeting that skeleton. It is scoped to
  the dying body now. Entity LOD had been quietly repairing the damage — it
  restarts a stopped group the next frame it judges a body visible — which is
  why nobody saw it.

- **The health orb rendered as a black hole ringed in colour**, and megahealth
  the same in red. The shell writes depth: it is alpha-blended with back-face
  culling, so its near hemisphere rendered first and depth-rejected the cross
  behind it, meaning the emblem was never drawn however the fresnels were tuned
  — while its own comment promised the emblem stays visible through the centre.
  What did survive carried no colour either, since emissive is multiplied by
  opacity and the face-on fresnel floors were 0.06 against 0.12. Both floors now
  hold the tier colour, still well under the rim so the orb keeps its depth
  instead of flattening into a ball. Both health tiers share the material, so
  one fix covers the orange orb and the red one.

- **A failed player-model load claimed success.** The loader catches its own
  errors, so loading resolves either way and the renderer logged "Player model
  loaded" over the top of a failure — leaving invisible players as the only
  symptom, with the real error scrolled away.

- **Map weapons could lie somewhere other than where they are picked up.** A
  map weapon's landing was a Havok toss run on each client alone, with a random
  spin, while the server's pickup trigger stayed at the mapper's origin. The two
  were never the same place, and they drifted apart by tens of units: the rocket
  launcher beside a ledge on wdm2 sometimes tumbled off it onto the level below,
  invisible where you went for it and collectable only at the spot above. Dropped
  weapons never had the problem, because the server already simulates their
  throw and the trigger follows the result.

  Map weapons now get the same throw. One shared, deterministic function tosses
  each from its pickup id through the shared collision world to where it comes to
  rest, and the server's trigger, the model every client draws and bot item goals
  all use that spot. Server and client run identical collision code over the same
  BSP, so it needs no replication: two independently built collision worlds agree
  on every landing on wdm2 and acidwdm2, where weapons settle 3–8u from their
  authored spots. The random tumble is gone; each weapon rests at a yaw derived
  from its id instead. A throw that never settles keeps the authored spot.

- **Weapon models and rockets could lose their geometry from the second join
  on.** Joining a game runs a scene clear whenever a scene already exists, and
  that clear disposes every mesh in it — including the hidden source models two
  caches keep for cloning: the preloaded pickup weapons and the projectile models.
  Neither cache was told. The next map load found both already loaded, so map and
  dropped weapons cloned meshes with no vertices, and rockets and grenades drew
  only their trail and light, while the first join of a page load was always
  fine. The plasmagun showing only its loading chambers was put down to this
  mechanism too — those load fresh for every pickup while the body came from the
  cache — but it recurred after the fix, and the body survives a simulated second
  join intact, so its cause is still open.

  Both caches now check a model before handing it out — meshes alive, materials
  still attached, textures not released — and load it again otherwise. Two other
  routes to the same state are closed as well: disposing one map pickup disposed
  the material and texture every clone of that weapon shares, and a map load
  disposed cached textures that projectile materials went on using. Preloaded
  pickup models are now released with the map that loaded them, keeping anything
  a live clone still renders with.

- **A KTX2 texture whose decoder worker failed to start never loaded, and never
  fell back.** Babylon's worker pool runs a queued decode only once its worker
  has started, and ignores a failed start, so the texture waited forever instead
  of falling back to its source image — as did every later KTX2 texture queued
  for that worker. A failed start, or one silent for 30 seconds, now fails its
  decodes at once, which lets the existing fallback run; the slot is freed so a
  later decode tries a real worker again, and a failed fetch of the decoder
  binaries is retried rather than remembered.

- **Fast-firing projectiles blinked, and shots fired during a weapon switch were
  invisible.** Two defects in how the client presents projectiles, each pinned by
  a test that failed before the fix.

  Every shot of one type shares its model's material, and each new shot faded in
  by setting that material's alpha to zero, restarting the fade of every shot
  already in flight. At the plasmagun's ten shots a second the newest bolt is
  always under 100ms old, so every bolt on screen spent most of its flight partly
  transparent. Each shot now fades in through its own meshes' visibility.

  Projectiles were also moved, faded and given trails only inside the view
  weapon's per-frame update, after a line that returns while no weapon model is
  loaded. A weapon switch clears the model before loading the next, so shots
  fired in that gap stayed transparent with no trail, and explosions and hitscan
  effects froze with them. Projectiles and hitscan effects now update whether or
  not a view weapon is loaded.

- **A loading screen could stay up after a load that finished in a background
  tab.** The overlay moved from showing to loading on its first animation frame,
  whatever state it had reached by then. A background tab runs no frames, so when
  the load completed first the late frame overwrote that, and releasing the FPS
  client's post-load hold no longer started the fade. The frame now advances only
  a screen that is still showing. Found by a test, not seen in play.

- **A map weapon could sit below the floor, invisible where you pick it up.** The
  shared landing throws each weapon to its resting spot and the server's trigger
  sits there — but the client then dropped the model 20 units onto "the floor
  beneath it" with a raycast of its own. Wherever that ray reached past the floor
  the landing had chosen — a gap, a thin brush, a start inside geometry — the
  model seated itself below while the trigger stayed above: nothing to see, yet
  collectable where the mapper put it. That was the rocket launcher on wdm2's
  lower floor. A weapon is now placed at its resting spot and left there. Only a
  pickup with no computed landing still looks for the floor beneath it.

- **Returning from a background tab levels the view.** A frame drawn while the
  controller is not running keeps whatever roll it had until updates resume, so
  coming back now clears the effects that tilt the view and puts it on the
  horizon. The tilt has stopped reproducing, but this is **not proven to be what
  cured it**: the first play-test after this change still came back at an angle,
  unmoved by looking around and levelled only by pressing forward, and nothing
  since has been captured to say which change ended it.

  What that play-test established still stands. Roll is zeroed on every frame the
  controller runs, so a surviving tilt is written after that point, and the
  arithmetic rules out the view effects: they cap at about 9° combined and go
  neutral while standing still. The only remaining writer of that magnitude is
  the 40° death-camera fallback, which lifts only when the local player is seen
  alive again — and the flag it rests on is driven by event edges that are gated
  on a local entity id the snapshot may not carry. If the tilt returns, the new
  developer `camera_audit` command reports the deciding values in one line: roll,
  death-cam phase, and whether that id resolves.

- **Map weapons drew with their bodies missing, or did not draw at all.** Every
  map pickup is a clone of a preloaded model, and the preloader stores its
  sources hidden — each mesh disabled and invisible. Babylon clones a mesh
  together with its children, but only the mesh named in the clone call was
  turned back on, so any part that came along as a child stayed hidden, and
  nothing downstream turned it on either: the pickup only walks the meshes the
  clone handed back. A plasmagun showed just its chambers, which are imported
  fresh for every pickup and never cached, standing over an invisible body; a
  rocket launcher, which has no such parts, showed nothing at all while its
  trigger still worked. The same weapon dropped by a player was whole because a
  mid-match drop usually finds the cache invalidated and falls back to a fresh
  load, and the fresh loader makes every mesh it returns visible. The whole
  cloned subtree is now turned on. The same loop also cloned a cached mesh a
  second time when it had already arrived inside its parent's clone — the same
  geometry drawn twice in one place — so a mesh carried by another is now
  skipped.

## Technical Notes

- Lift state is clamped and validated on restore — a packet can move a known mover,
  never invent one.
- `lift_state` is a fixed binary record (count, then per lift: `uint16` model index,
  `float32` offset, `uint8` phase, `float32` remaining, cooldown list). This replaces
  a JSON blob that cost ~377 B/snapshot on a four-lift map (~11 KB/s per client at
  30 Hz).
- Phase indices are positional on the wire — append only.
- Fire-once callers are modelled as a large finite cooldown rather than extra state,
  so they survive serialization unchanged.
- Movers are parented to the map's world mesh, so map unload disposes their meshes,
  materials and render observers.
- `LiftSystem.step` returns the bodies it squashed rather than dealing damage
  itself; the shared simulation core stays out of the business of hurting anyone,
  and client prediction simply discards the result.
- Rewind history is pruned on a tick window and dropped wholesale if the tick count
  ever moves backwards, so a match restart cannot strand old entries.
- `MovementStateComponent`'s flags widened from `uint8` to `uint16` to carry
  `onLadder`. Water level had taken the last two bits of the first byte; seven of
  the sixteen are now free. Both sides ship together, so this needs no version
  negotiation, but it does change the component's wire size from 9 to 10 bytes.
- The extrapolation cap is now a named `MAX_EXTRAPOLATION_SEC` in
  `SnapshotBuffer` rather than a literal at the point of use, so the blind-travel
  budget is stated once and can be found.
- Player model instances share the source container's materials until something
  tints them, at which point the material is cloned per instance. Disposing a
  manager disposes the container, so tearing one down while untinted instances
  are still alive would take their material with it. Teardown-order only, and
  the same exposure the pre-container code had.
- Ladder tuning (`climbSpeed` 168, `acceleration` 30, `friction` 20) has one
  constraint worth keeping: acceleration must stay at or above friction, since the
  two settle at `acceleration * climbSpeed / friction` and a profile with more drag
  than push never reaches its own climb speed.
- Babylon clones inherit their source's parent even when `clone(name, null)` is
  passed, so a clone made from a cached source needs its own parent or it is
  disposed along with the source root. Caches that hand out sources for cloning
  go through `ModelSourceCache`, which releases a source's materials, textures
  and skeleton only once nothing live still uses them.
- A map weapon's resting spot is computed on each side rather than sent: the
  server, every client and bot map knowledge all call `landMapPickups` from
  `shared/items/ItemThrow`, and dropped weapons step with the same function. A new
  consumer of pickup positions has to use the landed table, not `extractPickups`
  alone. `pickup_audit` reports, per weapon, frustum membership, where the skinned
  vertices actually are and, for a mesh that is not ready, what it is waiting on.
- Three console warnings name the causes still open from play, each from a
  single capture. `[ProjectileSync]`: a server projectile arrived without its
  one-tick `projectile_spawn` event, so it flies undrawn. `[SnapshotReceiver]`: a
  delta snapshot was dropped for a missing baseline, and the events it carried
  were lost with it. `[MapLoader]`: world meshes were not ready to draw when the
  loading screen closed, each with what it is waiting on. The first two are
  rate-limited to one per five seconds.
- `loading:hidden` is emitted once the loading screen has finished fading out,
  the moment the player first sees the world.
- `?map=` startup is removed: every map is played on a server the lobby spawns.
  The developer `map` console command, which launches a server-backed map, stays.
- A dropped player keeps their seat for twenty seconds. The server holds the
  client record, its entity, score, weapons and slot instead of clearing them,
  and hands them back to whoever presents the resume token it issued at join. The
  client asks for its seat back on its own: a stalled connection is dropped and
  reopened, since nothing was crossing it anyway. Only what belonged to the old
  socket is reset — the snapshot history and acknowledged tick, so the next
  snapshot is full, and the input sequence, because a reconnected client counts
  its commands from one again. Nothing is held once the match is over, when the
  server closes connections on purpose; the challengers queue leaves a held seat
  alone; and a lobby-spawned server stays up while anyone is mid-resume. A demo
  still finalises the moment the last player's connection goes, because
  recording one is "play, then leave", not "play, then wait".
- A connection can stay open while nothing crosses it: neither side sees an error
  or a close, the player's inputs stop reaching the server, and their world
  freezes. Both ends now say so. The client warns after 2s without a snapshot,
  with whether its socket is open and how many bytes wait to send, and logs an
  error after 8s; time it spent hidden or blocked is not counted. The server warns
  when a playing client has sent nothing for 2s, and again when it is heard from.
  Neither closes anything yet: until a dropped session can be resumed, closing
  would only remove the player from the match.

- **Anything thrown inside the tick loop stopped the server for good.** Each tick
  scheduled the next one at the end of its own timer callback, so a single throw
  anywhere in that callback ended the match: no further tick was ever scheduled,
  the simulation stopped, and the sockets stayed open — every player left hanging
  in a world frozen exactly where it stood, with nothing further written to the
  log. The loop now always schedules its successor, and names what failed at most
  once per 5s. The silence monitor above was itself one such thrower: it read the
  connection of every playing client, and a client record without one took the
  whole server down. Caught by the suite, which reported it as an unhandled error
  while every test still passed.

## Known Unverified Items

- **Played and confirmed:** the empty-gun click and weapon trade, the auto-swap
  raise gate, `cl_fov` with its Display slider, the jumppad launch sound, the
  crossed projectile trail, and remote players rendering correctly again after
  the multi-skin fix.
- **The placement bug is believed fixed, not proven fixed.** Bodies inside walls
  and floors have not recurred since the extrapolation clamp and the skeleton
  work, but the original symptom was intermittent and no controlled reproduction
  was ever built, so absence over one session is weak evidence. The remaining
  discriminating test is cheap and still worth running: `cl_remotehitbox 1`
  separates "the model is wider than the hull" from "the transported position is
  wrong" in a single round. Extrapolation frequency has still never been
  measured; if it turns out common, the correct fix is to sweep the
  dead-reckoned path against the client collision world and clamp at the first
  hit, which makes penetration impossible at any cap.
- **The shared map weapon landing is not yet play-tested.** Loading after the
  cache fixes was play-tested and reported solid; the landing came after. It
  relies on client and server computing identical collision, which movement
  prediction already depends on: a divergence would show as a weapon resting a
  few units from its trigger, and `docs/research/v0.9.23-pickup-landing-probe.ts`
  checks that both sides agree on a given map. The resting yaw replaces the Havok
  tumble, so map weapons no longer lie at varied tilts. The KTX2 fallback is
  proven against Babylon's real upload path with stand-in workers, never with a
  worker that actually failed in a browser.
- **The lower-floor rocket launcher and the tab-return camera were both reported
  still broken after their fixes.** Each fix closed a real defect and has a test
  that fails when it is undone — a client-only re-drop that could seat a model
  below the floor, and a frozen frame keeping its roll — but neither was the cause
  of what was reported. The launcher is still not drawn while still collectable at
  its authored spot, and the view still comes back tilted. Both are open again,
  with `pickup_audit` and `camera_audit` to name the next capture.
- **The projectile fixes are not yet play-tested, and may not account for every
  projectile report.** Both defects were reproduced in tests and are fixed. Play
  also showed rockets and grenades drawn untextured on some loads, and plasma
  bolts vanishing mid-game along with their trails, which may have other causes.
  The `[ProjectileSync]` and `[SnapshotReceiver]` warnings tell a lost spawn event
  from a lost snapshot. Also open from the same sessions: world surfaces
  see-through for a while after a map load (`[MapLoader]` names the meshes that
  were not ready), the camera rolling until the player moves forward, and the
  plasmagun body missing on map pickups.
- **A player froze mid-match while the server ran on.** In one play-test the
  server stopped receiving a client's messages while both sides kept the
  connection open and logged nothing, so the player stood still and the enemy
  froze in view (K in the bug hunt). What stalls the connection is not known. The
  new connection warnings name the stalled side next time, and resuming a dropped
  session within a grace window is the planned remedy.
- **Still open from the bug hunt** (tracked in
  `docs/research/v0.9.23-bughunt.md`): a bot strafing with no strafe
  animation, where both leading hypotheses have now been eliminated; bots in
  Search & Destroy clustering and pushing each other instead of navigating; and
  a flickering winner name with a misplaced model on the post-game showcase.
- **The impact spark shader has not been compiled yet.** `NullEngine` cannot
  compile GLSL, so its nine tests cover scatter geometry, pooling and lifetime —
  never the shader source. The same is true of the muzzle, rail and Voltaic
  materials, which have no compile coverage either; all of them rely on
  `prewarm()` reporting a failure in the browser. Colour, size, streak length
  and the star's alpha steps are therefore first guesses awaiting a playtest,
  and explosion and projectile contacts do not spark yet — only hitscan does.
- **Client presentation is frame-rate dependent.** Tested in a browser with
  vsync disabled, a number of things went flaky, which points at smoothing or
  timing still driven per frame rather than per unit time. Low priority, but it
  means uncapped frame rates are not currently a supported configuration.
- **PVS is reported working in the browser** — roughly 35 to 120 FPS from one
  spawn — but that is a user observation, not a controlled benchmark: map, cell
  size, hardware and route were not captured. Spatial batching now has a
  controlled comparison (see `r_bsp_cellsize` above); PVS itself still does not,
  and neither has systematic visual-correctness capture.
- **Babylon's per-frame CPU counters cannot be trusted as totals.** In 9.17
  `PerfCounter.endMonitoring(false)` assigns its current duration rather than
  accumulating, so later camera and draw phases overwrite earlier ones. With an
  empty weapon camera rendering last, `cpuRenderMs` reads 0–0.1ms and
  `activeMeshes` reads zero. Neither means world rendering is free, and neither
  can be used to prioritise mesh-candidate work until the timing explicitly sums
  per-camera durations.
- The culler owns `isVisible` for registered static surfaces. Anything that
  temporarily overrides it must restore it and call `invalidate()`. Water probe
  and reflection passes already do; that does not establish correctness for every
  shader, shadow or auxiliary view.
- **Not yet played:** mover audio mix levels, how a ridden lift feels under real
  latency, and how lag-compensated hit registration reads to both shooter and
  target. Rewind is the likeliest thing to need tuning — `maxCompensationMs` is
  100ms, now one number for every server rather than a preset.
- Two feel constants are first guesses, both one-liners in `WeaponSystem`:
  `DRY_FIRE_SWAP_TICKS` (200ms before a held trigger swaps) and
  `WEAPON_RAISE_TICKS` (264ms before an auto-swapped weapon fires).
- `cl_fov` 110 stacked with `cl_speedfov` 0.38 reaches roughly 130° horizontal at
  full bunny-hop speed. Within the intent, but the combination worth a sanity check
  before the range is called final.
- **The interpolation assumption is measured at the server, not the client.** One
  snapshot interval matches `SnapshotBuffer`'s steady state, but that buffer adapts
  up to 150ms under jitter, and the server cannot see a given client's actual value.
  A jittery connection therefore gets slightly under-compensated — deliberate, since
  erring high punishes the player who took cover. Confirming this needs the client's
  real `interpDelay` reported as **telemetry only**, never fed back into the rewind.
- Only hitscan is rewound. Projectiles still spawn against the present.
- **Ladder feel is tuned by arithmetic, not by play.** Climb speed was lowered 30%
  after a first pass felt fast; the coast after releasing the keys is about eight
  units. `CLIMB_NATURAL_SPEED` (the rate the climb clip reads at 1x playback) is
  still a first guess, so the hands may look hurried or sluggish against the new
  speed.
- Bots do not use ladders — navigation does not know the volumes exist.
- Ladder climbing is unreachable on 35 of 39 installed maps, so it will not be
  exercised outside the `wbomb` series.
- Player animation clips live under `public/games/`, which is gitignored, so
  `climbing_ladder.glb` is a local asset like every other clip. A missing clip
  falls back to idle rather than failing the load.
- A client that reports a stale view tick is clamped to the 100ms budget, so the
  most a dishonest one can buy is the same rewind a genuinely lagged player gets.
- `func_button` is activated by touch. Shootable buttons (`health` key) are not wired,
  and the button brush itself does not visually depress.
- Crush damage is applied server-side only; single-player local mode (`MovementSystem`)
  discards the crush events since that path has no combat system.
- Other mover classes — `func_train`, `func_bobbing`, rotating and horizontal doors —
  are still unhandled; horizontal `func_door` continues through the existing handler.
- The physics probe warning in `npm run test:physics` ("Y position changed
  significantly") is pre-existing and unrelated: verified identical on a clean
  pre-lift baseline. It is a naive heuristic in the CLI that expects a falling probe
  to hold its height.
- No browser session, QUIC datagram loss, reordered delivery or custom-rate client
  was exercised for any of the networking work. The bot and demo runs are WebSocket
  only, so they prove the envelope and baseline agreement end to end, not loss.
- The reconciliation suppression bounds (400 units, 500ms) are reasoned but not
  tuned against a capture. Nothing yet measures how often a real player holds wall
  eligibility, so if a correction snaps near a wall that did not before, the timeout
  is the thing to raise.
- The reset-and-replay parity harness uses a box world with axis-aligned surfaces
  and a constant positional nudge, not shipped BSP geometry and not true float32
  wire quantisation. Beyond the wall-jump cooldown it exposed, retained movement
  state is not audited on real maps, and trace disagreement on angled surfaces and
  input divergence remain untested.
- Re-sim bundles recorded before the effect-clock change encode the old timing and
  will not reconcile. None are committed, and `buildReSimBundle` generates its
  goldens at record time.
- Knockback drag replication has not been playtested. The client does not predict
  impulses, so the first snapshot after a hit still corrects velocity; only the drag
  that follows is now predicted exactly.
- Every player's `knockback_state` goes into the shared snapshot, so recorded demos
  carry one small event per player per frame. Only the live wire is filtered to the
  owner.
- N07 and N09 in the QA ledger are reproduced or source-confirmed and remain
  unfixed.
