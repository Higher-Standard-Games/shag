# v1.0.0-beta.13

**Release Date:** unreleased — living changelog

## Upgrade Notes

- **Servers: bots move into the lobby.** The lobby seats bots itself and plays
  each match's bots in a match runner, a child process of about 175 MB per
  match with bots; `washoi-bots` is no longer needed. The release works with
  the installed scripts unchanged, but each host then needs the new activation
  script installed and `washoi-bots` disabled, and a rollback to beta.12 needs
  `washoi-bots` enabled first. Check `washoi-lobby`'s memory limit before
  publishing. Steps:
  [v1.0.0-beta.13 operator steps](https://github.com/Higher-Standard-Games/wash-fps/blob/main/scripts/deployment/README.md#v100-beta13-operator-steps).
- `lobby:server -- --bot-server` keeps the bot server path, and
  `bot:server -- --in-process` plays a bot server's matches in itself.

## Changes

### Bots

- The bot server builds a map's nav graph in a worker thread when its disk
  cache has none (`bot-nav-worker.mjs`, beside `bot-server.mjs`). The build
  took about 9 s on washoi_snd1 in the thread every bot's commands go
  through, so every bot in every match the server ran stood still for it.
  Bots on the map play without the graph until it is ready. Run from source,
  as the bot tools are, the graph is still built in the bot server's thread.
- `bot:motion` and `bot:ab` report what a bot costs: a snapshot's handling
  and its decision, as p50, p95, p99 and the longest (`BotClient.timings`),
  for all bots in `bot:motion` and per arm in `bot:ab`.
- A bot decides for less: the nav graph remembers nearest-node lookups until
  its nodes change, and its own standing node across the items a decision
  weighs, and perception traces each item spot once per snapshot. In a 10-bot
  S&D match choosing an item goal took 1.9 s instead of 5.2 s, and a
  snapshot's median cost fell from 0.36 ms to 0.22–0.30 ms.
- The bot server holds a map's collision and entities, not its render data:
  bot vision parses the BSP as the game server does and lets the pk3 archive
  go. One map took about 450 MB in the bot server; it takes about 60 MB. The
  BSP loader copies the PVS out of the file instead of keeping a view into
  it, which kept the whole file alive.
- A bot starts each life with nothing of the last one's route, goals, plans
  or moment (a climb, a pad ride, a charged shot): they live in one object,
  `BotLife`, made new at each death. Before, fifteen were cleared by hand and
  ten were never cleared, relying on their own expiry.
- The bot's route following and its traversal sequences are modules of their
  own (`bot/navigation/BotNavigator.ts`, `BotTraversal.ts`), each reaching the
  brain through a typed host interface. So are its steering (wall clearance,
  pad throws, climbs and wall jumps, `bot/movement/BotSteering.ts`) and where
  it looks while roaming (`bot/view/BotLook.ts`). The steps that adjust what
  each state chose run from one method that lists their order, and ask
  `InputClaims` before touching movement that a sequence or an exact
  approach holds. Each state's executor is a module (`bot/states/BotFight.ts`,
  `BotRoam.ts`), as is the bot's side of the gametype's orders
  (`bot/orders/BotOrders.ts`). `StateMachineBrain` went from 3,807 to 1,508
  lines; bots play as before. `bot:motion --trace` reports who held movement.
- A learned route's landing links to the floor around it through the same walk
  test as the nav graph's own nodes: the wall cost, and the way round when the
  straight line is blocked. It used to link by a straight sweep alone.
  `bot:routes --check` reports the edges that fail the test they were built
  by and exits 1 when any do; on `washoi_dm2`, `snd1` and `dm16` it finds 4,
  39 and 17 walk edges that only walk one way (the sweep is tested one way and
  the edge added both ways) and a learned route or two whose start walks to
  none of its nearest nodes.
- Duel's habits (keeping a territory, keeping the height, the lead handicap)
  are gametype data beside the weight profiles (`GametypeHabits`), not
  checks of the gametype's name.
- `bot:server --match-runners` plays each match's bots in a process of their
  own, which loads the map once for them and exits with the match; the bot
  server keeps their seats in the room. A bundled runner with ten bots on
  `washoi_snd1` used 240–290 MB. Without the flag, bots play in the bot
  server as before.
- The neural-network bot brain and its training are gone: `bot:train`,
  `bot:bench`, `--models` on `bot:server` and `demo:record`, and the
  TensorFlow dependency (925 MB of `node_modules`). Bots always play the
  rules and the goal layer, as every bot in a room already did.
- The lobby runs bots with no bot server: it seats invited and campaign bots
  itself, on connections inside its own process, and their matches play in
  match runners. Rooms, admission and ratings see the same bots as before.
  `--bot-server` asks a running `bot:server` instead.
- A roaming bot decides on every second snapshot (fights and movement
  sequences on every one, aim at full rate), and chooses between an item, the
  latest sighting and, in Duel, its high ground by score instead of a fixed
  order: in Duel bots camp their ground less and chase a fresh sighting.
- A walk edge in a bot's nav graph exists only the way it walks: the straight
  sweep is tested each way, where it was tested one way and added both, and a
  ledge or step that walks down but not up gave routes a bot could not run.
- Blood splats lie on the floor, and gibs bounce off it: both looked for the
  floor with a player-sized column rather than a point, so splats hung about
  24 units in the air.
- A death's weapons scatter in a direction of their own each time; with one
  weapon to drop they always flew within half a radian of the same compass
  heading. In demos, dropped weapons now spin and tumble in the air and lie
  down at rest, as they do in play.
- Bots see for less: a sight line between areas the map's visibility data
  says cannot see each other is not traced (25–60% of bots' sight checks),
  collision skips a switchable brush model or button a trace cannot reach
  (a full trace on `washoi_snd1` 28% faster, for the game server too), and
  a bot's first decision on a map no longer builds the whole distance table.
  A 10-bot S&D match's slowest snapshot went from 57 ms to about 20 ms, and
  bots trace about a third of the sight lines they did. All give the same
  answers as before.
- Bots, game servers and the browser trace the world in WebAssembly: the
  BSP walk, brushes and patches,
  compiled from Rust (`native/collision-wasm`, built into
  `src/engine/physics/WorldTrace.wasm` by `npm run build:collision-wasm`),
  with the same answers bit for bit and the movers still in TypeScript. A
  full trace is 1.55–1.8× faster. Match runners start with a 4 MB young
  generation: a 10-bot runner on `washoi_snd1` holds about 175 MB instead of
  420 at the same cost, and `SHAG_DEBUG=memory` logs a runner's memory.
- Route lines are shared by every bot running the same stretch, and a wall
  jump check stops as soon as no wall jump can happen; with them a 10-bot
  match has a fifth of the slow snapshots it had, the slowest about 22 ms.
- A bot or game server reads its map's BSP straight out of the map's pk3
  instead of loading the whole package: loading `washoi_snd1` for bots peaks
  at 250 MB instead of 289.
- A demo shows the death card when the recorded player dies ("YOU GOT
  FRAGGED", who did it, the respawn countdown), in playback and in a video
  export.
- Every bot in a process sends its commands from one timer instead of one
  each. Two test options for `bot:ab`: `decideEvery` (decide on every n-th
  snapshot while roaming; 2 cut S&D decisions by a third with no difference
  in rounds) and `scoredGoals` (choose between an item, a hunt and holding
  ground by score). Both are off by default.
- A bot in slime or lava jumps for the nearest dry ground, back up to a ledge
  or on to an island, whatever it was doing, keeping its aim and fire. On
  `washoi_amphi1` they used to wade the pool until it killed them.

### Search & Destroy bots

- Bots play the bomb as a team. One bot goes onto a placed or armed bomb and
  two teammates guard it, each between the bomb and one way in; the rest fight
  for the ground round it. Before, every defender walked onto the bomb past
  whoever was shooting them and stood there. The bot on the bomb fights what
  it sees while the clock leaves time to finish, and a defuser waits beside
  the bomb until no attacker has been seen near it for two seconds.
- Guarding bots never stand still: they run about their ground watching the
  way in, and a fight does not pull a guard off it. Out of a fight the blade
  goes away for a gun.
- Bots call the team's plan in team chat ("Going A", "2 on A, 3 on B",
  "Arming A, cover me", "Retake B, go!", "Defusing, cover me"), and a person
  can order the team: `go`, `wait`, `retake`, `stack a`.
- Strafe jumps chain off each landing and accelerate with forward and a side
  key, as people do; `bot:demo-motion` reports how far bot movement is from a
  person's.
- Bots steer their feet clear of walls, corners and ledges in every state,
  fights included, instead of only on some navigation: a sweep of the body
  ahead and a fan of rays lean them off walls and round corners. In S&D they
  run within 8 units of a wall about half as often. Before a climb or a wall
  jump they run the movement forward to check it works from where they are.
- On the go, the bot paired with the bomb carrier goes into the site first
  and the carrier follows two seconds behind. Strafe-jump chains take the
  side away from a wall beside them, and bend off a wall coming up.

### Campaign

- Bot Trap gives you one respawn: your second death ends the mission, where
  the first did. A Survival mission sets its players' lives with `lives` in
  its `survival` rules (1 when absent); the mission card says so.
- A story campaign of eight operations against bots, from **Campaign** in the
  lobby's menu. The operations run down the page, each with its whole comic
  card and its details beside it, on a track that shows how far you have got:
  cleared (with your most frags in a win), next (with **Play**), or classified. The page opens at your next one.
  Across the top the squad stands on their street, fading into the page's
  own deep purple; scrolling the operations drifts the street and the squad
  at different speeds, and an idle handheld-camera sway slides the street
  gently behind them. The
  first four are written: Amphi against the Cartel King on `washoi_amphi2`,
  free for all against four rioters on `washoi_dm1`, S&D with a crew of four
  on `washoi_snd1`, and a duel with the Glitch Queen on `washoi_dm2`.
- **Play** shows the operation's comic card on a black screen, one
  framed panel at a time with the rest blurred, moving on after five seconds or
  at a click or key. Behind it the lobby opens a private room with the
  operation's map and bots; the match loads when the card is done.
- A campaign match draws you as the robot and your opponents in the
  operation's model, whatever the model settings say.
- Winning clears the operation and unlocks the next. The lobby keeps progress
  per account in `campaign.db` beside `players.db`, from the game server's
  signed result; the browser keeps a copy. Missions are defined in
  `config/campaign.json`. Campaign rooms are built for co-op: everyone in one
  must have unlocked its mission.
- A campaign match has no warmup or ready-up: once you are in, a 10-second
  countdown ("get ready", three, two, one) holds everyone at their spawn, then
  the match goes live.
- A campaign match is closed to everyone but its own players: its game server
  (`--campaign <mission>`) turns away spectators and the lobby never offers a
  drop-in seat.
- Demo format v8 records the campaign mission in the header. Campaign demos
  stay out of **Latest**, the featured picks and the recent demos; each player
  finds theirs under **Your demos**. The reader still plays v1–v7.
- The lobby notes when an account first finishes the whole campaign
  (`completedAt` in `campaign:state`), for rewards to come.
- Concrete Strike (S&D on `washoi_snd1`) is a sabotage run: your side attacks
  every round with no swap at the half, and the first side to 10 rounds wins,
  10-9 included (`"side": "attack"` in `config/campaign.json`, passed to the
  server in `--campaign-rules`). The defenders are police; your crew is a
  mix of cartel and riotkitty, set per bot (`model` on a campaign bot).
- In a campaign match teammates are always drawn green (the Lime colour,
  tinted and outlined), whatever the colour, tint and outline settings say.
- Operations 5-8, written, each with its comic card: Bot Trap (Survival on
  `washoi_dm18`), Siege Breaker (Amphi on `washoi_amphi1` against a Heavy
  Siege Bot two and a half times a player's size, spawning with 200 health
  and 200 armor and a different random kit every time), Depot Heist (attack-only S&D on
  `washoi_snd6`, 10 rounds, against three rogue police and two Unit 07
  robots, all Insane; your crew is four Hard bots: the Cartel King, a cartel
  and two riotkitties) and Road's End (a
  1v2 team deathmatch on `washoi_dm5`, you as the Cartel King against the
  Metropol Police duo, Officer_Wasabi and Officer_Mochi, both Insane, for
  the full ten minutes with no frag limit, a tie played on in one-minute
  overtimes; a mission's `"scoreLimit": 0` is no limit). An
  operation without art starts straight from the black screen.
- The Campaign page opens on the campaign's story, in a cream caption box
  like the comic cards' under the title and the cleared count (one line of it
  on a screen under 1000 px tall), and each operation shows its part of the story beside
  its card. The briefing over a mission's opening countdown adds a line of
  story under the goal.
- Clicking an operation's comic card on the Campaign page reads it panel by
  panel without starting the mission. The operations' titles and the cleared
  count sit on dark purple plates, the count with a segment per operation.
- The campaign has a finale card (`card9.webp`) under the last operation:
  classified until all eight are cleared, then a larger card turning slowly,
  as the comic does before a match, under a deep purple **Campaign complete!**
  plate. Clicking it reads it panel by panel.
- Survival, a gametype only the campaign plays: players spawn with the blade
  and a machine gun, and arm themselves from the map, healing a point a second up to
  100; one death loses the match.
  Robots (each with one kit, and they pick nothing up) come in waves, each one
  killed bringing the next: four alive at a time in the first minute, five in
  the second, six in the third and seven after, spawning with 30, 40 and then 50 health by the minute they spawn in. Their kits go round in turn: a
  machine gun that aims, a machine gun fired from the hip only, a grenade
  launcher (`robotKits` in the mission's `survival` rules). Robots waiting for their wave
  are listed under spectators. Lasting the five minutes wins.
- A campaign bot can be bigger than a player (`scale` in
  `config/campaign.json`): drawn bigger, holding a weapon as much bigger, and
  bigger to hit in every hit test, scaled about its feet as it is drawn
  (lag-compensated shots, beams, melee and direct projectile hits), with head,
  body and legs where they are on its body. It shoots from its own eye, and
  aims from there too: the lobby tells the bot its size. It moves faster by
  the square root of its size (about 1.6 times at 2.5), its walk and run
  animations paced to its longer stride and its crouch and slide drawn as
  much lower as it is bigger; its collision hull stays a player's.
- The lobby passes a campaign match's rules to the game server as JSON in
  `--campaign-rules` (attack side, limits, survival waves, bot sizes).
  Survival and team deathmatch missions are not rated: they have no rating
  pool.
- A spawn kit can disable aiming down sights (`adsDisabled` on
  `WeaponLoadout`): for that life, holding aim does nothing and every shot
  keeps the hip's spread. Survival gives it to its hipfire robots.
- A campaign bot can be immune to slime and lava (`"slimeImmune": true` in
  `config/campaign.json`): the game server burns it no more, and the bot,
  told so at the match start, fights on in a pool instead of climbing out.
  The Siege Bot is, wading through `washoi_amphi1`'s slime.
- A campaign bot can spawn with its own health and armor (`health`, `armor`
  in `config/campaign.json`); health above 100 is then its full health, and
  overheal decays only down to it.
- The campaign has its own music, from `washoi_campaign_soundtrack.pk3`. The
  operations page plays *Campaign Opener*, looping; opening it fades the
  lobby's music out and pauses it where it is, and leaving it brings it back
  from there (the opener likewise). Cartel Contract plays *Cartel Dreams*,
  Bot Trap *Campaign Opener*, and Siege Breaker and Road's End *Boss Fight*,
  each looping, in place of the match music; other matches are unchanged. The
  playlists are `data/campaign.playlist.json`,
  `data/campaign_cartel.playlist.json`, `data/campaign_survival.playlist.json`
  (its own file, so the lobby music key leaves Bot Trap's music playing) and
  `data/campaign_boss.playlist.json`. A one-song playlist now loops its song
  without a gap.
- `AudioManager.switchPlaylist` crosses to another playlist, pausing the one
  left to carry it on later; the newest playlist request wins over one still
  loading. A game names a match's music with `setMatchPlaylist`
  (`src/engine/audio/MatchPlaylist.ts`), which the network host plays in place
  of the game playlist.
- A campaign demo plays as its mission did: the mission's models, its bots'
  own models and sizes (the Siege Bot at its size) and the crew in green, from
  the look each mission's match is drawn with, which the client keeps from the
  lobby's campaign. It opens on the mission's comic card, then fades into the
  match; a full-match video of it opens on the comic too, drawn into the
  movie, with the music running over it.
- A full-match video's song can loop (**Loop the song**), playing again from
  its top in place of the game's songs, and the campaign's songs are in the
  song list.
- Every campaign mission shows a briefing over its opening countdown: a yellow
  plate in the upper left with the goal and the rules that decide it ("You
  must finish as top scorer!", "Win 10 rounds against the Riot Police.").
- A campaign match you did not win ends with a **Retry** button over **Back to
  the lobby**: it goes back to the lobby and starts the same operation at
  once, without its comic card.
- No account may take a campaign bot's name (`Siege_Bot`, `Cartel_King` and
  the rest), as it may not take the bot list's: a campaign gives its bots
  their looks and size by name. The game server gives a bot's size only to a
  bot, as it already did its health, kit and slime immunity. The bot tools
  (`bot:learn`, `bot:people`, `bot:demo-motion`) count campaign bots as bots.
- `config/campaign.json` refuses a key it does not know, naming it and where
  it is. A misspelt rule now stops the campaign loading, where it used to do
  nothing, silently.
- A campaign demo keeps its mission's look after the lobby stops running the
  mission: the client adds to the looks it keeps instead of replacing them.

### Lobby

- Quick play no longer readies you up. It opens the room, adds the four bots
  and votes a map, then waits for you to press **Ready**, so you can look
  around the menu first without the match loading.
- The small label over a page's title is gone where it only repeated the page
  or its lit filters: Play, Leaderboard, Demos and Settings, the welcome guide,
  credits, highlight export and the connection-lost card. The labels that say
  something of their own stay (the match lobby's status, the match menu's
  gametype and map, the player key screens).

### Search & Destroy

- The bomb is a new model, an EMP charge (`models/bomb_emp.glb` in
  `washoi_models.pk3`), in place of the bundle of dynamite built from
  cylinders. Its purple parts glow, and the lightning disc on each side
  ripples: rings run outward from the centre and the lightning wobbles.
- The carrier wears the bomb on their back like a pack, turned with them so a
  lightning disc faces whoever is behind. On a back it glows brightest and a
  purple light follows it (off with `r_dynamiclight 0`).
- Armed, the whole bomb flashes purple on each fuse beep, in place of the red
  timer light.
- The ring around a bomb on the floor is now a soft glow on the floor, turning
  slowly and fading out to the arm/defuse radius, with the floor's texture
  showing through: purple while the bomb lies loose, amber once planted, red
  and pulsing once armed, turning faster as the fuse runs down.
- Dead, you watch a teammate again, never an enemy. The camera chose whom to
  watch by reading the match's team table, which is keyed by player, with
  entity numbers, which differ once a match is under way: it could settle on
  an enemy, hide that enemy's model (bots shot at a player nobody could see)
  and put the enemy's weapons on your HUD and in your hands, among them weapons
  you never chose and could not fire, or just the blade once that enemy died.
- The machinery at wbomb1's bomb sites is solid until the site goes up, then
  gone with it. Its pipes and casing are curved patches, which collided only in
  the world model; at site A only a thin clip column in the middle was solid,
  and players, shots and bots passed through the rest. Bots rebuild their map
  graphs once to route around it.

### Combat

- Holding aim (alt-fire) through a weapon switch no longer charges the blade:
  a gun that ran dry swapped you to the blade, which started charging at once
  and threw a charged blade when you let go. A hold carried over from the
  weapon before charges nothing until it is let go and pressed again, nor does
  the aim the game adds for a gun that cannot fire from the hip; the charge
  glow on your own blade follows the same rule.

- A player could be left alive on a fraction of a point of health, shown as 0
  HP. Armor now soaks whole points, its share rounded up as in Quake 3, so
  health and armor stay whole numbers, and less than one point of health is
  death.

### HUD

- Round modes (S&D, Amphi) show an intermission between rounds, over a dimmed
  screen like the end screen's: what ended the round, the winner on a gold
  plate ("won the round!"), both sides' rounds, and "Get ready for the next
  round" counting down to the next round going live, when it lifts. It covers
  the round end and the next round's freeze, replacing the round-end banner.
  The server sends `nextRoundIn` in `match_state` for the count; a recording
  without it shows the intermission over the round end only.
- The intermission puts the two sides in the scoreboard's order, Soba left
  and Udon right; it had them the other way round, so a 4–2 lead read 2–4.
- Talk mode no longer gets stuck open. A click while typing (firing, in
  Firefox) took the cursor out of the chat line, which then took neither
  Enter nor Escape, and Enter could not open chat again; now Enter, T or Y
  puts the cursor back in the line.

### Highlight reels

- A victim's-eyes shot ends on the frag and cuts straight into the ending
  orbit. Before, the camera jumped from the victim's eyes into the killer's at
  the moment of the frag, mid slow motion, which read as a confusing switch.
  The ending orbit also keeps watching where the victim died; it used to swing
  to the killer as soon as the victim left the recording.
- Frag sequences: one player's frags chained two within 5 seconds or three
  within 10 (and on while the run lasts, ended by the killer's death) become a
  `frag_sequence` highlight, filmed as it happened: a third-person chase
  between frags, each frag through the killer's eyes with a frag counter, a
  long wait skipped through speed lines, then the ending orbit. Multi-kills
  are frags within 3 seconds; they were frags within 200 ticks, which shrank
  with the server tick rate (1.6 seconds at 125 Hz), and their window started
  3 seconds before the last frag, cutting off the first ones.
- Speed-line transitions (after the campaign comic's panel moves) jump ahead
  in time: across long waits in a frag sequence, and into about one scene in
  three, never two running.
- Freeze frames: three frag scenes of a reel end on a 1.4 s comic panel with
  a caption burst (TRIPLE!, AIR ROCKET!, SLICED!, ...). Three-frag plays, air
  rockets and blade frags get them first.
- New highlight tags: `air_rocket` (a rocket or grenade frag on a victim in
  the air, ×1.9) and `blade` (×1.6). A highlight's weapon is now the weapon
  (`rlauncher`, `blade`, ...) where the recording has it, not the kind of
  damage (`explosion`, `melee`).
- The shot card in the top right is replaced by a scene tag in the lower
  left: a comic caption with the player's name and the play (AIR ROCKET,
  4-FRAG RUN, ...), once per scene, without the kicker, victim, weapon and
  tag chips.
- The demo viewer and the video export draw the speed lines, freeze frames,
  counters and scene tags with the same code (`client/ReelEffects.ts`).
- Slow motion follows a planned speed curve with eased ramps instead of
  easing after each step, so a shot's length is known in advance.
- A highlight video with a song puts the cuts between scenes on the song's
  beats (`client/video/MusicBeats.ts` finds the tempo and beat grid).
- Reel selection counts a frag sequence's own length against the target, so a
  2-minute reel of sequences no longer runs to 2:20.
- A highlight video no longer fails with "Audio listener traversal diverged"
  when a first-person shot follows a player through a teleporter. The demo
  renderer's per-frame sample memo was keyed on the playhead alone: an event
  that sampled the followed player before the frame's lookahead snapshot
  arrived left the camera an uninterpolated pose for that frame, so the
  export's two passes could disagree. The memo is keyed on the timeline's
  version too.

### Rendering

- Hits spray from where they land, away from the shooter: tiny red cubes from
  a person, orange and yellow spark shards from a robot model, more for a
  harder hit, and a headshot sprays more with a short puff at the head. Blood
  that reaches the floor leaves a few splats there for six seconds
  (`cl_blood_splats 0` turns them off). Every piece of a colour is one thin
  instance, at most 256 pieces and 48 splats at once, and the floor is one
  trace per hit; the pieces shrink away rather than fade, so nothing blends.
  Demos show it too. Your own body, in first person, does not spray.
- Death ragdolls no longer spin and shake on the ground. A thrown body
  bounces once where it lands, its bones' spin is damped and capped, and once
  it comes to rest it lies still in its pose until it bursts.
- The quad glow shows on the carrier's body in a demo, and on the gun in
  front of you while you watch through their eyes, in a demo or spectating a
  live match. Demo playback lost a player's held powerups between recorded
  snapshots, and with them their water level and ladder: live play and demos
  now blend a player through one function (`interpolateEntity`), so a field
  added to the snapshot reaches both. In a video the glow pulses on the
  movie's clock.
- A full-match video's HUD carries only the style rules something in the HUD
  matches (about 0.38 MB in place of 1.5 MB), and is redrawn with more when
  something new shows. Every frame decodes that style, so frames decode faster
  and leave the browser less to collect: a 6:24 match now exports headless.

- Coming back to the game tab no longer rebuilds every material. The rebuild
  cost a freeze of about half a second on each return (469–551 ms worst frame
  on washoi_snd6, WebGPU), and on one return left the whole map black for the
  rest of the match. A hidden tab keeps its GPU resources; materials are now
  rebuilt only after the renderer restores a lost context or device, with
  whole-frame snapshots and the world surface replay paused meanwhile, so no
  recording made in the middle of the rebuild is replayed after it.

### Code quality

- Biome reports nothing on the whole repository, and the gate's baseline is
  zero: any new warning fails it.
  - The 21 classes that held only static members (`Cvar`, `EventBus`,
    `TimerManager`, `UIStyles`, `MessageCodec`, `BinaryProtocol` and others)
    are modules: an object of the public functions under the old name, so
    callers read the same, with their private state module-private. Tests
    reset cvars with `Cvar.clearAll()`.
  - Stylesheets order each rule after the more specific ones it could tie
    with, without changing what any rule wins; the reduced-motion download
    bar no longer needs `!important`.
- The rated gametypes are one list, `RATING_MODES` in
  `src/shared/ranking/RatingPolicy.ts` (with `isRatingMode`), where the lobby,
  the stored results, the stats queries and the profile page each wrote out
  their own.
- The match state the HUD reads resets in full when a demo ends: team
  scores, names and roles, the winner, overtime, the round's state and result
  and the campaign countdown went back with the rest. Each was replaced by the
  next match's first snapshot, except the countdown, which a match sets when
  it connects.

### Fixes from the release review

A review of the cycle's code and the systems around it before the last beta.

- **Demos** draw the S&D bomb and its sites. Their renderer was updated only
  from the game's frame, which playback does not run; demo playback now has
  its own, paused and slowed with the playhead.
- **S&D bots:** the bomb jobs (collect, arm, defuse) go to the nearest bot,
  never to a person nearer the bomb. A person picked as defuser left every
  bot on the side clearing the site while the bomb went off. The armer and
  defuser also read the round clock from the match's time limit, not the
  mode's built-in 90 seconds.
- **Campaign:**
  - a room whose mission bot drops while it waits invites that bot again;
    it used to wait for ever;
  - a cutscene skipped during its fade-in finishes playing (it held its card
    for good);
  - a boss's size and slime immunity last one match, not the bot's next;
  - splash reaches a boss's whole body: a rocket by Siege Bot's chest
    measured to the point at its feet and missed it;
  - a full-match video of a campaign demo whose card will not load starts
    with the match instead of failing.
- **Quick play** holds a Ready pressed while its bots are still coming, and
  sends it when the last is seated. Sent at once, the room started as soon as
  it reached its minimum: in S&D, a duel with the first bot. A bot request's
  safety timer ends only its own request.
- **Music:** a track put aside by a playlist switch (the campaign page's
  over the menu's) no longer moves the new playlist on when it reaches its
  end during its fade.
- **Highlight reels:** a frag chain runs at most thirty seconds; a long
  spree against weak bots became one scene of several minutes, the whole
  reel or past the four-minute export limit. A killer who dies in the frame
  of their own frag (a trade) ends the chain there; their next frag after
  respawning used to join it. Frags closer together than their slow-motion
  beat share one slow stretch in the eyes shot; the speed used to return to
  full through the second frag and drop to half after it.
- **Match runners:** a bot reaching a runner as it shuts down (its port
  reused by the next match) goes to a new runner; a runner that cannot
  start, or loses its channel, fails its bots at once instead of leaving
  them waiting; a failed nav graph build is tried again for later bots (up
  to three times a map); a failed nav cache save leaves no temporary file.
- **Lobby:** an in-process bot connection delivers the frames sent before it
  closed.
- **pk3:** reading one small file out of an archive no longer detaches
  Node's shared Buffer pool, which emptied unrelated buffers in the process.
- **Collision:** a map the WebAssembly trace cannot take (memory refused)
  traces in TypeScript on servers and bots instead of failing the map load.
- **Rendering:** material revalidations after a restored context run one at
  a time; two at once could leave snapshot frames and world bundles off.
- **Spectating:** moving on to a player already charging the blade shows
  the charge at once.
- **UI:** a confirm dialog answers once with the right callback (Confirm ran
  Cancel's too) and Escape takes all of it down; a popup closes once, keeps
  no Escape listener and can be shown again under its id at once.
- **Deployment:** the US activation checks the stage for the match runner
  before publishing anything.

### Manuals

- **The game manual looks like the game:** dark only, with the lobby's ink
  pages, gold sidebar and violet edge, stamped plates for headings, raised
  keys for buttons, the logo in the bar and on the home page, and keycaps as
  the lobby's tips draw them.
- **Bots** are documented as they run: the lobby seats them and plays each
  match's bots in a match runner, so a lobby is all a local setup needs. The
  pages that said to start `bot:server` alongside it (getting started,
  troubleshooting, server commands, the FAQ, the engine's lobby guide) now
  describe it as the alternative behind `--bot-server`. The bot page lost its
  TODO list.
- **Corrections:** the contributing guide branched from `main` (feature
  branches start from `staging`) and listed a `src/bot/` that does not exist;
  the game's home page sent you to port 5173 (the dev server is on 3000); a
  movement tip named a map that does not ship; notes that a setting needs a
  server from v1.0.0-alpha are gone, as are version histories and TODOs.
  Weapon, movement, gametype, campaign and key-binding numbers were checked
  against the source, as was every cvar the game manual names.
- **SHAGGER**, the Rust counterpart of SHAG that the native client is built
  on, has an engine manual page: how its crates map onto SHAG, bit-for-bit
  parity through golden vectors, and which SHAG changes it must follow.
- **The WebAssembly world trace** is described in the engine's physics guide.
- References from the game manual to engine guides are links.

### Known

- Rebuilding materials after a restored context reports WebGPU validation
  errors on two frames (a destroyed 256×256 `rgba16float` texture used in a
  submit) when the context was not really lost; the map draws correctly
  afterwards. Seen by firing the restore event on a healthy device; a real
  device loss has not been tested.
