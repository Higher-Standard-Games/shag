# v0.9.26

**Release Date:** 2026-10-09

## Summary

A quality release. Head hits register on hitscan weapons, and shots are judged
where the shooter saw the target. Snapshots are less than half their former
size, and the server is quieter, steadier and closed to unbounded client input.
A sweep of the client's presentation code fixed 43 problems: things that
vanished behind walls, leaked memory or carried over between sessions, plus
demo playback and the S&D spectator camera. Remote players cost far less to
draw, the bomb's blast gibs players at round end, and the post-game result
screen has its final layout.

## Changes

### Head hits on hitscan weapons

Head hits could never register for hitscan weapons: the head threshold sat
above the edge of the hit sphere. Head hits now register and do 10% more
damage for every weapon except the Riotgun, whose pellets count as body hits;
leg hits keep their 25% reduction. A head hit shows an orange damage number and
a longer crosshair flash. On the wire, a head or leg hit is a new `damage`
event code (23) with one extra byte; body hits keep code 10 and its bytes, so
older demos decode unchanged. Client and server must ship together.

### Faster snapshot encoding

`BinaryEncoder` writes strings straight into its buffer and copies the result
out more cheaply. Encoding a snapshot for 16 clients drops from about 2.4 ms to
0.4 ms, with byte-identical output.

### Smaller snapshots

Each client now gets the scoreboard roster and other players' weapon state only
until it acks a snapshot that carried their current value; after that they are
left out until they change, and every 125th snapshot (2 s) carries them anyway
as a safety net. A client's own weapon state and every gameplay event still go
out in every snapshot, and recorded demos are unchanged. A 16-player snapshot
drops from 5,809 to 2,091 bytes per client when idle, and from 5,282 to 3,415
during a firefight, about 120 KB/s less per client at 62.5 snapshots a second.
The client stores this state before anything else in a snapshot runs, and a
`match_state` without its roster says so with `rosterOmitted`. Client and server
must ship together. Plan, review and status:
`src/games/fps/docs/research/v0.9.25-network-improvements.md`.

### Fixed server tick rate

The dedicated server no longer accepts `--tickrate`. The game runs at a fixed
125 Hz and refused any other value at start-up, so the flag could only cause a
failed launch.

### Quieter server console

Per-tick, per-hit and per-message server logging is now opt-in with
`SHAG_DEBUG=phys,kb,falldamage,input,perf,discharge` (or `all`); lifecycle
messages stay.

The lines that still repeated on a healthy server are opt-in too. With 16
players (10 of them bots) a server used to print about 7 lines a second at
rest and 7 more on every death:

- The tick rate line prints only when the server falls behind (under 95% of
  125 Hz, or one tick's work taking longer than two ticks), as a warning.
  `SHAG_DEBUG=tickrate` prints it every 5 s as before.
- The per-player `[Telemetry]` line every 5 s is `SHAG_DEBUG=telemetry`.
- Respawn requests, spawn points and respawns are `SHAG_DEBUG=spawn`; kill
  lines are `SHAG_DEBUG=kills`.
- The WebSocket server no longer prints a count every 1,000 messages per
  client (one line every 8 s per player at 125 Hz input).
- Bot server: each bot's status line, its deaths, respawns and respawn retries
  are `SHAG_DEBUG=bot`. A dead bot in a round-based mode used to print a retry
  every couple of seconds until the round ended. A snapshot or message error
  prints at most once per 5 s per bot instead of on every snapshot.
- The lobby prints an unknown message type at most once per 5 s.

### Weapon switching fixes

- Picking up a weapon switches to it and stays there. Before, the server
  switched back to the weapon in your last-pressed slot on the very next tick.
- Holding alt-fire on another weapon and switching to the blade no longer fires
  a full-damage charge on release. A held alt-fire now starts a fresh charge,
  with the charge-up other players see.
- A picked-up weapon no longer inherits the old weapon's reload.

### Server robustness

- A tick that keeps failing no longer makes the loop retry it back to back at
  full CPU; the failed tick is skipped.
- Player names a client chooses are cleaned and capped at 32 characters, as chat
  is. Every name is re-sent to every client in every snapshot.
- The WebSocket server refuses messages over 64 KiB (`maxMessageBytes`), closing
  the connection with 1009. The `ws` default was 100 MiB.
- Auto-shutdown runs one countdown at a time and keeps the server for a player
  whose seat is held.
- Per-player state no longer grows for the life of the server. Weapon state is
  forgotten when a player leaves or goes to spectate (a rejoin gets a new
  entity, so each rejoin used to leave one behind), lag compensation forgets a
  player's latency on leave, and clock-sync pings are answered at most every
  25 ms.
- Anti-warp strikes now follow the player across spectate, rejoin and resume,
  and are dropped only when they leave. Before, toggling spectate wiped the
  record. The validator's documentation now says what it does: input over the
  per-tick rate cap is dropped; running out of time budget only counts a
  strike, and the real defence is one command per tick with a short input
  buffer.

### Shots are judged where the shooter saw the target

The client drew other players up to a full network trip ahead of the newest
snapshot it had received, so every remote body was extrapolated and a shot was
judged up to 58 ms (at 50 ms one way) earlier than what the shooter saw.
`SnapshotBuffer` now shifts server timestamps by the measured transit time, so
render time follows what has actually arrived. The error is under one tick at
any ping. The server still caps lag-compensation rewind at 100 ms; checking the
claimed rewind against measured ping is planned, not done (B7,
`src/games/fps/docs/research/v0.9.26-lagcomp-rewind.md`).

### Search & Destroy

- The bomb's blasts now hurt. Each blast of the detonation chain damages
  players inside its radius, falling off with distance and stopped by walls (a
  second sight line at chest height, so a low railing gives no cover). They
  land in the round-end intermission, credited to no one: no frag, no suicide,
  no death counted, and the round result is already decided.
- Spectating in S&D: every death now gets the corpse camera. Before, only the
  first death of a match did; the next ones cut straight to a teammate. A
  teammate view also ends the moment you are alive again.
- Watching a teammate shows their weapon and ammo. Your own weapon state kept
  repainting the HUD and view model over theirs.

### Client fixes from the presentation sweep

A read-through of the client's presentation code found 43 problems, most of
them one of four shapes: something switched off on one path and not switched
back on another, state left stale while a loop skipped, two cleanup paths that
drifted apart, and loads or timers that left debris. All are fixed, each with a
test that failed on the old code. What a player would have seen:

- **The game thought you always held the blade.** Every weapon got the blade's
  crosshair, there was no out-of-ammo crosshair or empty click, and rocket,
  plasma and grenade launcher never raised to the sights when fired from the
  hip. The weapon in hand is now shared with the game correctly.
- **Leaving and re-entering view** (PVS): a rocket or grenade that left your
  view and came back was never drawn again; a dropped weapon was rebuilt with a
  new toss and spin every time; a remote player came back without their hand
  weapon; a corpse could come out invisible. Dropped weapons are now always
  sent by the server and hidden by the client when out of view; projectiles
  keep their type for 11 s after last seen; models are switched on together.
- **Explosions lost their sparks after the first one**, because finishing one
  disposed the particle texture they all share.
- **Rocket and plasma lights lit the wrong spot** as far from the map origin as
  the projectile was. A light also kept dimming and moving after the pool took
  it back for a newer effect.
- **POW! hit sprites** were advanced twice a frame and lasted half as long.
- **Memory that was never released**: player models and the materials cloned
  for them, hand weapons and dropped weapons with their loader leftovers, bullet
  holes on map change, ragdolls, gibs, tracers and explosions left over on map
  unload or shutdown. One disposal path now serves death, leaving, ragdoll
  expiry and shutdown.
- **A new session started dirty**: after a match the winner showcase and endgame
  music did not return, and spectating, dead and respawn flags, powerups, air
  and water level carried over. Shutdown now resets them. Connecting to a game
  stops a demo still playing in the page.
- Smaller: the Voltaic beam kept drawing after you died; the air meter and
  drowning kept ticking while dead and showed the watched player's death;
  a blade charge ended silently on a switch or death, so others kept seeing the
  glow; dropped weapons kept a physics body after settling; the pickup prompt
  stayed up for a weapon someone else took; the teleport effect's clock stopped
  while idle; zoom did not work under water.

Findings and fix status: `src/games/fps/docs/research/v0.9.26-client-bug-sweep.md`.

### Demo playback

- Resuming a paused demo replayed the frame already on screen: shots and
  deaths sounded twice, the kill feed doubled. So did every cinematic segment
  start. A frame is now presented once.
- Cinematic reels no longer freeze on the first segment's view with the gun
  drawn on top, and flybys aim and zoom their camera.
- At 4x speed every recorded frame is delivered (catch-up is 250 ms of
  recording scaled by speed, not 4 frames). A long stall still skips.
- Picking a player while paused shows their gun and HUD at once. The reel's end
  pauses the viewer. Starting a demo while another is loading or being stopped
  no longer leaves half of it wired up. Freefly and spectator cameras are made
  once instead of on every attach (one leaked per cinematic cut).

### Cheaper remote player rendering

The client did about 460,000 short-lived allocations a second at 16 players
and 144 fps drawing other players, mostly walking each skeleton to find the same
three root-motion nodes. Root-motion nodes are found once per model; PVS
visibility is decided once and each body, hitbox and weapon is switched once
instead of on and off again; settings are read once per frame; and snapshots are
sampled into one reused object (`SnapshotBuffer.beginFrame` /
`sampleInFrame`). What a player sees is unchanged, which is pinned by a test
that records every remote player every frame against a checked-in recording.
This needs a play test for the frame-time gain. Plan:
`src/games/fps/docs/research/v0.9.26-remote-renderer.md`.

### Post-game result screen

- The winner plate ("SUNDFLUX WINS!") no longer shakes between sizes. Every
  ping change rebuilt the board and replayed the plate's slam-in, several times
  a second; pings now update in place and the plate stamps in once.
- Your own row is marked again, in gold, and your side takes the ally colour.
  The board was never told which player was you, so both sides showed the
  enemy colour.
- One composition at every window size: the winner's model stands in the left
  third with their name and stat chips above it, the board fills the right
  column without reaching over the model, and the lobby key sits under the
  board in space held for it from the start. Before, the model stood in the
  middle of the screen under the board.
- A 1v1 shows a head-to-head: each name once, and between them the big figure
  with what it counts (`2 — 0` rounds, or frags in modes without rounds). Before,
  each name appeared twice, with the plate's rounds and the row's frags side by
  side and unlabelled.

### Other

- HUD: the warmup message and ready bar no longer rewrite themselves 20 times a
  second. The warmup title's entrance animation used to restart every 50 ms
  and never finish.
- Client log lines that repeat in play (reconcile, visual offset, prediction
  reset) are behind `developer 1`. The bot server logs a fault at most once per
  5 s per bot.
- `Game.ts` shrank by about 1,300 lines: spectating (`SpectateView`), the
  match's map load (`MatchMapLoader`), liquid presentation (`LocalLiquid`),
  per-frame effects (`FrameEffects`) and input bindings (`MatchInputBindings`)
  are modules of their own, and the network host is reached through a typed
  accessor instead of casts. Snapshot events are typed end to end, which also
  fixed `item_pickup` sending the picker's id as a number on a string field.
- Benchmarks: `src/games/fps/bench/` measures snapshot broadcast to 16 clients
  and hitscan resolution. New tests cover snapshot convergence under loss and
  reorder, a golden snapshot, and what a shooter sees against what the server
  judges.
- Manual: the player and developer manual was brought in line with the game
  (lobby and accounts, gametypes, maps, combat and damage rules, settings,
  screens, a first-match walkthrough, a glossary, troubleshooting, server
  commands, and how to add a gametype or a weapon).

## Validation

On the merged `main`: typecheck, production build, Biome gate, all 470 test
files, simulation and physics checks, server tick and 1,000-tick fuzz checks
(determinism checksums match), and headless `wdm2` BSP loading passed. The
physics diagnostic still prints its step-slide warning while exiting
successfully, as in v0.9.25.

Needs a play test: remote player rendering and its frame time, shot timing at
real ping, head hits, the smaller snapshots under a lossy link, S&D spectating
and the bomb blast, dropped weapons and projectiles leaving and re-entering
view, a full match end followed by a rejoin, and cinematic demo playback. The
post-game screen was checked in a match. Not done this cycle: checking the
claimed lag-compensation rewind against measured ping (B7), and splitting
`WeaponSystem.ts` and `GameServer.ts` (B11).
