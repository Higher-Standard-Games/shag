# v0.9.15

**Release Date:** 2026-05-20

## Summary

Engine QA continuation, with two headline changes:

1. **Matrix #56 closed** — the local `map <name>` command now spawns a dedicated game server via the lobby and connects the client to it, instead of loading the BSP directly in the client and running an isolated local-only simulation branch. Single-player play, headless tests, and networked play now share the dedicated-server gameplay pipeline (`FPSSimulation` + `PickupSystem` + `CombatSystem` + `WeaponSystem` + `GametypeController`).

2. **Matrix #11 closed** — the 10 `TS18048` bitfield-narrowing false positives in `BinaryProtocol.ts` are now resolved inline with `flags & FLAG && value` guards. `tsc --noEmit` is clean for the first time in the QA series.

Plus a manual pass:

3. **`docs/manual/` accuracy pass + three new guides** (`pickup-system`, `map-launching`, `service-registries`) covering the v0.9.13–v0.9.15 architectural changes. The SHAG manual stays engine-only — no game-specific content.

4. **Washiki Washoi manual** stood up inside the fps submodule (`src/games/fps/docs/manual/`) with a full Player section (concrete numbers from code: movement, weapons, pickups+inventory, HUD) plus skeletons for Gametypes / Multiplayer / Developer / Tools / FAQ.

## Changes

### Engine QA Pass — Headless Map-Via-Server [CHANGED]

- **`map <name> [gametype]` is now server-backed.** The command no longer loads a BSP into the client and runs a one-off local `Game.initializeLocal()` simulation. It asks the lobby (`spawnDevServer`) to spawn a dedicated game server with the requested map + gametype, then `Game.initializeNetwork(serverUrl, { autoJoin: true })`. Defaults to gametype `duel`. Accepts the shorthand aliases `1v1` → `duel`, `dm`/`deathmatch` → `ffa`, `team`/`teamdeathmatch` → `tdm`.
- **`map reload`** restarts the last `(map, gametype)` pair. **`map unload`** disconnects and tears down both the gameplay launch and the client-side mesh. **`map current`** reports both gameplay map and rendered map.
- **`map` is now developer-only.** The previous always-available behaviour was masking that no real player flow ever ran `map` — players join through the lobby panel. Marking it developer-only is honest documentation.
- **Single gameplay path.** The previously-divergent local branches in `FPSController.attach()` (`initializeLocal` → manual `setCollisionWorld` + `setSpawnPoints` + `spawnLocalPlayer`) and `JoinCommand` (random spawnpoint + manual controller registration) have been removed. Both files now exclusively expect an authoritative network host; the server provides spawn points, collision, and authoritative state.
- **`bsp` family of commands** is the new path for inert mesh inspection (`bsp info`, `bsp render`, etc.) — no server needed; `map` is gameplay-only.

### Engine QA Pass — Gameplay Map Launcher Registry [ADDED]

- **`GameplayMapLauncher` interface + registry** in `src/engine/console/GameplayMapLauncher.ts` mirrors the v0.9.14 `NetworkConnector` pattern. Engine `MapCommand` doesn't know how a game starts gameplay; the registered launcher does. Two methods: `launch(map, gametype)` returns `{ serverUrl, map, gametype, matchId? }`; `unload()` disconnects.
- **FPS implementation** in the fps submodule (`src/games/fps/client/FpsMapLauncher.ts`): asks the lobby (via the new `FpsLobbyService`) to dev-spawn a server, then `Game.initializeNetwork` against the returned URL. Normalises gametype aliases.
- **Shared lobby connection** in `src/games/fps/client/FpsLobbyService.ts`: one `LobbyClient` across `FpsMapLauncher`, `DemoService`, and any future consumer. `ensureFpsLobbyConnection()` is idempotent and re-uses the in-flight connect promise. Lobby URL from `import.meta.env.VITE_LOBBY_URL` with a `ws://localhost:9000` fallback.
- **`src/main.ts` wiring**: after `registerFpsCommands()` and `registerNetworkConnector()`, also `registerGameplayMapLauncher(fpsModule.fpsMapLauncher)`.

### Lobby — Developer Dev-Spawn API [ADDED]

- **`LobbyServer` accepts `dev:spawn_server` messages** from connected clients on loopback addresses only (cross-LAN dev-spawns are rejected with an explicit error). Spawns through the existing `GameServerSpawner` and replies `dev:server_spawned` or `dev:server_spawn_failed`. Tracks `matchId → playerId` so the requesting player is associated with the spawn.
- **`LobbyClient.spawnDevServer(map, gametype, timeoutMs?)`** is the client helper. 30-second default timeout; returns `{ serverUrl, matchId, map, gametype }`.
- **`GameServerSpawner` public address override.** The spawned server's `url` field can now be derived from `SHAG_PUBLIC_GAME_PROTOCOL` / `SHAG_PUBLIC_GAME_HOST` env vars instead of being hardcoded to `ws://localhost`, so a lobby reachable from a real device can advertise a real address for the spawned game server.
- **Coverage**: new `src/lobby/__tests__/LobbyDevSpawn.test.ts` and `LobbyClientDevSpawn.test.ts`. The server-side test includes the localhost-only rejection path.

### Client Map Loader (extracted) [ADDED]

- **`src/engine/loader/map/ClientMapLoader.ts`** factors out the pure render path that used to live inside `MapCommand`. `loadClientMap(name)` does scene clear → ambient-color/material-dirty reset → `MapLoader.loadMap(name, scene)` → SkyLightSystem worldspawn reload → spawn-position teleport → `EventBus.emit("map:loaded")`. `unloadClientMap()` disposes via `MapLoader.disposeCurrentMap()`.
- The fps `Game.onServerInfo` callback now calls `loadClientMap(serverInfo.map)` directly instead of round-tripping through the console `map` command (which is no longer a render-only path).

### Type Narrowing — BinaryProtocol [FIXED]

- **Matrix #11 closed.** The 10 `TS18048` "possibly undefined" errors in `BinaryProtocol.ts` are resolved inline by tightening the bitflag guards from `if (flags & 0x01)` to `if ((flags & 0x01) && pos)`. Same for `velData`, `rot`, `weaponMeta`. The behaviour is unchanged — the flag was always coupled to truthiness — but the type system can now see that. `tsc --noEmit` is clean for the first time in this QA series.

### Server Transport Hardening [FIXED]

- **`src/engine/server/network/transport/WebSocketTransport.ts`** picks up small adjustments around graceful close and reconnect paths exercised by the new dev-spawn flow. Test coverage at `WebSocketTransport.test.ts`.

## Technical Notes

- **Architecture decision**: matrix #56's plan in `docs/research/0.9.13-QA-improvements.md` §11 proposed an in-process `ListenServerHost` (option A) as the architecturally honest answer. The shipped implementation went with **option C** (talk to a server spawned by the lobby) because:
  - The dedicated server pipeline already exists end-to-end and works correctly; no new transport bridge to maintain.
  - The real `WebSocketTransport` + `BinaryProtocol` round-trip is exercised on every `map` invocation, so the headless regression battery now faithfully covers network code without any extra binary-bridge work.
  - It mirrors actual production topology: lobby spawns servers, clients connect over WebSocket.
  - The trade-off is a lobby-server dependency and one extra child process per map launch — acceptable for dev workflows.
  - The `ListenServerHost` path remains a viable future direction if/when in-browser hosting becomes desirable (Electron desktop builds, isolated single-player without lobby).
- **Test count**: 1027 → 1041 (+14 across `MapCommand`, `WebSocketTransport`, `LobbyDevSpawn`, `LobbyClientDevSpawn`). `tsc --noEmit` clean.
- **After this release**, the only remaining engine→games/fps imports are 3 camera controllers (matrix #6/#7), `EntityManager` (type-only + dynamic, documented), and the engine `DemoViewer.test.ts`. The lobby-dev-spawn path is a hard dependency on the lobby module being present, but lobby is in `src/lobby/` (shared, not a game submodule) so this is fine.
- **`map` becoming developer-only** is intentional: real player flows go through the lobby panel UI ("press play" → match server). `map` is dev-ergonomics.
