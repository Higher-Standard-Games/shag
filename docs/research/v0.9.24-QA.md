# v0.9.24 — documentation QA and the bugs it finds

**Branch:** `0.9.24-qa-improvements` (both repositories)
**Cycle:** v0.9.24, a bugfix and documentation release
**Living changelog:** `docs/changelog/v0.9.24.md`

The manual was last written in bulk on 2026-08-12. Two releases have landed
since — water and liquid simulation (v0.9.22), then movers, lag-compensated hit
registration, the renderer and networking audits, and a lobby with accounts,
private rooms, Amphi and ranked results (v0.9.23). So the pages most worth
reading are also the ones most likely to be wrong.

This cycle reads the manual against the code, one engine part at a time. The
reading is the point: a page is only correct if someone has just looked at the
code that makes it true, and looking at that code is how the bugs turn up.

## The loop, per part

1. **Read the page.** Note every claim it makes: a command, a cvar, a default,
   a file path, an order of operations, a limit.
2. **Read the code that would make each claim true.** Not a search for the
   claim's words — the actual call path.
3. **Sort each claim** into: true, wrong, no longer exists, or true but
   incomplete.
4. **Fix what the reading found in the code.** Small, obvious defects are fixed
   in a batch as part of the same work order, each with a test that fails
   without the fix. Anything larger becomes a row in **Bigger tasks** rather
   than a detour.
5. **Rewrite the page** so it describes what the code does today. Delete claims
   that are no longer true rather than softening them.
6. **Update the matrix below and the changelog**, and commit the part as one
   commit.

## Rules

- **Evidence, not memory.** "Confirmed" means the code was read this cycle, on
  this branch. Name the file when it matters.
- **A page describes what is, not what was intended.** No aspirational
  documentation, no "should", no features that exist only in a research note.
- **`docs/known_bugs.md` is stale and is not evidence.** Entries there predate
  several releases; treat each as a rumour to verify against the code before
  acting, and correct or delete the entry as part of the part it belongs to.
- **Every code fix carries a test** that fails without it, unless it is
  unreachable from tests (a shader, a renderer draw call) — say so in the log.
- **Comments describe current code.** No before/after, no provenance, no
  references to the engine this project came from; that belongs in the commit
  message.
- **Keep this file current as you go.** Another agent, or another branch, picks
  up from the matrix alone.

worth recording.

### 2026-09-23 — WO-18 opened: the demo → training → bot loop

The goal of this stack, stated by its owner: **demos of humans playing become
training data, so bots move from hand-written rules toward human-like play over
time.** That is behaviour cloning from real matches, not only self-play RL. The
review asks one question — does that loop actually close? — and the first pass
says no, in two places.

**Finding 1: a bot a player adds can never use a trained model.**
`BotClient` loads `HybridBrain` only when constructed with `modelDir`.
`bot-server.ts`'s `--models` flag reaches bots it spawns itself at startup
(`--auto`, `--lobby`), but `BotServer` holds **no default model directory**, and
a bot requested over the control socket takes its options from the message.
The lobby sends `{ difficulty }` and nothing else (`LobbyServer`, the bot
invite). So every bot added from a room runs `StateMachineBrain`, whatever is
trained and whatever `--models` was passed. The end of the pipeline is
disconnected.

**Finding 2: demos do not contain the thing behaviour cloning needs.**
`DemoRecorder` writes full `BinaryProtocol.encodeSnapshot()` frames — *state*.
The snapshot carries `ackedInputSeq` and no buttons or aim input at all.
`DemoTrainingExtractor` says so itself ("demos store state, not inputs") and
reconstructs buttons with heuristics: `dirZ > 0.3` for forward, `speed > 1` for
**sprint**, `vy > 50` for **jump**, strafe direction from the velocity vector.
Each of those is questionable as a label:

- speed > 1 unit/s labels almost any moving player as sprinting;
- `vy > 50` labels the whole ascent as jump-held rather than the press;
- strafe from *velocity* is precisely wrong for air-strafing, where the input
  direction and the velocity direction differ on purpose — the technique the
  bots most need to learn would be taught backwards.

Aim is the exception and is sound: view angles are recorded state, and they are
what the human actually aimed.

**Sound, checked:** `HybridBrain` saves to and loads from the same layout
(`file://<dir>/tactical`, `file://<dir>/combat`), so trainer output and bot
input agree. `TFBackend` degrades native → pure-JS → none without crashing.

**The audit is now its own document.** `docs/research/BOT_TF_IMPROVEMENTS.md`
carries the goal, a map of the pipeline as it stands, eight findings — three of
them blockers — and nine work orders with an order to take them in. Two more
blockers turned up after the first pass: the training targets encode reward
rather than behaviour, so a neutral-reward frame teaches nothing whatever the
human did; and extraction takes every player in a demo including our own bots,
though demo v2 carries the verified account id that would tell them apart.

**A doc error this turned up, missed in WO-12:** `multiplayer/demos.md` listed
"All player inputs (movement, aim, fire flags)" among a demo's per-tick
contents. It records state. I verified that page's commands, transport and
phase-gating and took its format bullets at face value — the lesson being that
a list of fields deserves the same reading as a claim about behaviour.

`strings.xml`, and `MainActivity.java`'s package line — with the file moved to
`java/net/washoi/game/` to match, which is what makes this a rename rather than
a find-and-replace. The manifest names the activity relatively as
`.MainActivity` and needed no change. `npx cap sync android` regenerated the
native config with the new identity, so this is verified rather than assumed.

**Why this id, since it is permanent once published:** reverse-DNS wants a
domain the publisher controls, and washoi.net is owned while no studio domain
is. The studio name — Higher Standard Games — belongs in the Play listing's
developer field and in `game.json`'s author, not in the package id, which
identifies *this app* rather than its maker or its engine. The engine name has
no business there at all: Unity and Unreal ship placeholders naming a
fictional company (`com.DefaultCompany.*`, `com.YourCompany.*`), and no shipped
title carries the engine it was built with.

### 2026-09-23 — BT-3: the mobile splash hides

`main()` now initialises `CapacitorBridge` before anything draws, and calls
`hideSplashScreen()` the moment the engine's own loading screen is up — not at
the end of the boot. That ordering is the point: `launchAutoHide: false` means
the native splash waits for the app, and waiting until the lobby is ready would
hide every progress line behind a still image.

Both calls no-op in a browser, which is what makes calling them
unconditionally safe: `init()` adds the platform classes and returns, and
`hideSplashScreen()` returns immediately when the platform is not native. Five
tests pin that contract, including the plugin rejecting.

**This is not verified on a device.** It is correct against the plugin's API
and the bridge's own guards, and it replaces a path that definitely did not
work, but an emulator or a phone is the only thing that can close it.

### BT-2: what changing the Android identity actually touches

Not done — the application id is a product decision, and changing one changes
package identity and signing. Every place it lives, so the decision can be made
with the whole picture:

| File | What |
| --- | --- |
| `capacitor.config.ts` | `appId`, `appName` |
| `android/app/build.gradle` | `namespace`, `applicationId` |
| `android/app/src/main/res/values/strings.xml` | `app_name`, `title_activity_main`, `package_name`, `custom_url_scheme` |
| `android/app/src/main/java/com/iwmengine/ganjawars/MainActivity.java` | the `package` declaration **and the directory path itself** |

The Java package directory has to move with the id, which is why this is a

installed base to break.

### 2026-09-22 — BT-1: `bind` now binds

`bind <key> <command>` runs a console command from a key press, `unbind <key>`
and `unbind all` remove them, and `bind` alone lists what is bound. Keys are
written the way a player says them — `f`, `5`, `f5`, `space`, `esc`, `` ` ``,
`up` — or as a browser key code. Bindings persist per browser under
`engine_binds`.

The part worth stating, because it is where this could have gone wrong: this is
**not** the action map. An action binding answers what a key means while it is
held; a command binding fires once on the press. A key can be both, so binding
`space` to a command does not stop it being Jump. A press is ignored while a
text field has the keyboard, while the console is open, and when Ctrl, Alt or
Meta is held, so a binding can never eat a browser shortcut.

`CommandBindings.attach()` is wired into `registerEngineCommands()`, so every
composition that has commands has bindings without a separate wiring step to
forget, and it no-ops where there is no window.

24 tests across `CommandBindings.test.ts` and `BindCommands.test.ts`.
