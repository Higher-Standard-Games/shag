## 2026-10-02: shadow/environment audit and SSR ownership repair

Source audit findings:

- `SkyLightSystem.init()` unconditionally resets `enableShadows` to false.
  Its shadow-generator field is never constructed. `MapLoader` also explicitly
  requests shadows off for BSP maps. This is a shared existing restriction, not
  evidence of a WebGPU shadow regression. `shadow on` only changes
  `scene.shadowsEnabled`; it cannot produce missing shadow maps. Keep large-map
  shadow restoration separate from backend parity, with an isolated receiver/
  caster/depth-bias fixture before altering gameplay defaults.
- `SSREffect` selected its skybox environment only during pipeline creation.
  `ClientMapLoader` and `EngineScene` emit `map:loaded`, but the effect did not
  subscribe. Enabling SSR before a map or retaining it across map changes could
  therefore leave a null or stale off-screen reflection environment.
- Current map loading supplies its sky environment to the water path; this is
  not a general assignment of `scene.environmentTexture`. PBR materials and SSR
  should not be described as having identical environment-lighting ownership.

Implemented a bounded shared-backend repair in `SSREffect`:

- Refresh the borrowed cubemap on map completion, scene-environment changes
  and disposal of the currently bound texture. Prefer an explicit cube scene
  environment, otherwise use the map sky cube. Never dispose borrowed textures.
- Keep the same pipeline across map-environment changes; changing its existing
  environment property lets Babylon update the required shader bindings.
- Own the pipeline before configuration, so a later configuration failure
  disposes it. Scene disposal now removes effect subscriptions and its pipeline.
- New scene/texture/EventBus listeners are removed when the effect is disposed
  or rebound. Retired environment tracking uses weak references.

## Initial assessment

WebGPU needs a staged compatibility effort with observable failures and explicit
resource ownership. A shader-language rewrite by itself will not address the
startup, lifecycle, texture-upload, or render-pass problems found here.

The best first implementation is a renderer diagnostic scene and a shared
scene-initialization contract, followed by the bounded lifecycle defects below.
Keep Babylon as the backend abstraction. There is no evidence here to justify
replacing Babylon, implementing a second engine, or migrating the entire frame
to Frame Graph before the existing passes work.

**RG-2 lifecycle fixes, RG-3 KTX1 uploads and RG-1/RG-4 startup slices are implemented**
(see the implementation logs below). The accompanying
probe records defects and supplies reproductions for follow-up fixes. The latest
user log identifies oversized BSP StandardMaterial layouts behind the 14/12 UBO
failure. The glTF loader's scene-wide cap write is now reproduced and guarded;
the latest implementation log distinguishes the repair from pending GPU acceptance.

## Scope and assumptions

Audit the renderer from startup through BSP materials, lighting, auxiliary
passes, and disposal, with a practical route to supported WebGPU rendering.
This is an architecture/QA pass, not a promise to finish a renderer migration.
Keep the existing FPS composition and WebGL baseline. Bot/training work is
concurrent and outside this audit. No new branch, dependency upgrade, or
submodule edits are planned for this pass.

**Compatibility requirement reaffirmed by the user (2026-09-25):** retain full
WebGL and WebGPU support. The intended endpoint is feature and visual parity on
supported adapters, with shared material inputs and renderer ownership contracts.
The current WebGPU 2/1 forward-light caps and disabled clustered-light path are
temporary recovery measures, not accepted parity. Native Babylon materials may
select GLSL/WGSL; custom shaders can use translation or explicit variants, but
both paths must satisfy the same visual acceptance matrix. CPU/headless language
coverage does not establish GPU or pixel parity.

`wdm2` is the baseline map; water and skinned actors need separate coverage.
Headless checks establish CPU-side contracts only, never GPU shader correctness.
Distinguish source-confirmed defects, observed runtime failures, and hypotheses.

**Working preference (2026-09-26):** the user is on unreliable remote 4G. Prefer
installed source/assets, saved references and cached packages; retain useful
downloads locally and avoid repeated network fetches. Renderer research cache:
`.cache/renderer-research/` (gitignored). Current WebGPU compiler JS/WASM already

failed against the original postprocess/cel/unload code. A tenth regression

only disposes the depth texture when the renderer is in the scene registry.

Behavior changes:

- Scene service `init(scene)` binds the existing world camera, or waits until a
  camera exists. Camera changes rebuild managed pipelines and release old depth
  targets. A before-render observer handles whole `activeCameras` array
  replacement, which Babylon's array-change observable does not report.
  The first camera in a multi-camera pair remains the world camera.

  independent. Mutations no longer corrupt later resets or fresh instances.

- Dispose/reset removes the clock listener, controller-change listener and
  scene observers, and clears scene/camera references. Dispose/reinit is covered.
- Cel depth no longer mutates a scene-cached renderer belonging to another
  consumer. Its own target is camera-registered and removed/freed on disable,
  camera change and disposal. Water also frees its privately owned texture.
- `unloadClientMap()` resolves only after asynchronous map cleanup completes.

## Implementation log — RG-1 / RG-4 startup slice (2026-09-24)

Implemented an opt-in `?rendererqa=1&renderer=webgpu` / `webgl2` path before
Capacitor, game paths, service initialization and PK3 indexing. Existing static
module imports still load; this is an isolated execution path, not a separate
minimal application bundle. It compiles StandardMaterial and PBRMaterial in
turn and submits three frames per material. Reports include an explicit
`standard-pbr-smoke` scope, requested/actual backend, Babylon version,
capabilities, selected negotiated device limits, fallback stage/reason, and
first failure with stage/material/mesh/pass context. Only the first failure is
retained, capped at 4,096 characters. Reports are rendered with `textContent`,
published as `window.rendererQAReport`, and printed as `RENDERER_QA_REPORT`.

Each stage times out after 15 seconds; failure cannot become late success.
GPU validation scopes surround each fixture's compile/draw sequence, with
queue completion awaited before acceptance. Context loss, uncaptured device
errors and page errors are captured while QA runs. Device internals are limited
to the diagnostic adapter. The harness removes listeners, cancels pending frame
callbacks and disposes its scene/engine. It also disposes an engine returned
after startup timed out. Babylon initialization itself is not cancellable; a
permanently stalled internal initialization can retain partial resources until
page reload. No live-game automatic recovery is claimed.

Startup now returns the effective canvas. After attempted WebGPU initialization
fails, WebGL uses a cloned replacement canvas with the original attributes;
`main.ts` binds controls to that returned canvas. A support-only rejection keeps
the untouched original canvas. WebGL creation is outside the WebGPU catch, so
its own failure is terminal, not a second attempt. Partial WebGPU disposal is
best-effort, preserving the initialization error even if Babylon's cleanup
throws. Actual backend labels include WebGL1 and NullEngine.

Both `main.ts` and `EngineScene` call the idempotent shared light-cap setup.
Existing caps/cluster policy are preserved; this does not infer that 2/1 caps
resolve the historic 14-UBO failure. Babylon defers material-added notification;
the helper also applies caps immediately to existing materials, allowing QA to
prepare newly constructed fixtures before explicit compilation. The earlier
commentary suspicion of a synchronous constructor notification was disproved
by `Scene.addMaterial`'s deferred notification.

## Architecture traced

| Boundary | Current owner / contract | Assessment |
| --- | --- | --- |
| Backend startup | `main.ts` -> `RenderingEngineFactory` -> Babylon `AbstractEngine` | Useful existing abstraction; fallback and diagnostics need stronger contracts. |
| Scene composition | `main.ts`, `EngineScene`, `ServiceLocator.initScene` | Duplicate policy and an untyped variadic service-init boundary allow camera requirements to disappear. |
| Playable map | `loader/map/ClientMapLoader.ts` -> `MapLoader` -> `BspMeshBuilder` | Includes world, lighting, water, physics and gameplay setup; CPU loading success is not GPU acceptance. |
| Inspection map | `BspManager.load/render/clearRender` | Separate lifecycle from gameplay; test and document both rather than assuming the CLI exercises gameplay rendering. |
| Q3 compatibility | parser/registry -> `BspMeshBuilder.applyTextures` -> Standard/PBR or special material | Keep content semantics independent of backend compilation. The NodeMaterial builder is currently unused by map loading. |
| Visibility | `BspManager` + `PVSCuller` | Compiled cluster membership and fail-open behavior are useful. Visibility is mutable mesh state, so auxiliary passes must restore overrides. |
| Water | `LiquidSurfaceSystem` owns depth, refraction, probes, actor reflection and lighting | Good local ownership model and lazy shader-error fallback; GPU behavior still unverified. |
| Postprocessing | default/SSAO manager, cel outlines, SSR, god rays, FPS underwater view | Several independent camera/pipeline owners; attachment order and camera rebinding are distributed. |

## Findings

These describe the initial audit state. RG-2 fixes R5, R6, R7 and the missing
client-unload await in R8; the broader map ownership work in R8 remains open.

Priorities: **P1** affects reliable rendering/recovery or blocks trustworthy
WebGPU diagnosis; **P2** is an architectural/lifecycle defect or a substantial
coverage gap. "Probe" means CPU-side reproduction; it never implies a GPU draw.

### R1 — P1: recovery is narrower than the factory promises

[`RenderingEngineFactory.ts`](../../src/engine/rendering/RenderingEngineFactory.ts)
returns a WebGPU engine after `initAsync`, before map materials or draws exist.
Its catch only covers support/initialization failures. Shader errors and GPU
validation errors later cannot trigger its WebGL fallback.

There are two distinct initialization hazards:

- Installed Babylon acquires `canvas.getContext("webgpu")`, then initializes
  main attachments and resizes. If failure occurs after context acquisition,
  retrying WebGL on the same canvas cannot work: a canvas retains its context
  mode. A new canvas/reload is needed for this recovery path.
- The factory calls `engine.dispose()` unconditionally after initialization
  rejection. Babylon 9.17's `dispose()` dereferences `_timestampQuery`,
  `_textureHelper`, `_bufferManager` and `_device` without all being optional.
  An early rejection can therefore replace the original error with a cleanup
  error. This is a source-confirmed failure path, not a reproduced driver fault.

Existing factory tests inject whole fake engines and a rejected factory promise;
they do not exercise partial Babylon initialization or a real canvas mode.
Also distinguish requested backend from actual capabilities: `new Engine(...)`
can use WebGL1, while our result and performance report label it `webgl2`.

**Repair:** define initialization stages and a fresh-canvas/reload recovery
contract; preserve the primary error through best-effort cleanup. Add fault
injection before device creation, after context acquisition, during material
compilation, and during an auxiliary pass. Device loss and ordinary validation
errors must be reported separately; Babylon already handles device-loss recovery.

### R2 — P1: the native Q3 path is not connected

[`Q3NodeMaterialBuilder`](../../src/engine/loader/shader/Q3NodeMaterialBuilder.ts)
selects WGSL, but repository references consist of its definition, barrel export
and a factory comment. [`Q3ShaderMaterialFactory`](../../src/engine/loader/shader/Q3ShaderMaterialFactory.ts)
routes glow overlays and StandardMaterials. `BspMeshBuilder.applyTextures`
calls that factory for the glow-overlay pattern only.

Therefore the historical statement that Q3 map materials already emit WGSL via
this builder is not evidence of the live path. Nor is an unused builder a
plausible explanation of current map pipeline UBO counts.

The unused builder also treats `NodeMaterial.build()` as synchronous success.
Installed Babylon can defer build completion until block shader code loads and
reports failures through `onBuildErrorObservable`. If this path is adopted,
return a readiness promise, dispose failed materials, and preserve Q3 blending,
alpha and animation semantics; do not simply wire it in to obtain WGSL.

### R3 — P1: a stale KTX1 upload bypasses Babylon's texture ownership

**Historical finding; repaired by RG-3 above. Hardware parity remains unverified.**

[`KTX1Loader.createTextureFromKTX1`](../../src/engine/loader/texture/KTX1Loader.ts)
directly calls GL for supported compressed formats. It binds
`internalTexture._webGLTexture`; Babylon 9.17's `InternalTexture` instead holds
`_hardwareTexture`, whose wrapper exposes `underlyingResource`. The old field
exists inside the WebGL wrapper, not on `InternalTexture`.

The shape-based upload probe records **undefined passed to bindTexture**, then
`isReady = true`. Actual driver output is unverified, but the API mismatch is
confirmed. Direct GL binding also bypasses Babylon's binding cache/recovery
bookkeeping, so changing the field alone is not a complete architectural repair.

WebGPU cannot take this compressed path at all: support checks require `_gl`.
DXT falls back to CPU RGBA decoding and regenerated mipmaps; other unsupported
compressed formats return null. That is a performance/content parity difference
even on an adapter that supports BC/ETC/ASTC textures. Retain image fallbacks and
move uploads through Babylon's texture APIs with explicit capability checks.
Keep KTX2 worker timeout/retry handling: it already addresses a real failure mode.

### R4 — P1: renderer policy differs between composition paths

[`EngineScene.createScene`](../../src/engine/EngineScene.ts) registers a global
material-light cap observer. Active [`main.ts`](../../src/main.ts) constructs
its own scene without it. Major model/BSP/effect factories do call
`applySafeMaxSimultaneousLights`, so this finding does **not** prove the
historical 14-UBO material has been located.

Cluster support, GPU rain eligibility, model caps and weapon overrides are
distributed among subsystem files. The cluster gate checks only `!isWebGPU`;
the light policy uses fixed 2/1 Standard/PBR budgets, not observed layout costs.
These policies protect known configurations but do not form a complete hardware
support contract. Do not raise caps or request every optional feature blindly.

**Repair:** one shared scene-renderer setup function and an immutable capability
profile, built from actual backend, device limits and explicitly validated
features. Keep conservative feature policies distinct from hardware capabilities.
Report material family, mesh, pass, defines and binding counts when compilation
or layout creation fails. Measure the offending layout before trading away lights.

### R5 — P2: the service contract loses the initial camera

[`ServiceLocator.initScene`](../../src/engine/core/ServiceLocator.ts) calls
`init(scene)`; [`PostProcessingManager.init`](../../src/engine/effects/PostProcessingManager.ts)
requires `(scene, camera)`. Probe: the scene has an active camera, but the manager
reports initialized with neither a camera nor a pipeline. A subsequent
`camera:controller_changed` event can repair this through `setCamera`, which
makes startup correctness depend on event order.

**Repair:** explicitly accept a scene/camera context or resolve the active camera
inside this service; represent waiting-for-camera separately from ready. Add
tests for initialization, no camera yet, first camera, and camera replacement.

### R6 — P2: postprocess lifecycle and settings are not isolated

The same manager has three confirmed problems:

- `clock:tick` subscription is never saved/unsubscribed. Probe listener count is
  0 before initialization and 1 after disposal. A reset can retain an old manager.
- Both initial settings and reset shallow-copy nested defaults. Calling
  `setBloomIntensity(0.73)` then `resetToDefaults()` leaves 0.73, not initial 0.3.
- Master disable returns before `updateSSAO()`. A disposal-sentinel probe shows
  zero SSAO disposals and a retained pipeline. Individual setters can also enable
  effects while the master setting is false. The sentinel tests control flow,
  not a real GPU SSAO pass.

**Repair:** own all subscriptions, clone fresh nested defaults, and make one
effective-settings application path enforce the master flag consistently.
These are bounded fixes suitable for the first implementation batch.

### R7 — P2: disabling outlines leaves their depth pass enabled

[`CelOutlinePostProcess`](../../src/engine/effects/CelOutlinePostProcess.ts)
obtains a scene-cached depth renderer but `destroyPostProcess` only disposes the
postprocess. Enable -> disable on NullEngine leaves one registered depth renderer
with `enabled = true`. Changing cameras can leave old-camera depth resources too.

Water's [`WaterDepthProvider`](../../src/engine/rendering/water/WaterDepth.ts)
already demonstrates a better contract: its encoding, camera registration and
disposal belong to one consumer. Reuse that ownership principle. Do not blindly
disable a scene-cached renderer if another consumer could own it. A future depth
pool must key by camera, encoding, format, dimensions and render-list policy.

### R8 — P2: map ownership is split across several cleanup paths

[`BspManager.clearRender`](../../src/engine/loader/bsp/BspManager.ts) disposes
meshes and lightmap textures but not their materials. The probe confirms both
root/child mesh disposal with the material still in `scene.materials`.
`MapLoader.disposeCurrentMap` similarly clears geometry and caches, whereas
`MapRenderer.clearMap` uses material-name prefixes. Normal client map loading
also executes `scene clear`, which can mask deficiencies in a lower-level API.
This audit proves the isolated cleanup gap, not an end-to-end per-map GPU leak.

There is also a definite missing await:
[`unloadClientMap`](../../src/engine/loader/map/ClientMapLoader.ts) invokes async
`disposeCurrentMap()` without returning/awaiting it. Awaiting the public unload
function therefore does not guarantee materials/caches are released.

**Repair:** make the map build return one disposable resource owner for meshes,
materials, owned textures, observers and auxiliary passes. Shared cache textures
need explicit shared ownership; do not indiscriminately force-dispose every
material's textures. Make both inspection and gameplay cleanup use that owner.

### R9 — P1: loading success is not a renderer readiness gate

[`MapLoader.loadBspMap`](../../src/engine/loader/map/MapLoader.ts) catches shader
warmup/readiness exceptions and continues. `scene.whenReadyAsync()` does not by
itself prove a successful GPU submission; no bounded timeout/cancellation wraps
it here. Background maps skip warmup and readiness entirely.

The method also adds a DOM `visibilitychange` listener before PK3/BSP work, but
removes it only on the later success path. A null BSP early return or an exception
leaves the listener and loading flag behind. The outer catch reports failure
without a transaction that disposes partially created render resources.
Async area-light source loading/preprocessing is launched with `void` without
an error handler in [`AreaLightPanel`](../../src/engine/lighting/AreaLightPanel.ts);
failed texture loading can become an unhandled rejection.

**Repair:** one cancellable map-load transaction, cleanup in `finally`, generation
checks before committing results, and explicit distinction between required
render resources and optional effects. Required render failure must be visible
as failure; optional effects can fall back with a recorded reason.

### R10 — P2: pass ordering is an informal convention

`PostProcessingManager.rebuild()` documents a requirement for outside passes to
notify the manager after attachment. Repository search finds its definition but
no caller. God rays and cel outlines attach independently; SSR manages its own
pipeline; water attaches camera render targets. This is a contract with no
enforcement, not fresh proof of a black-frame bug.

**Repair:** a small pass registry that owns ordering, cameras, input/output
encodings, attachment and teardown. Express linear HDR vs display color,
view-space depth vs normalized depth, world vs weapon visibility and size policy
in each pass description. Preserve water's existing color-space flags and
visibility restoration. Frame Graph can later implement this contract; migrating
to it is not a prerequisite for making ownership explicit.

### R11 — P2: current tests cannot close WebGPU acceptance

The renderer suite is substantial, but Node/NullEngine does not validate native
GPU shader compilation, resource layouts, render targets, or output pixels.
Factory tests use fake engines. Many water tests intentionally grant float-target
capabilities to NullEngine to test lifecycle behavior. These tests are useful
and should remain, with a separate GPU gate.

The initial audit lacked a current 14-UBO reproduction; the later user log above
now provides one, but shader attribution remains open. Babylon's GLSL processor groups leftover uniforms into a
UBO; counting source `uniform` lines is not a valid UBO-budget measurement.
It also adjusts `gl_FragCoord` and vertex Y for WebGPU. Raw GLSL spelling alone
does not prove a water UV flip, and adding another unconditional Y flip is unsafe.

Physics/map smoke scripts also have limits: they print warnings while exiting
zero, and the fuzz invocation ran 10,000 rather than requested 1,000 ticks.
Check output and requested configuration, not only process status.

Installed Babylon 9.17 source establishes two problems:

1. `KhronosTextureContainer2._createTexture` temporarily replaces width/height
   for each raw mip upload and never restores the base extent. The default KTX
   loader then passes the last mip's 1×1 extent to the engine's load callback.
2. WebGPU's raw upload forwards `invertY` to its texture manager. The optimized
   `invertYPreMultiplyAlpha` path caches a temporary target and bind group on the
   hardware texture, including the first source mip view. Subsequent mip uploads
   reuse that view/target, then copy progressively smaller rectangles into later
   mips. This is a concrete mechanism for the camera-dependent enlarged pattern.

The sidecar converter and runtime TGA parser both produce top-to-bottom rows.
Compressed uploads already retain that order, while the raw fallback requested
an extra flip. The new narrow `KTX2SidecarLoader` keeps Babylon's decoder/upload
loop, suppresses that flip, restores the decoded base dimensions after upload,
and retains a dedicated loader extension for device restoration. The public
Texture constructor also retains `invertY: false` and the forced extension.
The registry entry does not replace Babylon's normal KTX/glTF loaders. Existing
PK3 source-image fallback, texture caching and compressed mip selection remain.
No camera, billboard geometry, material UV or shader-language change is needed
for this repair. Both backends use the same sidecar row-order contract.

The scene has three white boxes: Standard, PBR and synthetic one-bone PBR.
Ambient + directional sun + one cluster occupy three material light slots;
caps are 6/4/4. It exercises five phases:

1. One intensity-zero clustered light establishes each material's dark baseline.
2. Light 0 contributes red.
3. Grow to 40 lights, then light 32 contributes green (second WebGPU mask batch).
4. Freeze all materials, then light 39 contributes blue.
5. All 40 lights contribute together while materials remain frozen.

Equal-depth light placement preserves insertion order in Babylon's stable sort,
so indices 32/39 really target the second 32-bit WebGPU batch. The WebGL path
uses the same logical lights with its own native batch size. Pixel readbacks
sample each box face in the render task before presentation, normalize RGBA/BGRA
using the actual WebGPU attachment format, and require the intended channel to
increase over baseline. A ready effect with missing illumination fails the test.
The report records material/phase, compiled cluster/light counts, membership,
frozen/skinned state, mean RGB and readback format. It keeps all 15 records.
Compilation, GPU validation and readback are bounded by the existing stage
timeout; scene/device cleanup remains owned by the outer QA entry.
