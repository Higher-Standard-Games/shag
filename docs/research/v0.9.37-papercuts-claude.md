## 1. Leaked match servers

### What production shows

At 2026-10-19 13:40 UTC two lobby-spawned servers from the previous evening
(ports 7782 and 7784, private FFA, `--shutdown --single-match`) were still
running after 15–16 hours, with no established connections, each at
~275 MB RSS and 2.7 % of a core (ticking an empty world at 125 Hz).

The lobby journal for port 7782:

1. 21:55:48 — the last human leaves; `No human clients remaining — shutting
   down in 5 seconds...`
2. The same client reconnects at once to resume:
   `Shutdown timer cancelled — client connected`.
3. The match is in post-game, so no seat is held:
   `Resume refused: no seat is held for that token`.
4. That connection never joins. It closes on its own 11 minutes later
   (22:08:02); nothing re-arms the shutdown. The server runs forever.

Port 7784 shows the identical sequence.

### Cause

`GameServer` cancels the shutdown countdown on any WebSocket connect
(`GameServer.ts` ~1171), but `handleDisconnect` returns at once for a
connection that never became a client (`if (!client) return;`, ~1182), so the
empty-server check that arms the countdown never runs again. The
post-game grace close (`Post-game grace elapsed — closing remaining
connections`) iterates only joined clients and does not close it either.

### Fix

- Run the empty-server check on every connection close, joined or not, and
  after a refused resume; or cancel the countdown on **join** (a real client),
  not on a bare connect.
- Close unjoined connections in the post-game grace close too.
- Optionally a backstop: a single-match server that has been empty of humans
  for, say, 60 s exits regardless.
- Test: connect, start the countdown, connect a socket that never joins and
  closes; the server must still shut down.

The two leaked processes can be stopped by hand now (owner's call; they hold
no players).

## 2. Demo save freezes the match

### Evidence

Production logs `maxTickWork` 300–498 ms in ten 5-second windows over 24 h,
each at a match end (for example port 7810 at 13:20:49, the minute its duel
demo was written). Every player in that match freezes for that long: at the
end of a match, and — through save-on-leave — **mid-match** for anyone still
playing when the last human leaves.

`DemoRecorder.stop()` runs on the tick thread: `_buildDemoBuffer` (concatenate
every frame), `zlib.gzipSync(level 6)`, then `fs.writeFileSync`. Locally the
largest recording (`wfbomb1_snd_20261018_193741`, 26 minutes) is 218 MB raw:
`gzipSync` takes 650 ms here and the concatenation another 22 ms. The
production CPU is slower.

The recorder also keeps every encoded frame uncompressed in memory until the
end (full snapshots at 62.5 Hz, ~2.2 KB each in a 4-player FFA), so a long
match grows the server by up to ~200 MB just to record it.

### Fix

- Finish the save off the tick thread: `zlib.gzip` (libuv thread pool) and
  `fs.promises.writeFile`. `stopRecording()` is already async; the tick must
  not await it.
- Better: compress as it records. A streaming gzip (`zlib.createGzip`) fed a
  frame at a time keeps memory at the compressed size (~12 MB for the same
  match) and leaves only a small flush at the end. The index table and footer
  (with the duration) already follow the frames. The header does not: it
  carries the player list, which grows as players join late, so it is known
  only at the end. Two ways round it:
  - write header, frames and index/footer as three concatenated gzip members
    (frames compressed while recording, the other two at the end). Node's
    `gunzipSync` reads concatenated members; the browser path in
    `DemoReader` uses `DecompressionStream("gzip")`, whose handling of a
    second member must be verified in Chrome and Firefox first;
  - or move the player list to the footer, a demo format version bump with a
    reader for both versions (`protocol-change` skill).
- Measure: tick-rate diagnostic around a save on a long recording, before and
  after; server RSS over a long match.

## 3. Bundled server processes

### Evidence

Production runs the lobby, the bot server and every match server through
`vite-node`, which transpiles the TypeScript sources at start
(`/srv/washoi.md` §9). The repo already builds bundles
(`npm run build:server` → `dist-server/*.mjs`), and the spawner already runs
`dist-server/headless-netserver-v2.mjs` when the lobby itself runs from a
bundle.

| Match server start, `washoi_dm2`, local | Ready for connections | RSS 5 s after ready |
| --- | --- | --- |
| `vite-node src/cli/headless-netserver-v2.ts` | 1.11–1.20 s | 264–272 MB |
| `node dist-server/headless-netserver-v2.mjs` | 0.26 s | 122–123 MB |

Production: 41 spawns in 24 h took 1.9–4.4 s (median 2.5 s) from
`Starting game server` to `Server ready`. Live RSS: matches 275–325 MB,
lobby 326 MB, bot server 591 MB, all under the lobby's 10 GB cgroup cap
(matches are its children).

### Change (production — owner's decision)

- `deploy.sh`: run `npm run build:server` with the backend, writing to a
  temporary directory and renaming it over `dist-server/` so a spawn never
  reads a half-written bundle.
- `washoi-lobby.service` (and `washoi-bots`): `node dist-server/<entry>.mjs`
  instead of `npx vite-node`.
- Consequence to accept: match-side code then changes on **rebuild**, not on
  the next spawn from the working tree. The deploy rebuilds on every backend
  change, so in practice it is the same, but the rule in `/srv/washoi.md` §9
  ("match-side changes apply without a lobby restart") must be rewritten.
- `scripts/build-servers.mjs` bundles the match server and the lobby, not the
  bot server (`src/cli/bot-server.ts`); add it (it loads TF.js native modules,
  which may need to stay external). Keep bundle sourcemaps out of any public
  path.

### Production switch (deferred)

Kept as it is for now by the owner. When it is done, on `washoi.net`
(`/srv/washoi.md` §9 and §13 describe the current setup):

1. `deploy.sh`: when the engine or fps commit changed, run
   `npm run build:server` as `washoi` after `npm ci` (it stages and swaps
   `dist-server/` itself).
2. `washoi-lobby.service`: `ExecStart=/usr/bin/node dist-server/lobby-server.mjs --port 9000 --data-dir /srv/washoi/server-data`
   (same `WorkingDirectory`, `EnvironmentFile`, `User`, `KillMode=mixed`).
   The spawner then launches `dist-server/headless-netserver-v2.mjs` itself.
3. `washoi-bots.service`: `ExecStart=/usr/bin/node dist-server/bot-server.mjs --port 9100`.
4. Build once by hand, then `systemctl daemon-reload` and restart both units
   while no room is live (a lobby restart ends its rooms).
5. Verify: `ps` shows `node dist-server/...` for lobby, bots and the next
   match; spawn-to-ready in the lobby journal (2.5 s median today) and match
   RSS (275–325 MB today) drop; a bot joins a lobby match.
6. Rewrite the runbook rule "match-side changes apply without a lobby restart":
   with bundles they apply at the next spawn **after a rebuild**.
7. Rollback: restore the two `ExecStart` lines (`npx vite-node src/cli/...`)
   and restart.

## 4. Commands sent three times over TCP

`NetworkGameHost.sendCommand` keeps the last three encoded commands and sends
all three as separate messages, every command (`COMMAND_REDUNDANCY = 3`). The
redundancy is for lossy datagrams; over WebSocket (TCP) every message arrives
exactly once and in order, so two copies in three are discarded by the
server's sequence check — after `decodeCommand` has parsed them.

Upstream per client: ~375 command messages (42 bytes each, plus the
WebSocket frame header) and 62.5 ACK messages a second. Browsers send
WebSocket frames with Nagle off, so on an idle socket most become separate
TCP segments, each with ~52 bytes of TCP/IP header. Rough upload: ~40 KB/s
today, ~16 KB/s with one copy, ~8 KB/s with one message per frame — an
estimate to confirm with a packet capture, not a measurement.

The v0.9.36 production test showed the upload is where a busy or tunnelled
connection queues first.

### Steps (network: one at a time, each measured)

1. **Client only:** send each command once when the transport is a reliable
   stream (`WebSocketTransport`); keep the redundancy for the datagram
   transport (`WebTransportTransport`). The server already accepts this
   unchanged. Validate with a two-client local test and the netcode
   simulation (`.cache/netsim/e2e-spike.ts`), and count bytes and messages
   per second on the server socket.
2. **Protocol change (later):** one message per frame carrying that frame's
   commands, with the snapshot ACK folded in. Needs a new message type, the
   server accepting both shapes, and the `protocol-change` skill's checklist.

## 5. The editor's default texture is gone

The editor's default brush shader is `blx/blx_grid` (`Operations.ts:51`,
`Generators.ts:51`, `EditorSession.ts:343`, `RoomTemplate.ts:3`). It came
from the Warsow data; none of the shipped `washoi_*` packs, the map packs or
the engine assets contain it (`washoi_textures.pk3` has other `blx_*`
families, not `blx/blx_grid`). So:

- in production, every new brush and room template in SHAGGED uses a missing
  texture;
- `ConvexCompile` (2), `NaturalCompile`, `PlaytestCompile` and
  `RoundPatchCompile` fail on every full test run, so `test:run` is never
  green and a real regression can hide behind "the known five".

Fix: ship an engine-owned grid texture with the engine assets (the editor is
engine code) and point the four defaults at it; the compile tests then run
against data the repository controls.
