## Fixed

### 1. The lobby ran out of reachable game ports

`GameServerSpawner.allocatePort` counted up from 7777 for the life of the lobby
and never handed a freed port out again. Production's ufw allows
`7777:7850/tcp` (`/srv/washoi.md`), which is 74 ports. The production lobby has
run since 2026-10-20 16:38 UTC, spawned 14 matches, and its last match is on
port 7790 (read-only check of the `washoi-lobby` journal). At that rate it
crosses 7850 in about nine more days of uptime, sooner with launch traffic.
From then on every new match starts on a port the firewall drops, until the
lobby restarts.

The spawner now takes the lowest port from 7777 that is:
- not held by a running match;
- not reserved by a match that is still starting;
- free on the machine (`portIsFree`, a bind probe on `0.0.0.0`, which is how a
  game server binds it).

The reservation keeps two matches that start together off the same port. This
also fixes finding 5: during the playtest, a port held by another local lobby
failed a match with `EADDRINUSE`.

Tests: `src/lobby/__tests__/SpawnerPorts.test.ts`:
- a port another process holds is passed over;
- two concurrent spawns get different ports;
- a freed port is reused.

`GameServerSpawnerAdmission.test.ts` now waits for the child to exist before
writing its ready line, because port allocation is asynchronous. All 39 lobby
test files pass (347 tests), including the integration tests that spawn real
match servers.

**Deployment note:** the production lobby keeps the old behaviour until this
reaches `main` and it restarts.

### 2. Live gibs never drew

In live matches every gib draw failed with `GL_INVALID_OPERATION`, "uniform
buffer too small". A draw hook on `Mesh.render` with `gl.getError()` found:
- all failures were on `gib_*` meshes;
- 84 of 84 gib draws failed in the first diagnostic run;
- every one of five natural live duels failed every gib draw.

Demos were fine, which matches the report "they show in demo".

At the failing draw, WebGL's own uniform-block query showed:

```text
Material@0 need 1168 bound 1072     (96 bytes short)
Scene@1 need 272 bound 272
Light0..Light4  need ≤ bound
```

Why the Material block was 96 bytes short:
- 96 bytes is exactly the six `vec4` uniforms of `AtmosphericFogPlugin`.
- The plugin is registered with `RegisterMaterialPlugin`, which gives it only
  to materials created afterwards. It registers when `WorldFogController` is
  first built, inside the `MapLoader` constructor.
- `FrameEffects` creates the live gib system's three `StandardMaterial`s on the
  first game frame, before any map loads. Of 237 StandardMaterials in a live
  match, those three were the only ones without the plugin.
- With fog off, a material with the plugin and one without have the same
  define set. Babylon's effect cache can therefore hand the gibs a program that
  declares the plugin's uniforms, sized for a buffer the gib material never
  built.
- Which material compiles that program first decides whether gibs draw, which
  explains why the failure was intermittent between runs.
- Demo playback builds its gib system after the map has loaded, so its
  materials carry the plugin.

Fix:
- `src/main.ts` builds `WorldFogController` right after creating the game
  scene, before any game material exists, so every Standard and PBR material
  gets the plugin.
- So that materials outside the game (the menu logo, model previews) are not
  fogged now that they also carry the plugin, the plugin only switches on for
  materials in the scene whose map set the fog: `WorldFogController.isDrawingIn(scene)`.

Verified in the browser:
- all 237 StandardMaterials carry the plugin;
- three natural live duels with frags and gibs had no failed gib draws;
- a direct gib-burst probe drew 84 of 84.

Test: `WorldFogController.test.ts`, "fogs only the map's scene".

### 3. A tab return froze the gibs' materials

`revalidateMaterials` (`EffectPreloader.ts`) runs after a map load that was
backgrounded and on every tab return (`Game.revalidateAfterTabReturn`).
- Its first step unfreezes every frozen StandardMaterial.
- Its last step froze every unlit StandardMaterial in the scene, including ones
  nobody had frozen, such as the gibs'.
- A frozen material keeps the shader built for the light set it was frozen
  with. When the set changes, its draws fail.

Reproduced in a live match:
- simulate a tab return: the gib materials go from unfrozen to frozen;
- toggle the moon light, which the day/night cycle does, or add a light: the
  next gib bursts fail 8 to 26 draws each.

The last step now re-freezes exactly the materials the first step unfroze.
After a tab return the gib materials stay unfrozen, and the moon toggle no
longer breaks them.

A side effect, intended: lightmapped world materials, which `MapLoader`
freezes and `trackFrozenWorldMaterials` watches, are frozen again after a tab
return. Before, they stayed unfrozen for the rest of the session.

Test: `EffectPreloader.test.ts`, "re-freezes only what it unfroze". It fails on
the old code.

### 4. Two ways to lose gibs at load

In `FrameEffects`:
- **Ragdoll bursts.** The ragdoll→gib burst callback was wired only if the gib
  system had finished loading before the ragdoll system. Both load in the
  background, so a ragdoll that loaded first never burst into gibs on expiry.
  The callback is now always wired, and queues the burst until the gib system
  is ready.
- **Queued spawns.** The queue of gibs waiting for the gib system was replaced
  with a new array on flush and on `clearWorld`. Game's event context holds the
  original array, so later queued gibs were never spawned. The queue is now
  emptied in place.

Tests: two new cases in `FrameEffects.test.ts`. Both fail on the old code.

Not changed, and worth a design decision: body-part "drop" gibs never bounce
(`bounced = isDrop`, "just fall through"). They sink through the floor about a
second after the burst, in demos and live alike, which reads as gibs
disappearing.

### 6. Dropped weapon barrels

`DroppedWeaponRenderer.loadBarrelModel` imported
`/data/models/weapons/glauncher/glauncher_barrel.glb` (and the plasma gun's)
as a loose URL. Those files ship only inside `washoi_weapons.pk3`, so the
request got the HTML page back ("Unexpected magic") and the dropped weapon had
no barrel. It now resolves the model through `resolveModelAsset`, as the view
weapon's `WeaponBarrels` does. In a demo replay, barrel warnings went from 3
to 0.

### 7. Highlight card over the kill feed

In a match the kill feed is top left (`.fps-event-feed`). The top right holds
only the FPS plate. The reel's shot card (`.dvh-card`) now sits top right,
mirrored: slant on the left, gold edge on the right, text right-aligned. It was
checked in a screenshot of a reel.

## Open

### Voltaic beam disappearing in a highlight reel (not reproduced)

Played `washoi_dm2_duel_20261022_202135` (10 minutes, 34 recorded beam runs
from both players):
- plain playback: the beam was live in every sample taken during 7 seeked beam
  runs;
- highlight reel: the beam was live in 25 of 26 samples during beam runs.

Ruled out:
- frustum culling: the beam meshes use `alwaysSelectAsActiveMesh`;
- GL errors during demo playback: none, with the draw hook over every beam run;
- a stuck presentation clock: it follows the playhead.

The samples count live beam instances. They cannot see a beam that is live but
drawn somewhere wrong. The time in the reel where it vanished would narrow
this down.

### Smaller leads, not investigated

- Live duels counted 36–58 prediction corrections per 75 s, the largest
  467–868 units. Those sizes look like respawn teleports counted as
  corrections, but this was not traced.
- One `GL_INVALID_VALUE` on the player-outline `ProxyMesh` in one of four live
  runs.
- Console noise:
  - `[EntityRegistry] Overwriting existing definition` ×40 per match:
    `initializeEntityDefs` runs from both `MapLoader` and `Game`;
  - `[ProjectileManager] Explicit texture not found` for four projectiles: the
    definitions name `.tga`, the files are `.png`, and the MD3s load their own
    textures anyway;
  - a missing `ammobox.md3`.
- `src/engine/version.txt` still reads 0.9.37, which the lobby shows as
  "v0.9.37".

## Reviewed and sound

Server and netcode, read against the source:
- **Health privacy (fps `ec32081`).** Clients and bots decide death from the
  `dead` flag, never from health. Spectators and teammates keep the bars, and
  demos record the unfiltered state.
- **`copyOnWrite: false` on the live server.** Re-simulating weapons, combat
  and projectiles with copy-on-write on and off gave identical per-tick
  checksums: 5 seeds × 1,500 ticks × 4 players. Lag compensation and snapshots
  copy values. The gametype's `lastState` reads only `ownerId`.
- **Input sequence peek.** It matches the full decode's layout, and is tested
  against it.
- **PVS cluster cache.** Equivalent to `isVisible`, including the fail-open for
  points outside the BSP.
- **Damage merged once per snapshot.** Equivalent; the buffer was already
  accumulated across ticks.
- **Kill list view, reused movement input.** Nothing keeps a reference past
  the call.
- **Blade ammo, pickup writes through `getEntityMut`, bot LOS cache sharing.**
- **Allocation-free BSP trace recursion.** Each split point is only read by
  its own subtree. The lift and brush-model loops write in place, from their
  own copies of the start and end points.
- **Demo save off the tick thread, empty-server and spectator-only shutdown.**
  In the playtests, match servers exited with code 0 five seconds after the
  last human left.
- **Account deletion.** The row is kept and renamed, a random hash replaces
  the key's, and settings are dropped. Every connection on the account is
  closed, and demo listings are renamed on every rescan.
