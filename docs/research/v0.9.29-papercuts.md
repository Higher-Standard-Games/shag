## Findings and acceptance criteria

### PC01 — retain keys when persistent storage fails

[`AccountSession.ts`](../../src/lobby/AccountSession.ts#L72) catches storage
errors, but `storedPlayerKey()` reads only localStorage. No in-memory accepted
key survives, despite the comment saying it lives for the session. Login can
succeed while Profile cannot retrieve/export its key.

**Reproduce:** allow reads, throw `QuotaExceededError` on writes, log into a
fresh account, then log in on a new connection. Probe observed a null stored
key and two different account IDs. This does not claim that every private
browser window blocks storage.

**Fix:** retain the accepted key in memory for reconnect/export and show a
session-only warning when persistence fails. Preserve unknown-key recovery and
invalid-restore behavior. Never log the key or put it in profile JSON.

**Done when:** reconnect keeps the same account, Copy/Save remain usable,
failed restore retains the old key, and normal persistent accounts still work.
A reload with all storage blocked cannot preserve a key without an export;
explain that limitation to the player.

### PC02 — settle every connect attempt

[`LobbyClient.connect`](../../src/lobby/LobbyClient.ts#L41) clears its timer on
close without rejecting a promise that never opened. Explicit
[`disconnect()`](../../src/lobby/LobbyClient.ts#L98) makes the socket noncurrent;
its timeout later returns without settling. Both probes remained pending after
six seconds with a five-second timeout and no timer left to settle them.

**Fix:** one settlement/cleanup path per attempt; reject early close,
cancellation and replacement while preserving protection against late old-socket
events. **Done when:** early close, cancel, replace, error, timeout and success
settle once, leave no timer, and permit the next reconnect.

Browsers commonly emit an error before a failed connection's close, which is
already handled. These controlled probes establish unhandled paths, not their
production frequency.

### PC03 — offer offline recovery

[`LobbyPanel.logInToLobby`](../../src/games/fps/client/LobbyPanel.ts#L492) gives
`lobby_full` a retry notice, but other failures leave the disconnected state.
Its disconnect listener clears modes and disables play/chat.
[`FpsLobbyService`](../../src/games/fps/client/FpsLobbyService.ts) clears its
authentication flag without reconnecting. LobbyClient's `reconnectTimer` field
does not schedule a retry. No ordinary offline Reconnect key was found, even
though the chat text asks the player to reconnect.

**Fix:** a visible Reconnect key using the existing login function; disable it
while attempting and keep settings accessible. Automatic backoff is optional.
**Done when:** initial outage and later disconnect recover on the same account
without reload/console; overlapping attempts and updates after destroy are
prevented. Pin these UI paths with tests before coding; no live outage was induced.

### PC04 — bound lobby requests before parsing

[`LobbyServer.start`](../../src/lobby/LobbyServer.ts#L501) omits `maxPayload`.
Installed `ws` defaults to `100 * 1024 * 1024` bytes, confirmed from
`node_modules/ws/lib/websocket-server.js` and a `noServer` instance. The
[`game transport`](../../src/engine/server/network/transport/WebSocketTransport.ts)
already defaults to 64 KiB. Player admission caps do not bound requests from
unauthenticated sockets.

**Fix:** an explicit lobby request limit, starting from 64 KiB and checking
legitimate request sizes, plus text-type checks before `trim()`. This concerns
inbound messages, not the potentially larger outbound welcome/demo list.
**Done when:** oversized requests close with 1009 before application parsing;
auth, chat, rankings, room and bot-reference requests still work; malformed chat
does not repeatedly produce parse-error logs. No large-payload flood was run.

### PC05 — show boot failures and recovery

[`main.ts`](../../src/main.ts#L371) ends in `main().catch(console.error)`.
Awaited initialization can reject after boot UI is shown;
[`GamePaths.init`](../../src/engine/core/GamePaths.ts#L66), for example, throws
when required `engine.json` is unavailable.
[`LoadingScreen`](../../src/engine/ui/LoadingScreen.ts) has progress and
Start/Starting states but no terminal failure action.

**Fix:** an accessible startup error, Reload/Try again and a copyable diagnostic
summary. Reload is enough for alpha; retrying partially initialized systems
requires cleanup. Exclude credentials from diagnostics. Keep PK3 mirror fallback
with its owner. **Done when:** injected bootstrap rejection shows a usable error
and recovery action, never an endless Starting screen or false Ready state.
Actual deployed failure appearance remains unverified.

### PC06 — reserve Escape consistently

[`SettingsModel.assignKey`](../../src/games/fps/client/settings/SettingsModel.ts#L260)
protects `FIXED_KEYS`, which omits Escape. The diagram includes it and
[`ControlsPage.wireInput`](../../src/games/fps/client/settings/ControlsPage.ts#L185)
offers its assignment menu, while press-to-bind treats Escape as cancellation.
Probe bound Jump to Escape while the engine's Cancel binding remained.

**Fix/done:** mark Escape reserved for menus/cancel; clicking explains that
purpose, press-to-bind cancels, and the model refuses another gameplay action.
No key-binding redesign is needed.

### PC07 — guard optional session metadata

[`FPSPauseMenu`](../../src/games/fps/client/hud/widgets/PauseMenu.ts#L92) reads
sessionStorage directly during construction; a throwing getter reproduced a
constructor failure. [`FPSHud`](../../src/games/fps/client/FPSHud.ts#L174)
also reads it unguarded in post-game Return, bypassing its plain-reload fallback
when storage throws.

**Fix/done:** guard optional metadata; menus and ordinary leaving/return still
work when storage is blocked. Preserve editor-return and private-invite return
when available. This differs from PC01: return metadata and account credentials
have different lifetimes.

### PC08 — explain full servers correctly during restore

[`ProfileView.switchAccount`](../../src/games/fps/client/ProfileView.ts#L648)
and [`WelcomeOverlay.useKey`](../../src/games/fps/client/WelcomeOverlay.ts)
map every LoginError except `unknown_key` to "Too many tries." `lobby_full`
now has its own meaning and wait, so that text describes the wrong problem.

**Fix/done:** explicit full/rate-limit messages, preferably shared; known/unknown
keys, a full lobby and throttling get distinct answers. Failed switches retain
the old key. Source-traced; full-cap account-switch browser acceptance remains.

### PC09 — corrected: global chat already limits input

Re-reading [`LobbyPanel`](../../src/games/fps/client/LobbyPanel.ts) and its
committed HEAD shows `input.maxLength = 500`. The original audit missed this
line. Global and [`RoomChatView`](../../src/games/fps/client/RoomChatView.ts)
inputs already match the server's 500-character cap. Closed without a code
change; this is not counted as an improvement delivered by this batch.

### PC10 — reset key reveal on reopening/account change

Profile's reusable plate starts hidden but
[`open/close`](../../src/games/fps/client/ProfileView.ts#L121) never resets
reveal state. Probe revealed, closed and reopened it: still visible. Identity
refresh replaces key text without resetting reveal either.

**Fix/done:** reopen/account change resets the plate, Show label and aria-pressed;
explicit Show still works, and export does not require visual reveal. This is a
suggested usability default, not a claim of a server credential leak.

### PC11 — recover from a missing archive reply

[`DemosView.requestArchive`](../../src/games/fps/client/DemosView.ts#L297)
sets `archiveRequested` and sends a fire-and-forget request without deadline or
error state. While connected, a withheld reply leaves "Loading the archive…".
Leaving/reopening the tab does resend, so the whole application is not stuck.

**Fix/done:** bounded request and Retry; reuse featured-demo timeout/correlation
patterns. Retry succeeds, late replies cannot replace a newer account/scope,
and timers/listeners are released on disconnect/destroy. Source-traced; pin the
withheld-reply scenario before implementation.

  offline card with countdown at once, backoff about 2/5/10/30 s, reconnected

- Fixed: a deliberate `disconnect()` (account switch) also scheduled the outage

lobbies still accept archive requests from old clients without request IDs).
Room recovery is an attempt, not a promise that an empty room survives a server
restart. Storage fallback cannot preserve an unsaved key across page reloads;
the explicit copy/save warning is essential. None of these adds a new account
scheme, a retry framework or gameplay features.
