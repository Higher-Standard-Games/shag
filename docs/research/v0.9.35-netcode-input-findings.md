Date: 2026-10-19. Branch: `v0.9.35-firefox-player-performance`. Companion
notes: [firefox_performance.md](firefox_performance.md) (first profiling pass
and the fixed-recording benchmark), [linux_mouse_hold.md](linux_mouse_hold.md),

## Summary

| Issue | Cause | Status |
| --- | --- | --- |
| Warping / back-and-forth correction, worst at low FPS and on lossy links | Server dropped low-FPS command bursts (rate cap of 4 per tick); stalls were replayed on top of the client's prediction, then trimmed | **Fixed in code**, tests and regression set pass; needs live confirmation |
| Firefox 20–40 FPS | Main thread saturated with JavaScript; SpiderMonkey runs Babylon's per-frame work 2.5–4× slower than V8. Not GPU, fill rate, GC or automation | **Diagnosed**; work-reduction plan below, nothing shipped yet |
| Linux: moving the mouse ends ADS / Voltaic fire | Most likely an empty `buttons` mask on locked plain motion, which the input system read as a release | **Hardened in code**; not confirmed on Linux |

The two main issues compound: a Firefox client at 20–30 FPS lost a fifth of
its movement on the server. The netcode fix removes that coupling; the
Firefox work is still needed for frame rate itself.

## 1. Netcode

### What was wrong (verified in source)

1. `FPSController` emits one command per 8 ms tick, all at once each rendered
   frame. `NetworkGameHost` sends each command plus the previous two as three
   WebSocket messages over TCP.
2. `GameServer.handleInput` passed every new command through
   `MovementValidator`, built as `new MovementValidator(144, 125)`:
   `ceil(144/125) + 2 = 4` new commands per tick, the rest silently dropped.
   At 25 FPS a frame carries 5; at 20 FPS, 6–7.
3. `FPSMovementSubsystem` consumed one command per tick and, when starved,
   repeated the last one **without advancing the ACK**. The client then
   replayed its own commands on top of a server state that already contained
   the repeated steps — a forward correction — and when the late backlog hit
   the 6-command buffer the oldest were trimmed — a backward correction.

### Policy comparison

A model of the full path (client frames and hitches, three-copy redundancy, TCP
in-order delivery with stalls, server queue, snapshots, client reconciliation)
measures the visible correction per reconciliation. 60 s per scenario, 80 ms
RTT. "Uneven" is the share of snapshot intervals where other players would see
this player move a different number of steps.

Rejected along the way (the model scripts compare them):

- **Removing the rate cap only.** Fixes 30 FPS, leaves 22 FPS at 1.8
  corrections/s and stalls at 36 u.
- **Claiming every guessed tick, no grace.** Leaves no jitter buffer: a
  healthy 144 FPS client went from 0 to 0.8 corrections/s.
- **Pausing a starved player and running two steps later.** Smoothest for the
  player, but knockback drag, lifts, separation and the effect clock all run
  once per world tick; a 0- or 2-step tick desynchronises them from prediction.
- **Claiming again after dropping a late command.** Locks into a steady state
  where every command arrives one tick "late" and is replaced by a guess of
  itself. Caught by a unit test; the shipped rule never claims in that tick.
- **Client accumulator cap left at 100 ms.** Hitches over 100 ms lose real
  time, and the client's commands then trail the server's guesses.

A hitch longer than the client cap (250 ms) still produces one large
correction. Nothing sampled the mouse during it, and the correction coincides
with the frozen frame the player is already seeing.

### What shipped

| Change | File |
| --- | --- |
| Flood guard of 64 new commands per tick (`MAX_BURST_INPUTS`); the time budget still only records strikes | `src/games/fps/server/MovementValidator.ts` |
| First 2 starved ticks repeat unclaimed; later guesses stand in for the next command and advance the ACK, at most 32 ahead; late commands for claimed slots are dropped with their aim, buttons and weapon request kept; never claim in a tick that dropped a late command; buffer 12; one-command drain after a second at depth ≥3; a sequence at or below the newest real one restarts the stream (resume) | `src/games/fps/server/systems/FPSMovementSubsystem.ts` |
| `removeEntity` clears `lastInput` and the new per-entity state; a reused entity id no longer inherits the previous player's last command | same |
| Client keeps up to 250 ms of frame time when generating commands (was 100 ms) | `src/engine/camera/controllers/FPSController.ts` |

Unchanged on purpose: exactly one physics step per tick (lifts, knockback,
effect clock and other players' view stay as they were), the wire format,
the client, and the starvation button strip after 3 silent ticks.

### Still open

- **Redundancy over TCP.** Three messages per command, about 375 a second,
  buy nothing on TCP. Bundling one message per frame is a protocol change
  (`protocol-change` skill).
- **Remote-player playout margin.** `SnapshotBuffer` renders `avg + 1σ` of
  inter-arrival gaps behind the fastest transit, then extrapolates up to
  60 ms. A lateness percentile would cover TCP clumping; measure first.
- **Visual smoothing.** Corrections between 5 and 50 u are clamped to a 5 u
  blend and otherwise pop. Fewer corrections now reach it.
- **Replay cap.** `MAX_REPLAY = 32` is not reached at 80 ms (max 26 unacked
  with a 120 ms stall); relevant above ~230 ms RTT.
- **Telemetry.** Starved ticks, claimed guesses, late drops and drains per
  player would make the next report a number. None is exported yet.

## 2. Firefox frame time

### Method

The fixed ten-bot recording (`wdm2-ffa10-v1-8c2e550fe162-e13755ef`, 20 s,
two repetitions) via `timedemo`, Firefox 158 over WebDriver BiDi and Chrome 155
over CDP, RTX 4070 SUPER / ANGLE D3D11, render effects as in the earlier pass
(`r_ssr 0`, `r_glow 0`, `r_daynight 0`, outlines on). Four instruments:

1. Every `WebGL2RenderingContext` method wrapped: calls and time per frame.
2. Total time inside `requestAnimationFrame` callbacks per frame.
3. Firefox's own sampling profiler (`MOZ_PROFILER_STARTUP`, 1 ms, written at a
   clean shutdown). Its JIT frame names proved unreliable — freed and reused
   code addresses produce impossible callers — so it was used for category
   shares and suspects only.
4. Wrappers on suspect Babylon and game methods, inclusive time per frame, in
   both browsers.

### Findings

| --- | --- | --- |
| Frame interval | 43 ms | 13 ms (with call wrappers) |
| JavaScript in frame callbacks | 30 ms | ~11 ms scene CPU |
| All WebGL calls (page side) | 6.7 ms, of which 3.6 ms one shader link | 1.2 ms |
| WebGL calls per frame | ~3,900 | ~3,700 |
| Frame interval at 320×180 instead of 1366×683 | 39.6 ms | — |

### Where the avoidable work is

**Unfrozen materials.** Babylon re-prepares every unfrozen material's defines
in `isReadyForSubMesh` and rebinds all its uniforms on every draw; its early-out
only covers repeat checks within one frame. In the scene census, 273 drawn
submeshes used unfrozen materials and 29 frozen ones; 74 of 744 materials
were frozen. `MapLoader` deliberately leaves lightmapped BSP materials unfrozen
(`8029af96`: frozen materials skipped the light defines of runtime
`PointLight`s). Gameplay lights now all go through one `ClusteredLightContainer`
(`DynamicLightCluster.ts`), which presents a stable light set, so that reason
needs re-testing. Freezing all `bsp_*` materials mid-benchmark changed the
measured window little (second-repetition median 36 ms against 40), because
most expensive unfrozen draws are weapons, players, gibs, wall marks and effects.

**Runtime object creation, per second in steady state (Chrome counts):**

| Source | Rate |
| --- | --- |
| `ProjectileManager.spawn`: `Mesh.clone` per projectile | 22 / s |
| `RemotePlayerRenderer.updateWeaponModel` → `ModelInstanceCache.createInstance`: mesh clones on every remote weapon switch or respawn | 14.8 / s |
| The same path: `PBRMaterial.clone` per instance (`MaterialCloneBatch`) | 14.6 / s |
| `DroppedWeaponVisual.loadModel` | 9.4 / s |
| `PlayerModelManager.createInstance` via `createHitbox` | 3.3 / s |
| `scene.addLight` (each one dirties every material's light defines) | 0.5 / s |
| `Material._markAllSubMeshesAsDirty` calls (each scans every scene mesh) | ~330 / s |

Each clone also refreshes bounding info from vertex data, and each cloned
material is new to the effect cache path.

**World matrices.** 786 meshes and 1,270 transform nodes; 137 meshes have a
frozen world matrix. About 1,350 world-matrix evaluations a frame.

### Plan, in order

| # | Item | Expected Firefox saving | Risk |
| --- | --- | --- | --- |
| P1 | Pool remote weapon instances per weapon type and share their materials instead of cloning per switch | 1–2 ms/frame in combat, fewer hitches | Medium: attachment, disposal, visual style |
| P2 | Pool projectile and dropped-weapon meshes (instances or a reuse pool) | 1.5–2.5 ms/frame in combat | Medium |
| P3 | Freeze shared effect materials (wall marks, gibs, projectile and explosion materials) once ready; stop writing material properties every frame where the value has not changed (`ProjectileManager.updateTrail`, explosion acquire paths) | 1–2 ms/frame | Low–medium |
| P4 | Re-test freezing lightmapped BSP materials now that dynamic lights are clustered: dynamic lights on walls, fog, shader animation, render toggles | ~1 ms/frame on map-heavy views | Medium (renderer) |
| P5 | Freeze world matrices of static non-BSP meshes (map models, decor) | 0.5–1.5 ms/frame | Low |
| P6 | Prewarm the gameplay shader variants before spawn (the 225 ms link hitches) | Hitches, not average | Low |

Each needs the same fixed-recording comparison in both browsers, a visual check
and the renderer regression set. Together they plausibly take Firefox from
about 30 ms to about 20 ms of script per frame; a separate pass on the
remaining Babylon per-draw cost would be needed to go further.

Rejected as Firefox-specific switches: render resolution (no effect), an
opaque or non-antialiased context, disabled uniform buffers and lower quality
presets (earlier pass), and GC tuning (5 % of samples).

## 3. Linux mouse holds

`InputSystem.boundPointerChange` read the `buttons` mask of every `pointermove`
from the tracked mouse. Per Pointer Events, a move that changes a chord carries
the changed button in `button`; plain motion carries `-1`. Under pointer lock
every release reaches the page as `pointerup`/`mouseup`, so plain locked motion
is now ignored for button state. Unlocked plain motion still releases, so a
release outside the window is not missed. Two unit tests cover both cases.

Still needed: a native trace on Linux (Wayland and X11, Firefox and Chromium)
using the checklist in [linux_mouse_hold.md](linux_mouse_hold.md). Ask
reporters for the in-game version: before v0.9.34 Firefox lost mouse-look
while firing, which is the second report's symptom.

## Assumptions and unverified

- The netcode model is simplified (uniform jitter, fixed stalls, 2D movement).
  The direction and order of magnitude are what it shows, not production rates.
- No live multiplayer session with injected latency was run after the change.
  Verify in a match with an 80 ms client before release.
- Firefox numbers come from headless Windows Firefox 158; Linux Firefox was not
  measured.
- The Linux input change is a hardening against the most likely cause.
