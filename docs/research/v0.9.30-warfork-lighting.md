# Warfork lighting and apparent missing textures

Date: 2026-10-15. Investigation only; no runtime loader/material fix in this task.

## Scope and reference

The target is the user's Qfusion screenshot: readable brick, wood and model
surfaces, warm baked light and local highlights. A numerical brightness match
cannot be established from the screenshot alone: its exact camera, renderer
settings and BSP revision were not supplied. The active lobby map is `wfdm11`;
`wdm11` is a separate, older map package and is not silently treated as the same
BSP. The user referred to both names, so both installed files were inspected.

## Findings in priority order

### 1. Confirmed: baked vertex colors darken already-lightmapped surfaces

`BspMeshBuilder` supplies a color attribute to faces through
`mesh/faceBuilders.ts` and `mesh/vertices.ts`, taking FBSP's first baked color.
Babylon meshes retain `useVertexColors=true`. `applyLightmaps()` then attaches
a second baked lighting source without disabling this vertex-color factor.
Babylon's default fragment shader multiplies base RGB by `vColor.rgb`.
Consequently a black baked vertex color suppresses a valid base texture even
when the lightmap is populated. PBR meshes exhibit this too in the browser.

Headless Edge / real-GPU WebGL2 evidence:

- 294 BSP mesh surfaces were inspected; 148 lightmapped mesh surfaces contained
  at least one exactly black RGB vertex. This is not a count of wholly black
  surfaces, and does not imply every such vertex is incorrectly dark.
- `bsp_tex_106`, shader `models/mapobjects/crates/crate_wood2/albedo`, has 1704
  vertices, 1231 with black RGB. Its albedo, gloss, normal and `lightmap_0`
  textures are all loaded and ready. The shader uses a PBR material.
- An actual nondegenerate triangle was extracted from that mesh, with the
  original material, UV/UV2, normals and all three vertex RGB values `(0,0,0)`.
  At fixed camera/settings it renders almost black. Turning off vertex colors
  in browser memory reveals the texture without fetching any new assets.
  Removing the lightmap afterward brightens it further. The first toggle
  proves a vertex-color factor, while the second also confirms genuine baked
  shadowing contributes to the remaining darkness.

Artifacts: `.cache/wf-lighting-browser.{mjs,json,log}` and screenshots
`.cache/wf-lighting-original.png`, `.cache/wf-lighting-no-vertex-color.png`,
`.cache/wf-lighting-diffuse-only.png`. All three screenshots were inspected.
The triangle is thin and deliberately isolated: it establishes the lighting
factor, not complete Qfusion appearance parity.

Fix direction: use the shader's intended lighting source. Ordinary lightmapped
surfaces should not also multiply by baked fallback vertex lighting. Preserve
intentional `rgbGen vertex` / `exactVertex`, vertex-lit surfaces, alpha semantics,
water and custom materials. Audit static surfaces and inline movers together;
do not globally strip color buffers or disable all vertex colors as a shortcut.
Test both backends after implementing the policy.

### 2. Confirmed: upstream uses 2048 lightmaps; installed scratch BSP uses 512

| BSP inspected | Authored lightmap size | Lump 14 bytes | Actual RGB pages | Face page indices |
| --- | ---: | ---: | ---: | --- |
| Installed `map_wfdm11.pk3` | 512 | 11010048 | 14 | -1, 0, 2, 4, 6, 8, 10, 12 |
| Qfusion checkout `assets/data1_21pure/maps/wfdm11.bsp` | 2048 | 50331648 | 4 | -1, 0, 2 |
| Installed older `map_wdm11.pk3` | absent; FBSP default 512 | 6291456 | 8 | -3, 0, 2, 4, 6 |

The paired even-index layout is consistent with Qfusion's diffuse/deluxe page
convention. The installed wfdm11 page count and UV sample ranges are internally
consistent at 512; 2048 cannot fit even one full RGB page in its lightmap lump.
Thus a 2048/512 mismatch is not the explanation for the **installed** scratch
map's current dark surfaces.

However, `BspLoader.ts` hardcodes FBSP pages to 512. It never reads worldspawn's
`_lightmapImageSize`. Loading the upstream BSP today would incorrectly split
four 2048 pages into 64 512 chunks; its normalized UVs and face page numbers
would sample unrelated regions. Merely swapping the ready-made BSP is unsafe.

Qfusion handles the key case-insensitively in `source/ref_base/r_q3bsp.c` and
uses it in `Mod_LoadLighting`; absent values use the format default. It validates
a positive power of two. SHAG should read the declared dimension before parsing
lightmaps, validate the byte count and referenced page indices, keep the 512
legacy fallback, and reject inconsistent metadata rather than silently flooring
partial pages. Do not infer size from divisibility alone: the upstream lump
also divides cleanly into 512 and 1024 pages, so that heuristic is ambiguous.

Binary evidence: `.cache/wf-lightmap-binary-audit.json`, recording each actual
BSP's worldspawn, lump bytes, face counts, indices and candidate dimensions.
The source files were read, not replaced.

### 3. Confirmed: the active map is a different, fast local bake

Installed wfdm11 has 1608 faces, 512 lightmaps and `gridsize 128 128 128`.
The upstream BSP has 668 faces, 2048 lightmaps and `gridsize 64 64 64`.
Their worldspawn settings also differ in grid ambient/radiosity scales and
`__texelsize` (8 locally versus 4 upstream). Earlier local compiler logs report
missing brick/tile/water/decal inputs because that bake predated the media
installation. Installing textures fixes runtime asset resolution, but cannot
retroactively change the lighting baked without those inputs.

The appropriate appearance baseline is the upstream BSP after dimension support
is correct, or a deliberate rebuild with the complete Warfork dependency set.
Do not tune global brightness against the scratch bake and call that Qfusion
parity. Do not assume every visual difference is a material-loader fault.

### 4. Confirmed, separate: FBSP light-grid records are misread

World surface lightmaps (lump 14) and dynamic model light grids (lumps 15/17)
are different systems. SHAG reads lump 15 as Quake's flat 8-byte records and
ignores lump 17. Qfusion FBSP stores four-style 30-byte grid records plus an
indexed uint16 light array. The installed map has 375 records and 9744 grid
indices; SHAG reports 1406 invented 8-byte records from the same bytes.

The grid origin/dimensions also need the Qfusion contract audited:
`calculateLightGrid()` rounds bounds outward and infers one dimension from the
incorrect record count. Fixing only the record stride will not establish correct
spatial sampling. This affects model/entity lighting and is independent of
512/2048 surface page sizing. See the earlier migration investigation for the
upstream type/function references.

### 5. Missing textures: no missing ordinary base image found in this probe

The installed package audit resolves all four formerly missing material names.
The browser loads the ordinary BSP materials' base textures. Eight surfaces have
no Standard/PBR diffuse/albedo property, but each is an expected specialized
case: chrome and bloom glass use emissive textures; three graffiti decals use
custom filter materials; three liquid surfaces use the unified water shader.
Their active textures were ready. Absence of a diffuse property is not evidence
that those images are missing.

The names `noshader` and `textures/common/_miscmodelclip` remain in the BSP shader
list, but binary face inspection found **zero drawn faces** referencing either
in both installed and upstream wfdm11. They do not explain the visible black
crates. A previous suspicion about lost model material names is not supported
by this face audit. MTL files with zero diffuse coefficients were also inspected;
that alone does not establish a compiler fault and was not changed.

A face-vertex lightmap sampling audit found genuine low/black baked samples as
well as black fallback vertex colors. These are vertex samples, not a coverage
or average-brightness measurement of complete triangles. Evidence:
`.cache/wf-material-binary-audit.json`, `.cache/wf-lighting-samples.json`.

This does not prove every surface in a playable match is correct. For any
remaining suspect location, capture `shader surface` at the exact surface and
camera, then compare albedo-only, lightmap-only and combined output. In
particular, compare the two engines with the same BSP and camera before judging
water, alpha, normal, gloss or fog parity.

## Recommended implementation order

1. Implement validated authored FBSP lightmap dimensions, with 128 IBSP / 512
   FBSP defaults and synthetic 512/1024/2048 regression fixtures. Verify the
   upstream wfdm11 parses four 2048 pages without changing the installed map yet.
2. Correct baked vertex-color versus lightmap selection, preserving authored
   vertex/alpha cases. Verify real crate/wall A/Bs and inline movers on both
   WebGL2 and WebGPU.
3. Stage the upstream BSP as a separate local candidate and compare fixed camera
   views with the Qfusion reference; replace the scratch trial only after
   collision/entities/material checks. Avoid brightness tuning before this.
4. Correct FBSP light-grid records, index indirection and spatial bounds, then
   check weapons, players and pickups in bright/dark areas.
5. Audit the remaining lighting transform: authored `_lightingIntensity`,
   overbright/gamma, texture color space, PBR response and dynamic scene light.
   SHAG applies RGB `pow(0.7) * 2` in its lightmap texture conversion and another
   format-dependent intensity; that is an approximation, not verified Qfusion
   transfer behavior. Establish matching data first before changing these gains.

## Follow-up: authored page dimensions implemented

The investigation led to a scoped loader fix in `BspLoader.ts`: read the FBSP
worldspawn key case-insensitively, use 512 when absent, and reject invalid
(nonpositive/noninteger/non-power-of-two or numerically unsafe) dimensions and
incomplete RGB pages. IBSP keeps 128. Unlike Qfusion, which warns and ignores an
invalid declared size, SHAG rejects it explicitly to avoid ambiguous sampling.
The installed scratch map was not replaced or rebuilt.

Synthetic regression fixtures cover 512, 1024 and 2048 page boundaries, absent
keys, mixed key casing, IBSP independence, malformed declarations and partial
pages. A read-only parse of the actual upstream BSP now reports four 2048 pages,
each 12582912 bytes, and a maximum referenced face page of 2:
`.cache/wf-upstream-lightmaps.{ts,json,log}`.

The whole-scene fixed-camera A/B (`.cache/wf-world-ab.mjs`, WebGL2) temporarily
disabled vertex colors on 219 meshes with attached lightmaps. Both screenshots
were inspected: `.cache/wf-world-original.png` and
`.cache/wf-world-no-vertex-colors.png`. Brick detail becomes readable, but some
surfaces become overbright/yellow. This reinforces the need to handle authored
vertex semantics and baked gain together; the all-mesh toggle is a diagnostic,
not a shipped solution. Vertex-color policy, upstream map installation and
compressed light-grid decoding remain unfinished. The earlier implementation
order above is a plan; only authored page dimension support is implemented here.

## Exact black house façade: KTX2 upload bug, independently confirmed

The later screenshot exposed a second cause in addition to vertex darkening.
A fixed courtyard view at Babylon `(-700,350,-600)` aimed at
`(-900,600,-1100)` reproduces the same triangular black gable with its hanging
lamp. Binary triangle/ray intersection identifies face 116,
`textures/wood/woodplank04`, with lightmap page 0. At the intersection its raw
baked light sample is RGB `(153,139,110)` and its interpolated vertex color is
approximately `(21.11,11.79,0)` on the 0–255 scale. The attached 2048-page lightmap
is present; browser readback at that coordinate is bright after the existing
lightmap transfer/gain. The base TGA is 554×554.

Disabling just wood vertex colors brightens the trim, but the exact gable
remains black. Disabling its bump map and lightmap, or making it unlit, also
fails to restore the sidecar texture. In contrast, setting `r_ktx2 0` before
map load restores the planks and nearby decal with the existing vertex colors
and lightmaps intact. This is a direct source-versus-sidecar comparison, not
an inference from readiness alone. General vertex-darkening evidence earlier
in this document remains valid, but does **not** fully explain this façade.

The runtime selects `data/ktx2cache/textures/wood/woodplank04.ktx2` instead of
the PK3's TGA. Its manifest predates the migration and names `tex_wood.pk3`, but
the old and new source TGAs are byte-identical, SHA-256
`a6af39468c13f57af37bfd172b17fcdb810b7b9145b6ed3465f40d94a2902c0c`.
Thus changing package ownership did not change this source image. Rebuilding
only the PK3 index cannot fix the faulty texture upload path.

### Implemented correction

`KTX2SidecarLoader.ts` reads the KTX2 base extent from the header before
transcoding. If either dimension is not divisible by four, it asks the Babylon
KTX2 decoder for RGBA rather than an incompatible block-compressed target.
It preserves authored dimensions and UVs, including mipmaps, and retains
ordinary compressed target selection for aligned images. The same loader
handles texture restoration. This avoids padding/rescaling texture coordinates
or turning KTX2 off globally.

Browser confirmation with default `r_ktx2 1`: both WebGL2 and WebGPU now load
the sidecar as unsigned-byte RGBA (`format=5`, `type=0`) at the authored 554×554
size. Both show the plank surface. Readback begins `(109,76,51,255)`, versus
original TGA `(105,70,52,255)`; small differences are expected from the existing
ETC1S encoding. Lighting remains dark with vertex colors enabled; disabling
that factor in scratch views further brightens it, as previously diagnosed.
No permanent vertex-color/gain adjustment was bundled into this texture fix.

Artifacts inspected:

- `.cache/wf-house-upper-0-original.png` and `-0-no-vertex.png`: exact gable
  remains black when only wood vertex colors are disabled.
- `.cache/wf-house-no-ktx2-original.png`: original TGA restores the planks.
- `.cache/wf-house-fixed-original.png` and
  `.cache/wf-house-fixed-webgpu-original.png`: default sidecars with the fix.
- `.cache/wf-house-ray.json`, `.cache/wf-house-exact.json`,
  `.cache/wf-house-no-ktx2.json`, `.cache/wf-house-fixed.json` and
  `.cache/wf-house-fixed-webgpu.json`: geometry/material/texture diagnostics.

An earlier GPU readback of the compressed sidecar returned zeros, but that
alone is not valid proof of empty texture contents: compressed attachments
can be non-renderable for readback. The visible source/sidecar/RGBA comparisons
above establish the defect. Scratch camera ray-picking calls also returned
EVAL-ERR due to an unavailable browser picking helper; binary triangle
intersection was used instead. No claims rely on those failed picks.

## Qfusion source comparison: lighting and shininess

The follow-up [Qfusion lighting parity investigation](v0.9.30-qfusion-lighting-parity.md)
traces worldspawn intensity/ambient, deluxe directions, vertex/lightmap
composition and specular semantics against both engines. It confirms a
particularly important PBR translation bug: Qfusion specular-strength RGB is
being multiplied into Babylon roughness, turning weak-gloss brick into a smooth
surface. Authored shader gloss factors are also lost. The document records
fixed-camera diagnostics, the real brick-material A/B and an implementation
order; this follow-up changes research notes only.
