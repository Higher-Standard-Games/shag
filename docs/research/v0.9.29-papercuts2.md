## 1. Loading and failure recovery

### L01 — P1: bound asset requests and make fallback reachable

**Sources:** [Pk3Mirror.fetchPk3](../../src/engine/loader/pk3/Pk3Mirror.ts),
[PK3Index.loadPublishedIndex / ensureIndex](../../src/engine/loader/pk3/PK3Index.ts),
[PK3TextureLoader.getKTX2Manifest / tryLoadKTX2Sidecar](../../src/engine/loader/pk3/PK3TextureLoader.ts),
[PK3Loader.fetchAndValidatePK3](../../src/engine/loader/pk3/PK3Loader.ts),
[main startup](../../src/main.ts).

The mirror GET and origin HEAD are awaited through `Promise.all` without a deadline.
A mirror that never supplies headers prevents fallback to the healthy origin.
The no-mirror fetch, archive body read, published-index metadata requests and
optional KTX2 manifest fetch also have no application deadline. The shared cached
KTX2 manifest promise means one stalled optional request can hold up its consumers.
Boot awaits `ensureIndex`; the existing boot error UI only helps once an error is
actually returned.

**Probe:** fake mirror fetch stays pending; origin HEAD succeeds immediately.
After an 80 ms observation window, the operation was pending and no origin GET
had been attempted. This is a controlled settlement check, not a claim that an
80 ms real request should time out. Source confirms no application timer ends it.
Browser/network-level timeouts may eventually intervene, but the app controls none.

**Bounded fix:** define appropriate metadata/header and body-idle deadlines,
abort abandoned requests, and propagate cancellation through the asset pipeline.
A mirror deadline should release the origin fallback. Optional KTX2 failure should
release the ordinary texture path. Large progressing archives need a generous
policy, not an indiscriminate short total-download timeout. Keep errors retryable
and distinguish a slow download from an unavailable package.

**Acceptance:** stalled mirror, stalled origin HEAD, stalled metadata and stalled
body each settle predictably; origin fallback works; optional sidecars never trap
base texture loading; a slowly progressing large archive still completes; all
abandoned work/timers are cleaned up. No rewrite of PK3 indexing is needed.

### L02 — P2: retry actual ZIP corruption, not only bad magic bytes

**Source:** [PK3Loader.fetchAndValidatePK3 / processPK3ArrayBuffer / loadPK3](../../src/engine/loader/pk3/PK3Loader.ts).

The retry loop tests minimum byte length and the four ZIP magic bytes. Actual
`JSZip.loadAsync` parsing happens later, outside that loop. A truncated archive
with an intact beginning passes the checks and then fails without retrying that
URL. For a corrupt mirror copy this can bypass the documented origin retry.
`loadPK3` also swallows each error and ultimately says the package was not found,
even when the package was found but corrupt.

**Probe:** return 32 bytes beginning `50 4b 03 04` to `loadPK3FromUrl`. It makes
one fetch and fails with `Corrupted zip: can't find end of central directory`.
This exercises actual JSZip parsing, without loading game media.

**Bounded fix:** put structural ZIP parsing inside the bounded retry/fallback
operation; reuse the parsed archive so success is not parsed twice. Preserve the
underlying corruption/HTTP cause in the final loading error. This is structural
validation, not a proposal to hash every asset on every load.

**Acceptance:** truncated archive with intact magic retries; corrupt mirror falls
back to a valid origin; permanently corrupt data ends after the retry limit with
an accurate error; a valid archive incurs one successful parse.

## 2. UI and accessibility

### U01 — P2: disabled controls must actually be disabled

**Sources:** [SettingsFields.trackEnabled / slider / seg](../../src/games/fps/client/settings/SettingsFields.ts),
[FPSSettingsView.css](../../src/games/fps/client/settings/FPSSettingsView.css),
[VideoPage](../../src/games/fps/client/settings/VideoPage.ts),
[GameplayPage](../../src/games/fps/client/settings/GameplayPage.ts).

`enabledIf` sets `aria-disabled` on the wrapper. CSS dims it and disables pointer
hits, but its native inputs/buttons are not disabled and their handlers do not
check the predicate. Keyboard users can still reach and change controls that
mouse users cannot: reflection strength with reflections off, player water
reflections below High water, and disabled crosshair tuning.

**Probe:** disabled slider and segmented-button wrappers report
`aria-disabled=true`, while both native controls report `disabled=false`.
Dispatching input and activating the button invokes both setters. This verifies
the handler gap; actual Tab/arrow navigation still needs browser acceptance.

**Fix:** synchronize native `disabled` state and guard handlers against stale
activation. Re-enable cleanly when the dependency changes; retain the explanatory
label/help and selected value.

**Acceptance:** pointer and keyboard agree, inactive controls cannot mutate
preferences, focus remains usable, and changing the parent option restores control.

### U02 — P3: finish reduced-motion coverage for repeating HUD effects

**Source:** [WashikiTheme.css](../../src/games/fps/client/hud/styles/WashikiTheme.css),
including `w-crit-flash`, `fps-ammo-warning-pulse`, `fps-powerup-timer-expiring`,
`fps-bomb-status-urgent`, `fps-bomb-carry-pulse` and `fps-air-meter-drowning`.

Ready/death effects have explicit reduced-motion overrides, but several other
continuous warning animations do not. Existing reduced-motion blocks cover only

**Fix:** provide a static, equally clear warning treatment under

This does not require removing the default animations or creating a new setting.

**Acceptance:** with reduced motion emulated, each warning remains recognizable
without continuous animation; default-motion behavior is unchanged. Browser
visual acceptance is required. No medical-risk or compliance claim is made here.

## 3. Code and preference quality

### C01 — P2: validate the remaining legacy movement-storage shape

**Source:** [MovementVars.loadFromStorage / initVars](../../src/engine/movement/MovementVars.ts).

The earlier Q04 hardening validates `engine_cvars` and bindings. The separate
`engine.movementVars` key still returns arbitrary `JSON.parse` output as a
`Record<string, number>`, and initialization indexes it directly. Valid JSON
`null` passes parsing and throws on the first variable access. Per-entry values
also lack validation at this legacy boundary; do not assume Cvar's later coercion
makes the entire input safe.

**Probe:** set only `engine.movementVars` to the string `null` in isolated storage
and construct MovementVars: `TypeError: Cannot read properties of null (reading
'cl_speed')`. Normal settings do not write this value; this is malformed-storage
recovery, not evidence of ordinary-session corruption.

**Fix:** accept only a non-array object and finite numeric entries, apply declared
bounds, ignore invalid entries independently. Keep the new FPS/speed defaults and
saved preference precedence. Avoid a full preference-system migration for alpha.

**Acceptance:** null, arrays, scalars and invalid entries fall back safely; valid
siblings survive; legacy-only settings and engine_cvars-only settings agree with
runtime values; Reset restores declared defaults. This is a remaining storage
boundary, not a reopening of all completed Q04 work.

## 4. Networking and diagnostics

### N01 — P2: give netgraph the real cadence and reset per connection

**Sources:** [NetGraph.recordTickForLoss / init / setTicksPerSnapshot](../../src/engine/network/client/NetGraph.ts),
[NetworkGameHost Welcome handling](../../src/engine/network/client/hosts/NetworkGameHost.ts),
[GameEvents snapshot recording](../../src/games/fps/client/GameEvents.ts),
[SnapshotReceiver](../../src/engine/network/client/SnapshotReceiver.ts).

Netgraph learns its tick step from the first positive gap and never refines it.
`setTicksPerSnapshot` exists but has no production caller in this checkout.
Its singleton has no per-connection metrics reset. A first gap containing a lost
snapshot therefore becomes the expected cadence; later matches can inherit the
old cadence, loss history and graph samples.

**Probe:** feed increasing ticks `100, 104, 106, 108, 112` for a stream expected
every two ticks. Netgraph selects step four and reports 0% loss despite the
missing 102 and 110. The arrival sequence is compatible with the live receiver's
monotonic-tick rule; no duplicate tick is needed.

**Fix:** initialize cadence from the negotiated effective rate and reset metrics
on connect/resume as appropriate. Bound loss-window work before inserting gaps,
so a very long stall does not first allocate a large list then repeatedly shift
it back to 100 entries. Describe this as a snapshot-gap estimate: rejected
baselines / intentional send suppression also differ from literal wire packet loss.

**Acceptance:** initial loss does not alter cadence; reconnect/rate change starts
cleanly; large tick gaps take bounded work; no artificial loss on clean cadence.
This improves diagnostics, not prediction or hit registration.

**Rejected lead:** a direct component probe with `100,104,100,108` reports false
loss, but SnapshotReceiver already filters duplicate/out-of-order snapshots in
the live route. Do not present that component-only sequence as a reproduced
live-match defect.

### N02 — P2, measure first: bound a slow reader's outbound WebSocket queue

**Sources:** [server WebSocketClientConnection.sendDatagram / sendReliable](../../src/engine/server/network/transport/WebSocketTransport.ts),
[SnapshotBroadcaster](../../src/games/fps/server/SnapshotBroadcaster.ts),
[client watchdog](../../src/engine/network/client/hosts/NetworkGameHost.ts).

Server sends check only OPEN and call `ws.send`. There is no `bufferedAmount`
policy in this server transport. Snapshots continue to be serialized/enqueued for
a connection whose downstream cannot keep up. Client-side buffered-byte logging
in the watchdog observes the other direction and is not a server output bound.

**Risk, not a reproduced outage:** queued old snapshots can increase latency and
memory for a slow reader. No load test or production memory measurement was run.

**Next experiment:** throttle a test reader while it continues sending commands;
record queue bytes, process memory, delivered snapshot age and healthy-client tick
timing. Choose limits from those measurements. Prefer a bounded disconnect/resume
policy or explicitly designed snapshot coalescing over silently dropping arbitrary
messages. Preserve reliable events and acknowledged delta-baseline semantics;
transport send outcome and broadcaster history accounting must agree.

**Acceptance before shipping a fix:** bounded queue growth, unaffected healthy
clients, useful disconnect/recovery behavior and snapshot-convergence coverage.
This is sensitive netcode work, not a one-line `if` around `send`.

## 5. Rendering and client performance

### P01 — P2: stop resetting netgraph's canvas every frame

**Sources:** [NetGraph.render](../../src/engine/network/client/NetGraph.ts),
[Game update loop](../../src/games/fps/Game.ts).

Each visible render assigns canvas width and height even when unchanged. These
assignments reset the backing canvas/context. The graph samples at 100 ms but
redraws at the full game frame rate, including its text, lines and bars.

**Probe:** two renders at unchanged settings perform four dimension assignments.
No GPU/main-thread timings were collected; the optimization is concrete but its
FPS benefit is unknown, and it only matters while `cl_netgraph` is enabled.

**Fix:** resize only on dimension changes and redraw at an appropriate diagnostic
cadence, with explicit clearing/path setup after removing the implicit resize
reset. Keep mode changes responsive; check device-pixel-ratio readability.

**Acceptance:** steady-state renders make no dimension assignments; switching
Numbers/Graph resizes once; no accumulated paths/stale pixels; compare overlay-on
frame cost before/after on both renderers, preferably also the integrated GPU.
Do not extrapolate from the RTX 4070 Super to low-end browser hardware.

### P02 — P3, measure first: coalesce settings persistence during slider drags

**Sources:** [SettingsFields.slider](../../src/games/fps/client/settings/SettingsFields.ts),
[FPSSettingsView field host / redraw](../../src/games/fps/client/settings/FPSSettingsView.ts),
[Cvar.set / saveToStorage](../../src/engine/core/Cvar.ts),
[MovementVars onChange / saveToStorage](../../src/engine/movement/MovementVars.ts).

Each input event sets its cvar, serializes persisted cvars to synchronous browser
storage and asks every registered settings refresh callback to run. Movement
preferences also save their legacy map through onChange. Hidden pages participate
in the refresh list. This is a plausible settings-jank source, not a measured
in-match renderer bottleneck.

**Next experiment:** drag sensitivity/FOV/volume in a trace and count storage
writes, scripting time and frame stalls. If material, keep immediate runtime
feedback but coalesce persistence and refresh only dependent controls. Flush at
interaction end/page hide and retain the existing truthful save-failure indicator.
Avoid a broad reactive-UI rewrite for release.

### Measurements and limits

- A synthetic jsdom burst of 100 FOV input events previously performed 200 storage
  writes and took 686.33 ms. With coalescing and a final change event it performed
  two writes and took 8.47 ms. These are local probe timings, **not browser FPS
  gains**. Runtime FOV updates remain immediate; save failures still report
  session-only status. Closing the settings view flushes queued preferences.
- A real temporary localhost WebSocket with its reader paused accumulated
  33,362,914 queued bytes before the change. The same send loop now disconnects
  at 8,324,342 queued bytes before the next payload would exceed the cap. This
  validates a resource bound, not the ideal threshold for every slow connection.
- Netgraph steady-state draws no longer assign canvas dimensions. Cadence remains
  inferred because welcome messages do not carry snapshot cadence. Consistently
  missing every other snapshot is still ambiguous; the display says `gaps`, not
  a claim of measured wire packet loss. No protocol change was introduced.
- Asset headers have a 15-second deadline; archives have a renewable 60-second
  idle deadline and a 15-minute total limit. Small metadata uses 15/60 seconds.
  Corrupt/transient failures get two retries; permanent HTTP 4xx errors other
  than 408/429 do not. Local Node PK3 loading retains its buffer entry point.
- Assumptions: current FPS game, existing reconnect/resume handling, `wdm2` for
  headless map validation. No production service or live match was changed.
  Browser layout/motion acceptance, real throttled-network behavior and low-end
  GPU impact remain unverified. Demo/highlights and other agents' work are outside
  this implementation's scope. No commits were made.
