# Server memory attribution and optional Bun runtime

Date: 2026-10-17. Branch: `v0.9.31-server-profiling` in both repositories.
Status: source investigation and implementation plan; no new memory baseline
has been measured, no runtime changes implemented, and Bun is not on this
machine's PATH. The reported 300–500 MB per match is the investigation input,
not an independently reproduced result. Record bytes and display MiB in results.

## Outcome

Explain retained memory and startup peaks per match, reduce the largest measured
avoidable costs, and establish capacity for ten concurrent matches. Compare
Node and Bun using equivalent workloads. Keep Node supported. A Bun-started
lobby must spawn Bun game servers throughout their lifecycle.

Preserve simulation, collision, protocol, accounts, rankings and demo behavior.
Do not trade away tick rate, PVS, collision accuracy, recording or network
safety to obtain a better benchmark. The Warsow comparison is useful context,
but its map, workload and memory accounting have not been matched here.

## Verified source findings

| Finding | Evidence | What remains to measure |
| --- | --- | --- |
| Lobby and dedicated CLI use `npx vite-node` | `package.json`, `src/lobby/GameServerSpawner.ts` | Runtime, npm/shell wrappers, Vite transforms/module graph and retained source overhead |
| Spawner hardcodes `spawn("npx", args, { shell: true })` | `src/lobby/GameServerSpawner.ts` | Descendant process tree, readiness and termination under each runtime |
| Normal map resolution is lazy | `src/cli/HeadlessMapLoader.ts`, `src/engine/loader/pk3/NodePk3.ts` | Actual packages opened; fallback scans can ingest several archives before finding a map |
| Loaded archives remain in the PK3 loader | `src/engine/loader/pk3/PK3Loader.ts` retains JSZip packages | Compressed buffers/entry metadata retained after BSP extraction; indexing also calls JSZip separately |
| Shared BSP parser reads all lumps | `src/engine/loader/bsp/BspLoader.ts` | Render vertex objects, faces, lighting/lightgrid, raw buffer, entities and collision data, counted separately |
| Collision retains the full parsed BSP | `src/engine/physics/SweepCollisionBackend.ts` assigns `this.bsp = bsp` | Reachability and retained sizes after initialization; derived collision structures versus source data |
| Lightmap and PVS byte arrays are views into the BSP buffer | `BspLoader.parseLightmaps`, `parseVisData` | A small retained view may keep the entire raw BSP alive; deleting lightmaps alone is insufficient |
| Patch facet planes use packed Float64 storage | `SweepCollisionBackend.buildFacets` | Exact allocated bytes, facet counts and per-map share; preserve the tested precision fix |
| Recorder accumulates encoded frames and inputs | `src/games/fps/server/DemoRecorder.ts` | Growth during a real match, final encoding/compression peak, release after completion |
| Lobby owns SQLite data; servers use `ws` | `src/lobby/RatingStore.ts`, `src/engine/server/network/transport/WebSocketTransport.ts` | Bun compatibility with the exact APIs, buffering, TLS and lifecycle used here |

These are allocation/retention candidates, not a measured ranking of causes.
Do not claim every archive is decompressed in full, every map is loaded, or
that all referenced BSP data is duplicated. Shared references need attribution
by their owning allocation.

## Implementation order and commit checkpoints

### 1. Reproducible baseline and instrumentation

Add an opt-in profiling harness around the real dedicated server and real
lobby-spawn path. Use scratch account/result/demo directories and isolated
ports. Never attach to, stop or mutate live matches. Record the complete
process tree, executable, runtime version, launch arguments, commit, OS,
architecture, map/package hashes, clients, gametype and recording state.

Capture stages separately:

1. Empty runtime control process.
2. Loader/bootstrap ready, before application imports where practical.
3. Server modules imported, before map load.
4. PK3 resolution/BSP extraction complete.
5. BSP parse complete.
6. Collision/PVS/game tables ready.
7. Listening and idle after warm-up.
8. Active match, disconnect/reconnect, post-game and shutdown.

Static imports execute before ordinary entry-point code. An early bootstrap
measurement needs a small dynamic-import wrapper; a log at the top of `main`
does not measure the import cost. Count packages and bytes actually read.

Collect timestamped JSON and a summary table:

- Process RSS, OS private/committed memory and peak process-tree memory.
- JS heap used/allocated, external memory and ArrayBuffer bytes where supported.
  Node's ArrayBuffer bytes are included in external memory: do not add them
  twice. These counters also must not be added to RSS as separate allocations.
- On Linux, collect PSS/private memory or cgroup totals when available. Summed
  RSS double-counts shared pages, so distinguish it from ten-instance capacity.
  Windows working set/private bytes have different meanings; label both.
- Startup/listening latency, CPU time, GC activity, event-loop delay, tick
  work/deadline lateness (p50/p95/p99/max), snapshot cost and queued bytes.
- Exact `byteLength` totals for unique backing buffers and counts for BSP
  records, PK3 entries, facets/BVHs, PVS, histories and demo queues. These
  counters explain ownership but do not replace retained-heap measurements.

Use heap snapshots/allocation profiles on disposable replicas to identify
dominators and retaining paths. Snapshot runs are separate from timing runs.
Measure natural steady state; an optional forced-GC diagnostic distinguishes
temporary allocations from retained objects and is not a production policy.
Node and Bun profiling tools/counter semantics require separate adapters.

**Checkpoint:** instrumentation and a baseline report, before optimizations.

### 2. Separate launcher cost from server data cost

Compare the existing Node 24 + Vite runner with a production Node artifact
that resolves the same aliases without carrying a Vite server/transform graph
per match. Inspect the dependency graph for accidental browser/editor/rendering
imports before choosing bundling boundaries. Preserve dynamic imports, relative
asset/config paths and subprocess behavior. Merely renaming a TS entry to JS
will not resolve extensionless imports and project aliases.

Use the same map/client workload and production behavior. If launch cleanup
saves memory, report it independently of any Bun comparison. Avoid redundant
npx/npm/shell wrappers in child spawning where direct executable spawning works;
test Windows and Linux shutdown/process-tree handling.

**Checkpoint:** production launch path and measured comparison, if beneficial.

### 3. Reduce the largest retained owners, in measured order

Likely candidates, with decisions made from checkpoint 1:

- **Server map representation:** parse only authoritative collision, patch
  controls, contents/flags, entities/models, triggers, spawns and PVS needed by
  gameplay. Maintain a typed contract and differential tests against full BSP
  loading. Runtime collision is shared with the client; avoid stripping or
  mutating its source object behind other consumers. Confirm the full
  transitive field requirements before changing the loader/backend interface.
- **Backing-buffer ownership:** copy small retained slices when that releases
  a much larger raw buffer, including PVS. Copying everything can instead
  increase startup peaks. Verify the old buffer is actually unreachable.
- **PK3 ownership:** preserve canonical published/indexed resolution, priority
  and hashes, while separating metadata lookup from archive retention and
  releasing archive bytes once no consumer needs them. Do not replace the
  index with an ad-hoc map-file search. Test fallback and missing-map paths.
- **Collision storage:** count derived structures and source references before
  compressing/packing. Keep the cap/seam precision regression and identical
  movement. Do not revert Float64 planes to claim a memory saving.
- **Match-duration growth:** inspect bounded snapshot/lag histories, disconnected
  clients and send queues; quantify recorded frames and compression buffers.
  If recording dominates growth, evaluate incremental writing/compression with
  format and crash-recovery tests, preserving random access and verification.

Each optimization gets its own before/after report, correctness regression and
commit. A high stable footprint, an unbounded leak and allocator-retained RSS
are different problems; report which the evidence supports.

### 4. Optional Bun runtime and inherited child launches

Proposed npm scripts (not implemented yet):

```text
npm run lobby:server:bun -- --port 9000 --data-dir <scratch-directory>
npm run net:server:bun -- --map wdm2 --port <isolated-port>
```

The Bun scripts should execute the actual TypeScript entry point with Bun,
not launch the current npm script that invokes Node/Vite again. Retain npm as
the package manager and its lockfile; adopting a runtime does not require a
package-manager or test-runner migration.

Centralize child launch construction. Detect the current runtime using
`process.versions.bun`, and use the parent runtime's executable (`process.execPath`)
with its validated entry/arguments. Node launches Node; Bun launches Bun. Make
runtime identity observable in startup/benchmark output. Fail visibly if the
chosen runtime cannot start; do not silently fall back to Node. Do not inherit
profiling/inspector flags blindly, which can conflict across child processes.

Preserve CLI flags, cwd, readiness timeout, stdout/stderr framing, stdin
admission updates, environment secret handling, exit reporting and process
cleanup. Test an actual Bun lobby creating a room and spawning a Bun match;
unit tests that check argv alone do not prove inheritance. Test Node as well.

Compatibility gates before declaring support:

- TypeScript aliases, dynamic imports, Node builtins, JSZip and Babylon math.
- `node:sqlite` schema/transactions, accounts, results and rankings using scratch
  databases (copies of real data if schema/ranking behavior must be changed).
- Existing `ws` behavior: upgrade/TLS, binary frames, ping/pong, limits,
  backpressure, close/error handling and disconnected/slow consumers.
- Child pipes, readiness, admission/recovery, signed result delivery, natural
  exit, timeout kill and lobby shutdown on Windows and the Linux deployment OS.
- Simulation determinism, replay and tick scheduling. Compare identical
  usercmds/state checksums across runtimes, not only tests run separately.

Start with the existing transport API. Evaluate a dedicated `Bun.serve`
transport only if the compatible path is insufficient or profiles show the
transport is a substantial bottleneck; it would be a separate networking change.

**Checkpoint:** optional scripts, inherited spawning, compatibility results.

### 5. Equivalent workload matrix, soak and capacity decision

Use `wdm2`, `wfdm5`, `wfdm11` and at least one installed high-complexity map
chosen from measured BSP/collision counts. Record hashes, not names alone.

| Dimension | Cases |
| --- | --- |
| Runtime/launch | Current Node/Vite; production Node; direct Bun; Bun running the same production artifact as Node |
| Match load | Idle; 2 active network clients; 8 and 16 active clients where the gametype supports them |
| Behavior | Fixed-seed movement/combat; projectiles/pickups; reconnects; slow client; recording through finalization |
| Duration | Warm-up, repeated 5-minute samples, 30–60 minute active soak |
| Lifecycle | Repeated room → match → results → child exit cycles; verify lobby returns to a stable range |
| Concurrency | 1, 2, 5 and 10 match processes, stepped up while checking host capacity |

Run at the existing 125 Hz with identical effective snapshot rates. Separate
external client-driver/bot-service memory from server memory and account for
driver CPU contention. Repeat trials and report distributions, not a single
best number. Run expensive profilers separately from clean benchmark trials.
Use the common production artifact to isolate runtime effects; source versus
bundle comparisons measure launch/build effects as well. If a common artifact
cannot run under both, document why and do not attribute the whole difference
to the runtime.

Deliver per-map startup peaks, retained-memory attribution, per-client and
per-minute growth, ten-match host totals, tick deadline misses and Node/Bun
differences. Set a supported capacity/budget from those results before release;
50–100 MB is a comparison goal, not a promised outcome. Any Bun recommendation
depends on measured memory, tick latency and lifecycle stability together.

**Checkpoint:** reproducible results, release capacity budget and runbook.

## Validation and completion

Keep the current gates: `npm run typecheck`, `npm run test:run`,
`npm run gate:biome`, `npm run build`, `npm run docs:build`. Changes in server,
networking or BSP loading additionally run `npm run test:simulation`,
`npm run test:physics`, `npm run server:tick`,
`npm run server:fuzz -- --ticks 1000`, and
`npm run cli:game -- --exec "bsp load wdm2; bsp info; quit"`.
Add focused loader/ownership, runtime-launch and real lobby/match lifecycle
tests as those changes land. Keep Node's existing CI gates; add Bun smoke and
equivalence coverage rather than assuming `bun test` replaces Vitest.

Completion requires an attributed baseline, demonstrated memory reductions,
bounded duration/lifecycle growth, a tested runtime inheritance path, and a
repeatable capacity report. Update the living changelog and the headless,
lobby and deployment guides as functionality becomes available. Do not present
the proposed scripts or profiling commands as shipped features yet.

## Bun primary references

Checked 2026-10-17. Pin and record the exact installed version during testing;
documentation describes its current release, not compatibility of every version.

- [Node API compatibility](https://bun.sh/docs/runtime/nodejs-compat): documents
  `node:sqlite` support and runtime-specific limitations in child processes,
  TLS and V8-compatible profiling APIs. Heap statistics describe JavaScriptCore;
  use runtime-appropriate tooling and OS memory as the cross-runtime reference.
- [Module resolution](https://bun.sh/docs/runtime/module-resolution): documents
  TypeScript path remapping and replacement of `ws` with a native-backed
  compatibility implementation. Exact methods used here still need tests.
- [WebSockets](https://bun.sh/docs/runtime/http/websockets): native server API;
  its benchmark results do not establish SHAG throughput or memory usage.

Only this research document changes in the planning checkpoint. No server,
runtime, dependency, account database or game behavior was modified.
