# v1.0.0 security, privacy and anti-cheat review

A review ahead of the public release, on branch `review/v1-security` in both
repositories (from `staging`, 2026-11-18), after the papercuts pass
([v1.0.0-beta13-papercuts.md](./v1.0.0-beta13-papercuts.md)), which already
covered message limits, floods and the console script hole. Three questions:
what personal data we hold and could lose, whether the servers and the code
protect it, and whether cheating is prevented or at least seen.

How it was checked:

- **Personal data:** every table the lobby creates, what account deletion
  touches, every server log line that prints a client address, and the
  production journals (read-only, addresses masked) for what they actually
  keep.
- **Servers:** a read-only survey of both hosts: listening ports, firewall,
  SSH settings, fail2ban, automatic updates, service users and sandboxing,
  file permissions of the data directory, journal size and age.
- **Code:** login, keys, private rooms, seat tickets, settings, practice and
  dev servers; every HTML sink in the client; `npm audit`.
- **Anti-cheat:** each field of the input command and how the server treats
  it, fire rate, weapon switching, lag compensation, S&D bomb rules, what the
  snapshots send, the calibration tool, and what production logs.

I am not a lawyer: the GDPR section lists the questions, not answers.

## Checked and sound

| Area | Finding |
| --- | --- |
| Data held | Name, SHA-256 of a 120-bit random key, match results, ratings and stats, campaign clears, synced settings. No email, password, real name or payment. The app logs no IP address (the game server lines above were the exception). |
| Keys | 120 random bits: unsalted SHA-256 is enough at that entropy. Wrong keys are rate-limited per address, and so is account creation. No key in URLs, logs or referrers. |
| Account deletion | Asks for the whole key again and a confirmation; erases name and key, settings and campaign clears; results stay under the id, shown as `[deleted account]`. |
| Bot login | Needs a loopback address and the shared secret, compared in constant time. |
| Real address behind Caddy | `X-Forwarded-For` is trusted only from loopback and its last entry used; Caddy replaces a client-sent one. No one can pose as loopback to get dev powers. |
| Seat tickets | 256-bit random, one use, expiring; the game server holds only hashes. |
| Private rooms | 192-bit invite token. |
| Settings, seat reissue | Bound to the caller's own account. |
| Practice servers | One per player, rate-limited; training demos only from the lobby's machine. |
| Client HTML | Kill feed, phase messages, chat, lobby and scoreboard build text, or escape names. The other sinks take only our own strings. |
| Servers | SSH key-only (root key-only), fail2ban on, automatic security updates on and none pending, firewall allows 22, 80, 443 and the game ports only (the lobby's 9000 is reached through Caddy), backups `drwx------`, Node 24. Security headers added 2026-11-18. |
| Input command | Non-finite values are refused; the move vector is capped at length 1 (no speed hack), pitch clamped, yaw wrapped, weapon slot bounded; a flood buys no extra movement. |
| Fire rate | Enforced on the server tick; the last shot is shared across weapons, so switching does not skip a refire. Firing straight out of a manual switch is a deliberate technique, open to anyone with a bind. |
| Lag compensation | Rewind follows the command's view tick, clamped to 100 ms: a client claiming an old view gets what a 100 ms connection gets, nothing more. |
| S&D bomb | No plant button; plant, arm and defuse follow server positions and speeds. |
| Wallhacks | Snapshots leave out entities outside the viewer's potentially visible set; production logs show it on for every map but one (below). |
| Detection signal | `anticheat:calibrate`: synthetic humans average 36% hitscan accuracy, a plain aimbot 100%; 0% false positives from 60% up on synthetic data. Real players have not been calibrated against. |

### GDPR questions

The terms (`src/games/fps/TERMS.md`) are frank about what is public, but they
are not a privacy notice. Questions to settle, ideally with someone who
knows the law:

1. **Controller and contact.** Who is the controller (Higher Standard Games:
   which legal entity and country), and a contact for data requests. GitHub
   issues are public, and the only contact the terms give.
2. **Legal basis per purpose.** Running matches and accounts (contract);
   leaderboards and public demos; promotion videos; AI training on demos.
   Consent bundled into terms is not valid GDPR consent; legitimate interest
   needs a balancing test and a way to object.
3. **Erasure versus permanent demos.** Deletion renames the account in the
   lobby's lists, but the demo files keep the name and the chat as recorded,
   and the terms say demos are never edited or removed. The right to erasure
   has limited exceptions. Options: rewrite names and chat in a deleted
   player's demos, or stop serving them; or document why they are kept.
4. **Retention.** IP addresses: in memory only now, plus the old lines in
   the journals (500 MB cap, about a month) until this deploys, and Caddy
   keeps no access log. Results, stats and demos: kept indefinitely. A
   notice should say so.
5. **Rights.** Access (a player's results and settings are already
   retrievable by key), rectification (rename), erasure (above), objection.
6. **Age.** The terms say 13; the age of digital consent is 13–16 depending
   on the country, which matters only where consent is the basis.
7. **Breach plan.** What we hold is small, but a leak of `players.db` must
   still be reported within 72 hours: who does it, from which backups.

The admin panel merged after that (`/admin`, `AdminPanel.ts`,
`AdminCredentials.ts`) was reviewed too: scrypt hashes (N 2^15) compared in
constant time, unknown names costing the same; sign-in limited to 5 failures
per address and 50 overall per 15 minutes, checked before scrypt runs, so it
cannot stall the lobby; 256-bit session tokens in an HttpOnly, Secure,
SameSite=Strict cookie scoped to `/admin`, two hours; every change a POST
with a CSRF token and a same-origin check; every player-written field
escaped, under its own `default-src 'none'` policy. Nothing to fix. For the
owner: our Caddy header snippet would override its policy (use
`?Content-Security-Policy`), the overall limit lets anyone lock admins out
for 15 minutes, and a password alone guards it (the release checklist has
the Caddy route and a second-gate option).

Found on the way: the US activation hook created `.maintenance` as root in
`washoi`'s directory, where a link planted by a compromised `washoi` would
be followed. It now runs that step as `washoi`; the activation test passes
(run on US as `nobody` in a temporary directory). The installed hook needs
reinstalling.
