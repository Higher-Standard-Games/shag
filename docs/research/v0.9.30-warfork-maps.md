## Recommendation

Keep the Warfork checkout as the source repository. Do not copy its complete
contents into `public/data`. Use a separate build workspace containing
`maps/`, `models/`, `scripts/`, textures and the existing media PK3s. Publish
only runtime packages under `public/data`, preserving their virtual paths:

```text
public/data/map_wfdm11.pk3
  maps/wfdm11.bsp
  textures/...                  (new dependencies)
  scripts/...                   (new shader definitions)
  levelshots/wfdm11.jpg          (when supplied)
```

The PK3's internal paths are relative to its root: no `public/data/` prefix.
`misc_model` geometry is baked into the BSP by MakeBSP; shipping every raw
ASE/OBJ/LWO/FBX/Max source is unnecessary. Its materials/images can still be
runtime dependencies and must be included. Runtime model entities, if introduced,
need a separate dependency check. Shared new textures can instead go in one
shared media PK3, provided every client/server deployment receives it.

## Existing compiler integration: important configuration trap

Relevant source: `CompilerConfig.ts`, `BuildRecipe.ts`, `CompileJobs.ts`,
`ModelAssetPreflight.ts`, `MapStore.ts` and `PublishedBuild.ts` under
`src/engine/editor/server/`.

- The local binaries are `tools/makebsp/makebsp.exe` and `makelight.exe`.
- Washoi's profile is `editor/makebspdata/washoi.json`. It inherits Qfusion and
  requests FBSP v1, 512-pixel internal RGB8 lightmaps and retained light entities.
- The bundled Warfork profile requests 1024-pixel lightmaps and `basewf/`.
  Use Washoi's profile for this engine instead.
- `npm.cmd run shagged:compile -- --check-config` reports `available: true`.
  However, the installed MakeBSP v0.5-Hardened binary searches for profiles
  **relative to the executable**, even with `editor/` as its working directory.
  Without an adjacent Washoi profile, it warns and silently falls back to
  Qfusion defaults, searches `<media>/basewf/`, and can still exit successfully.
- Therefore the config check currently proves file presence, not that the binary
  will actually load that profile. A future tooling fix should stage the profile
  beside the compiler or use a verified supported profile-search mechanism, then
  validate the logged active game and VFS paths before accepting a build.
- MakeBSP writes collision diagnostics/cache under its first media root. Use an
  isolated writable media copy; do not pass an external source checkout as a
  writable working root.

For this investigation, independent copies of executables, DLLs, base profiles,
Washoi profile, media PK3s and model files were staged under `.cache/wf-compile/`.
No source files in the Warfork checkout were edited. The first diagnostic run
used shared media, but its output is rejected as invalid: it loaded defaults
and found no shaders/models. Automatic approval review blocked a further shared
media retry; subsequent runs use only isolated scratch paths.

## Verified compile recipe

The following commands use the scratch layout created during this investigation.
Run from the engine repository root; input maps must already be copied to the
scratch `maps/` directory. The compiler's `makebspdata/` must contain both
`washoi.json` and its `qfusion.json` template.

```powershell
$wfBuild = Join-Path (Get-Location) '.cache/wf-compile'
& "$wfBuild/toolchain/makebsp.exe" -game washoi `
  -fs_basepath "$wfBuild/media" -threads 4 -leaktest -fast -samplesize 8 `
  "$wfBuild/maps/wfdm11.map"
if ($LASTEXITCODE -ne 0) { throw 'MakeBSP failed' }

& "$wfBuild/toolchain/makelight.exe" -game washoi `
  -fs_basepath "$wfBuild/media" -threads 4 -fast "$wfBuild/maps/wfdm11.map"
if ($LASTEXITCODE -ne 0) { throw 'MakeLight failed' }
```

MakeBSP computes visibility inline; its README says a separate `-visonly` pass
is only needed for standalone visibility work. Do not apply a legacy Q3
BSP/VIS/LIGHT command sequence without checking this tool's behavior.

Pilot: `wfdm11` BSP compilation succeeds with the correct active game, VFS root,
shader discovery (102 files / 1,749 shaders) and model geometry. The compiler
reports **54 seconds** with four threads. This is a fast-development build,
not a release-quality visual acceptance.

Warnings include three missing brush materials listed above, missing decal
`textures/decals/frontier_firearms`, and model material names `noshader` and
`tag_light`. The latter need checking against the source model/tag geometry
rather than being treated as proof that a visible texture is missing.
A mixed DETAIL/STRUCTURAL brush warning also needs author review.

1. Recover missing media; fix confirmed stale paths in a reproducible staging
   step or in the source repository. Include OBJ MTL references, ASE material
   paths, shader stages, normal/gloss/emissive maps, sky and decal dependencies.
2. Compile each map in isolation; fail on leaks, missing models, wrong active
   profile, missing shader/media dependencies and unexpected output formats.
   For final builds remove `-fast`; Washoi's existing release recipe adds
   `-upscale` to MakeLight. Measure cost/appearance before committing to it.
3. Package compiled BSP and required new media as conventional
   `map_<name>.pk3` archives. Preserve existing base-media packages as
   dependencies; avoid bundling the entire 2,170-file model source tree.
4. Install packages in `public/data`, then run `npm.cmd run tools:manifest`.
   This updates both manifest and PK3 index. Merely copying loose `.map` files
   into `public/data/maps` does not create playable indexed maps.
5. Add approved maps to engine `config/maps.json` with display names and intended
   modes. The lobby uses this manifest plus installed `map_*.pk3` filenames;
   an `.arena` file alone does not opt a map into matchmaking. Restart the lobby
   to load its new map pools. Keep the original `wf*` IDs to avoid collisions
   with installed `wdm*` and `wbomb*` packages.
6. Headless-load each published map through PK3Index, validate collision/spawns,
   then browser-check lightmaps, props, shader effects, water and visibility.
   Playtest movement routes/jump pads/teleporters and check bots independently.

## Finished pilot and light-grid compatibility finding

MakeLight also completes successfully: **1 minute 26 seconds**, fast mode,
four CPU threads. Finished BSP: **27,165,984 bytes**. A scratch BSP-only
`map_wfdm11.pk3` is **10,230,381 bytes**, under `.cache/wf-compile/media/`;
it is diagnostic output, not an installed or complete media package.

`npx.cmd vite-node .cache/wf-parse-probe.ts` packages the output, resolves it
using `resolveMapBspViaIndex`, then calls the real `BspLoader.load`.
FBSP v1, 512-pixel lightmaps and nonempty PVS checks pass: **1,608 faces**,
**173,440 vertices**, **976 brushes**, **14 lightmap images** and
**360 visibility clusters**. The retained entity lump includes 11 deathmatch
spawns, jump/teleport entities and the authored pickups/lights.

However, the loader logs a light-grid dimension mismatch: it reads **1,406**
records while its inferred dimensions imply **1,612**. This is a compatibility
failure, not a harmless warning or a successful model-lighting acceptance.

Concrete binary/compiler evidence:

- MakeLight reports `24 x 29 x 14 = 9744 grid`, then
  `9744 points compressed to 375 unique points`.
- Lump 15 is **11,250 bytes**, exactly `375 * 30`.
- Lump 17 is **19,488 bytes**, exactly `9744 * 2`; interpreting it as uint16
  indices yields a maximum of 374 and 375 distinct entries.
- `BspLoader.parseLightVols()` unconditionally divides lump 15 into 8-byte
  records and ignores lump 17. `floor(11250 / 8) = 1406` explains its count.
- Fast MakeLight explicitly scales the horizontal grid spacing to 128 units;
  grid origin/dimensions and serialized spacing also require verification.

The sizes and index range strongly indicate a compressed FBSP light-grid table
plus an index array. Confirm the 30-byte record fields and grid alignment against
the compiler's source before implementing decoding or conversion. The Washoi
profile's comment that lump 17 is ignorable custom data is not true for this
output. `-nogrid` would hide the issue by dropping model lighting, not validate
compatibility. This needs a targeted follow-up with a known spatial-lighting
fixture and stock-map regressions; no loader changes were made here.

Logs: `.cache/wf-compiler-config.log`,
`.cache/wf-compile/wfdm11-bsp-isolated.log`, `wfdm11-light.log` and
`wfdm11-parse.log`. Compiler processes have finished. First-pass success alone
is insufficient: all six maps still require media fixes, and this pilot also
requires light-grid compatibility work before release.

Investigation artifacts are under `.cache/wf-compile/`, with dependency audit
`.cache/wf-audit.json`. These are scratch data and are not part of deployment.
No runtime engine/game code, matchmaking pools or public map packages were
changed by this investigation. Full game regressions are not run for this
documentation-only change. Browser rendering and live gameplay remain unverified.
