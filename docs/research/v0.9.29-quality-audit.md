## Q01 — Release held controls when the page loses focus

**Trigger:** hold W, switch away, release W outside the page, then return and
capture the mouse again. Another route is pressing a mouse button over the
canvas and releasing it outside the canvas while the cursor is free.

[InputSystem](../../src/engine/input/InputSystem.ts), `init()` and
`clearPerFrameState()`, has no blur/hidden reset. Key/button hold state persists
across frames; mouseup is attached only to the canvas. `touchcancel` is also
unhandled. The probe observes `rawW=true`, `fps_move_forward=true` after
blur/hidden/visible events without a keyup, and `fps_fire=true` after a mouseup
dispatched on the document instead of the canvas.

The [FPS controller](../../src/engine/camera/controllers/FPSController.ts),
`update()` and `syncKeysFromInput()`, **does zero its local keys while pointer
lock is absent**. The remaining bug is that re-capturing reads the stale held
state again. This finding does not claim that an unlocked player keeps moving.
[Game.onTabReturn()](../../src/games/fps/Game.ts) resets visuals and prediction
state but does not clear input. Pointer unlock callbacks similarly clear local
controller keys rather than InputSystem's held state.

**Small fix:** one release/reset path for held keys, mouse buttons, touch points
and transient deltas; invoke it on blur/hidden and lifecycle cleanup. Handle
outside-canvas mouseup and touchcancel. Decide pointer-unlock behavior explicitly
so menu interactions do not leave gameplay holds behind. Detach added listeners
in `dispose()`.

**Done when:** releasing controls away from the page causes no movement/fire on
return; fresh presses still work; chat/menu contexts and release edges remain
correct. Headless checks should cover keys, outside mouseup, touch cancellation
and init/dispose/reinit. Verify Alt+Tab and click-to-recapture in a browser.

## Q02 — Treat theme persistence as optional during startup

[UITheme](../../src/engine/ui/UITheme.ts) reads `localStorage.getItem()` without
a guard in its constructor. [main](../../src/main.ts) calls `getInstance()`
while initializing UI. A storage access exception reaches the startup failure
path even though choosing the default theme would let initialization continue.
The earlier account-storage fix PC01 does not cover this reader.

There is a second inconsistency in `setMode()`: it changes the in-memory theme,
then calls unguarded `setItem()`, then updates CSS/listeners. The write-failure
probe leaves `getMode()="dark"`, unchanged CSS and no listener notification.

**Small fix:** guard storage reads and writes; choose the default on read failure
and always apply the selected theme in memory. Keep optional persistence failure
from interrupting UI initialization or theme notification.

**Done when:** unavailable storage still permits UI initialization; failed theme
writes leave CSS, mode and subscribers consistent. Test both a throwing storage
getter and throwing getItem/setItem. A full blocked-storage browser startup is
still needed; this audit tested the component and traced its startup caller.

## Q03 — Give each demo selection ownership of its download and playback

[DemosView.run()](../../src/games/fps/client/DemosView.ts) disables only the
clicked button. Another card or its Highlights action can start another run.
Each run awaits [DemoService.fetchAndLoad()](../../src/games/fps/client/DemoService.ts),
then starts playback and leaves the menu. Neither the file-fetch stage nor the
UI run has a selection generation/cancellation check.

The probe starts A (`wdm2`) followed by B (`wdm7`), completes B first, then A.
The actual run method invokes playback callbacks in the order **wdm7, wdm2**
and calls menu leave twice. Thus download completion order wins over the latest
selection. Playback callbacks were recorded rather than rendering maps; the
real parser and synthetic recordings from the server encoder were used.

DemoService already protects overlapping **playback starts** with
`startGeneration`; those regressions pass. A late download initiates a new start
after that protection, so the existing guard does not establish user-intent
ownership for this earlier stage. `DemosView.destroy()` clears archive requests
and menus, but does not invalidate a pending run either.

**Small fix:** either serialize selection with one view-wide loading state, or
make the latest selection supersede the previous one with cancellation and a
generation check. Invalidate pending selection when the view loses ownership
(including navigation/teardown). Keep parsed bytes/readers associated with the
owning request through playback startup. Validate the file before tearing down
a live session, preserving the current protection for invalid demos.

**Done when:** deliberately reversed A/B responses cannot start A after B;
leaving Demos prevents late playback; normal Watch and Highlights work; stale
errors/finally blocks cannot alter a newer selection's controls. Existing
playback-stop/start-generation tests must continue to pass.

## Q04 — Validate preference values, not only JSON syntax

[InputSystem.loadBindingsFromStorage()](../../src/engine/input/InputSystem.ts)
casts parsed JSON to binding arrays without runtime shape validation. A valid
blob such as `{"fps_move_forward":{"key":"KeyW"}}` loads successfully, then
`updateActionStates()` throws **“bindings is not iterable”**. The
[Controls model](../../src/games/fps/client/settings/SettingsModel.ts) also
iterates bindings; opening Settings can encounter the same bad value.
`importBindings()` has the same assumption, although the probe exercised storage.

[Cvar.loadFromStorage()](../../src/engine/core/Cvar.ts) can pre-load a value
before its declared type is registered. With `{"s_musicenabled":null}`, later
boolean registration throws on `toLowerCase()`. The probe calls that registration
directly, matching its declared type in
[AudioManager](../../src/engine/AudioManager.ts); it did not run a complete boot
with malformed cvars.

**Small fix:** validate the stored object and each binding entry before accepting
it; require appropriate primitive cvar values and finite numeric values. Fall
back per invalid entry, preserving other valid preferences. Keep intentional
empty binding arrays, existing coercion/bounds and fixed-key rules working.
Apply the same validation to actual import entry points.

**Done when:** malformed JSON, valid JSON of the wrong shape, null bindings,
non-array bindings, invalid modifiers and null boolean cvars cannot break
Settings or the frame loop. Valid siblings survive, and the player can reset
or repair the affected setting. Frequency in real profiles is unmeasured.

## Q05 — Make a stalled demo download recoverable

`DemoService.fetchAndLoad()` awaits both fetch and the entire response body with
no AbortController or application deadline. The probe confirms the calls have
no abort signal. While those promises remain pending, `DemosView.run()` leaves
the selected key at “Loading…”; its finally block cannot run. There is no
download cancel action. A request can also finish after navigation (Q03).

This is separate from PC11: that fix adds a 10-second deadline and correlation
to the **archive listing**, not the recording file transfer.

**Small fix:** a cancellable file request with a stall/idle watchdog and a
generous bounded total duration suitable for large recordings. Cover body
reading as well as response headers. Restore usable controls and show Retry
after a failure; retire superseded work quietly. An active transfer on a slow
connection should not be judged by the short metadata-request timeout.

**Done when:** stalled headers and stalled bodies release the loading state;
Cancel/navigation prevents playback; retry succeeds; a large recording making
steady progress still loads. Actual slow/stalled HTTP acceptance remains open.

## Q06 — Report whether settings actually persisted

[FPSSettingsView](../../src/games/fps/client/settings/FPSSettingsView.ts) always
renders “Saved as you go”. Cvar catches failed writes and only logs a warning;
InputSystem catches them silently. Changes can work for this session and then
disappear on reload while the screen still claims they were saved.

**Small fix:** expose persistence success/failure to the existing settings
feedback area. Keep changes usable in memory and say when they could not be
saved in this browser. Preserve the account-key-specific warning from PC01.

**Done when:** blocked/quota-limited writes produce one clear, non-spamming UI
notice; successful writes retain the normal saved state. No storage failure or
quota behavior was exercised through the complete Settings UI in this audit.

## Q07 — Explain failed browser control requests

[CameraInputHandler](../../src/engine/camera/CameraInputHandler.ts) calls
`requestPointerLock()` on canvas click without handling a returned rejection
or listening for `pointerlockerror`. Capture failure has no callback carrying
a player-facing explanation. If the API returns a rejected promise, that
rejection is unhandled at this call site.

[VideoPage.setFullscreen()](../../src/games/fps/client/settings/VideoPage.ts)
swallows fullscreen request/exit rejections. It re-reads the actual state, which
is good, but a failed click has no explanation despite the available settings
toast. InputSystem's Alt+Enter route similarly swallows failures.

**Small fix:** handle both supported error routes and show a short retry/help
hint through existing UI. Account for APIs that return void as well as a promise.
Keep Escape release a normal action, and preserve actual-state-based toggles.

**Done when:** a denied capture/fullscreen request produces useful feedback and
no unhandled rejection; the next permitted click works. Actual permission/
embedding/repeated-Escape behavior needs browser acceptance; source tracing
alone does not establish how often players hit it.

## Implementation — Q03–Q07, 2026-10-13

Implemented on the existing shared `v0.9.29-global-fog` branch. Fog and effect
material changes belong to the other agent and were not edited by this batch.

**Q03/Q05:** the UI serializes playback selections and supplies an AbortSignal.
Cancel, navigation, closing the lobby, disconnect and destroy retire the selection.
DemoService also owns loading with a generation and controller, covering console
loads, raw bytes, stop and live-game handoff. A late fetch or parser cannot commit
obsolete data. Header and index validation finish before replacing the loaded
recording. Playback starts retain the reader/bytes they selected.

The download watchdog covers both headers and streamed bodies: **60 seconds idle**,
renewed by incoming nonempty chunks, and **15 minutes total**. Cancellation and
timeouts settle even a transport that ignores AbortSignal. Timers and abort
listeners are removed on success/failure; unfinished readers are cancelled.
Timeouts retain their explanation even when fetch rejects with AbortError.

The menu offers Cancel, retains failures with Try again, and disables all playback
buttons during transfer, including cards rebuilt by filtering. File validation
finishes before the deliberate menu/map handoff. Owned map or wiring failures
restore the menu; obsolete startup failures retire quietly. Partial viewer wiring
is cleaned up. A reopened GamePanel removes the old close-animation handler, so
an earlier animation cannot hide the recovery menu. DOMException cancellations
also retire loading feedback without being mistaken for playback errors.

**Q04:** runtime shape validation applies to stored bindings, imports, configuration
and rebinding. Invalid overrides fall back to defaults; valid siblings and explicit
empty arrays survive. Bindings are copied, including validated modifiers. Cvars
accept finite primitives, reject null/arrays/objects/nonfinite values, and validate
persisted numeric strings against their declared type before coercion. Invalid
persisted numeric text now uses the declared default rather than a coerced zero
clamped to the minimum; the existing test was updated to reflect that behavior.

**Q06:** preference writes publish only key and save status, never preference
contents or account keys. Settings shows **Session only · could not save** when
any relevant write fails. In-memory controls/cvars/theme keep working. Repeated
failures do not generate repeated status events; successful writes clear each
affected key's failure. Settings unsubscribes when destroyed. Account-key recovery
and its existing Profile warning are unchanged.

**Q07:** pointer capture handles promise rejection, synchronous errors and legacy
pointerlockerror events. One dismissible notice gives a retry hint; successful
capture clears it. Teardown suppresses late failures and removes the new listener.
Fullscreen uses a shared request helper for Settings and Alt+Enter, supporting
legacy void returns and Electron. Settings uses its toast and re-reads actual
state after failure; Alt+Enter shows the dismissible notice. Electron toggles read
the native window state rather than document.fullscreenElement.
