## Group A — Crosshair & ammo feedback (items 1, 2, 3, 4)

### What's there

`src/games/fps/client/Crosshair.ts` (300 lines) is a canvas crosshair singleton
that *already* documents "per-weapon style (cross/dot/circle/cross_dot), COD-style
spread (hip widens, ADS tightens), movement spread, damage flash." Its
`update(config, adsProgress, horizSpeed, …)` computes all of that.

**The bug: nothing drives `update()`.** The only live call is
`Crosshair.getInstance().notifyHit()` on a damage event (`GameEvents.ts`). No
per-frame call feeds it ADS progress, weapon spread config, or movement speed —
so the dynamic behaviour is dead code and the crosshair renders static/plain
("pretty bad"). It's also unclear it's even added to the HUD render path.

### Fix plan

1. **Wire `Crosshair.update()` into the client render loop** (Game frame update),
   feeding: the equipped weapon's `CrosshairConfig`, current ADS progress
   (the same value the weapon view manager already lerps), and horizontal
   speed (from `V2NetworkClient.getMovementState().actualHorizSpeed`). This
   alone delivers **#4** (spread + ADS-converge) from existing code.
2. **Improve the draw** for #3 — crisp COD/Quake styles (gap-based cross, center
   dot, outline for contrast on light/dark). Keep it canvas so spread animates
   smoothly. Per-weapon default styles (e.g. dot for rail, wide cross for
   plasma with visible spread).
3. **Out-of-ammo (#1):** when the equipped weapon has 0 usable ammo, draw a
   **large red X** in place of the crosshair, and show a **yellow stamped
   "OUT OF AMMO"** banner (reuse the HUD "clock" gold-slab look — `--w-gold`
   fill, dark ink text, hard shadow) positioned just above the speedometer.
4. **Low-clip warning (#2):** for `reloadModel: "clip"` weapons, when the clip
   drops below ~20%, show a subtler **"RELOAD"** hint (same slab vocabulary,
   maybe amber). Clip/reserve is already server-tracked (`InventoryManager`
   ammo `{clip, reserve}`), so this is a HUD-state read.

Files: `client/Crosshair.ts`, `client/Game.ts` (render loop wire),
`client/HUDState.ts` (expose ads/speed/clip), a new small HUD message widget +
`WashikiTheme.css` for the gold banner. Model: **Opus** (crosshair draw + wiring
is fiddly), banner/warning **Sonnet**.

## Group B — Pickup notifications (items 5, 7, and bug 6)

### Bug 6 — bogus blade swap prompt (trivial, isolated)

`client/DroppedWeaponRenderer.ts` ~line 494:

```ts
const currentWeapon = inventory ? inventory.getCurrentWeaponId() : null;
if (currentWeapon === "gunblade") {   // ← default is now "blade"
  // suppress prompt (default weapon is free to drop)
} else {
  showPickupPrompt("dropped", `PRESS [F] TO SWAP TO ${weaponName}`);
}
```

The intent (per the manual): while holding the **default** weapon, at-capacity
pickups auto-swap silently — no prompt. The check hard-codes `"gunblade"`, but
the default melee is now `"blade"`, so holding the blade falls into the `else`
and shows the prompt. **Fix:** replace with the shared
`isDefaultWeapon(currentWeapon)` predicate (already defined in
`WeaponSlots.ts` and `PickupSystem.ts` — it returns true for `blade`/`gunblade`).
One-liner. (Also confirm the *server* swap logic uses the same predicate so
behaviour matches the prompt.)

### Items 7 + 5 — pickup message for ANY item, cartoonish

`client/hud/widgets/PickupToast.ts` only reacts to the **weapons array growing**:

```ts
if (weapons.length > this.lastWeapons.length) { … showPickup("Picked up …") }
```

So armor/health/ammo pickups are silent (**#7**), and the toast is the old style
(**#5**). Two ways to source the signal:

- **Preferred — server pickup event.** Pickups went server-authoritative with
  the active-set mask (no per-player `item_pickup` event anymore), so there's no
  "you grabbed X" signal on the wire. Add a small **per-player pickup event**
  (like the `chat` event pattern: a one-shot `pickup { entityId, kind, label }`
  addressed to the grabber) → exact, works for armor/health/ammo/weapons,
  rides into demos for free. This is the robust fix.
- **Quick — client-diff all vitals.** Extend `PickupToast.update()` to also
  toast on armor/health/ammo *increases* from `HUDState`. Simpler but heuristic
  (can't distinguish a pickup from mega-health decay reversal or regen; may
  double-fire). Acceptable stopgap.

Then **restyle the toast** big + cartoonish: the gold "clock" slab look
(`--w-gold` fill, dark ink text, clip-path stamp, hard shadow), bottom-center,
brief pop-in. Item icon optional.

Files: `client/hud/widgets/PickupToast.ts`, `WashikiTheme.css`; if server event:
`server/SnapshotBuilder.ts` + `PickupSystem.ts` + `BinaryProtocol.ts` (new EVT
code 15) + `GameEvents.ts`. Model: **Sonnet** (client-diff path) / **Opus** (if
adding the server event + protocol).

## Group C — Spectator (items 8, 9, 10)

### 8 — panel is old UI + mislabeled

`client/SpectatorOverlay.ts` (535 lines) is hand-inline-styled (orange corner
brackets, `--w`-less colors) — pre-washoi. Restyle to the print-slab language
(navy scan panel, cyan edge, gold stamps) like the ESC menu.

**While restyling, fix the control labels.** The panel in the screenshot reads
`MOUSE1 CHASE PLAYER` / `MOUSE3 FLY DOWN`, but the code (`Game.ts`) binds:
- chase toggle → **middle click** (`e.button === 1`, i.e. Mouse3) + arrow
  keys ←/→ to cycle,
- there is no Mouse1 chase.

So a user following the panel clicks left and nothing happens — a direct cause of
"couldn't chase" (#10). Decide the intended binding (recommend: **Mouse1 = enter
chase / cycle next**, Mouse2 or middle = exit) and make the labels match the code.

### 9 — spectators missing from scoreboard

The scoreboard widget (`Scoreboard.ts`) *does* render a "SPECTATORS (n)" block —
but only for `state.scoreboard` entries whose `teamId` is neither udon nor soba.
Spectators never reach it: a spectating client has **no entity in the
simulation** (removed on `Spectate`), so it's absent from the snapshot player
list, so it's absent from the scoreboard payload entirely. **Fix:** the server
must include a spectator roster (name + id + `team:"spectator"`) in the
scoreboard/player data even though those clients have no sim entity — then the
existing client render path lights up. Verify the FFA/Deathmatch scoreboard
branch has an equivalent spectator block (the code read covers the team branch).

### 10 — can't chase real player / not true first-person

Symptoms: "couldn't chase my real player; only when entering the game could I
spectate a bot, badly (not real first-person)." Contributing factors found:

- **Mislabeled control** (above) — likely the main "couldn't chase" cause.
- **Initial state is freefly.** Spectators start in `freefly`; chase requires a
  manual toggle. `SpectatorCycling` filters `player_*` entities "not dead with
  valid position" — real players qualify, so the target list *should* include
  them; needs a browser check to confirm real players populate for a pure
  spectator (vs only bots).
- **POV quality.** `SpectatorController` is documented as a first-person
  chase-cam (`eye = target.origin + EYE_HEIGHT_OFFSET`), smoothed. "Not real
  first-person" suggests either the smoothing/offset is off or the followed
  model isn't hidden (you see the back of the head). Cross-check with
  `RemotePlayerRenderer.setHiddenEntity` (used in demo POV) — the live spectator
  path may not hide the followed player's own model.

This one needs a **browser debugging pass** (two clients: one plays, one
spectates). Plan: fix the control mapping + labels first (cheap, likely resolves
most of it), then verify target population and that the followed model is hidden
for a clean first-person POV.

Files: `client/SpectatorOverlay.ts`, `Game.ts` (bindings), `WashikiTheme.css`;
`engine/camera/controllers/SpectatorController.ts` + `SpectatorCycling.ts`;
server scoreboard/roster build. Model: **Opus** (chase/POV debugging),
restyle **Sonnet**.

## Group D — Remote model float (item 11)

`client/RemotePlayerRenderer.ts` positions the model anchor at:

```ts
let feetY = interp.y + PLAYER_MINS_Z + MODEL_Y_OFFSET; // = origin − 24 + 12 = origin − 12
if (interp.sliding)  feetY -= 20;
else if (interp.crouching) feetY -= 10;
```

True feet are at `origin + PLAYER_MINS_Z = origin − 24`. Anchoring at
`origin − 12` puts the model **12u above the floor** while standing/walking —
matching the reported "~8–16 units off the floor." `MODEL_Y_OFFSET = 12` was
presumably tuned for a mesh whose feet sit 12u below its local origin; if the
vanguard mesh's feet are actually at its origin, the offset floats it.

**Fix:** re-derive the correct offset by eyeballing one standing remote player
against the floor (likely `MODEL_Y_OFFSET → 0`, or measure the mesh's local
foot Y). Verify crouch/slide (`−10` / `−20`) still line up after the base fix.
Small change, needs a browser check. Model: **Sonnet** (+ browser).
