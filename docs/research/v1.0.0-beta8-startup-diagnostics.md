## Reproduced renderer cause and correction (PC-063)

`SnapshotFrames.learnMaterialValues` learns non-matrix changes from normal
frames. Its draw list is populated from a recording, so the initial replay can
start without knowing which materials change their own uniforms. In a real
WebGPU fixture, a moving shader shape froze at pixel X 133.5 through the first
six replay frames. After normal frames taught the controller that its values
changed, later replay updated it correctly. Before/after evidence is under
`.agent/startup-bugs/`, including `snapshot-before.json` and
`snapshot-fixture-report.json`.

Added `markSnapshotMaterialDynamic(material)` for uniform owners to declare that
requirement before their first recorded draw. The atmospheric-fog binding calls
it because it updates its eye and fog uniforms on every bind. Voltaic and the
map shader materials using that binding are therefore refreshed from the first
replay. The declaration is weakly held; the existing draw collection promotes
only declared materials into its existing dynamic binding path. Unmarked
materials retain bounded learning. No snapshot enable/disable policy, signature,
pass validation, instance handling, render topology or networking changed.

The corrected native fixture moves through pixel X 136.5, 139.5, 142.5, 145.5,
148.5 and 151.5 during the first six replay frames, with no GPU errors or failed
requests. Replay remains active. A NullEngine regression covers explicit and
fog declarations while proving an unmarked shader is not promoted by this path.
The final focused command below passes 24 tests.

The initial GPU readback fixture interfered with the swapchain lifetime and
produced a destroyed-texture validation error. Its results were rejected. The
replacement uses compositor screenshots and reads their pixels through an
independent 2D canvas; it does not insert GPU readback passes into the tested
scene. A temporary probe variable also shadowed its drawing function; the probe
now rejects evaluation-error strings rather than treating them as measurements.

## Actual Voltaic shader and client verification

The actual `VoltaicEffectRenderer` fixture compares the recorded uniform slot
and compositor pixels for 24 frames. With an unchanged scratch copy of the
original snapshot controller, all 21 replay frames retain start X -56 although
the requested start advances from -54 to -14. The yellow pixel centroid remains
293.79398 throughout. This is the owner's frozen-beam symptom, reproduced without
network snapshots. The expected regression exits one; evidence is
`voltaic-before-report.json`. The scratch controller changes only its relative
DevLog import so it can run outside `src/`; no production file was reverted.

With the correction, all 21 replay frames hold the requested start exactly, and
the yellow centroid progresses to 314.95256 by frame 23. It keeps one recording
and 21 replays, with six meshes and six materials throughout. Both before/after
runs have zero GPU validation errors and zero failed requests. The earlier
attempt to serve the scratch original hit a private-server EBUSY watch error;
that failed setup is preserved separately and is not used as renderer evidence.

The final cold Amphi WebGPU browser successfully runs `loadout status`: the
saved selection, authoritative event, local inventory and HUD all contain
blade/Voltaic/Plasma; the viewed-entity field is null and controller ownership
matches. Snapshots remain active (1,683 replay frames in this capture). No GPU
errors or failed requests occurred. The log retains existing missing-lightmap,
GLB common-root, missing map-handler and plain-ws WebTransport-fallback warnings.
No manual claim is made that the owner's particular platform appearance was
captured: its shader binding uses the same corrected first-replay mechanism,
but confirmation of that exact in-match appearance remains useful.
