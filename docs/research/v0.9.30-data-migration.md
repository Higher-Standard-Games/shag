# Warfork media migration and deployable data plan

**Status:** investigation and proposed implementation order; no data moved.
**Date:** 2026-10-15.

Follow-up implemented: [weapon packaging](v0.9.30-weapon-packaging.md) moves the
loose weapon exports out of public data, packages the GLBs/configs in
`z_weapons.pk3`, and updates all weapon model consumers. Earlier loose-weapon
inventory and preservation notes below describe the pre-migration snapshot.

## Intended result

`public/data/` becomes a reproducible runtime payload that can be copied unchanged
to a separate asset repository, object storage or CDN. It contains only approved
runtime packages, matched lookup metadata and explicitly allowed loose assets.
Sources, compiler workspaces, old releases and profiling output live elsewhere.

Build a new curated payload beside the existing data, validate it, then switch.
Do not clean the live directory in place or replace every legacy package with
Warfork's full development media set.

```text
warfork-qfusion/assets/          upstream input, pinned revision, read-only
warfork-maps/                   editable map/model source, pinned revision
assets-source/                  Washoi originals and conversion inputs
config/                         tracked selection/provenance rules (proposed)
data/staging/<build-id>/         candidate deployable payload (proposed)
data/archive/<snapshot-id>/      old packages, reports and rollback inventory
public/data/                    selected runtime payload only
```

`/data/archive/` is now ignored in the engine `.gitignore`. It is outside
`public/`: `public/data/archive/` would remain an HTTP-accessible directory and
Vite could copy it into production, even though the PK3 index scans only the
selected directory's immediate `.pk3` files. Gitignore is not a deployment filter.
The archive is a local recovery copy, not a substitute for a backed-up asset store.

## Compatibility and assets to preserve

**Do not replace the game's models and audio wholesale.** The inspected upstream
virtual tree contains **zero GLBs**. Our weapon definitions request GLBs; Vanguard
and its animations are already packaged in `player_model_vanguard.pk3` with
`config/player-model-vanguard.json` as the build contract.

The combat sound bank contains 31 literal paths, of which only 5 have exact
matches in the upstream loose roots. Examples such as rocket fire, empty clip
and Bobot death exist there as WAV rather than the OGG names requested by Washoi.
Preserve the working bank initially; any later conversion/remapping must update
the runtime paths or emit validated conversions. Do not rename WAV bytes to OGG.
This count does not cover footsteps, ambient audio, announcers or playlist roots.

Keep `z_weapons.pk3` initially: `MapLoader.ts` explicitly loads
`data/z_weapons.pk3`, beyond ordinary index lookup. Package renaming needs a code
change. It contains IQM/MD3 source models and textures, not the weapon GLBs.
Preserve the loose `public/data/models/weapons/` runtime exports too until they
are packaged with a loader path that supports archive-backed GLBs.
Preserve Vanguard's configured package name and the soundtrack/playlist
contract. `/engine/` fonts and UI branding are separate from upstream map media.
Keep existing Amphi/S&D map dependencies while those lobby pools remain enabled.
An absent Duel/FFA membership is not proof that an old map is unused: demos,
benchmarks, direct map commands and tests may still depend on it.

### Ready BSPs and the light-grid issue

The six selected upstream maps are FBSP v1 and also contain compressed grids.
For ready `wfdm11`, lump 15 is 280,230 bytes (`9341 * 30`), and lump 17 is
167,678 bytes (`83839 * 2`), with maximum uint16 index 9340.
The new checkout supplies the primary-source confirmation we previously lacked:

- `source/qcommon/qfiles.h`: `LUMP_LIGHTARRAY = 17`; `rdgridlight_t` stores four
  ambient colors, four diffuse colors, four styles and a two-byte direction
  (30 bytes with `MAX_LIGHTMAPS = 4`).
- `source/ref_base/r_q3bsp.c`: `Mod_LoadLightgrid_RBSP` loads those records and
  `Mod_LoadLightArray_RBSP` maps uint16 indices to them; its code also handles
  an opted-in invalid-site sentinel (`0xFFFF`).
- Washoi's `BspLoader.parseLightVols` still assumes flat 8-byte entries and
  ignores lump 17. Switching to a ready-built BSP alone cannot solve this.
- Upstream `qfiles.h`/`qcommon/bsp.c` declare 512-pixel FBSP lightmaps; our bundled
  compiler's separate Warfork profile requests 1024. Verify the actual shipped
  BSP/page layout before treating a profile name as a compatibility guarantee.

Ready `wfdm11` is 67,769,560 bytes, versus our fast pilot's 27,165,984 bytes.
Those are **uncompressed BSP sizes**, not measured downloads or evidence of a
better/worse map. Prefer the known pilot geometry for the first material repair;
compare the official BSP separately after the loader compatibility work.

## Packaging only what we use

Build a dependency graph from explicit roots and retain why each file is included.
No single browser session or source-string grep proves an asset unused.

Root sets:

1. Selected map IDs from `config/maps.json`, plus explicitly selected menu,
   demo and benchmark maps. For the first trial: `wfdm11` plus the current
   Amphi/S&D roots; do not silently expand this to every upstream BSP.
2. Gameplay weapon/player definitions, animation manifest, pickups, projectile
   effects, movement/combat/announcer sounds, music and playlists.
3. UI graphics, loading art, levelshots, fonts, game configuration and editor
   assets. Editor browsing is a broad optional asset set, distinct from the
   minimum player release; unknown dependencies remain retained until resolved.

Dependency expansion:

- BSP shader/material names, fog/sky materials and entity references: sounds,
  runtime models, effects and linked data. Source `misc_model` geometry is
  baked into BSPs; raw authoring files belong in build inputs, not automatically
  in runtime packages.
- Parse shader files with our existing Q3 shader parser/registry. Follow stage
  maps, all animation frames, sky cube sides, material channels and implicit
  `_norm`, `_normal`, `_bump`, `_gloss`, `_spec`, `_glow`, `_add` siblings using
  the runtime's resolution rules. Shader logic that the engine ignores may
  still be relevant to compiler inputs; track the two graphs separately.
- External GLTF/OBJ/MTL resources, skins, model material names, animation sets,
  playlists and nested configuration. Resolve case/extension fallbacks exactly
  as the loader does; report ambiguous case-only files rather than selecting
  whichever an extraction happens to overwrite.
- Compiler-only images (editor/light images), source models and intermediate
  lightmaps are a build dependency set. Do not turn them into player downloads
  unless runtime resolution also needs them.

Start by retaining **whole needed shader files**, with the closure of their
runtime definitions, rather than writing a fragile shader slicer for the alpha.
Then split scripts into owned subsets only if measured payload savings justify
it. Use source scans plus recorded browser/CLI requests as a cross-check;
fail on unresolved references, and keep an explicit small allowlist for genuine
built-in tokens such as `$lightmap` rather than treating them as missing files.

Proposed initial package boundaries (names new/provisional except existing ones):

| Payload | Boundary |
| --- | --- |
| `map_wfdm11.pk3` | One selected BSP and genuinely map-specific dependencies |
| `washoi_map_media.pk3` | Shared selected Warfork shaders/textures/env/effects |
| `player_model_vanguard.pk3` | Preserve existing model/animation package |
| `z_weapons.pk3` + loose weapon GLBs | Preserve override/source models, required textures and working runtime exports |
| Gameplay audio package(s) | Curated working sounds; split music from frequent SFX |
| `washoi_soundtrack.pk3` + playlists | Preserve current music contract initially |
| Approved existing map packages | Retain Amphi/S&D and explicit demo/test roots |
| Optional editor-media package | Needed for broad texture/model browser workflows |

A file should normally have one owner across the new graph. Resolve current
intentional overrides during generation, with explicit source priority and
ownership records. Alphabetically later PK3s override earlier ones today, so a
new package name can change content. Compare effective file **and shader**
ownership with the current runtime before accepting the new layout. Preserve
virtual filenames first; optimizing package count is secondary to correctness.

## Reproducible build contract

Propose one tracked selection file plus a generated inventory; do not introduce
a new database/service just for packaging. Minimum metadata per included file:

- Virtual path, source repository/revision and relative input path.
- Input SHA-256, chosen override owner, dependency parent/reason and output PK3.
- Transformation recipe/tool version/output hash when converting audio/images/models.
- Source attribution/license evidence, required notice and redistribution status.

Generate deterministic PK3s: sorted entries, fixed ZIP timestamps/compression,
stable paths and no editor exports or machine-absolute paths. Preserve original
inputs, emit collision/missing-reference reports and hashes, and generate the
matched `pk3_manifest.json` / `pk3_index.json` from the exact output directory.
The current index fingerprint is not a cryptographic archive integrity check;
retain SHA-256 in the build/release inventory separately.

### Rights and notices are source data too

`warfork-qfusion/assets/README.md` explicitly describes this checkout as an
internal development asset set with mixed licenses and says release assets are
reviewed individually. Repository availability is not evidence that all files
are approved for Washoi redistribution. Build the dependency graph locally,
record per-file evidence/attribution, and keep unknown-rights files out of the
public release candidate until their status is established. Keep notices with
the packages and published inventory. This is a concrete upstream provenance
constraint, not a reason to stop the local investigation.

For order 2, use a dedicated trial overlay in the candidate directory rather than
copying the entire Warfork media tree into current data. Restore textured walls
first, then evaluate lighting. Texture recovery and light-grid decoding solve
different problems.

Archive candidates, after reference checks: old map packages outside the selected
release/demo roots; compiler `base*` trees; old SHAGGED test packages and their
`shagged_*.json` publication pointers as one unit; superseded texture packs; old
profiles, screenshots and non-featured demos. Keep historical demos and their
needed map/media versions together, or explicitly retire their playback links.
Do not break tests that create/destroy their own fixture packages.

Before any move, resolve and verify all source/destination paths, save a full
inventory and package hashes, and prepare an exact dry-run move list. Move only
the reviewed set to `data/archive/<snapshot-id>/`, preserving paths/provenance.
Never recursively sweep all of `public/data` or merge a new staging directory
over it and assume obsolete files disappeared. Rollback restores the prior
complete payload/metadata and restarts the lobby; nothing is deleted initially.

## Future asset repository / blob storage

Publish the same candidate directory, not the Warfork source tree. Keep config,
build manifests and attribution tracked; large approved packages can live in an
asset repository or versioned blob prefix without changing virtual asset paths.
A payload may contain PK3s, paired lookup JSON, selected levelshots/UI/playlist
files, required KTX2 sidecars and licenses. Exclude recordings, server state,
source exports, compiler caches and archives with an explicit deployment allowlist.

Use immutable build/version prefixes and publish the complete package set before
switching metadata/client pointers. Keep rollback releases, upload size/hash
checks and cache behavior in the deployment manifest. Preserve URLs for selected
public demos separately from the immutable game-media payload.

The existing `VITE_PK3_MIRROR_URL` mirrors **PK3s only**. Its current implementation
checks the origin copy's existence/size before trusting the mirror. Simply
uploading PK3s to a bucket and deleting them from the origin would not work with
that contract. Loose files, metadata, KTX2 sidecars and demos still come from the
origin today. A future bucket-only asset origin needs explicit base-URL/CORS/cache
support for those paths; that is separate from the packaging migration.

## Near-as-is Warfork baseline: measured trial

The requested simpler approach is feasible for a **local development baseline**:
package upstream directory contents without changing virtual names, retain
Washoi-owned assets, and prune/repackage later. It is not a complete drop-in
replacement using only the three custom PK3s.

The checkout has loose asset directories, not four already-built base PK3s.
`source/dev_symlinks.sh` also treats their contents as virtual game-root files.
To package `data0_21`, put `textures/...` at ZIP root, not
`data0_21/textures/...`. The three existing loose `assets/map_*.pk3` files are
unrelated maps (pressure, return, shredder), not the required base-media set.

### Recommended next switch

Use the **two visual packages + 6.9 MiB legacy SFX bridge** as the first
near-as-is migration, preserving everything listed above. Upstream's two large
sound packages can wait until we intentionally adopt/remap its WAV bank; no
