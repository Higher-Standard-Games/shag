# v0.9.16 Weapon System Overhaul — QA & Tuning Pass

**Status:** Research / planning
**Branch:** `feature/v0.9.16-weapon-system-overhaul`
**Date:** 2026-07-05
**Author:** QA investigation (weapon system map-out)

> Goal of this branch: map the weapon system end-to-end, establish a QA baseline
> for all 11 weapons, and re-tune fire/projectile/reload timing so weapons play
> at their intended real-time rates after the v0.9.16 server tick-rate fix.
> Only **Rocket Launcher** (and possibly **Riotgun**) are currently considered
> shippable. Everything else is unverified against the corrected 125 Hz clock.

---

## 1. Why this branch exists

v0.9.16 fixed a server scheduler bug where the "125 Hz" dedicated server actually
ran at **~62.5 Hz** — half real time (`docs/research/TIMING_ISSUE.md`,
`docs/changelog/v0.9.16.md`). Every tick-count timer (fire interval, reload,
charge, projectile lifetime/integration) therefore ran ~2× slow in wall-clock
time. Weapon balance had been implicitly tuned *against that broken clock*.

The v0.9.16 balance commit (`afebe02`) did a **first-pass numeric compensation**:

- `projectileSpeed ×0.7` (glauncher, gunblade, plasmagun, rlauncher)
- `reloadTime ×1.3` (all weapons)
- Fire rate → 800 ms (1.25/s) for rlauncher, glauncher, riotgun
- `splashRadius 125 → 150` for rlauncher & glauncher

**Important:** those multipliers were a *blind rescale*, not a re-derivation from
reference values or playtest. `×0.7` projectile speed does **not** restore the
pre-fix felt speed (that would be `×0.5`) — it deliberately leaves projectiles
~40 % faster than the old feel. `×1.3` reload similarly does not restore the old
2× feel. So every weapon still needs to be **verified by measurement + playtest**,
which is what this branch is for.

## 2. Architecture map

```

        │
        ▼
WeaponSystem.update()               src/games/fps/server/systems/WeaponSystem.ts
  • edge-detect weapon slot switch
  • reload completion
  • melee branch (blade): FIRE=slash, ALT_FIRE=hold-charge projectile
  • standard branch: hipfire-ADS gating → fireWeapon()
        │
        ├── fireMelee()      cone check, pendingDamage
        ├── fireHitscan()    single-ray OR N-pellet seeded spread → traceHitscanRay()
        └── fireProjectile() spawn Projectile entity + registerProjectileType()
        │
        ▼

  • integrate velocity (fixed dt), gravity, BSP trace, player sphere test
  • direct hit → pendingDamage; world hit → bounce or explode + splash
        │
        ▼
CombatSystem  (armor/health/knockback)  →  snapshot events → client visuals
```

### Single source of truth

- **Stats:** `src/shared/entities/definitions/weapons/*.ts` (one file per weapon),
  re-exported through `src/shared/entities/definitions/weapons/index.ts`.
- **Interface:** `src/shared/entities/WeaponDef.ts` (+ `WEAPON_DEFAULTS`).
- **Server lookup:** `src/games/fps/server/weapons/WeaponDef.ts` → `WEAPONS` map
  keyed by id, plus a `blade_blast` alias (charged projectile, `knockbackScale 20`).
- **Spread PRNG:** `src/shared/SpreadUtils.ts` (deterministic, client/server-shared).
- **Client visuals (cosmetic only):** `src/engine/weapon/HitscanEffects.ts`
  raycasts along the server-sent fire-event direction; `AmmoCounter`, `WeaponRack`,
  `WeaponSlots`, `Crosshair`, `DroppedWeaponRenderer`. None are authoritative.

### F1 — Fire interval uses `Math.floor`, biasing every weapon *faster* than nominal ⚠️

**Evidence.** `WeaponSystem.update()` computes the cadence in two places — the
melee branch (`WeaponSystem.ts:471`) and the standard branch
(`WeaponSystem.ts:578`) — both as `Math.floor(125 / weapon.fireRate)` ticks.
`Math.floor` truncates the remainder, so any `fireRate` that doesn't divide 125
evenly fires a fraction of a tick early, every shot:

| Weapon | nominal | floor→actual | error | rate error |
|--------|--------:|-------:|------:|------:|
| machinegun (10/s) | 100ms | 12t = 96ms | −4ms | **+4.2%** |
| lasergun/voltaic (20/s) | 50ms | 6t = 48ms | −2ms | **+4.2%** |
| gunblade (1.67/s) | 599ms | 74t = 592ms | −7ms | +1.2% |
| blade (2/s) | 500ms | 62t = 496ms | −4ms | +0.8% |
| instagun (0.77/s) | 1299ms | 162t = 1296ms | −3ms | +0.2% |
| electrobolt (0.8/s) | 1250ms | 156t = 1248ms | −2ms | +0.2% |
| riotgun / rl / gl / plasma | exact | exact | 0ms | 0% |

The 20/s beams and 10/s MG are the worst (+4%), and they're the highest-DPS
sustained weapons, so the error compounds most where it matters.

**Fix.** Prefer storing the interval in **ticks** on the def
(e.g. `fireIntervalTicks`) and deriving `fireRate` for display only — author
intervals on exact tick boundaries so "correct speed" is explicit and the hidden
rounding disappears. Minimal alternative: `Math.round(125 / fireRate)` in both
branches, but note `round` mishandles `.5` cases (MG 12.5 → 13t = 104ms, i.e.
−4% the other way), so it only trades one bias for another. The tick-based
approach is the real fix.

**Risk/parity.** Server-authoritative only — the client does **not** replicate
fire cadence (confirmed: no `fireInterval` logic outside `WeaponSystem`). No
client change needed. Determinism/fuzz unaffected (still integer ticks).

**Effort.** S (minimal) / M (tick-based refactor + per-weapon re-author).

### F2 — Pitch-sign inversion: single-ray hitscan damage ray is vertically flipped 🔴 **confirmed**

**Evidence.** The canonical look-direction convention, used by `fireProjectile`
(`:903`), `fireMelee` (`:648`), `fireChargedProjectile` (`:744`), and the
`pendingFireEvents` tracer visual (`:618-628`), is:

```ts
const yaw = input.yaw;
const pitch = -input.pitch;                 // Babylon: up = negative rotationX
dir.y = Math.sin(pitch);                    // = sin(-input.pitch)
```

The **pellet** hitscan path passes raw `input.pitch` to
`generateSpreadDirections`, which internally does `p = -pitch` →
`forward.y = sin(-input.pitch)` — **matches canonical.**

The **single-ray** hitscan path (`fireHitscan`, `WeaponSystem.ts:792` then `:824`)
does:

```ts
const pitch = -shooter.input.pitch;         // = -input.pitch
...
const p = -pitch;                           // re-negates → p = +input.pitch  ❌
const dir = { x: sin(yaw)*cos(p), y: sin(p), z: cos(yaw)*cos(p) };  // y = sin(+input.pitch)
```

So machinegun / electrobolt / instagun compute a damage ray with the **opposite
vertical sign** to (a) their own tracer/impact visual — the client
`HitscanEffects` raycasts along the server-sent fire-event direction, which is
canonical — and (b) every other weapon. Horizontal shots (pitch ≈ 0) are
unaffected (sin 0 = 0 either way), which is why it survived to now; it only bites
when aiming up/down at range. **Confirmed** (not merely suspected): the visual and
the damage diverge, and two independently-tested paths (rockets, riotgun pellets)
both use the canonical sign, so single-ray is the outlier.

**Fix.** Delete the `const p = -pitch;` re-negation and build `dir` from `pitch`
directly, identical to `fireProjectile`:

```ts
const dir = { x: Math.sin(yaw)*Math.cos(pitch), y: Math.sin(pitch), z: Math.cos(yaw)*Math.cos(pitch) };
```

(`cos(pitch)=cos(-pitch)`, so x/z are unchanged; only y flips to correct.)

**Test.** Headless: shooter at origin, target placed **above** (`+y`) at range;
aim up; assert `pendingDamage` contains the target. Repeat aiming down. Also
assert the single-ray `dir.y` sign equals the `pendingFireEvents` `dirY` sign for
identical input (guards against re-introduction).

**Risk/parity.** Server-only, one line. No client change. **Effort.** S.

### F3 — "Reload" semantics are a poor fit for Warsow-style ammo 🟡

**Evidence.** Standard weapons set `reloading = true` when ammo hits 0 and refill
to `maxAmmo` after `reloadTime` (`WeaponSystem.ts:591-594`, completion at
`:442-449`). Warsow has no magazine reload — it's a single depleting ammo pool
with a per-shot refire delay. `clipSize` is `0` for rl/gl yet an auto-reload still
runs when the pool empties, and `reloadTime` does double duty as "clip reload" and
"empty-pool lockout". This muddies felt cadence and the meaning of the stat.

**DECISION (locked): hybrid — a per-weapon `reloadModel` field.** Supporting more
than one model is cheap in code (one `switch`) and lets weapon classes feel
distinct. Three models:

| `reloadModel` | Weapons | Behavior |
|---------------|---------|----------|
| **`clip`** | machinegun, riotgun, plasmagun, lasergun, voltaic | magazine + reserve; per-shot deduct from clip; reload-from-reserve after `reloadTime`; **fire blocked during reload**; HUD shows `clip / reserve` |
| **`pool`** | rlauncher, glauncher, electrobolt, instagun, gunblade | single ammo count; per-shot deduct; **no reload**, only the refire delay (Quake/Warsow style); `clipSize: 0` is legit here; HUD shows one number |
| **`none`** | blade | infinite (melee) |

Rationale: sustained/rapid-fire weapons get a magazine (reload beat fits); slow
single heavy shots (rockets, bolts) stay a continuous pool (reloading a rocket
launcher feels wrong). This is the weapon-class variety we want.

**Implementation.**
- Add `reloadModel: "clip" | "pool" | "none"` to `WeaponDef` (default `"pool"` —
  the safe/simple model; explicit `"clip"` on the five above, `"none"` on blade).
- **Uniform data shape** (no fork): `WeaponState.ammo` always stores `{clip, reserve}`
  per weapon. Pool/none weapons keep everything in `clip`, `reserve` unused — so the
  snapshot ammo payload and state shape don't branch even though behavior does.
- `clip` branch: reload moves `min(clipSize - clip, reserve)` into clip after
  `reloadTime`; block fire while `reloading`; expose progress to HUD. Manual reload
  input (bind, e.g. `R`) plus auto-reload-on-empty.
- `pool` branch: current behavior minus the auto-reload refill — just refire delay;
  on empty, stop firing / auto-switch.
- **Data (Phase 2):** author `clipSize` (magazine) + `maxAmmo` (reserve) for the
  five clip weapons; leave `clipSize: 0` on the pool heavies. `AmmoCounter` gets a
  two-style render (clip/reserve vs single).

**Risk/parity.** Touches `WeaponState`, snapshot ammo payload, `AmmoCounter` HUD,
`reloading` flag. Uniform `{clip,reserve}` keeps the blast radius contained. Do
after F1/F2. **Effort.** M–L.

### F4 — Instagun `splashRadius: 80` is dead code 🟡

**Evidence.** `instagun.ts:38` sets `splashRadius: 80` with no `splashDamage`.
Splash is only ever applied in `ProjectileSystem.applySplashDamage`; instagun is
**hitscan**, handled by `traceHitscanRay`, which never calls splash. The field is
inert.

**DECISION (locked): implement it as self-knockback for "insta-jump" movement.**
The `splashRadius` isn't for enemy AoE — in Warsow instagib the instagun splash
exists so a player can **shoot a wall/floor near themselves and get launched**
(instajump), the instagib equivalent of a rocket jump. Right now it's *broken*,
not merely dead: instagun is hitscan and `traceHitscanRay` never applies splash,
so instajump doesn't work at all.

**Implementation.** The hitscan path currently only tests *player* targets and
never computes a world-impact point. To support instajump:
1. In `fireHitscan`/`traceHitscanRay`, also trace the ray against the BSP
   (`collisionWorld.trace`, as `ProjectileSystem` does) to find the world-impact
   point when no player is hit (or the wall behind the player).
2. At that impact point apply **radial knockback** in `splashRadius` (reuse the
   `applySplashDamage` shape, but knockback-focused). Give instagun an explicit
   `splashDamage` if any splash *damage* is wanted; for classic instagib, splash
   **damage to self is 0** (respect `selfDamageMultiplier`) while **knockback is
   full** — that's the whole point (movement without suicide).
3. Tune `knockbackScale` for the jump height (proxy metric: self-launch velocity).

**Risk/parity.** New hitscan-world-trace + radial knockback path; needs a headless
instajump test (fire at floor, assert upward impulse) and a "self-damage 0" assert.
**Effort.** M.

### F5 — `voltaic` is a stat-for-stat clone of `lasergun` 🟡

**Evidence.** `voltaic.ts` vs `lasergun.ts`: identical `damage 7`, `fireRate 20`,
`range 850`, `reloadTime 0.065`, `knockbackScale 1.5`, `hitscanType "beam"`; only
model / ammo (`cells` vs `lasers`) / color differ. Both are registered in
`WEAPONS`. Voltaic's own header comment advertises an "orange/yellow beam with
charge-up mechanic" that is **not implemented**.

**DECISION (locked): differentiate — give Voltaic a distinct beam mechanic.**
It should not stay a lasergun reskin. Candidate designs (pick one, then implement
in the beam fire path):

1. **Chain lightning (recommended, on-theme):** beam arcs from the primary target
   to 1–2 nearby enemies at falloff damage (100% → 50% → 25%). Distinct FFA/team
   role; reuses beam visual + secondary arc effects. New logic: after a beam hit,
   find nearest N other players within radius, apply reduced damage, draw arcs.
2. **Overcharge ramp:** damage-per-tick ramps while the beam stays on one target
   (~4 → ~12 over ~1s), resets on loss of contact. Delivers the "charge-up" the
   file comment already advertises. New logic: per-target contact timer.
3. **Overheat burst:** higher DPS than lasergun but builds heat; overheats → lockout.
   Ammo becomes a heat bar. New logic: heat accumulator + cooldown state.
4. **Zap + detonate:** beam stacks a charge on the target; second input / full
   stacks detonates for burst AoE. Combo weapon.

**DECISION (locked): #1 chain lightning.** Beam hits a primary target, then arcs
to nearby enemies at falloff damage.

**Server logic.** On a beam hit, find the nearest N (start N=2) other players within
`chainRadius` of the last hit target (not the shooter), apply falloff damage
(100% → 50% → 25%), and broadcast the ordered chain of hit positions/entity ids so
the client can draw arcs. New `WeaponDef` fields: `chainCount`, `chainRadius`,
`chainFalloff`. Chain hop is nearest-unhit-target each step (no revisits).

**Visual spec (locked — procedural, no textures, matches `HitscanEffects` idioms).**
- **Continuous stream**, not discrete zaps. Like Warsow/Quake LG, the primary is a
  *sustained* electric beam held while firing (voltaic auto-fires 20/s). Rendered
  as one persistent jagged bolt that **re-jitters every frame** for crackle
  (analogous to how `updateBeam` re-orients each frame), not 20 spawned meshes/sec.
- **Color: yellow**, to match the yellow gun model (and voltaic's warm muzzle flash
  `1.0/0.7/0.1`). Bright near-white-yellow core + softer amber glow. (Cyan/other
  styles remain possible later; yellow for now.)
- **Bolt geometry:** pinned-endpoint jittered path (see algorithm below) rendered
  as an emissive **`CreateTube`** core (thin, ~0.15, alpha ~0.9) + wider glow tube
  (~0.5, alpha ~0.2, backface off) + a pooled endpoint `PointLight`. ~10 segments,
  amplitude ~6% of segment length (capped ~15u). 1–2 short **forks** off a random
  interior node (taper to a dead end). Requires the `Meshes/Builders/tubeBuilder`
  side-effect import (modular-import gotcha).
- **Chain hops:** each arc (primary→t1, t1→t2, …) is its own jagged bolt, refreshed
  every beam tick while firing; falloff-dimmed per hop.
- Reuses `getPointLightPool()` and the `effects[]` fade lifecycle.

**Remote rendering (must render on enemy screens).** The primary beam already has a
remote path: `HitscanEffects.updateRemoteBeam(entityId, {origin, direction})`,
driven by the server `WeaponFireEvent` per shot and auto-cleaned after
`REMOTE_BEAM_TIMEOUT` (0.15s > 0.05s shot interval, so it stays continuous while
firing and stops shortly after). The jagged-beam renderer must plug into the **same
local + remote** entry points (add `updateLightningBeam` / `updateRemoteLightningBeam`
parallel to `updateBeam`/`updateRemoteBeam`). **Chain arcs need server data:** unlike
the primary beam (client raycasts along fire dir), secondary targets come from
server hit resolution, so the ordered chain endpoints must ride in the fire/impact
event payload and be drawn for that shooter on **all** clients.

**Risk/parity.** Medium–High: new server chain logic + snapshot payload + client
bolt renderer. **Effort.** M–L.

### F6 — Non-grenade projectiles get a hidden `−50 u/s²` "slight gravity" 🟡

**Evidence.** `ProjectileSystem.ts:176-180`: grenades use `meta.gravity` (their
configured drop); **all other** projectiles fall through to `velocity.y -= 50 * dt`.
So rockets, plasma, gunblade blast and blade blast all sag below the crosshair
over distance. At rlauncher speed (1814 u/s) over its 10000 range (~5.5 s flight)
the drop is non-trivial; at plasma's short range it's minor. The straight-line
client tracer/prediction won't match.

**Concrete impact.** Drop ≈ ½·50·t². Rocket (1814 u/s): ~7.5u @1000 range,
~30u @2000, ~68u @3000 — roughly half a player capsule (56u) at mid-long range, so
a dead-on shot lands low and the straight-line client tracer diverges.

**DECISION (locked): direct-fire projectiles fly straight.** Replace the blanket
`else` branch with a per-weapon field: add `projectileGravity?: number`
(default 0) to `WeaponDef`, and integrate
`velocity.y -= GRAVITY_ACCEL * (weaponDef.projectileGravity ?? 0) * dt`. Rockets,
plasma, gunblade/blade blasts → 0 (straight). Grenades keep their arc via the
existing `meta.gravity` (or the same field). No more magic `−50` literal.

**Risk/parity.** Affects hit feel + client prediction parity. Do alongside the
projectile-speed retune (Phase 2) so both are validated together. **Effort.** S–M.

### F7 — Direct-hit projectile radius is hardcoded `50` 🟢

**Evidence.** `ProjectileSystem.ts:236` uses a fixed 50-unit hit sphere
(`hitRadius = 50`) for **all** projectiles regardless of weapon — a rocket and a
plasma bolt share the same direct-hit generosity, and it isn't tunable.

**Fix.** Optional `projectileHitRadius?: number` on `WeaponDef` (default 50).
Low priority — only if Phase 3 playtest shows plasma/rocket hit-feel must differ.

**Risk/parity.** Low. **Effort.** S.

### F8 — Gunblade projectile registered under id `"gunblade"`, not `"gunblade_blast"` 🟢

**Evidence.** `fireProjectile` registers the projectile type with `weapon.id`
(`WeaponSystem.ts:941`), so a gunblade blast's `defId` is `"gunblade"`. It works
because `WEAPONS["gunblade"]` exists, but the def declares
`projectileId: "gunblade_blast"`, while blade uses a dedicated `blade_blast` alias
entry in the `WEAPONS` map. The two blast weapons use different conventions for
the same concept.

**Fix.** Unify: register projectiles by `weapon.projectileId` (ensuring every
projectileId has a `WEAPONS` entry/alias) so projectile identity is the
projectile's id — client impact effects can then key off it unambiguously.

**Risk/parity.** Client impact-effect mapping keys off `defId`; verify the client
switch handles the chosen id. **Effort.** S–M.

## 8. Decisions & open questions

### Resolved (2026-07-05)
- **Reference model:** Warsow `gs_weapondefs.c` is **inspiration only, not a
  reference.** Gameplay has diverged and will diverge further. Phase 2 tunes to a
  **bespoke spec / design intent**, not Warsow values.
- **Reload (F3):** **hybrid `reloadModel`** — `clip` (MG, riotgun, plasma, laser,
  voltaic), `pool` (RL, GL, EB, IG, gunblade), `none` (blade). Uniform
  `{clip,reserve}` data shape. (See F3.)
- **Projectile gravity (F6):** **direct-fire projectiles fly straight** — per-weapon
  `projectileGravity` (default 0); remove the magic `−50`. (See F6.)
- **Voltaic (F5):** **differentiate** with a new beam mechanic (not a reskin).
  Design direction still to pick — default assumption **chain lightning**.

- **Voltaic (F5):** **chain lightning** — beam arcs to nearby enemies at falloff.
- **Instagun (F4):** **implement splash as self-knockback for insta-jump** (it's
  currently broken, not dead — hitscan never applies the splash).

Chain-lightning visual is **locked**: continuous re-jittering **yellow** tube-bolt
stream, ~10 segments, forks on, local + remote via `updateRemoteBeam`-style path,
chain endpoints sent from server. (See F5.)

### Still open
- **Clip data:** magazine + reserve sizes for the five `clip` weapons (MG, riotgun,
  plasma, laser, voltaic); pool heavies keep `clipSize: 0`. Part of Phase 2.
- **Chain tuning:** `chainCount` / `chainRadius` / `chainFalloff` starting values
  (numbers only — mechanic + visual are decided).
