# Fullscreen movement-key protection

## Behaviour

`InputSystem` requests the browser Keyboard Lock API only while the game canvas
owns pointer lock, belongs to the fullscreen element, the page is visible and
focused, and a text field does not own input. The active context's actions
marked `lockInFullscreen` provide the keys, including binding overrides. FPS
marks its four horizontal movement actions; the engine's default movement
actions have the same flag. Escape is filtered out even if rebound to movement.

Fullscreen changes, pointer unlock, focus changes and context transitions
refresh capture. Frame updates also pick up rebinding changes. Menus without
movement actions release the lock. Input disposal removes listeners and releases
capture. Optional API support is feature-detected; fullscreen itself does not
fail when keyboard capture is unavailable. Permission failure shows a
dismissible notice; a successful later request clears that notice.

`FullscreenKeyboardLock` serializes requests. A generation change invalidates a
pending acquisition, releases it on completion and then processes the newest
target. Identical failed requests are not repeated every frame. Modified key
events for successfully captured keys call `preventDefault` while continuing
through normal movement input.

The browser requires game-initiated Fullscreen API mode (Alt+Enter or the
Fullscreen setting), a secure context and permission. Browser F11 fullscreen
alone and Electron's native window fullscreen do not satisfy the document
fullscreen check. Unsupported browsers retain ordinary browser shortcuts.
Primary references: [Chrome Keyboard Lock guide](https://developer.chrome.com/docs/capabilities/web-apis/keyboard-lock)
and [MDN Keyboard.lock](https://developer.mozilla.org/en-US/docs/Web/API/Keyboard/lock).

## Validation

Focused tests passed 23 cases: fullscreen/pointer prerequisites, movement-key
selection, modified key delivery, remapping, Escape exclusion, menu/chat/blur/
visibility/disposal release, unsupported API, permission denial without retry
loops, stale async acquisition and fullscreen failure/focus recovery.

```powershell
npx.cmd vitest run src/engine/input/__tests__/FullscreenKeyboardLock.test.ts src/engine/input/__tests__/InputFocusRecovery.test.ts src/engine/ui/__tests__/FullscreenFailure.test.ts
npm.cmd run typecheck
npm.cmd run test:run
npm.cmd run gate:biome
npm.cmd run build
npm.cmd run test:simulation
npm.cmd run test:physics

npm.cmd run server:fuzz -- --ticks 1000

npm.cmd run docs:build
npm.cmd run docs:fps:build
```

Full test suite: 4,988 passed, one skipped, 595 files. Logs for the full gates
are `.cache/collision-keyboard-lock-*.log`; player docs use
`.cache/keyboard-lock-fps-docs.log`.
All listed gates, headless regressions and both documentation builds passed.
The physics command printed its documented passing-run position warning.
Both repositories also passed `git diff --check`.

The private headless Edge probe `.cache/keyboard-lock-browser.mjs` used the
actual browser Fullscreen, Pointer Lock and Keyboard Lock APIs, with permissions
granted through CDP in its isolated profile. It captured `[KeyA,KeyD,KeyS,KeyW]`.
CDP-injected Ctrl+W reached the game with default prevented, and the tab remained
alive. A menu released capture, closing the menu restored it, pointer unlock
released it, and fullscreen exit left no captured keys. The browser log and
JSON report are `.cache/keyboard-lock-browser.{log,json}`; no browser errors
or failed HTTP requests were recorded.

Assumptions: keyboard protection belongs to mouse-controlled gameplay and does
not force fullscreen or capture Escape. The physical-key browser permission
prompt and unsupported browsers were not manually tested; denial and lack of
API support are covered by headless tests. This adds no renderer/networking
logic or protocol fields. Existing servers need no restart for this client
input change; reload the client to load it.

The user subsequently confirmed that shortcut protection works in game before
requesting the feature merge to main.
