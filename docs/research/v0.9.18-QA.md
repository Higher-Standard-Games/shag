## The theme that runs through everything

**The suite and architecture are strong exactly where the code is deterministic and pure, and weak exactly where state crosses a boundary** — a socket, the engine↔game seam, or the live↔demo split. The chat feature shipping completely broken (dead message routing, every unit individually correct, caught only by an ad-hoc socket probe) is not a fluke; it is the signature failure of this shape. Three separate audits independently converged on it.

## P0 — fix-first (structural traps that already shipped bugs)

### QA-1: No socket-level integration harness
The exact gap that shipped broken chat. Zero tests send a byte through a real `GameServer` — all three GameServer tests **mock the transport**. The routing layer (`handleDatagram`/`handleReliable`) has no coverage; codec golden tests are complete (all 9 event types round-trip, chat included) and still couldn't catch a wiring bug one layer up.

- **Cost paid:** chat broken for its entire life; caught manually.
- **Remedy:** a protocol smoke suite — real `GameServer` on an ephemeral port + a ws client helper; ~7 scenarios (join→JoinAccept, spawn/snapshot, input→movement, **chat→echo**, ready→phase, phase broadcast, disconnect). Every building block exists (`ws` installed, `MessageCodec` tested, `GameServerTickRate.test.ts` proves in-process construction, the chat e2e probe from 2026-07-15 is a working prototype).
- **Cost:** ~300 LOC, 1–1.5 days. **Highest ROI item in this document.**

### QA-2: Engine↔game build-time import cycle (across the submodule boundary)
`engine/camera/controllers/{FPSController,FreeflyController,SpectatorController}` **statically import** `games/fps/Game` and `FPSActions`; the game imports engine back. The engine cannot typecheck without the fps submodule checked out, and cannot be reused for the `tower` game. Self-confessed in code ("FPS-coupled, relocation tracked separately").

- **Coupling depth:** FPSController touches 8 fps modules — the deepest coupling in the codebase.
- **The game selector is split-brain:** TypeScript always resolves `@game/*` to `src/games/fps/*` (`tsconfig.json:21-23`), while Vite resolves it from `GAME || engine.json` (`vite.config.ts:9-17`). `main.ts:35-38,85` then directly imports/registers FPS code regardless of the selected alias, and runtime `GamePaths.init()` reads `engine.json` again without knowing Vite's `GAME` override (`GamePaths.ts:57-83`). The headless runner has a fourth selector, `GAME_PATH || ./public/game` (`headless-game.ts:135-145`). A nominal `GAME=tower` build is therefore neither typechecked nor bootstrapped as a tower-only application.
- **Remedy:** relocate FPS-specific controllers to `games/fps/camera/`; where the engine genuinely needs a hook, define a small interface (`PlayerContext`) in engine and inject from the game. Cost: medium (~1,400-line file moves + injection seam).
- **Selector remedy:** one resolved game manifest should generate/drive the TS alias, Vite alias, runtime asset path, and entry module. Until that exists, describe `GAME` as metadata selection rather than a supported game-module switch.

## P1 — causes bugs (several already have scars)

### QA-3: `shared/` imports the engine (breaks the layering contract)
`shared/collision/SharedCollisionWorld.ts`, `shared/demo/DemoReader.ts`, `shared/server/simulation/InputSanitizer.ts` all import from `engine/` — the deterministic shared core depends upward on engine networking/physics types. `SharedCollisionWorld` also has a runtime Babylon `Vector3` dependency (`SharedCollisionWorld.ts:12-20`), so headless/shared consumers do not have a lightweight structural-math boundary. **Remedy:** move the genuinely shared primitives (`Vec3`, collision interfaces, `NetworkCommand`, `GameState` shape, `BinaryProtocol`) **down** into shared; engine imports them. Keep Babylon conversion in an engine adapter. Mostly type-level; medium effort.

### QA-4: Duplicated + already-drifted wire types
`MatchPhase`/`MatchWinner`/`MatchStateSnapshot` are hand-copied in `fps/client/MatchStateManager.ts` and have **already diverged** from `shared/server/gametype/GametypeTypes.ts` (client added `spectators`, weakened `TeamId` records to `string`). Any server-side field addition silently misses the client type. **Remedy:** delete the copies, import from shared, add `spectators` to the shared type. Low effort, mechanical.

### QA-5: Identity crisis — two conflicting `EntityId`/`PlayerId` definitions + stringly `player_<n>` keys
Server: branded **numbers** (`shared/server/simulation/types`). Client: plain **strings** (`engine/network/core/Entity.ts`). Same names, zero boundary safety. The `player_<n>` prefix is minted in `SnapshotBuilder` (even for non-players — projectiles become `player_47`), parsed ad hoc elsewhere, and match-state uses bare ids. **Cost paid:** the post-game showcase silently failed on the key-format mismatch; the fix is scar tissue (`Game.ts` conditional normalize). **Remedy:** one `ClientEntityKey` codec module (`toClientKey`/`parseClientKey`), rename the client alias to `EntityKey`, make match-state winner ids use it. Medium-low effort, high value.

### QA-6: `GameEvent` is a duck-typed `any` bag with a silent unrouted default
`GameState.GameEvent = { type: string; [k: string]: any }` flows through the entire client dispatch (23 `any` sites in `GameEvents.ts`); the 15-arm if-chain has **no default** — an unhandled event type vanishes without a trace (the same silent-unrouted class as the chat bug, this time client-side). The codec's encode switch already IS the schema. **Remedy:** a discriminated union mirrored from `BinaryProtocol`'s event switch + exhaustive dispatch (`never` default). Moderate effort; kills a whole bug class and ~20 `any`s.

### QA-7: `handleReliable` router is a live trap + dead WebTransport server module
`handleReliable` is unreachable over WebSocket (proven by the chat bug); it remains in place with its own silent `catch {}` — any future message wired only there dies invisibly. `WebTransportServerTransport` (487 lines) is never instantiated. **Remedy:** delete both (or, if QUIC is roadmap, collapse routing into one function used by both channels + loud warn). Low effort.

### QA-8: `WeaponViewManager` singleton shared between live and demo (documented bug source)
One global instance serves live play AND demo playback; the class carries a whole live/demo mode split (`demoBobActive`, `attachToCamera`/`restoreToFPSCamera`, `resetDemoPlayback`), and an entire regression test exists solely to guard leaked observers from this sharing. This cycle's `demoplay stop` live-viewmodel destruction came from exactly this sharing. **Remedy:** instantiable WVM — separate instances for live and demo, each bound to its own camera. Medium effort; deletes the mode split.

### QA-9: Lobby lifecycle has zero tests
`LobbyServer.ts` (1,421 lines) broke repeatedly this cycle (isStarting not reset, lobby destroyed during the return trip, votes not cleared) — every one of those paths has **zero assertions**. The `LobbyDevSpawn.test.ts` fake-ws harness already exists to copy. **Remedy:** ~6–10 lifecycle tests (create/join/leave, `handleServerExit` reset, `keepAliveUntil` grace, votes). ~0.5–1 day.

### QA-10: God objects (5 files, 7–11 responsibilities each)
`Game.ts` (~9 jobs), `WeaponViewManager` (~11), `LobbyServer` (~7), `GameServer` (~8), `RemotePlayerRenderer` (~7, incl. a live/demo fork). Split seams documented in the architecture audit (e.g. Game → GameBootstrap/NetworkSession/MapLoadCoordinator/PostGameCoordinator; LobbyServer → Lobby domain model vs transport). **Remedy:** opportunistic splits when touching these files — no big-bang rewrite; the live/demo forks (WVM, RemotePlayerRenderer) go first since they breed bugs.

### QA-11 (cross-ref): The demo parallel presentation pipeline
Already documented in the demo-player review (2026-07-15): `_processDemoEffects` re-implements the live `handleServerStateUpdate` dispatcher; DemoEventOverlay re-implements AwardBanner/EventFeed/FPSChat. Three of four user-reported demo symptoms were structural consequences. **Remedy:** feed recorded snapshots through the live dispatcher with a demo context (its own WO; spec exists in the review findings + DEMO_PLAYER doc).

### QA-23: Required headless validation can fail and still exit 0
The Definition-of-Done commands are not reliable gates yet. This is broader than missing local PK3 data:

- `GamePaths.init()` uses browser-only `fetch("/engine.json")` (`GamePaths.ts:63-75`). The tracked `public/engine.json` exists, but the Node headless runner cannot resolve that relative browser URL; `initializeEngine()` catches the failed core-service phase and continues (`headless-game.ts:88-106`). The recurring “missing engine.json” result is therefore an adapter bug, not a missing-file diagnosis.
- The runner then ignores the selected game and searches `GAME_PATH || ./public/game`, with only a legacy `public/games/default/basewsw` fallback (`headless-game.ts:135-145`). It does not consume `GamePaths`, Vite's selected game, or the PK3-index path used by the browser.
- Console commands return human-readable error strings. `runBatch()` prints them as ordinary output and unconditionally exits 0 (`headless-game.ts:916-956`); the registered `quit` command also calls `process.exit(0)` immediately (`headless-game.ts:190-199`). A failed `bsp load` followed by `bsp info; quit` is therefore green at the process level.
- `test-server-physics.ts:219` and `server-fuzz.ts:340` end in `.catch(console.error)` rather than setting a failure status. Ten other CLI entry points use the same pattern. Unexpected top-level failures can be logged and still appear successful to CI/agents.
- ~~The mandated `npm run server:fuzz -- --ticks 1000` command is malformed by the package-script/argument boundary~~ **(CORRECTED 2026-07-15):** re-tested on the current toolchain (npm + vite-node), `npm run server:fuzz -- --ticks 3` prints `[CONFIG] Ticks: 3` — the flag *does* reach `server-fuzz.ts`. The trailing `--` in the `package.json:27` script forwards user args correctly here; parseArgs also harmlessly skips a stray `--`. This bullet does not reproduce; no script change is needed (QA-WO11 step 4 dropped). The earlier "default 10,000" observation was likely an older npm/vite-node version.

- **Cost already paid:** multiple v0.9.16–v0.9.18 work orders recorded asset/config “blocks” from a command that was never capable of representing failure reliably; the fuzz count had to be manually checked and rerun directly.
- **Remedy:** add a shared `runCli(main)` wrapper that catches, reports, and sets `process.exitCode = 1`; make batch commands return a structured `{ ok, output }`; do not let `quit` overwrite an existing failure code. Give `GamePaths`/PK3 discovery a Node adapter and add an explicit asset preflight. Add meta-tests that spawn each required command against one success fixture and one intentional failure and assert exit status.

### QA-24: `tickRate`/`snapshotRate` are advertised configuration, but only the 125 Hz default is coherent
The server CLI exposes `--tickrate` and `--snapshotrate` (`headless-netserver-v2.ts:74-78,134-135`), and `GameServer` constructs its base simulation from `config.tickRate`. The rest of the timing model does not consistently consume that value:

- All six FPS simulation subsystems declare `tickRate: 125` in their own module-level configs. `Simulation.tick()` can skip a slower subsystem, but its accumulator executes at most once per base tick (`Simulation.ts:120-142`). A base server below 125 Hz therefore cannot catch up to the requested subsystem rate and supplies only `1/125` seconds of subsystem time per slower base tick.
- Single-match bot release and grace close are fixed at `10 * 125` and `120 * 125` base ticks (`GameServer.ts:158-160`), so their wall-clock duration changes with the configured server rate.
- Snapshot cadence is rounded to an integer divisor (`GameServer.ts:174-177`). At 125/60 it broadcasts every two ticks—62.5 Hz—but logs and records the requested `60` in demo metadata (`GameServer.ts:394-401`). That metadata mismatch already caused nominal demo playback to run about 4.17% slow before the demo player switched to recorded-tick timing.
- `GameServerConfig` still documents a default snapshot rate of 30 (`Client.ts:20`), while `GameServer` defaults to 60.

This is not merely a magic-number cleanup: the public configuration surface promises operating points the scheduler cannot faithfully represent. **Remedy:** define one immutable `ServerTiming` value and inject it into every subsystem/lifecycle timer. Either constrain gameplay to exactly 125 Hz and reject other values, or make the scheduler perform the required number of fixed steps. Represent snapshot cadence as an accumulator/rational schedule and record the effective cadence (or frame tick deltas), never an unattained requested rate.

### QA-26: Two in-repo browser bootstrap/lifecycle owners are maintained, but only one runs
`EngineScene` presents itself as the engine's base scene and owns creation, initialization, render-loop setup, lifecycle listeners, map loading, and disposal (`EngineScene.ts:82-170,199-260,833-907`). A repository-wide source search found no runtime subclass or instantiation; the occurrences outside the class/export are comments and design-document examples. The shipped application instead repeats those responsibilities directly in `main.ts:43-162,258-266`. The copy is explicit: `main.ts:123,126` says its camera/clearing values must match `EngineScene`.

There is already in-path duplication, not only two alternative implementations. Both paths manually initialize `TextureManager` and also call `ServiceLocator.initScene()`, whose registration invokes `TextureManager.init(scene)` again (`EngineServices.ts:77-88`, `ServiceLocator.ts:267-303`). That init has no re-entry guard and reinitializes its procedural-texture dependency (`TextureManager.ts:71-76`). `SkyLightSystem` is similarly registered as a scene service but explicitly initialized as well: before the locator in `main.ts:146-162`, and after it in `EngineScene.ts:248-250,288`; its re-entry path tears down and recreates lights (`SkyLightSystem.ts:204-220`). The live `main.ts` path also installs an anonymous resize listener and contains no corresponding call to `FPSPlayer.dispose()`, `ServiceLocator.dispose()`, `scene.dispose()`, or `engine.dispose()`. This is mostly hidden during a one-page browser lifetime, but makes reload/re-entry/mobile lifecycle behavior ownership-dependent.

**Discussion / decision:** choose one composition root. Prefer a small owned `EngineHost` pipeline (`create scene -> initialize engine services -> mount selected game -> render -> dispose`) with game hooks/adapters over extending the current ~900-line base class. If `main.ts` is the intended authority, deprecate and eventually retire `EngineScene`; if `EngineScene` is intended, migrate the entry point and split its optional map/weather/debug concerns into composed modules. `EngineScene` is exported from `engine/index.ts` and documented as public architecture, so external consumers must be checked before deletion even though none exist in this repository. Whichever survives should be the only place allowed to initialize and dispose scene-scoped services.

### QA-27: The server-to-client snapshot projection is an implicit, hand-maintained schema
The server simulation and network/client state deliberately use different entity models: the server entity has branded numeric ids, direct optional component properties, and copy-on-write semantics (`server/ecs/Entity.ts:18-75`); the client entity has string ids and a `Map<string, IComponent>` (`network/core/Entity.ts:6-55`). Keeping optimized runtime models separate is reasonable, but their contract currently lives inside one large manual translator. `SnapshotBuilder.ts:24-53,99-213` manufactures structural components with no-op `serialize`/`deserialize` methods, quantizes values, invents wire ids, and later assembles heterogeneous event payloads. A component or field can therefore exist in server state yet silently be absent or differently shaped on the wire unless this file, `BinaryProtocol`, and client consumption all change together.

The builder is also not a pure projection: its own header says “Pure(-ish)” and declares side effects (`SnapshotBuilder.ts:1-8`); it mutates known-projectile/pickup tracking and drains subsystem, kill, chat, and award event queues (`SnapshotBuilder.ts:162-165,406-476,504-554`). This already caused a shipped recording bug when the server called it twice—the first build consumed the combat events, leaving none for the demo—and `GameServer.ts:670-682` now relies on the undocumented-at-type-level rule “build exactly once, then share the object.” The existing `ProtocolCodecs.test.ts` is a strong compensating control for `GameState -> bytes -> GameState`, but static search found no test that starts with a server `WorldState` or calls `buildSnapshot()`; it cannot catch projection omissions or destructive-read mistakes.

There is also a legacy second serialization path. Static search found `GameState.serialize/deserialize` used by tests, not production snapshots; its entity decoder does not consume the serialized entity payload (`GameState.ts:48-125`), and its `chat` shape is the older `playerId/message` form rather than the live `senderId/senderName/team/text` form (`GameState.ts:177-249,253-340`). The event tests pass because they serialize states with no entities and test that older event schema. Production instead uses `BinaryProtocol.encode/decodeSnapshot` (`BinaryProtocol.ts:142-205`).

**Discussion / decision:** keep the two runtime containers, but make the boundary explicit: define shared wire DTOs/codecs (including identity conversion), make the projection exhaustive over supported entity/component kinds, and add a contract test from a real server `WorldState` through `buildSnapshot` and encode/decode to the client shape. Separate event collection/draining from projection, or expose a one-shot `consumeSnapshotInputs()` operation so destructive behavior is explicit. Deprecate the incomplete generic `GameState` serializer or make it delegate to the canonical codec. Avoid unifying the containers themselves unless profiling shows the server's direct-property/COW model is unnecessary.

### QA-28: A protocol version exists in types, but no version is negotiated on the wire
`network/types.ts:13-37` declares `PROTOCOL_VERSION = 1` and requires `ServerInfo.protocol`, but the constant has no in-repo consumer beyond its definition/re-export. The active browser host and bot each redeclare a smaller `ServerInfo` without `protocol` (`NetworkGameHost.ts:78-88`, `BotClient.ts:29-38`). The actual join and welcome payloads contain no version or capability field (`MessageCodec.ts:68-110,113-166`), the WebSocket client opens without a subprotocol (`WebSocketTransport.ts:36-53`), and the lobby welcome carries no game-protocol metadata (`lobby/types.ts:194-202`).

There is a useful compensating control: `ProtocolCodecs.test.ts` locks message codepoints, payload round-trips, and byte-level behavior specifically to catch accidental mixed-build incompatibility. It cannot make two intentionally different but individually valid builds negotiate or fail fast at runtime. Compatibility is still handled ad hoc: the bot flag is an optional trailing byte specifically for older clients (`MessageCodec.ts:116-137`), while other payload changes have no general policy. A mixed-version client/server can connect and only later log decode errors or time out waiting for `JoinAccept` (`NetworkGameHost.ts:202-225,451-538`).

This is confirmed deferred architecture debt rather than a brand-new idea: the older networking design put `protocol` in both Welcome and Join (`NETWORKING_DESIGN.md:4587-4598,5040-5045`), and the v0.9.13 QA notes already required verifying that `PROTOCOL_VERSION` rejects mismatches (`0.9.13-QA-improvements.md:665-672`). The active implementation no longer honors that design.

**Discussion / decision:** put a protocol version (and optionally a compact capability bitset) in the first client/server handshake, reject incompatible peers with a stable machine-readable frame, and define the supported compatibility window. The reserved `MessageType.JoinReject` exists but has no active codec/server sender; either implement it as the stable pre-version rejection envelope or formalize the existing `ServerMessage` error shape. Keep additive trailing-field decoding only as a documented policy within a compatible version; require a version bump for breaking field/order/semantic changes. Add current-current, oldest-supported/current, and incompatible-version cases to the socket-level smoke suite from QA-1.

## P2 — friction (slows development, occasionally bites)

- **QA-12: No CI, no pre-commit, and the suite is globally serialized.** Nothing runs tests/tsc/biome automatically; 1,689 biome diagnostics drift unenforced. `vitest.config.ts:14-20` disables file parallelism and forces the entire suite through one fork. That may be a deliberate memory/global-state workaround, but it makes the 1,300+ test suite slower and prevents concurrency from exposing singleton/order coupling. Remedy: one GitHub Actions job (`test:run` + `tsc --noEmit` + biome fail-on-new) ~0.5 day; husky + lint-staged ~2h. Add a second CI shard that runs a safe subset in parallel, then remove global serialization as state ownership improves.
- **QA-13: `WashikiTheme.css` (3,506 lines, FPS-branded) lives in engine.** Engine HUD widgets hard-wire its variables. Remedy: move to `games/fps/client/styles/`, define a small CSS-custom-property contract for engine widgets; split the file internally (tokens/HUD/panels/animations).
- **QA-14: Client imports server code** (`fps/client/*` → `server/weapons/WeaponDef`, 5 sites) and there are **three** WeaponDef concepts (shared + server + view). Remedy: move the `WEAPONS` display/config table to shared; keep ballistics server-side.
- **QA-15: No logger or production diagnostics path.** ~900+ runtime `console.log`s, zero levels/tags; worst: BspMeshBuilder 47, GameServer 47, Game.ts 39. Production source maps are explicitly disabled (`vite.config.ts:35`), and there is no global error/unhandled-rejection reporter. A minified production failure therefore has neither structured breadcrumbs nor symbolicated stacks. Remedy: thin leveled `log.debug(tag, …)` + prod `drop_console`; migrate top-15 files only. Generate hidden source maps for CI/error reporting even if they are not shipped publicly.
- **QA-16: The 6 dangerous silent catches** (full table in audit): the reliable-router `catch {}` (GameServer:927), the post-game showcase pipeline `.catch(() => {})` (Game.ts), chat send swallow (FPSHud), bot snapshot decode, lobby frame parse ×2, per-client snapshot send. Remedy: rate-limited `warn` in each; keep the ~90 cosmetic ones.
- **QA-17: Magic numbers.** The server-rate consequence is elevated to QA-24; elsewhere, `36` means both Mixamo scale and crouch height, and ~20 z-index literals bypass the existing `UIManager.getZIndex()` system. Remedy: named domain constants + route z-indexes through UIManager.
- **QA-18: 81 singletons** (68 engine) — no multi-instance story; convert only the stateful, lifecycle-bound ones (`WeaponViewManager` QA-8, `EntityManager` QA-19, `Game`) to owned instances; leave stateless config singletons alone. The serialized Vitest configuration is additional evidence that global state is shaping the development process, not merely an aesthetic concern.
- **QA-25: `ServiceLocator` is a lifecycle façade over the same global singletons, not dependency injection.** All 14 `EngineServices` factories return `SomeService.getInstance()` (`EngineServices.ts:51-144`). ### QA-WO11 — Make required CLI/headless gates truthful (QA-23)
