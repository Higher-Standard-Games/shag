## TL;DR

Recording works. Reading/decoding works. **Playback is architecturally broken**: loading a
demo secretly spins up a *live dedicated server* and joins it as a player, instead of just
rendering the recorded map geometry and replaying frames. That single design decision explains
the symptoms the user reported:

- "loads on an empty Babylon scene" → the live-server launch path fails or half-completes, so
  the BSP geometry never renders, but the demo's own frame loop still positions player models.
- "doesn't load the correct map data" → geometry loading is a *side effect* of a live client
  connecting, not a deliberate step the demo player owns.
- "players move correctly on an empty scene" → snapshot decode + `RemotePlayerRenderer` are
  actually fine; they're just running against a scene with no world in it.

The fix is to give the demo player its **own local map-render path** (BSP geometry + lighting,
no server, no gameplay) and a deterministic camera/controller handoff. Everything downstream
(interpolation, viewmodels, HUD) is salvageable with smaller fixes.

## 1. Architecture map

### Record (server, submodule)
- [`GameServer.tick()`](../../src/games/fps/server/GameServer.ts) — on `MatchPhase.Active` calls
  `startRecording()`; every snapshot tick (`ticksPerSnapshot`) calls
  `demoRecorder.recordFrame(buildSnapshot(ctx))`; on `PostGame` calls `stopRecording()`.
- [`DemoRecorder`](../../src/games/fps/server/DemoRecorder.ts) — buffers full
  `BinaryProtocol.encodeSnapshot(state)` frames (no baseline → each frame independently
  decodable), writes `SHAG` header + frames + index table + footer, gzips to
  `public/data/demos/<map>_<gametype>_<date>_<time>.shagdemo`.

### Store / serve
- Files land in `public/data/demos/`. Client fetches them at `GET /data/demos/<file>`
  ([`DemoService.fetchAndLoad`](../../src/games/fps/client/DemoService.ts)).
- Lobby also exposes a `demos:list_response` message consumed by `DemoService.requestDemoList`.

### Read / decode (shared)
- [`DemoReader`](../../src/shared/demo/DemoReader.ts) — parses header/index, gunzips
  (Node `zlib` or browser `DecompressionStream`), `readFrame(i)` →
  `BinaryProtocol.decodeSnapshot(bytes)` → `GameState`.

### Playback (submodule client)
- [`DemoViewer`](../../src/games/fps/client/DemoViewer.ts) — transport state machine
  (play/pause/seek/speed), advances `currentFrameIndex` on a `snapshotRate` clock, emits
  `onFrame(state, tick)`.
- [`DemoService`](../../src/games/fps/client/DemoService.ts) — singleton orchestrator: loads the
  map, wires the frame callback into `RemotePlayerRenderer`, registers spectator/freefly
  controllers, drives the RAF loop, manages the HUD.
- [`RemotePlayerRenderer`](../../src/games/fps/client/RemotePlayerRenderer.ts) — feeds entities
  into `SnapshotBuffer`, samples interpolated transforms per frame, drives player models +
  animations + attached weapon meshes.
- [`DemoViewerHUD`](../../src/games/fps/client/DemoViewerHUD.ts) — DOM overlay: timeline, play/
  pause, speed, player list.
- [`CinematicDemoPlayer`](../../src/games/fps/client/CinematicDemoPlayer.ts) — highlight-reel
  wrapper over `DemoViewer` + `CameraSystem`.

### Console entry points
- `demolist [filter]`, `demo <n|file>` ([`DemoCommand`](../../src/games/fps/console/commands/DemoCommand.ts)),
  `demoplay [cinematic <min>|analyze|stop]` ([`DemoPlayCommand`](../../src/games/fps/console/commands/DemoPlayCommand.ts)).

## 2. Findings

Severity: 🔴 critical (breaks playback) · 🟠 high · 🟡 medium · ⚪ low / polish.

### 🔴 D1 — Demo playback launches a LIVE server instead of rendering the map

**Evidence.** [`DemoService.ensureDemoMapLoaded()`](../../src/games/fps/client/DemoService.ts#L237)
runs the console `map` command:

```ts
const result = await CommandRegistry.getInstance().execute(`map ${header.map}`);
```

`map` → [`MapCommand.launchMap`](../../src/engine/console/commands/MapCommand.ts#L123) →
`getGameplayMapLauncher().launch()` →
[`fpsMapLauncher.launch`](../../src/games/fps/client/FpsMapLauncher.ts#L23):

```ts
const client = await ensureFpsLobbyConnection();
const spawned = await client.spawnDevServer(map, normalizedGametype);
await Game.getInstance().initializeNetwork(spawned.serverUrl, { autoJoin: true });
```

So "play this demo" actually: connects to the lobby → **spawns a fresh dedicated server** →
**joins it as a live player**. The demo then plays *on top of* a live match.

**Impact.**
- Hard dependency on a running lobby + dev-spawn capability just to watch a file. If the lobby is
  down or `spawnDevServer` times out, `ensureDemoMapLoaded` throws → playback never starts (or, if
  the regex doesn't catch the error string, starts against a scene with no geometry → the reported
  "empty scene").
- When it *does* succeed, two worlds coexist in one scene: the live server's entities + your live
  local-player FPS camera, versus the demo's `RemotePlayerRenderer` entities. Live snapshots fight
  demo frames.
- Map geometry only appears as an accident of the live client's connect flow — the demo player
  never explicitly owns "render this map."

**Fix.** The demo player must render the map **locally, with no server**. We already have the exact
primitive: [`loadClientMap(mapName)`](../../src/engine/loader/map/ClientMapLoader.ts) —
"Render/load a BSP map for a client… intentionally not a gameplay starter." It clears the scene,
loads BSP geometry, applies worldspawn lighting + sky, and positions the active camera at spawn.
Replace `ensureDemoMapLoaded`'s `map` call with a direct import of `loadClientMap` (or a thin
`ClientMapLoader` wrapper), and make sure any live `Game` session is shut down first.

### 🔴 D2 — No teardown of a live session before playback; wrong ordering

**Evidence.** [`loadAndPlayNormal`](../../src/games/fps/client/DemoService.ts#L124) awaits
`ensureDemoMapLoaded()` **before** `stopAll()`, and `stopAll()` only disposes demo-owned objects
(renderer, HUD, viewer) — it never shuts down a live `Game`/network client.

**Impact.** If a live match is running (or D1 just started one), its render loop, local FPS camera,
and inbound snapshots remain active during demo playback. Combined with D1 this is the core of the
"garbage on screen / empty scene" behavior.

**Fix.** Reorder to: (1) stop/disconnect any live game (`Game.getInstance().shutdown()` if
connected), (2) local BSP load, (3) wire renderer + controllers, (4) load viewer + play. Make the
demo player assume it fully owns the scene.

### 🟠 D3 — Recorded map name may not match the loader's expected key

**Evidence.** [`DemoRecorder`](../../src/games/fps/server/DemoRecorder.ts#L342) stores
`map: this.config.mapName` verbatim. `MapLoader.loadMap` / `bsp load` expect a bare map key
(e.g. `wdm7`), lowercased. There is no normalization on either the record or playback side.

**Impact.** If `config.mapName` is ever a path, mixed-case, or has an extension, the local load
(D1 fix) silently fails → empty scene again.

**Fix.** Normalize on load: lowercase, strip any directory + `.bsp`/`.pk3` suffix before handing to
`loadClientMap`. Optionally normalize at record time too. Add a guard: if the map fails to load,
surface a clear console error and refuse to "play" onto an empty scene.

### 🟠 D4 — Camera/controller handoff is implicit and races the first frame

**Evidence.** `ensureCinematicControllers` registers `spectator` + `freefly` but activates
neither. The camera only becomes useful when
[`refreshHudPlayerList`](../../src/games/fps/client/DemoService.ts#L331) happens to run *after* a
frame has populated `latestState`, auto-selects the first `player_*` entity, and calls
`setController("spectator")`. Until then the camera is wherever the previous mode left it.

**Impact.** First seconds of playback frequently show "nothing" (camera pointing away / at old FPS
spawn), reinforcing the empty-scene impression even once geometry loads.

**Fix.** On playback start, deterministically: switch to a demo camera (spectator on first roster
entry, or freefly framed at the map's spawn/action centroid) *before or on* the first delivered
frame. Don't rely on the HUD refresh side effect to pick a camera.

### 🟡 D5 — Followed-player weapon/viewmodel derived only from live events, not entity state

**Evidence.** [`_updateDemoWeapon`](../../src/games/fps/client/DemoService.ts#L437) only switches
the viewmodel when a `weapon_state` **event** for the followed entity appears in the current frame.
`weapon_state` is emitted on change, so most frames (and every seek target) carry none.

**Impact.** After a seek, the viewmodel is whatever it was before (or nothing). First-person demo
POV shows a stale/absent weapon until the next switch happens to be replayed.

**Fix.** Read the current weapon from the entity's component in the decoded state as the source of
truth, and reconcile the viewmodel to it each frame / on seek. Keep events only for *transitions*
(recoil, switch animation).

### 🟡 D6 — Seeking drops all inter-frame events (kills, switches, effects)

**Evidence.** [`seekToFrame`](../../src/games/fps/client/DemoViewer.ts#L119) jumps
`currentFrameIndex` and delivers only the landed frame. Events on skipped frames are never
replayed.

**Impact.** Scrubbing loses kill feed, hit effects, weapon switches, recoil — state derived from
event streams desyncs from the visible world.

**Fix.** Treat seek as "rebuild state at frame N": deliver the landed frame, but reconstruct
event-derived state (current weapon, alive/dead, score) from entity/player fields rather than the
event stream. Optionally, for short forward seeks, fast-replay intermediate frames' events without
rendering.

### 🟡 D7 — SnapshotBuffer interpolation not designed for seeks / non-realtime playback

**Evidence.** `RemotePlayerRenderer.pushSnapshot` feeds `SnapshotBuffer` with
`serverLocalTime = undefined` (tick-based interp). A seek pushes a single frame whose tick is far
from the buffer's history; play at 4× or a scrub is not the realtime cadence the buffer's interp
delay assumes.

**Impact.** Visible stutter/rubber-banding right after seeks and at high speeds; models may snap or
briefly extrapolate to wrong positions.

**Fix.** Add a `reset()`/flush on the buffer when the demo seeks (discontinuous tick jump), and
consider driving interpolation off the demo clock rather than wall-clock during playback. Verify
`SnapshotBuffer` tolerates a cleared history without NaNing the first sample.

### 🟡 D8 — First-person viewmodel requires a prior live session

**Evidence.** Both `_attachWeaponViewToSpectatorCam` and `_updateDemoWeapon` bail unless
`WeaponViewManager.getInstance().isInitialized()`, which only becomes true after a live FPS match
has run. A fresh page-load → `demo` → `demoplay` has no viewmodel at all.

**Impact.** Cold-start demo playback (the common case for "just watch this file") shows third-person
models but no first-person weapon in POV mode.

**Fix.** Lazily initialize `WeaponViewManager` for demo playback (it only needs a camera + scene),
or explicitly document POV as third-person-only until a viewmodel manager is stood up for demos.

### ⚪ D9 — Player `team` is never in the wire format → team colors are faked

**Evidence.** [`encodePlayers`/`decodePlayers`](../../src/engine/network/protocol/BinaryProtocol.ts#L624)
encode `entityId/name/score/deaths/ping` but **not** `team`; decode defaults `team: ""`.
`RemotePlayerRenderer.createModelInstance` therefore hashes `entityId % 2` for a fake team color
(there's a `TODO: Use actual team assignment from server`).

**Impact.** Demo (and live) team colors are cosmetic noise, not real teams. For TDM/CTF demos this
is wrong.

**Fix.** Out of scope for the core demo fix, but note it: add `team` to the player codec (affects
live too) or carry team in the demo roster/header and map it in the renderer.

### ⚪ D10 — Static-file coupling for demo fetch

**Evidence.** `fetchAndLoad` hits `/data/demos/<file>` (relative). Works under `npm run dev`
(Vite serves `public/`). Production/lobby-hosted playback needs the lobby to serve the same path.

**Fix.** Confirm/lock the serving contract; make the base path configurable (env) like the lobby
URL already is.

### ⚪ D11 — Stale docs / magic numbers

- `DemoConfig` comments say `tickRate (e.g. 60)`; the server runs 125 Hz now. `tickRate` and
  `snapshotRate` are written as `uint8` — 125 and 60 both fit, but a future >255 tick rate would
  silently truncate. Consider `uint16`.
- `DemoRecorder.removePlayer` is a no-op by design (roster kept for replay) — fine, but the log line
  is misleading ("disconnected" with no state change).

### ⚪ D12 — Cinematic path shares all the above

`CinematicDemoPlayer` goes through the same `ensureDemoMapLoaded` + wiring, so every fix above also
repairs cinematic mode. Re-validate camera-path framing after D1/D4 land.

correct map, no live-server contamination, a camera pointed at the action). Then C4/C5 for scrub

regression suite required by `AGENTS.md` (networking-sensitive files touched: `BinaryProtocol`,
snapshot path).
