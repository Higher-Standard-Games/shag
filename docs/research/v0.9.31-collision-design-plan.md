# Collision performance and intended movement geometry

**Date:** 2026-10-16  
**Status:** proposed implementation sequence; no collision changes implemented

## Target

Make collision as cheap as practical while preserving deliberate FPS movement
geometry. Decorative corner softening is a visual feature and must not introduce
new gameplay ledges, ground loss, jumps, or altered stair traversal.

Two outcomes are required: avoid unnecessary collision calculations, and prevent
decorative geometry from changing intended movement. Faster tracing alone does
not resolve unwanted contacts. Simplification that restores authored collision
can be a correctness fix, rather than an approximation of intended movement.

Keep `SweepCollisionBackend` and the shared client/server collision path. First
improve geometry selection and honor authoring semantics; do not replace the
movement solver or change movement constants to conceal geometry problems.

## Evidence and unresolved questions

See the [stair investigation](./v0.9.31-stair-collision-performance.md) for
measurements, methodology and local artifacts. The wfdm11 recording exposes
repeated surface tests, large linear triangle scans, and repeated content/name
checks per facet. Existing fullclip supports sampled stair positions, but does
not remove enclosed detailed collision. Diagnostic acceleration preserved results
at 580 sampled positions; this is not a full deterministic input replay.

The player reports repeated jump sounds in the same area. The possible chain
is decorative contacts causing unstable grounding, followed by real jump
activation. Prediction/reconciliation or presentation event duplication are
other possibilities. None has been confirmed. Do not suppress sound or add
grounding grace periods as a substitute for finding the cause.

The user confirmed that `collisiontype none` is a compiler flag and that wfdm11's
stair entity has a typo in its collision-related key, causing it to compile solid.
No runtime entity-key handler is planned. The source entity/compiler contract
has not been independently inspected. A baked surface may no longer retain its
source entity or association.
Correcting this map typo is useful, but does not address the tracing cost of
intentionally solid complex geometry elsewhere in this and other maps.

The makebsp softening implementation and its treatment of collision have not
been inspected. Map provenance and authoritative collision intent must be
established before inferring which bevels to remove from compiled geometry.

Jal subsequently clarified that softening changes draw surfaces, not collision
brushes, and suspects automatic model collision generation may produce excessive
brushes. SHAG's triangle-soup extension separately builds runtime facets from
draw surfaces. Our profile identifies that facet path as the dominant isolated
cost. Keep compiler-generated BSP brushes and SHAG-generated facets distinct in
future statistics and provenance work; neither model origin nor brush generation
has been inferred from draw-surface counts.

### Jal's broadphase and containment checks

Jal is a co-author of Warsow; his recommendations are concrete implementation
checks. Source inspection of `SweepCollisionBackend` found:

| Check | Existing implementation | Planned action |
| --- | --- | --- |
| Retrieve brushes from regions touched by a trace | `traceNode` traverses BSP nodes with hull extents and `traceLeaf` reads leaf brush lists. `traceAllClipBrushes` additionally scans every indexed clip brush. Neither uses rendering PVS. | Test swept-hull BSP traversal and spatially restrict the extra clip path without losing brushes absent from leaf references. |
| Bounds/radius and early brush rejection | Query radius/height and hull extents exist. Whole-face and moving-model AABB rejection exist. Static `traceBrush` enters plane tests directly; no cached static brush bounds or sphere is used. | Precompute conservative brush bounds and early-cull candidates; measure whether spheres add value after AABB rejection. |
| Skip brushes wholly inside compatible brushes at load | No brush-containment removal pass is present. | Add conservative containment preprocessing alongside redundant-facet removal. |

The spatial objective is to visit regions the **swept hull** touches, including
neighboring leaves reached by its extents. PVS is visibility data, not a safe
collision filter: do not reject collision because a cluster is invisible from
the camera/start cluster. A cluster/leaf index may organize collision candidates
without using its visibility bitset to reject them.

## Invariants

- Client prediction and authoritative server use identical collision geometry,
  preprocessing rules and query results. No browser-only optimization.
- Acceleration-only phases preserve trace fraction, normals, solid flags,
  contents, hit identity and movement/event results, including equal-time hits.
- Intentional geometry corrections have explicit before/after expectations;
  do not require preserving the faulty decorative contacts being corrected.
- Preserve query-specific behavior: player hulls, crouch hulls, point/ray traces,
  projectiles and different masks. Playerclip cannot replace solid collision for
  every query. Preserve required surface properties and moving-model transforms.
- Retain triangle-soup support where it supplies real world collision. Shader
  path heuristics or face type alone do not prove geometry is disposable.
- Uncertain containment, provenance or simplification leaves geometry intact.
- Preprocessing has bounded load time and memory, deterministic output and
  complete cleanup on map replacement. Collision is not rebuilt every frame.

## Implementation order and checkpoints

Each numbered phase is a separate feature/checkpoint. Complete its acceptance
checks, update this plan with results and the commit SHA, and commit before
starting the next phase. Split a phase further if it introduces independently
reviewable behavior; never combine a solver change with an optimization merely
to make an end-to-end result pass.

### 0. Establish a durable baseline and diagnose jumping

Promote the useful scratch measurements into a reproducible tracked headless
tool/fixture. Record the demo and BSP hashes, revisions, parameters, runtime,
hardware, warmup and sample distribution. Keep baseline and candidate results
separate; avoid counters in the hot path during uninstrumented timing runs.

Add opt-in aggregate counters for traces, visited/unique brushes and surfaces,
candidate/tested facets and trace/movement time. Separate fresh prediction,
reconciliation replay and server simulation. Capture grounded transitions,
contact normals, step decisions, jump activations and sound/event emission ticks
around the stairs, including walking without jump held and with auto-hop input.

Compare local brush-only diagnostic collision against the existing path to
understand the intended support. This diagnostic must not become a blanket
production switch. Record a live CPU/frame profile as well: snapshot playback
or isolated displacement traces are insufficient to measure live prediction.

**Accept:** reproducible baseline; jump sound cause classified or explicitly
unresolved; regression map corpus and measurement recipe recorded.
**Checkpoint:** baseline tooling and evidence, before behavioral changes.

### 1. Deduplicate visits per trace

Use generation stamps for brushes and surfaces, including the extra clip pass.
Handle initialization, generation wraparound and query lifetime safely. Preserve
model-local/exclusion queries and any supported reentrancy. Preserve first-visit
order; a repeated equal contact must not silently change the chosen normal.

**Accept:** duplicate-leaf and clip-pass fixtures, exact baseline trace/movement
comparisons and demonstrably reduced unique-vs-total work.
**Checkpoint:** deduplication only.

### 2. Filter once per surface and precompute shader properties

Move eligibility checks ahead of each surface's triangle loop. Precompute
immutable name/flag properties while retaining query-mask-dependent decisions.
Avoid repeated lowercase/string searches and avoid unnecessary hot-path
allocations. Treat brush filtering similarly where useful.

**Accept:** unchanged results across all tested masks and flags; measured
reduction in eligibility calls and CPU cost, not just a faster synthetic loop.
**Checkpoint:** filtering/precomputation only.

### 3. Cull static brushes and restrict the clip-brush scan

Precompute conservative bounds for convex static brushes, with fallback for
malformed/unbounded input. Reject brushes outside the swept-hull AABB before
plane solving. Add sphere rejection only if measurement justifies it; elongated
brushes can make spheres loose and unhelpful.

Audit leaf references for clip brushes. Spatially index brushes missing from
those lists, or provide an equivalent conservative query; do not simply delete
the fallback scan. Preserve mask behavior and moving-model transforms. Reuse
per-trace deduplication.

**Accept:** leaf-boundary, large-hull, long-sweep, point, clip-only and moving-model
fixtures; exact trace parity and reduced brush/plane work. Compare against the
complete clip scan, including unreferenced brushes.
**Checkpoints:** brush bounds, then clip spatial indexing as a separate feature
if independently sized.

### 4. Accelerate triangle selection with a static BVH

Build deterministic spatial bounds/hierarchies for collision facets at load.
Query using conservative swept-hull bounds and retain the existing facet plane
solver. Account for facet construction and collision tolerances; raw visual
triangle bounds alone are not the correctness contract. Preserve candidate
ordering for tie-sensitive contacts, including embedded/stationary hulls.

Compare per-surface and spatially partitioned layouts on the real map corpus.
Use packed storage where justified, and measure load time, memory and query
time together. Keep moving models in the correct coordinate/query space.

**Accept:** baseline differential tests for edges, thin surfaces, rays, long
sweeps, masks, patches, lifts and steps; deterministic movement parity; live CPU
and frame-time improvement. Dense remote geometry must no longer require a
linear facet scan for a local movement query.
**Checkpoint:** BVH acceleration only, with before/after results.

### 5. Remove provably redundant collision

First identify static brushes wholly contained by another compatible convex
brush with the same contents. Contents equality is necessary but not sufficient
where surface properties, hit identity or other consumers remain observable.
Do not discard partial overlaps, trigger/ladder semantics or moving brushes.
Keep canonical BSP data intact for point-content, entity and diagnostic users;
prefer a collision-query index over destructive lump edits. Give duplicate
brushes a stable survivor. Validate brush pruning separately from facet pruning.

Preprocess facets fully contained inside compatible static collision volumes.
Start with containment in a single convex brush. Prove containment of the actual
collision facet, accounting for tolerances and relevant query categories, not
just its visual vertices or overlapping AABBs. Preserve exposed portions,
contact properties and boundaries where another volume does not substitute for
the original surface. Union-of-brush containment is a later extension.

**Accept:** contained, touching, protruding, partial, differently masked and
moving-volume fixtures; preservation of exposed geometry; measured facet/memory
reduction. Use explicit expected outcomes where clip-authoritative movement
replaces decorative contacts. If coverage cannot be proven, keep the facet.
**Checkpoints:** contained-brush pruning, then contained-facet pruning, each with
its own differential evidence and documented intentional contact changes.

### 6. Preserve intended collision through the asset pipeline

Preferred long-term contract: the compiler retains pre-softening collision
brushes or exports deliberate collision proxies, while rounded visuals remain
independent. Verify what the existing compiler already provides before adding
formats. Decide how runtime loaders identify authority for each query type;
retain a conservative fallback for legacy BSPs. If collision data changes, both
client and server must resolve the same version, including cache identity.

For legacy maps, investigate deterministic coplanar convex-facet merging before
lossy decimation. Preserve boundaries, holes and collision properties. General
convex decomposition or removal of small bevels requires an explicit error
budget plus gameplay validation; do not apply it globally by default. A single
convex hull around stairs can create an unintended ramp or fill openings.

**Accept:** original-intent stair fixtures without decorative grounding/jump
artifacts; retained ledges, openings, jump routes and projectile behavior;
documented legacy behavior and updated authoring guidance.
**Checkpoints:** compiler/proxy contract, runtime consumption and any legacy
simplifier must each be separately validated and committed.

## Validation and measurement policy

For every runtime feature above, run focused tests and headless route comparisons
first, then the project gates and regression suite before its checkpoint:

```powershell
npm.cmd run typecheck
npm.cmd run test:run
npm.cmd run gate:biome
npm.cmd run build
npm.cmd run test:simulation
npm.cmd run test:physics
npm.cmd run server:tick
npm.cmd run server:fuzz -- --ticks 1000
npm.cmd run cli:game -- --exec "bsp load wdm2; bsp info; quit"
npm.cmd run cli:game -- --exec 'sim replay \"W+CROUCH 60; JUMP 1; W 30\"; quit'
npm.cmd run docs:build
```

Run build after the full test run completes; they can contend over fixtures.
Use `demo:verify` only for compatible `.shagverify` bundles; it is not a verifier
for the supplied `.shagdemo`. A full recording replay harness must preserve or
reconstruct all required initial movement state, not assume snapshots alone
provide it.

Include wfdm11 and wfdm5, representative brush-heavy maps, patches, triangle-only
walkable world surfaces, triggers, ladders, lifts and thin railings. Validate
walking, stepping, crouching/sliding, jumping, wall interactions and high-speed
sweeps. Record intended changes separately from unexpected divergences.

Report median/p95/p99 trace, movement and live frame times; total collision CPU
per frame/tick; fresh/replayed simulation counts; facets visited/tested; load
time and memory. Establish budgets on the measured baseline hardware in phase
0. The 125 Hz tick interval is 8 ms for the **entire** simulation, not a collision
budget. No FPS guarantee follows from the current isolated measurements.

## Commit and recovery policy

- Commit the design/baseline separately from runtime implementation. No push or
  merge is implied by a checkpoint.
- After each feature passes validation, commit its implementation, focused tests,
  evidence summary, living changelog and affected manual pages together.
- Record checkpoint SHA, exact validation commands/results, map identities and
  unresolved items in the phase's completion entry. Do not start the next feature
  on an uncheckpointed passing implementation.
- If both repositories change, commit FPS first, then commit the engine changes
  and updated FPS pin. Keep corresponding checkpoint SHAs together.
- On failure, stop layering features and diagnose against the last checkpoint.
  Use a separate worktree for baseline comparisons; preserve unrelated work.
  Prefer reverting an identified commit over destructive reset in a shared tree.
- A phase is not complete merely because FPS improves. Unexpected movement,
  query-mask, event or client/server differences must be resolved or explicitly
  accepted as the documented intent correction before its checkpoint.
