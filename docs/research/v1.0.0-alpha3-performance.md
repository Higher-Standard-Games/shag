# v1.0.0-alpha.3 performance pass

Status: findings from the alpha.3 papercut and performance pass, measured on the
`v1.0.0-alpha.3-engine-separation` branch (October 2026). Fixes are recorded in
`docs/changelog/v1.0.0-alpha.3.md`; this note keeps the measurements, what was
ruled out, and what to do next.

## Summary

- **Frame drops in fights came from the CPU, not the GPU.** In a 10-bot FFA
  timedemo the GPU needs about 7 ms a frame (13 ms at the 95th percentile);
  gunplay frames take about 21 ms.
- **The spikes were mostly new work created mid-fight:** materials made or
  cloned per explosion, weapon switch, drop and respawn; textures decoded again
  for every cloned material; shaders released and compiled again; projectile
  models built on their first shot; frozen map materials re-checked on every
  light change. These are fixed.
- **The typical frame is unchanged.** It is bound by Babylon's per-frame CPU
  work for the map: choosing visible meshes and issuing about 300 draw calls.
  That is the next target, and it is a renderer project, not a papercut.

## How it was measured

| Tool | Use |
| --- | --- |
| `npm run benchmark:profile` | Timedemo profiler: drives a recorded fixture through free-fly and first-person gunplay segments and saves frame times and a CPU profile. |
| `npm run benchmark:fixture` | Builds a fixture from a recipe; accepts any installed map with 2–10 bots. |
| `perf capture [seconds]` | In-game percentiles for frame time, CPU/GPU, draw calls, particles, physics and shader compiles. |
| `perf shaders [seconds]` | Lists each shader compiled in the window, the defines that differ from its closest existing sibling, and shaders released and rebuilt (`src/engine/rendering/ShaderCompileCapture.ts`). |

Fixtures:

- **10-bot FFA on washoi_dm2**, 45 s at 1280×720, WebGL2.
- **6-bot plasma FFA on washoi_dm5** (`benchmarks/recipes/wdm5-ffa6.json`,
  seed 1), chosen because plasma fights reproduced the reported drops.

Profiling ran in a separate clone with its own copy of `public/data` (never a
junction), because other agents' edits in the shared tree invalidated runs. The
profiler needs `SHAG_APP=src/games/fps` there; it now defaults to it.

Every A/B below is one run each, so treat differences of a few percent as noise.

## Measurements

### 10-bot FFA, washoi_dm2 (material pooling and weapon sharing)

| Frame time (ms) | Median | 95th percentile | 99th percentile |
| --- | --- | --- | --- |
| Gunplay segment a | 21.6 → 21.1 | 41.3 → 38.1 | 88.8 → 71.5 |

Where a gunplay frame's CPU time went (sampling inflates these somewhat):

| Work | ms per frame |
| --- | --- |
| Issuing draw calls | ~7 |
| Choosing visible meshes | ~4.7 |
| Depth pass for soft halos (see below) | ~1.3–2 |

| Explosion spawning | ~0.9 |
| Hitscan effect ray pick | ~0.6 |

### 6-bot plasma FFA, washoi_dm5 (texture sharing)

Cloned materials reusing their source textures instead of decoding the image
again: the gunplay segments drew **19–28% more frames** (one segment
994 → 1269 frames). Before, slow frames held 60–80 ms of texture uploads.

## What was fixed

| Problem | Cause | Fix |
| --- | --- | --- |
| Spikes on explosions | Fireball and shockwave materials made and disposed per explosion | Shared material pool |
| Spark shader compiled again on most plasma explosions (7 times in 30 s) | Spark particle systems disposed per explosion; when none was alive the effect was released | Finished spark systems are pooled (`MAX_IDLE_SPARKS = 16`) |
| Spikes on other players' weapon switches | Every material of the new weapon cloned (except on Firefox) | Read-only materials shared on WebGL; WebGPU keeps clones |
| Dropped weapons and barrels | Each copied every material | Same sharing as held weapons |
| Texture uploads in fights | `Material.clone` clones textures; a texture from an embedded model image has no URL to share by, so each clone decoded and uploaded again | `MaterialCloneBatch` clones with the source textures |
| 60–120 ms stall when switching to the blade | Frozen world materials re-checked on any light change, including weapon-view and model-scoped lights | Only lights that can reach the world trigger the re-check |
| Projectile models and shaders built mid-fight | Projectiles arrived before definitions and models were ready; each shot retried | Projectile models load and compile with the map; definitions register once per connection |
| Plasma drawn untextured, then as grey opaque shapes | Side effects of early loading: texture loader not yet set up; shader scripts not yet read | Projectile loader sets up the texture loader and reads mounted shader scripts first |
| Other players' Voltaic beams (~44 ms in slow frames) | Scene-wide ray pick per shot, then replaced by the server's contact | Pick only when the snapshot carries no contact |
| "World meshes were not ready" counting 124 surfaces | Readiness checked in the weapon camera's render pass | Checked in the world camera's pass: 1 surface was still compiling |
| `Effect 'walkbob' already registered` ×5 per join | View effects never unregistered on detach | Unregistered when the controller detaches |
| Dead assets loaded | Instagun and MD3 pickup models (ammo box and icon quad, health, armour) | Removed, with `r_pickupProcedural` |

## Ruled out

These were tried and showed no measurable change, so they were reverted:

- Skipping the temporary light in `EffectPreloader`.
- Creating the explosion material pool before the map freezes its materials.
- Skipping a `WorldFogController` refresh.

Also not the cause:

- **Player models.** The whole player model, normal mapping included, costs
  about 0.35 ms GPU per player.
- **The water depth pass.** Idle without water in view.
- **The cel-outline depth pass.** Off by default (`r_cel_outlines 0`).

## Next targets

In order of expected gain:

1. **Fewer map draw calls.** About 300 draw calls and ~4.7 ms of visibility
   work per frame are the floor under every frame. Merging static map geometry
   by material (per PVS cluster or region, so culling still works) would cut
   both. This is the biggest lever and a renderer change: it needs the
   regression set and visual checks on every map, with special care for
   shaders with deforms, animated textures and lightmap atlases.


## Done after this note

### Hitscan impacts trace collision brushes

Each machinegun tracer, riotgun pellet, electrobolt and local Voltaic frame
found its impact with a Babylon scene pick: every rendered mesh, triangle by
triangle. Measured on washoi_dm5 with 500 seeded rays from each of 7 spawn
points at eye height:

| | ms per ray |
| --- | --- |
| Scene pick | 1.7–2.1 (3.4 from one open-area camera) |
| BSP ray trace | 0.015 |

A 20-pellet riotgun shot spent 35–70 ms in picks. The effects now trace the
map's collision brushes with the server's shot mask. Against the pick, 85% of
rays stop at the same place (median gap 0.05 units). Most of the rest end on
`common/fullclip`, which the maps define as weapon clip (`nodraw`, `nomarks`):
the server stops shots there, so impacts now appear where the shot really
ended, without a wall mark. Sky (`noimpact`) is a miss. About 1% of rays still
disagree on drawn surfaces.

A shot trace must pass `height: 0` as well as `radius: 0`: the sweep backend
defaults `height` to the player's 64 units, which made the first version stop
24 units above floors.


To check a change, run `npm run benchmark:profile` against the washoi_dm5
plasma fixture before and after, and use `perf capture 20` in a live fight.
Run each side at least twice before trusting a difference under 10%.

### Explosions are batched and animated on the GPU

Every explosion (rocket, grenade, plasma, blade blast, bomb) built a fireball
mesh whose vertices the CPU rewrote and re-uploaded every frame, 8 to 12 ray
meshes, a shockwave mesh and a CPU particle system: 11 to 15 meshes and draw
calls each, built and disposed per explosion. `ExplosionBatchRenderer` now
draws every live explosion as instances of four meshes (shockwave, fireball,
rays, sparks) whose vertex shader computes the animation from the spawn time.
Plasma impacts draw 4 to 6 rays instead of 8 to 12.

The look is kept: the fireball's spike noise, growth and spread across the hit
surface, the ray and shockwave timing, and the sparks (40 per explosion, the
old particle system's capacity) are ported formula for formula. Colours go out
in linear space when image processing runs as a post-process, as Babylon's own
materials do; without that they came out pale. Screenshots of all four
explosion types at fixed moments match the old renderer apart from random ray
directions.

`perf capture` on the washoi_dm5 plasma timedemo, and with about 60 plasma and
rocket impacts a second spawned in view:

| | Old | New |
| --- | --- | --- |
| Timedemo p95 frame | 15.1–15.8 ms | 12.4–13.3 ms |
| Timedemo frames in 25 s | 2286–2390 | 2522–2539 |
| Stress p50 / p95 frame | 20.1 / 30.0 ms | 11.1 / 19.1 ms |
| Stress p50 GPU frame | 11.8 ms | 6.7 ms |
| Stress p50 draw calls | 626 | 420 |

The shockwave disc is built in the XY plane and squashed along Y, so on a floor
hit it reads as a flat ellipse standing on edge rather than a ring on the
floor. The batch reproduces that; whether it should lie on the surface is a
separate look decision.

### No light-cap recompiles during play

Each timedemo repetition reloads the map, and its progress reads `measure`
before that reload, so a capture started on the word counts a map load: 80
compiles in 30 s. Started after the reload, playback compiled 18 shaders in
30 s. Ten were `MAXLIGHTCOUNT` changes: Babylon's glTF loader raises every
material's light cap to the scene's light count (8) after each import, and on
WebGL the raise is kept, so map, player and weapon materials compiled again,
with nothing else changed, whenever a model loaded. WebGL materials now start
at 8 (`SAFE_MAX_SIMULTANEOUS_LIGHTS`); the raises change nothing, and playback
compiles 6 shaders in 30 s, the same in two runs.

The remaining six are the plasmagun view model's sight materials drawn for the
first time in a render pass with no name (15, beside the weapon camera's 16)
and one player outline. They happen once per weapon, not per fight.

The view weapon caps its PBR materials at 2 lights (its own light and the
muzzle flash). WebGPU keeps that cap; on WebGL the loader raises it to 8 on the
next import, so the WebGL view weapon is also lit by the sun, moon and ambient
lights. Which is intended is a look decision.

### Soft-halo depth pass

Measured on the washoi_dm5 plasma timedemo (`perf capture`, 25 s after the
reload), the soft-halo depth pass costs about 157 of 441 draw calls a frame and
0.7 ms of GPU time; frame times on the profiling machine stayed within noise
whether it ran every frame, every other frame or not at all. Draw calls are what
Firefox and slower CPUs pay for, so:

- **The pass draws only meshes that can fade a halo.** A halo reads the depth of
  surfaces from itself to 50 view-depth units behind it, at the pixels it
  covers; nearer surfaces hide it, farther ones read as no fade, as does no
  depth at all. A mesh goes in the pass only if its screen rectangle overlaps a
  visible halo's and its depth range reaches into that span. The filter keeps
  about half of the candidates (286 to 153) and saves about 40 draw calls a
  frame. Screenshots of six halo views with and without it differ less than
  two shots of the same view do (animated shaders).
- **Smooth turns soft halos off** (`r_softhalos 0`, also in Video → Effects):
  halos end in a hard line at walls and the pass does not run, about 115 draw
  calls a frame fewer. Balanced and Pretty keep them.

Rendering the depth every other frame was dropped: about 100 fewer draw calls,
no frame-time change here, and a fade edge that lags a frame while moving.
