## A. Dropped weapon world models missing or partial

**Observed.** On `wdm2` the rocket launcher lying on the ground was invisible,
yet walking over it picked it up, showed it in hand, and dropped it again
correctly. The plasmagun on the ground renders **only its loading chambers** —
the gun body is absent. Grenade and rocket projectile models appear untextured.

**Confirmed.** Nothing yet; this cluster has not been instrumented.

**Analysis.** These are one cluster but likely *two* failures, and the split
matters because it points at different subsystems:

- **Missing geometry** (RL entirely, PG body) is a model-load failure, not a
  texture one. An untextured mesh still renders. That the plasmagun's barrel
  survives while its body does not is the strongest clue on the list: the barrel
  is a separately attached sub-model, so one part of a multi-part weapon loaded
  and the other did not.
- **Missing texture** (nade, rocket) is consistent with the KTX suspicion — the
  same family of problem as the skybox work earlier this cycle, where 291 ETC1
  textures were unreadable until the software decode was reused.

Pickup, hand rendering and drop all work, so the item logic and the viewmodel
path are healthy. Only the **world model** render path is implicated.

**Ruled out.** PVS. It enables and disables whole meshes; it cannot remove one
sub-mesh of a weapon and leave another, and it never touches materials.

**Investigate.**
1. Browser console during a `wdm2` load — a failed model or texture fetch
   almost certainly logs, and that likely names the cause outright.
2. Whether the failing assets share a texture format (KTX/KTX2/ETC1) or a
   loader path.
3. Whether `npm run tools:textures` covers the weapon/projectile texture set.

## B. Player models float above the floor, or sink into it

**Observed.** On `wdm2` an enemy stood visibly above the floor. On `wdm7` a bot
appeared partially sunk into it. Reloading the same `wdm2` match placed models
correctly. The defect is **intermittent across map loads**, not across players
within a load.

**Confirmed.** Nothing instrumented yet.

**Analysis.** The reporter's own observation is the most valuable evidence:
during the **death animation the model collided with the world correctly** while
the standing model floated. Collision uses the entity position; the model uses a
visual anchor. If one is right and the other is wrong, the entity position is
sound and the **anchor offset** is what drifts.

"Correct after a reload" makes this a race rather than a data error — the same
map and the same models produce different results on different loads.

There is a concrete suspect. `RemotePlayerRenderer` carries a **late model
assign** path (`[RemotePlayerRenderer] Late model assign for …`) for entities
that appear before the player model finishes loading. A model attached through
that path may miss anchor setup the normal path performs. That would produce
exactly this: usually fine, wrong when the load order happens to differ, and
consistent for the whole session once established.

**Ruled out.** PVS, which only toggles `setEnabled` and never writes a
transform. Also the collision facet-bevel change, which cannot move a render
anchor.

**Investigate.**
1. Log anchor Y against hitbox Y at spawn; a constant offset names the bug.
2. Record whether floating entities came through the late-assign branch.
3. Compare the anchor setup either side of that branch.

## C. Distant bots slide without animating

**Observed.** A bot strafing across the reporter's view was "standing and
sliding" — moving with no limb motion.

**Confirmed.** **This is caused by work committed in this cycle.** Distance-based
animation LOD pauses a player's `AnimationGroup` beyond a threshold while
leaving the model drawn, which is precisely this symptom.

The threshold was set at **2500 units** on the reasoning that limb motion is
sub-pixel there. That reasoning was wrong: 2500 Q3 units is roughly 60 metres,
where a player is small but their stride is plainly readable.

Babylon's resume path was checked and is **not** implicated:
`Animatable.restart()` sets `_paused = false` and nothing else, and
`AnimationGroup.play()` routes a started-but-paused group through `restart()`,
so resuming keeps the pose rather than snapping to frame 0.

**Analysis.** The saving is real — a hidden or distant model keeps evaluating
bones every frame, and on a bot-heavy map that is the larger half of the cost —
but the threshold was chosen by argument rather than by measurement, and the
argument was wrong.

**Next step.** Raise the threshold substantially, or remove distance LOD until
its benefit is measured. The PVS half (pause what the camera cannot see) is
sound and should stay: a player in another room cannot be observed sliding.

**Better long-term shape.** Gate on projected screen size rather than raw
distance, so the rule means the same thing at any FOV and resolution.

## D. End-of-match screen

**Observed (FFA, 8 players).** The board showed `TEAM SOBA 0` / `TEAM UDON 0`
in a free-for-all; every player was listed under `SPECTATORS (8)` with no
scores; the winner's name flickered in size; the winner's model stood in the
wrong place.

**Confirmed — and half fixed.**

*The team layout* came from `Scoreboard.ts` deriving team-ness as
`Object.keys(state.teamScores).length > 0`. `MatchState` initialises
`_teamScores` with both `udon` and `soba` **in every gametype**, so that test is
always true. `BaseGametype.teamBased` already existed and
`GametypeController` already passed it to `MatchState`; it simply never reached
the snapshot. It does now, and the three widgets that guessed —
`Scoreboard`, `PauseMenu`, `SpectatorOverlay` — read it instead. A later
screenshot confirms the team columns are gone.

*The spectator list* is a **separate, still-open bug**. With the team branch
correctly skipped, the FFA branch still files every player as a spectator, so
entries are arriving with `teamId === "spectator"` at match end. Uninvestigated.

*The flickering name and misplaced model* are untouched. `PostGameShowcase`
carries a comment claiming the "model in a weird map position" problem was
already addressed, so either it regressed or the fix is partial.

**Investigate.**
1. Where scoreboard entries get their `teamId` at match end, and why FFA players
   are marked spectators there.
2. Whether the winner-name flicker is a CSS/layout loop or a per-frame rewrite.
3. `PostGameShowcase` model placement against its own stated intent.

## E. Warping in `wdm2`

**Observed.** "Some small warping around" during a `wdm2` match. Not localised
to a player, an area or an action.

**Analysis.** Too vague to act on. The plausible causes are all things this
cycle changed — lag compensation, the interpolation interval correction, snapshot
handling — which makes it worth pinning down rather than dismissing, but also
means guessing would likely produce a wrong "fix".

**Investigate.** Reproduce with a bot count sweep; note whether it correlates
with bot count, with a specific area of the map, or with combat. `npm run
net:viewlag` already exists for the network half.

## F. Projectile trails are flat, not conical

**Observed.** Trails render as flat triangles rather than the crossed-quad cone
they are meant to be — "missing the other part of the X shape".

**Confirmed.** `ProjectileManager` builds the trail with `MeshBuilder.CreateRibbon`.
A single ribbon is one surface; the crossed look requires a second ribbon rotated
90° about the trail axis.

**Analysis.** Self-contained, independent of every other item here, and the
cause is understood without further investigation.

**Next step.** Add the second ribbon, or replace both with a billboarded trail
if the cross was only ever approximating view-alignment.

## G. Frame-rate-dependent presentation smoothing

**Observed.** Running the browser with VSync disabled (to measure peak FPS)
made "a lot of things flaky" at ~234 FPS.

**Confirmed.** The pattern exists in the codebase:
[FollowController.ts:172](../../src/engine/camera/controllers/FollowController.ts#L172),
[IsometricController.ts:330](../../src/engine/camera/controllers/IsometricController.ts#L330)
and [SideScrollController.ts:173](../../src/engine/camera/controllers/SideScrollController.ts#L173)
all call `Vector3.Lerp(current, target, smoothing)` with a constant factor,
which closes a fixed *percentage per frame* and therefore converges about four
times faster at 240 FPS than at 60.

**Ruled out.** Simulation timing. Movement derives its clock from
`sequence * dt` rather than accumulating frame time — the property that makes
reconciliation replays idempotent — so physics cannot fast-forward at high frame
rates, and `server:tick` / `server:fuzz` determinism would fail if it could.
Two of the four causes commonly cited for this class of problem (frame-dependent
timers, fixed-timestep mismatch) therefore do not apply here.

**Gap.** The three confirmed sites are the follow, isometric and side-scroller
cameras — **not** the FPS gameplay camera. So the class of bug is present but
the specific instances found are not the ones the reporter felt.

**Investigate.** The FPS camera and viewport effect stack, snapshot
interpolation timing, and weapon bob/recoil decay. The fix shape is the standard
frame-rate-independent form, `1 - Math.pow(1 - rate, dt * 60)`, so a smoothing
constant means the same thing at any frame rate.

**Priority.** Low. The game ships with VSync on, so this is latent rather than
active.

## Fixed this session (uncommitted)

- **Green debug box flickering on players.** `cl_remotehitbox` is registered
  with default `0`, but the read fell back to `true` when the lookup returned
  undefined — contradicting its own default, so any frame before registration
  drew a debug wireframe on every player. Absent now means off.
- **Jumppad activation had no sound.** Never implemented: `MovementProfile` set
  `jumppadLaunch` and nothing outside its tests ever read it. Now plays
  `sounds/world/jumppad.ogg` (Warsow's own, shipped in
  `data0_000_nonfree_21pure.pk3`) on the **rising edge** — the flag is held for
  every step the player overlaps the pad, because velocity replacement must stay
  idempotent for replay, so firing on the raw flag would retrigger all the way
  up. **Local player only**; remote players have no predicted flag to edge-detect
  and need replication or client-side volume detection.
- **FFA rendered the team scoreboard.** See D.

## Related work this session, for context

- **PVS for entities.** Players carry no compiled cluster, so they were never
  eligible for static culling and every body in the map was submitted every
  frame. They now test their own position against the camera's visible set, and
  **fail open** on every uncertainty — a wrongly hidden player is an invisible
  enemy, which is far worse than a wrongly drawn one. Six tests pin that
  direction.
- **Hitbox mesh churn.** Crouch/uncrouch disposed and rebuilt the twelve-edge
  wireframe; the box is centred on its origin so a Y scale is identical geometry.
  Now scales.
