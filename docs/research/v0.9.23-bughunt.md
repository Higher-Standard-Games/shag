## A. Dropped weapon world models missing or partial

**Observed.** On `wdm2` the rocket launcher lying on the ground was invisible,
yet walking over it picked it up, showed it in hand, and dropped it again
correctly. The plasmagun on the ground renders **only its loading chambers** —
the gun body is absent. Grenade and rocket projectile models appear untextured.

**Confirmed.** Nothing yet; this cluster has not been instrumented.

**Analysis.** These are one cluster but likely *two* failures, and the split
matters because it points at different subsystems:

- **Missing geometry** (RL entirely, PG body) is a model-load failure, not a
  texture one. An untextured mesh still renders. That the plasmagun's barrel
  survives while its body does not is the strongest clue on the list: the barrel
  is a separately attached sub-model, so one part of a multi-part weapon loaded
  and the other did not.
- **Missing texture** (nade, rocket) is consistent with the KTX suspicion — the
  same family of problem as the skybox work earlier this cycle, where 291 ETC1
  textures were unreadable until the software decode was reused.

Pickup, hand rendering and drop all work, so the item logic and the viewmodel
path are healthy. Only the **world model** render path is implicated.

**Ruled out.** PVS. It enables and disables whole meshes; it cannot remove one
sub-mesh of a weapon and leave another, and it never touches materials.

**Investigate.**
1. Browser console during a `wdm2` load — a failed model or texture fetch
   almost certainly logs, and that likely names the cause outright.
2. Whether the failing assets share a texture format (KTX/KTX2/ETC1) or a
   loader path.
3. Whether `npm run tools:textures` covers the weapon/projectile texture set.

## B. Player models float above the floor, or sink into it

**Observed.** On `wdm2` an enemy stood visibly above the floor. On `wdm7` a bot
appeared partially sunk into it. Reloading the same `wdm2` match placed models
correctly. The defect is **intermittent across map loads**, not across players
within a load.

**Confirmed.** Nothing instrumented yet.

**Analysis.** The reporter's own observation is the most valuable evidence:
during the **death animation the model collided with the world correctly** while
the standing model floated. Collision uses the entity position; the model uses a
visual anchor. If one is right and the other is wrong, the entity position is
sound and the **anchor offset** is what drifts.

"Correct after a reload" makes this a race rather than a data error — the same
map and the same models produce different results on different loads.

There is a concrete suspect. `RemotePlayerRenderer` carries a **late model
assign** path (`[RemotePlayerRenderer] Late model assign for …`) for entities
that appear before the player model finishes loading. A model attached through
that path may miss anchor setup the normal path performs. That would produce
exactly this: usually fine, wrong when the load order happens to differ, and
consistent for the whole session once established.

**Ruled out.** PVS, which only toggles `setEnabled` and never writes a
transform. Also the collision facet-bevel change, which cannot move a render
anchor.

**Investigate.**
1. Log anchor Y against hitbox Y at spawn; a constant offset names the bug.
2. Record whether floating entities came through the late-assign branch.
3. Compare the anchor setup either side of that branch.

## C. Distant bots slide without animating

**Observed.** A bot strafing across the reporter's view was "standing and
sliding" — moving with no limb motion.

**Status:** root cause NOT settled. The first diagnosis was wrong and is
corrected below. The animation LOD has been rebuilt on sounder terms anyway,
and a second, stronger candidate has been found and made observable.

### First diagnosis, and why it was wrong

This was attributed to the distance-based animation LOD added in this cycle,
which pauses a player's `AnimationGroup` beyond a threshold while leaving the
model drawn — exactly this symptom. The threshold was 2500 units, and the
reasoning given for it ("limb motion is sub-pixel there") was wrong, so the
conclusion looked safe.

Working the arithmetic out properly undermines it. A 64-unit body at 1080p
under a 59 degree vertical field of view covers 24 pixels at **2545 units** —
within 2% of the constant being blamed. So the old threshold only fired where a
player really is a thumbnail, and unless that bot was more than ~2500 units
away, the LOD did not cause this.

Recorded because the reasoning error is the interesting part: a plausible
mechanism plus a genuinely bad justification read as a confirmed cause, and it
took doing the sums to separate them.

### What changed anyway

The LOD now gates on **projected screen height** rather than world distance:
pause below `ANIMATION_LOD_MIN_PIXELS` (24). Distance was never the question —
"can a viewer resolve limb motion" is about projected size, and the same
distance is a different picture at 70 degrees and at 110, or on 1080p and on a
phone. The radius is solved once per frame from the live camera, so the
per-player test stays a squared-distance compare.

It fails toward animating: an unmeasurable camera, a non-perspective projection
or a zero render height all return "pause nothing".

| render height | vertical FOV | pauses beyond |
| --- | --- | --- |
| 1080 | 59 deg | 2545 units |
| 1440 | 59 deg | 3394 units |
| 1080 | 73 deg | 1946 units |

The spread across that table is the reason to prefer it: one constant meant
three different things.

### Leading candidate now: a silently missing clip

`PlayerModelManager.playAnimationOn` returns early when a clip is not loaded:

```ts
const animData = instance.anims.find((a) => a.name === name);
if (!animData) return false;   // leaves the PREVIOUS animation playing
```

It does **not** fall back to idle, despite a comment elsewhere in the file
claiming it does. The previous clip keeps playing, so a bot going from idle into
a strafe with `strafe_l` missing stays in **idle while sliding sideways** —
precisely the reported symptom, and with no console output to hint at it.

Both `strafe left.glb` and `strafe right.glb` exist on disk, so this is not an
obviously absent file; loading could still fail for other reasons, and the
directory also holds `strafe.glb` and `strafe (2).glb`, which suggests the set
has been reworked.

A one-time warning per missing clip now makes this loud:
`[PlayerModelManager] animation "…" is not loaded; players needing it keep their
previous pose`.

**Next step.** Play a round and read the console. Either the warning names a
clip — in which case this is solved — or it stays quiet, which rules the
hypothesis out and points back at the LOD or at `deriveAnimation` choosing a
name that never plays.

## D. End-of-match screen

**Observed (FFA, 8 players).** The board showed `TEAM SOBA 0` / `TEAM UDON 0`
in a free-for-all; every player was listed under `SPECTATORS (8)` with no
scores; the winner's name flickered in size; the winner's model stood in the
wrong place.

**Confirmed — and half fixed.**

*The team layout* came from `Scoreboard.ts` deriving team-ness as
`Object.keys(state.teamScores).length > 0`. `MatchState` initialises
`_teamScores` with both `udon` and `soba` **in every gametype**, so that test is
always true. `BaseGametype.teamBased` already existed and
`GametypeController` already passed it to `MatchState`; it simply never reached
the snapshot. It does now, and the three widgets that guessed —
`Scoreboard`, `PauseMenu`, `SpectatorOverlay` — read it instead. A later
screenshot confirms the team columns are gone.

*The spectator list* is a **separate bug, now root-caused.** The chain:

1. The match ends and every client is flagged `isSpectator` — the post-game
   camera puts the whole lobby into spectator state.
2. `SnapshotBuilder` builds the scoreboard's spectator roster from exactly that
   flag, so it collects all eight players.
3. Their simulation entities are gone, so `gameState.players` is empty and
   `HUDState` produces **no scored rows at all**.
4. Every name then arrives through the roster append, hard-coded
   `teamId: "spectator"`, and lands in the SPECTATORS block.

That matches the screenshot precisely: a `SCORE` column with no rows under it,
and `SPECTATORS (8)` holding the entire match.

The deeper problem is that **final standings have no source once the match
ends**. The scoreboard reads score and deaths from live entities, and
`MatchStateSnapshot` carries `winner` but no per-player score table — so at the
exact moment the result matters most, the data is gone. `MatchState` still holds
`_scores` and `_deaths` server-side; they simply are not shipped.

**Fixed.** `MatchStateSnapshot` gained `standings` — player id, name, score,
deaths and ping, built in `SnapshotBuilder` from the match's own tally rather
than from entities. The scoreboard uses them whenever the live pass yielded no
rows, which is exactly the post-game case, and the spectator roster appends
after that so nobody is listed twice.

Found while testing it: `MatchStateManager.reset()` cleared phase and scores but
**not** `_spectators`, and would not have cleared the new `_standings` either.
Both now clear. Left as they were, the next match's result screen would open
showing the previous match's names until a snapshot replaced them — a
pre-existing bug for spectators that the new field would have joined.

Covered by `EndgameStandings.test.ts`: standings survive the entities, absent
standings default to empty rather than undefined, free-for-all reports as
teamless, and reset clears the roster.

*The flickering name and misplaced model* are untouched. `PostGameShowcase`
carries a comment claiming the "model in a weird map position" problem was
already addressed, so either it regressed or the fix is partial.

**Investigate.**
1. Where scoreboard entries get their `teamId` at match end, and why FFA players
   are marked spectators there.
2. Whether the winner-name flicker is a CSS/layout loop or a per-frame rewrite.
3. `PostGameShowcase` model placement against its own stated intent.

## E. Remote players warp, drift into walls, float and sink

**Observed.** Warping on `wdm2`. A bot drifting *inside* a wall. Earlier in the
same cycle: a player floating above the floor on `wdm2`, a bot partly sunk into
the floor on `wdm7`, all intermittent and none reproducible on demand.

**Root-caused.** These are **one mechanism**, not four bugs. When the snapshot
buffer runs dry — renderTime past the newest snapshot, i.e. a late or dropped
packet — remote entities are dead-reckoned from their last known velocity, and
that extrapolation is **completely collision-blind**. It was capped at 200ms.

| extrapolation | at run speed (320 u/s) | off a rocket jump (~900 u/s) |
| --- | --- | --- |
| 200ms (old) | 64 units | 180 units |
| 100ms | 32 units | 90 units |
| 60ms (new) | 19 units | 54 units |

A player hull is 32 units across, so the old cap permitted **two full player
widths of travel through solid geometry** before the authoritative position
arrived and snapped the body back. That snap is the warp; the interval before it
is the body standing inside the wall.

The vertical branch explains the rest. Airborne entities have gravity applied
during extrapolation, so a bot caught mid-jump projects *upward* — a player
floating above the floor — and one caught falling projects *downward* — a bot
sunk into it. Grounded entities hold their Y, which is why this never affected
anyone standing still.

It fires only when a snapshot is late, which is exactly why every symptom in
this family has been intermittent, unreproducible on demand, and "fine after a
reload".

**Fixed, partially.** The cap is now a named, documented constant at **60ms** —
one snapshot interval at 30Hz plus margin. Past that a body freezes where it was
last seen, which reads as a brief stall rather than a player inside a wall.

**Not yet fixed: extrapolation is still collision-blind.** 60ms still permits 19
units at run speed and 54 off a rocket jump. The proper fix is to sweep the
extrapolated path against the client's collision world — which this client
already has — and clamp at the first hit, making penetration impossible at any
cap. That is the next step for this item.

**Also unmeasured: how often the buffer actually runs dry.** The cap bounds the
damage but says nothing about frequency. If it is running dry routinely rather
than rarely, that is a separate problem in snapshot pacing or the interpolation
delay, and shortening the cap would trade wall-clipping for visible stalling.
Worth instrumenting before tuning further.

## F. Projectile trails are flat, not conical

**Observed.** Trails render as flat triangles rather than a volume — "missing
the other part of the X shape". The reporter also noted the projectile appears
to start somewhere other than the player's own position.

**Root-caused and fixed (the trail half).**

The trail was never meant to be an X. It is a single **camera-facing** ribbon:
the half-width direction is `Cross(tangent, toCamera)`, which should keep its
face toward the viewer and read as a tapered streak.

That construction degenerates in the one case that matters most. A projectile
travels along the view axis, because players shoot where they are looking, so
`tangent` and `toCamera` become antiparallel and their cross product collapses
toward zero. The guard at `perp.lengthSquared() < 0.001` then falls back to
`Cross(tangent, Vector3.Up())` — a **world-horizontal** ribbon. Hence "flat
level triangles", which is the wording that identified it.

A billboard viewed down its own axis has no valid orientation, so the fix is not
a better fallback but a second blade: a crossing ribbon at 90 degrees
(`Cross(tangent, perp)`), sharing the material and disposal of the first. Two
crossed quads read as a volume from any angle, including straight down the
barrel — which is the classic shape and what the reporter's "X" intuition was
describing.

**Still open: the spawn position.** `computeMuzzleOffset` deliberately starts an
own-shot at the viewmodel muzzle — `MUZZLE_FORWARD` 34 units ahead and
`MUZZLE_DOWN` 9 below the camera — and converges onto the authoritative
trajectory over time, so the projectile leaving from somewhere other than the
player origin is *by design*. Whether it currently looks wrong because those two
constants are mis-tuned, or because the convergence is not running, is not yet
established.

**Investigate.** Fire at a wall at close range and watch whether the visual
converges onto the true path or stays displaced for the whole flight. That
separates a tuning problem from a broken convergence in one shot.

## G. Frame-rate-dependent presentation smoothing

**Observed.** Running the browser with VSync disabled (to measure peak FPS)
made "a lot of things flaky" at ~234 FPS.

**Confirmed.** The pattern exists in the codebase:
[FollowController.ts:172](../../src/engine/camera/controllers/FollowController.ts#L172),
[IsometricController.ts:330](../../src/engine/camera/controllers/IsometricController.ts#L330)
and [SideScrollController.ts:173](../../src/engine/camera/controllers/SideScrollController.ts#L173)
all call `Vector3.Lerp(current, target, smoothing)` with a constant factor,
which closes a fixed *percentage per frame* and therefore converges about four
times faster at 240 FPS than at 60.

**Ruled out.** Simulation timing. Movement derives its clock from
`sequence * dt` rather than accumulating frame time — the property that makes
reconciliation replays idempotent — so physics cannot fast-forward at high frame
rates, and `server:tick` / `server:fuzz` determinism would fail if it could.
Two of the four causes commonly cited for this class of problem (frame-dependent
timers, fixed-timestep mismatch) therefore do not apply here.

**Gap.** The three confirmed sites are the follow, isometric and side-scroller
cameras — **not** the FPS gameplay camera. So the class of bug is present but
the specific instances found are not the ones the reporter felt.

**Investigate.** The FPS camera and viewport effect stack, snapshot
interpolation timing, and weapon bob/recoil decay. The fix shape is the standard
frame-rate-independent form, `1 - Math.pow(1 - rate, dt * 60)`, so a smoothing
constant means the same thing at any frame rate.

**Priority.** Low. The game ships with VSync on, so this is latent rather than
active.

- **C: missing-clip hypothesis eliminated.** The new warning stayed silent for a
  whole session, so every clip a player asked for was loaded. The animation
  failure was also not reproduced this time. Both candidates — distance LOD
  (eliminated by arithmetic) and a missing clip (eliminated by instrumentation)

  should note range, direction of travel and whether the bot was visible
  throughout.
- **A: did not reproduce.** The weapon spawn was present on `wdm2`. Consistent
  with an intermittent asset-load failure rather than a deterministic one, which
  makes the console capture during a *failing* load the thing worth waiting for.
- **B: did not reproduce.** No floating player this session, supporting the
  load-order race reading rather than a constant offset.

## Fixed this session (uncommitted)

- **Green debug box flickering on players.** `cl_remotehitbox` is registered
  with default `0`, but the read fell back to `true` when the lookup returned
  undefined — contradicting its own default, so any frame before registration
  drew a debug wireframe on every player. Absent now means off.
- **Jumppad activation had no sound.** Never implemented: `MovementProfile` set
  `jumppadLaunch` and nothing outside its tests ever read it. Now plays
  `sounds/world/jumppad.ogg` (Warsow's own, shipped in
  `data0_000_nonfree_21pure.pk3`) on the **rising edge** — the flag is held for
  every step the player overlaps the pad, because velocity replacement must stay
  idempotent for replay, so firing on the raw flag would retrigger all the way
  up. **Local player only**; remote players have no predicted flag to edge-detect
  and need replication or client-side volume detection.
- **FFA rendered the team scoreboard.** See D.

## Related work this session, for context

- **PVS for entities.** Players carry no compiled cluster, so they were never
  eligible for static culling and every body in the map was submitted every
  frame. They now test their own position against the camera's visible set, and
  **fail open** on every uncertainty — a wrongly hidden player is an invisible
  enemy, which is far worse than a wrongly drawn one. Six tests pin that
  direction.
- **Hitbox mesh churn.** Crouch/uncrouch disposed and rebuilt the twelve-edge
  wireframe; the box is centred on its origin so a Y scale is identical geometry.
  Now scales.

## Observations not yet defects

- FFA performance was "maybe a little better" after the entity-culling work.
  Not a measurement: map, bot count, route and hardware were not held constant.
  The skeleton-pausing half is expected to matter more than the draw-call half,
  and neither has been measured. `scripts/bsp-performance-check.mjs` (added
  outside this session) may be the place to extend.
