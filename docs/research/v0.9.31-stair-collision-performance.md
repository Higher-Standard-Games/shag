# wfdm11 stair collision investigation

Date: 2026-10-16. Investigation only; no runtime changes.

Implementation sequence and movement-intent policy:
[collision design plan](./v0.9.31-collision-design-plan.md).

Follow-up authoring clarification: the user reports that a typo in the stair
entity's collision-related key caused this model to compile solid; the key may
be compiler-only. This does not invalidate the measured engine hotspot or prove
that a runtime entity-key handler is missing. The original entity/compiler
contract has not yet been independently inspected.

## Finding

The recorded stair route exposes a substantial CPU hotspot in
`src/engine/physics/SweepCollisionBackend.ts`. It is reproducible without a
renderer. This confirms expensive collision work at the reported location;
it does not establish what fraction of the live browser's frame time it consumes.

Input: `public/data/demos/training/wfdm11_performance_investigation_1.shagdemo`.
The v5 duel recording contains 4,635 frames at 125 snapshots/ticks per second,
spanning 37.072 seconds. Map bytes were resolved through `resolveMapBspViaIndex`
against `public/data` and `dist/data`, using the engine's real BSP parser and
sweep backend. The other Babylon backend was not benchmarked.

## Measurements

The indexed wfdm11 contains 850 brushes, 668 draw surfaces, and 446 generated
collision surfaces containing 108,430 triangles. Three overlapping surfaces
around the stair route account for 5,295 triangles:

| Face | Shader | Triangles |
| --- | --- | ---: |
| 351 | `textures/wood/testwood1` | 2,186 |
| 352 | `textures/wood/woodplank04` | 1,181 |
| 463 | `textures/bricks/bricksbrown` | 1,928 |

At 15.048 seconds, a short player-hull trace visits three leaves and tests
16,236 facets: each of those three surfaces is tested three times, plus 351
triangles from face 482. Clear route locations require no facet tests and
repeatedly take approximately 0.007 ms per trace. Stair traces take roughly
0.6–0.95 ms after warmup. These are local Node measurements, not FPS estimates.

Representative movement experiments use the previous recorded position and
the displacement to the next snapshot, call `stepSlideMove`, then trace two
units down. They do **not** reconstruct the original pre-collision velocity,
run the complete movement simulation, or replay client reconciliation.
Each table entry is the median of 61 repetitions in the final diagnostic run:

| Demo time | Existing path | Deduplicate faces | Deduplicate + triangle bounds |
| --- | ---: | ---: | ---: |
| 10.888 s | 4.060 ms | 2.070 ms | 0.914 ms |
| 15.048 s | 1.867 ms | 0.745 ms | 0.309 ms |
| 17.672 s | 1.969 ms | 0.684 ms | 0.297 ms |

At 10.888 s, the movement/check sequence performs 67,099 facet calls. Face
deduplication reduces that to 33,577; triangle bounds admit only 109 of those
to the existing facet plane solver. The prototype still scans triangle bounds
linearly, so a spatial hierarchy could avoid much of that remaining scan.

All 580 sampled route positions produced identical serialized movement results
(position, remaining displacement, hit count, step status) and ground trace
results between the baseline and combined diagnostic. This is limited route
coverage, not a general proof of collision equivalence.

A Node Inspector CPU sample capture of 822 representative movement/check
sequences attributes approximately 84% inclusive sample time to `traceLeafFaces`.
`shouldCollideWith` accounts for about 43% self time and `traceFacet` for about
29%. Inspector overhead is included; these percentages describe the isolated
workload, not the running game. The repeated texture lowercase/name checks are
performed at the beginning of **every** facet test.

wfdm5 also has large collision batches: 957 generated surfaces, 79,996
triangles, and a largest individual surface of 6,868 triangles. This establishes
the same exposure to the algorithm, but no wfdm5 movement route was profiled.

## Clip brushes and map semantics

Fullclip adds a blocking volume. It does not remove or suppress enclosed draw
surface collision in this backend. `processFaces` builds collision without
testing brush containment. `traceLeaf` checks both brushes and faces, and a
separate fullclip/playerclip scan runs **after** BSP traversal.

A diagnostic fullclip box enclosing face 351 was hit correctly, while the same
trace still invoked 5,295 facet tests and retained face 351's collision data.
This box was temporary in-memory diagnostic geometry, not a map edit.

There is already useful clip collision here: downward traces at 13.448,
15.048, 17.672 and 27.528 seconds hit `textures/common/fullclip` when face
collision is disabled, at exactly the same height/fraction as the wooden face
with face collision enabled. This verifies support at those sample points,
not complete clip coverage of the stairs or map.

The local Qfusion source at
`C:/Users/sundf/Desktop/warfork-qfusion/source/qcommon/cm_trace.c` uses
per-trace check counts to skip repeated brushes/patches and checks patch
contents before its facet loop. Its `cm_q3bsp.c` collision face loader accepts
patches, whereas SHAG additionally collides triangle soup. The reason for
SHAG's extension is documented in `SweepCollisionBackend.processFaces`:
some shipped vertex-lit world surfaces depend on soup collision. Disabling
all type-3 collision would therefore be unsafe.

This investigation has not inspected makebsp's corner-softening implementation
or proved which triangles were created by it. The measured problem is how the
backend handles large collision surfaces, independent of their authoring origin.

## Recommended next implementation

1. Add per-trace visit stamps for static brushes and surfaces, including the
   extra clip-brush pass. Preserve model-local trace behavior and reset stamps
   safely across initialization and counter wraparound.
2. Move surface collision eligibility outside the triangle loop; precompute
   shader properties that are independent of the trace content mask.
3. Build a conservative triangle spatial index once at load time. Query it with
   the swept hull bounds, then run the existing facet solver on candidates.
   Bounds must account for facet construction, numeric margins and contact
   epsilon. Keep stable candidate ordering where equal contacts can affect normals.
4. Validate masks, rays, stationary/embedded hulls, triangle edges, patches,
   sliding, stepping, lifts, and deterministic client/server behavior. Compare
   complete recorded input simulation and live browser profiles before claiming
   an FPS fix; run required regression gates for the implementation.

Prefer those changes before automatic decimation, which changes the collision
shape and can alter stair/edge movement. A map author can separately make visual
stair geometry nonsolid and provide deliberate clip collision. Simply adding a
clip envelope does not eliminate the detailed tracing cost. Removing fully
contained geometry could be a later load-time optimization, but must prove
containment and compatible masks; AABB overlap alone is insufficient.

## Artifacts and validation

Only this research note is a tracked change. Production source, map packages,
and the FPS submodule were not edited. Scratch artifacts remain local under
the ignored `.cache/` directory:

- `stair-collision-investigation.ts`: measurement/diagnostic harness.
- `stair-collision-investigation.log`: geometry, timing, parity, clip and profile output.
- `stair-collision-results.json`, `stair-collision-experiments.json`: route samples/results.
- `stair-collision.cpuprofile`: Node Inspector capture.

Validation command, run repeatedly while extending the harness:

```powershell
npx.cmd vite-node .cache/stair-collision-investigation.ts > .cache/stair-collision-investigation.log 2>&1
```

Final run exited 0, with 580 sampled positions and zero diagnostic mismatches.
The first sandboxed attempt failed because esbuild subprocess creation was
denied; subsequent authorized runs completed. No runtime implementation was
changed, so implementation regression gates were not run for this investigation.
No browser/GPU profile was captured. Live FPS, prediction replay amplification,
wfdm5 route timing, and complete collision equivalence remain unverified.
