## Architecture Context

**This repository is the SHAG engine.** It is the outer git repo. Games are always **git submodules** under `src/games/<game>` pointing at separate repositories:

- `src/games/fps` → `wash-fps`
- `src/games/tower` → `tower`
- (more SHAG-based games in development, each as its own submodule)

Implications for this QA pass:

- **"Engine-generic" really means "shareable across all SHAG games."** A module without an `fps` consumer is not dead code — there are other game submodules under development.
- **Edits to anything under `src/games/<game>/**` need a submodule commit first, then the outer repo bumps the submodule pin.** The two are separate `git commit` invocations.
- **Engine code (outer repo) must not depend on game code (submodule) at runtime.** Type-only imports are erased at compile time and are tolerable as a stepping stone, but values/instances reaching from engine into a submodule are layering violations.
- `BuildableSystem`, `SpawnValidator`, `Pickup`, `PickupPrompt`-style HUD primitives, etc. exist in the engine to be picked up by any game — not to be the FPS module's exclusive collaborators.

This framing replaces the early-draft assumption that "no fps consumer = dead code." Several items in the matrix below were re-classified after this clarification.

## 2. TypeScript Compiler Status

`npx tsc --noEmit` exits with **2** (i.e. 14 reported errors).

### Errors in [BinaryProtocol.ts](src/engine/network/protocol/BinaryProtocol.ts)

```
337,30: error TS18048: 'pos' is possibly 'undefined'.
338,30:                  'pos'
339,30:                  'pos'
344,30:                  'velData'
345,30:                  'velData'
346,30:                  'velData'
356,30:                  'rot'
357,30:                  'rot'
371,29:                  'weaponMeta'
372,28:                  'weaponMeta'
497,44: error TS2345: Argument of type 'TransformShape & Record<string, unknown>'
        is not assignable to parameter of type 'IComponent'.
```

**Verdict (per sub-investigation):** The 10 `TS18048` errors are **bitfield-narrowing limitations**, not real null-deref bugs. The code at e.g. [BinaryProtocol.ts:337](src/engine/network/protocol/BinaryProtocol.ts#L337) sits inside `if (flags & 0x01)`, and the flag is only set ~60 lines earlier when `pos` was confirmed truthy. TypeScript cannot correlate the two through the bitfield, so it reports the access as potentially undefined.

Fix options (all non-functional, network protocol unchanged):
1. **Local non-null assertions** (`pos!.x`) — fastest, lowest risk, but suppresses the warning rather than encoding the invariant.
2. **Introduce a "flag → component" record** before flag assembly — e.g. compute `const components = { pos, velData, rot, ... }` and the decoder reads them via the record. The control flow then narrows naturally.
3. **Encode-side helper functions** that take the (already-narrowed) value and the encoder, keeping each delta-write self-contained.

The `TS2345` at line 497 is a real interface contract mismatch: `IComponent` (Entity.ts:47) requires `serialize/deserialize/clone`; `TransformShape` declares them as optional. The runtime object provides them all, but the type lies. Fix: tighten `TransformShape` to mandate the three methods, or split the type into "serializable component" vs "raw shape".

- **Leak — `onNewMaterialAddedObservable.add` at [:193](src/engine/EngineScene.ts#L193)**: observer reference not stored. Scoped to the scene so disposed with the scene, but if `createScene()` is re-entered (it can be called more than once) the second registration overlaps the first.
- **Leak — `IsometricController` registered in `createScene` ([:282-285](src/engine/EngineScene.ts#L282-L285))**: a fresh controller is constructed and registered on the `CameraSystem` singleton each time. Re-creating the scene leaves the prior controller registered in the singleton.
- **Leak — weather effect singletons reconstructed on every `createScene`** ([:307-311](src/engine/EngineScene.ts#L307-L311)): `new PrecipitationEffect(this.scene)`, `new ThunderEffect`, `new FogEffect`, `WindSystem.getInstance(this.scene)`, `new DebrisEffect`. The previous instances become unreachable but their resources (particle systems, textures) may still be parented to the previous scene; only safe because `this.scene.dispose()` chains.
- **Leak — `exposeDebugFunctions` attaches `window.loadMap`, `window.setZoom`, `window.fx`, `window.weather`, etc.** ([:646-790](src/engine/EngineScene.ts#L646-L790)). These are never cleared in `dispose()`, so they retain references to the disposed scene's effects. The `window.weather` `debris*` and `rain*` setters would call methods on disposed Babylon resources.
- **`dispose()` is shallow**: it does not call dispose/reset on `PostProcessingManager`, `SkyLightSystem`, `StreetLampSystem`, `BuildableSystem`, `ServiceLocator`. It does call `InputSystem.dispose()` and `CameraSystem.dispose()` and `SpriteManager.clear()`. The Babylon `scene.dispose()` reaches most child resources but the singletons keep stale references.
- **Per-frame singleton lookups** at [:622-630](src/engine/EngineScene.ts#L622-L630): `StreetLampSystem.getInstance()` (twice — `isInitialized` then `.update`), `SkyLightSystem.getInstance()`, `BuildableSystem.getInstance()`. Cache the references at construction.
- **Hot-loop camera override** at [:637-640](src/engine/EngineScene.ts#L637-L640) — forces `alpha = -π/4`, `beta = π/4` every frame when the active controller is null or isometric. The `IsometricController` itself probably already sets these; this is redundant and overrides any easing/tweening the controller might want to do.
- **`start()` is not idempotent**: re-entry stacks listeners and effect instances. No flag protects against double-`start()`.

## 4b. Lifecycle / Memory-Leak Findings

A second pass focused on EventBus subscriptions, Babylon observables, intervals, and singleton teardown. Citations are absolute file_path:line_number.

### P0 — Critical leaks (accumulate per map / per frame)

- **[Pickup.ts:211](src/engine/game/Pickup.ts#L211)** — `getScene().onBeforeRenderObservable.add()` per Pickup, no observer reference stored, no `dispose()` cleanup. A 50-pickup map produces 50 orphaned per-frame callbacks once the map unloads.

### P1 — High (session-long accumulation)

- **[InputSystem.ts:191,194](src/engine/input/InputSystem.ts#L191)** — Two `onBeforeRenderObservable.add()` callbacks, no observer reference. Per-frame, lifetime of app.
- **[HUDManager.ts:373](src/engine/ui/hud/HUDManager.ts#L373)** — `setInterval` started in `start()`; no `dispose()`/`stop()` path during scene teardown.
- **[PersistenceManager.ts:431](src/engine/core/PersistenceManager.ts#L431)** — `autoSaveIntervalId` cleared only by `stopAutoSave()`; not invoked on map unload.
- **[MD3Loader.ts:716](src/engine/loader/model/MD3Loader.ts#L716)** — `mesh.onBeforeRenderObservable.add()` in loader, observer not stored.
- **[WeaponViewManager.ts:303](src/engine/weapon/WeaponViewManager.ts#L303)** — Frame observer added with no stored handle.

### P2 — Medium

- **[TickOrchestrator.ts:50](src/engine/server/tick/TickOrchestrator.ts#L50)** — Game loop interval has `stop()`, but no guaranteed teardown call during graceful shutdown.
- **[ClockSync.ts:221](src/engine/network/client/ClockSync.ts#L221)** — Resync timer cleared via `stop()`, double-`stop()` safe but recreate path uncertain.
- **[SpriteSheet.ts:73](src/engine/sprites/SpriteSheet.ts#L73)** — Texture allocated per sheet load; no `disposeSheet()` in `SpriteManager`. Map reloads duplicate textures.
- **[LogoCanvas.ts:226](src/engine/ui/components/LogoCanvas.ts#L226)** — Persistent frame observer in menu UI.
- **[RainEffect.ts:496,521](src/engine/effects/RainEffect.ts#L496)** — Canvas textures disposed only after 3 s; if scene tears down inside the delay, leak.

### Singleton teardown gaps

- `GameTimer.resetInstance()` exists but is never called (defined at [:78](src/engine/core/GameTimer.ts#L78)).
- `AudioManager`, `HUDManager` lack `dispose()` / `reset()` entirely.
- `AssetPreloader` / `EffectPreloader` only clear on a successful map load.

### Map cleanup-tag inconsistency

[MapRenderer.clearMap](src/engine/MapRenderer.ts#L893) walks `metadata.mapOwned`, but prefab/sprite/NPC paths rely on **name-prefix matching** instead. Any dynamically spawned mesh that doesn't get the tag and doesn't match the prefix survives `clearMap`. Worth documenting the tagging contract explicitly.

While executing the matrix, several findings the sub-agents flagged turned out to be **false positives** under closer inspection. Recording the pattern so future QA passes adopt "trust but verify" discipline:

- **#37 `AudioManager` fade-interval leak** — audit claimed `setInterval` was reassigned without `clearInterval`. False: `fadeInMusic` (lines 172-174) and `fadeOutMusic` (lines 196-198) both call `clearInterval(this.fadeInterval)` before reassigning.

- **#43 `FreeflyController` 12 `new Vector3()` per frame** — audit claimed per-frame allocation. False: both 12-vector blocks (lines 544-557, 719-730) are inside `startSolid` recovery paths, only firing when the camera is stuck in solid. ## 11. Plan — Headless Map-Via-Server (matrix #56)

_Drafted 2026-05-19 on the `0.9.15-qa-improvements` branch. Superseded during implementation by the simpler server-role split: `map <name> [gametype]` is developer-only, asks the required lobby server to spawn a shutdown dedicated server, and connects the client through the existing network path. Client-local gameplay is not retained; BSP/mesh inspection belongs to `bsp` commands._

### 11.1 Problem statement

Today there are **two gameplay paths** with different physics-relevant code running:

- **`map wdm2` then `join` (local play)** → `MapLoader` renders the map → `FPSController` calls `Game.initializeLocal({ tickRate: 60 })` → spawns a `LocalGameHost` that ticks an `FPSSimulation` in-process. That gets movement physics right, BUT does **not** run `PickupSystem`, `CombatSystem`, `WeaponSystem`, `GametypeController`, or bot AI — those only exist inside the dedicated `GameServer` orchestration class.
- **`connect ws://…` (network play)** → `Game.initializeNetwork` → `NetworkGameHost` → real `GameServer` running on the other end (out-of-process via `headless-netserver-v2.ts`) with the full subsystem suite.

The asymmetry is the bug: local play silently skips pickups-as-server-events, gametype rules (duel timer, frag count, CTF flag carrier), combat events, scoring, bots, and match phase transitions. Drift between the two paths is invisible until manual testing on a real server reveals it.

AGENTS.md's headless regression battery (`npm run cli:game -- --exec "map wdm2; bsp info; quit"` + the test:simulation/physics/server suites) inherits this asymmetry: the `cli:game --exec "map X"` path doesn't exercise the server pieces that matter for network correctness.

### 11.2 What already exists (do not re-build)

- **`FPSSimulation`** ([src/games/fps/simulation/FPSSimulation.ts](src/games/fps/simulation/FPSSimulation.ts)) — already the unified physics core. Both `LocalGameHost` and the dedicated `GameServer` instantiate it. The physics is NOT the split point.
- **`GameServer`** ([src/games/fps/server/GameServer.ts](src/games/fps/server/GameServer.ts)) — the orchestrator that composes Simulation + PickupSystem + CombatSystem + WeaponSystem + GametypeController + transport. **Transport-agnostic in principle** but currently wired to WebSocket clients in `headless-netserver-v2.ts`.
- **`LocalGameHost`** ([src/engine/network/client/hosts/LocalGameHost.ts](src/engine/network/client/hosts/LocalGameHost.ts)) — single-player IGameHost that wraps Simulation without transport. Implements the fixed-timestep accumulator the client renders against.
- **`NetworkGameHost`** ([src/engine/network/client/hosts/NetworkGameHost.ts](src/engine/network/client/hosts/NetworkGameHost.ts)) — talks to a real `GameServer` over WebSocket. Implements `IGameHost`.
- **`IGameHost`** ([src/engine/network/core/IGameHost.ts](src/engine/network/core/IGameHost.ts)) — the abstraction. **The client doesn't know which host it's talking to** — perfect seam.
- **`GameServerSpawner`** ([src/lobby/GameServerSpawner.ts](src/lobby/GameServerSpawner.ts)) — Node-only child-process spawner the lobby uses. **Does not work in browser** (no `node:child_process`).
- **Gametype classes** in `src/games/fps/server/gametypes/` — `Deathmatch`, `Duel`, `TeamDeathmatch` already exist and slot into `GametypeController`.

### 11.3 Goal

One gameplay path. `map wdm2`, `cli:game --exec "map wdm2"`, and `connect ws://localhost:7777` all run through the same `GameServer` → `FPSSimulation` → `GametypeController` → `PickupSystem` chain. Only the transport differs.

### 11.4 Architecture — `ListenServerHost`

Introduce a third `IGameHost` implementation, **`ListenServerHost`**, that runs a real `GameServer` in-process and bridges client↔server through a queue instead of WebSocket bytes.

```
┌──────────────── client process (browser or vitest) ────────────────┐
│                                                                    │
│  Game ◀──IGameHost──▶  ListenServerHost                            │
│                              │                                     │
│                              │ direct calls (no serialization)     │
│                              ▼                                     │
│                        GameServer  (full orchestrator)             │
│                              ├── FPSSimulation                     │
│                              ├── GametypeController(Duel|DM|TDM)   │
│                              ├── PickupSystem                      │
│                              ├── CombatSystem                      │
│                              ├── WeaponSystem                      │
│                              └── (Bots, lag-comp, etc.)            │
└────────────────────────────────────────────────────────────────────┘
```

#### Why this works in browser AND in Node.js without forking

- `GameServer` doesn't *intrinsically* require a WebSocket. Today `headless-netserver-v2.ts` plugs it into a WS server; ListenServerHost plugs it into a direct method/queue bridge.
- No `node:child_process`. No port allocation. No certificate handling.
- Tests can spin one up the same way the browser does.

#### Transport bridge

Two queue lanes between the client and the in-process `GameServer`:

- **Input lane** (client → server): the client's `sendCommand(MoveCommand)` pushes onto a `Command[]` that the server drains at tick time.
- **State lane** (server → client): the server's snapshot/event emitter pushes onto a `(GameState | GameEvent)[]` that the client drains on the next render frame.

For absolute fidelity to the WebSocket path, the bridge **could** also serialize-then-deserialize through `BinaryProtocol` — exercising the wire format end-to-end even in single-player. That's strictly optional; the in-process direct-object path is faster, and for "headless test for networking" we likely DO want the binary serialization step so the regression battery covers the wire protocol.

Decision to make at implementation time:
- **(a) Direct-object bridge** — faster, simpler, but doesn't cover `BinaryProtocol` round-trip.
- **(b) Binary-serializing bridge** — slower, but the headless test path is then a real-network-equivalent test (this is the matrix #56 motivation; arguably the right answer).
- **(c) Configurable** — `ListenServerHost(config: { serializeOnWire: boolean })`. Probably the eventual answer: default `true` for the test/headless flow, `false` for browser local play if perf is a concern.

### 11.5 New `map` command syntax

```
map <name> [gametype]
```

Examples:
- `map wdm2` — default gametype (likely `duel`, configurable per-game in the registry below).
- `map wdm2 duel`
- `map wdm2 dm` or `map wdm2 deathmatch`
- `map wdm2 tdm` or `map wdm2 team_deathmatch`
- `map wdm2 ctf` — once the gametype exists.

Behavior:
1. Tear down any existing `ListenServerHost` / `NetworkGameHost` (re-uses the idempotency guards added in v0.9.13/14).
2. Render the BSP/map (mesh assembly, same as today — `MapLoader.loadMap`).
3. Start a `ListenServerHost(map, gametype, gameRules)`.
4. Connect the local client through the same `Game.attachHost(...)` path that `connect` uses.
5. Local client auto-joins as a player.

`map reload` re-runs the same `(map, gametype)` cycle. `map unload` shuts down the ListenServerHost cleanly.

### 11.6 Engine ↔ FPS separation (gametype registry)

The `map` command lives in the engine (`src/engine/console/commands/MapCommand.ts`). The gametype taxonomy (`duel`, `dm`, `tdm`, `ctf`) is **FPS-specific** — other SHAG games (the isometric building project, etc.) will have different or no gametypes.

Use the same pattern as `NetworkConnector` (v0.9.14):

- **Engine:** `src/engine/network/HostStarter.ts` — interface + single-slot registry.
  ```ts
  export interface HostStarter {
    /** Map name validation, default gametype, etc. */
    canStartMap(mapName: string): boolean;
    /** Start an in-process host for the given map + game-specific args. */
    start(mapName: string, args: string[]): Promise<IGameHost>;
    /** Tear down the active host. */
    stop(): Promise<void>;
  }
  export function registerHostStarter(starter: HostStarter): void;
  export function getHostStarter(): HostStarter | null;
  ```
- **FPS submodule:** `src/games/fps/host/FpsHostStarter.ts` — parses `args` as a gametype keyword and constructs `ListenServerHost(map, gametype)`.
- **`main.ts`:** after `registerNetworkConnector`, also `registerHostStarter(fpsHostStarter)`.

The engine `MapCommand` then just calls `getHostStarter().start(mapName, args.slice(1))` and stays game-agnostic.

### 11.9 Open questions / risks

1. **`LocalGameHost` retirement.** After ListenServerHost lands and is the only single-player path, is `LocalGameHost` still useful? Probably not — it becomes redundant with the listen-server. Decision: deprecate after phase 3, remove after one release of soak.

2. **Bot AI in single-player.** GameServer's `registerBot()` was designed for the dedicated-server flow. Listen-server should expose the same. Console command: `bot add [count]` after `map wdm2`. Already exists for the dedicated server — verify it works through ListenServerHost.

3. **Gametype default per-map.** Some maps are duel-only (`dueltest_aerowalk`), others are DM-only. Worldspawn might want to carry a default. Today: `Worldspawn → DefaultGametype` not standardized. Decision needed: where does the default come from? Options:
   - Hardcoded per game (FPS module's `FpsHostStarter` picks `duel` if no arg).
   - Worldspawn entity key (`_default_gametype "duel"`).
   - Map metadata in `game.json` / `maps.json`.
4. **Existing demo replay.** Demo files contain server snapshots. After this refactor, listen-server snapshots should be byte-identical to dedicated-server snapshots **if** phase 4 (binary bridge) is on. With direct-object bridge, demos played back vs live-played would differ slightly. Plan: demos always replay through the binary bridge for fidelity.

5. **Headless `npm run cli:game` performance.** Today's `cli:game --exec "map wdm2"` is fast because it skips a lot of server-side work. After the change it'll be slower (full simulation + gametype tick). Measure; if it's a problem, expose a `--no-server` flag for cases that genuinely only want a BSP mesh check (e.g. `bsp info`).

6. **Lobby-spawned servers stay around.** `GameServerSpawner` (Node child_process) is still useful for the lobby's "matchmaker spawns a dedicated server" flow. Don't remove it. ListenServerHost is **complementary** to it, not a replacement.

7. **Authority over the local player.** In listen-server mode, the local player is *both* the server-authoritative entity AND the locally-predicted entity. Reconciliation should be a no-op (zero latency), but the prediction code path still runs. Verify no double-correction artefacts.

8. **Should `map` retain a "no-server, mesh-only" mode?** Useful for the `bsp info` and rendering-only debug commands. Suggest: keep a `map <name> --inert` flag that skips the listen-server spawn. The dedicated `bsp` command can also do this without `map`.
