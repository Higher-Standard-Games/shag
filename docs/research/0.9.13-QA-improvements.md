## 2. TypeScript Compiler Status

`npx tsc --noEmit` exits with **2** (i.e. 14 reported errors).

### Errors in [BinaryProtocol.ts](src/engine/network/protocol/BinaryProtocol.ts)

```
337,30: error TS18048: 'pos' is possibly 'undefined'.
338,30:                  'pos'
339,30:                  'pos'
344,30:                  'velData'
345,30:                  'velData'
346,30:                  'velData'
356,30:                  'rot'
357,30:                  'rot'
371,29:                  'weaponMeta'
372,28:                  'weaponMeta'
497,44: error TS2345: Argument of type 'TransformShape & Record<string, unknown>'
        is not assignable to parameter of type 'IComponent'.
```

**Verdict (per sub-investigation):** The 10 `TS18048` errors are **bitfield-narrowing limitations**, not real null-deref bugs. The code at e.g. [BinaryProtocol.ts:337](src/engine/network/protocol/BinaryProtocol.ts#L337) sits inside `if (flags & 0x01)`, and the flag is only set ~60 lines earlier when `pos` was confirmed truthy. TypeScript cannot correlate the two through the bitfield, so it reports the access as potentially undefined.

Fix options (all non-functional, network protocol unchanged):
1. **Local non-null assertions** (`pos!.x`) — fastest, lowest risk, but suppresses the warning rather than encoding the invariant.
2. **Introduce a "flag → component" record** before flag assembly — e.g. compute `const components = { pos, velData, rot, ... }` and the decoder reads them via the record. The control flow then narrows naturally.
3. **Encode-side helper functions** that take the (already-narrowed) value and the encoder, keeping each delta-write self-contained.

The `TS2345` at line 497 is a real interface contract mismatch: `IComponent` (Entity.ts:47) requires `serialize/deserialize/clone`; `TransformShape` declares them as optional. The runtime object provides them all, but the type lies. Fix: tighten `TransformShape` to mandate the three methods, or split the type into "serializable component" vs "raw shape".

### 3.10b [EngineScene.ts](src/engine/EngineScene.ts) — abstract base, 899 LOC

The class every game scene extends. Reading it cover-to-cover surfaced several issues:

- **Leak — orphan `map:loaded` listener**: [start():146-149](src/engine/EngineScene.ts#L146-L149) calls `EventBus.on("map:loaded", ...)` and **never stores the unsubscribe handle**. `dispose()` (line 816) only removes the one registered at [:289](src/engine/EngineScene.ts#L289) inside `createScene()`. The first one orphans on every dispose+restart. (Distinct from the GameTimer leak.)
- **Leak — `onNewMaterialAddedObservable.add` at [:193](src/engine/EngineScene.ts#L193)**: observer reference not stored. Scoped to the scene so disposed with the scene, but if `createScene()` is re-entered (it can be called more than once) the second registration overlaps the first.
- **Leak — `IsometricController` registered in `createScene` ([:282-285](src/engine/EngineScene.ts#L282-L285))**: a fresh controller is constructed and registered on the `CameraSystem` singleton each time. Re-creating the scene leaves the prior controller registered in the singleton.
- **Leak — weather effect singletons reconstructed on every `createScene`** ([:307-311](src/engine/EngineScene.ts#L307-L311)): `new PrecipitationEffect(this.scene)`, `new ThunderEffect`, `new FogEffect`, `WindSystem.getInstance(this.scene)`, `new DebrisEffect`. The previous instances become unreachable but their resources (particle systems, textures) may still be parented to the previous scene; only safe because `this.scene.dispose()` chains.
- **Leak — `exposeDebugFunctions` attaches `window.loadMap`, `window.setZoom`, `window.fx`, `window.weather`, etc.** ([:646-790](src/engine/EngineScene.ts#L646-L790)). These are never cleared in `dispose()`, so they retain references to the disposed scene's effects. The `window.weather` `debris*` and `rain*` setters would call methods on disposed Babylon resources.
- **`dispose()` is shallow**: it does not call dispose/reset on `PostProcessingManager`, `SkyLightSystem`, `StreetLampSystem`, `BuildableSystem`, `ServiceLocator`. It does call `InputSystem.dispose()` and `CameraSystem.dispose()` and `SpriteManager.clear()`. The Babylon `scene.dispose()` reaches most child resources but the singletons keep stale references.
- **Per-frame singleton lookups** at [:622-630](src/engine/EngineScene.ts#L622-L630): `StreetLampSystem.getInstance()` (twice — `isInitialized` then `.update`), `SkyLightSystem.getInstance()`, `BuildableSystem.getInstance()`. Cache the references at construction.
- **Hot-loop camera override** at [:637-640](src/engine/EngineScene.ts#L637-L640) — forces `alpha = -π/4`, `beta = π/4` every frame when the active controller is null or isometric. The `IsometricController` itself probably already sets these; this is redundant and overrides any easing/tweening the controller might want to do.
- **`start()` is not idempotent**: re-entry stacks listeners and effect instances. No flag protects against double-`start()`.

## 4b. Lifecycle / Memory-Leak Findings

A second pass focused on EventBus subscriptions, Babylon observables, intervals, and singleton teardown. Citations are absolute file_path:line_number.

### P2 — Medium

- **[TickOrchestrator.ts:50](src/engine/server/tick/TickOrchestrator.ts#L50)** — Game loop interval has `stop()`, but no guaranteed teardown call during graceful shutdown.

Any dynamically spawned mesh that doesn't get the tag and doesn't match the prefix survives `clearMap`. Worth documenting the tagging contract explicitly.

## 9b. Audit Verification Notes (added 2026-05-19)

While executing the matrix, several findings the sub-agents flagged turned out to be **false positives** under closer inspection. Recording the pattern so future QA passes adopt "trust but verify" discipline:

- **#37 `AudioManager` fade-interval leak** — audit claimed `setInterval` was reassigned without `clearInterval`. False: `fadeInMusic` (lines 172-174) and `fadeOutMusic` (lines 196-198) both call `clearInterval(this.fadeInterval)` before reassigning.
- **#42 `FreeflyController` per-frame `scene.meshes.filter()`** — audit claimed per-frame allocation. False: line 435 is inside a one-shot `_debuggedMethods` log; line 451 is inside a 1Hz-throttled debug log.
- **#43 `FreeflyController` 12 `new Vector3()` per frame** — audit claimed per-frame allocation. False: both 12-vector blocks (lines 544-557, 719-730) are inside `startSolid` recovery paths, only firing when the camera is stuck in solid. The static-const refactor is still cleaner code, just not a hot-path fix.
- **#38 MD3Loader / LogoCanvas observers** — audit flagged both as orphaned. False: MD3Loader's `applyTcMod` observer is per-mesh and dies with the mesh; LogoCanvas's observer is cleaned via `scene.dispose()` in its own `dispose()`.
- **#39 HUDManager / PersistenceManager intervals** — audit claimed missing teardown. False: HUDManager has a `running` flag preventing double-start; PersistenceManager.startAutoSave() calls stopAutoSave first. Both intervals are intentionally app-lifetime work on singletons whose lifetime IS the app lifetime.

**Lesson:** Sub-agent "hot path" / "leak" claims should always be confirmed by reading the actual call-site guards, throttles, and conditional branches. Allocation density inside a `if (rareEvent)` block is not equivalent to allocation density per frame. "Persists for the app's lifetime" is not the same as "leak" when the owner is a singleton with the same lifetime.

**Real fixes (verified before applying):** #36 GameTimer EventBus, #48 EngineScene second `map:loaded` listener, half of #38 (InputSystem + WeaponViewManager observers).

**False positives so far:** #37 (AudioManager), #39 (HUDManager, PersistenceManager), #42 (FreeflyController filter), #43 (FreeflyController Vector3s), half of #38 (MD3Loader, LogoCanvas).

Roughly **50/50 hit rate on leak claims**, which is below useful for a future automated audit. Treat agent output as hypotheses, not findings.

### Notes on Pickup Option-B refactor

`src/engine/game/Pickup.ts` (788 LOC) read end-to-end revealed the FPS-specific pieces are interleaved with generic code, not a clean trailing section. Detailed split plan:

**Stays in engine (`src/engine/world/Pickup.ts`):**
- Constructor + `PickupOptions` (modelPath, position, scale, gravity, bobbing, glowColor, velocity, respawnTime, optional `metadata: Record<string, unknown>`).
- Model loading via `AssetPreloader` / `ModelLoader`.
- Physics toss (Havok dynamic body, settle check, freeze) — `_scheduleSettleCheck`, `_freezePhysics`.
- `dropToGround` (BSP raycast + collision fallback).
- `updateGlowLight`.
- `respawn`, `removePhysics`, `lerpToPosition`, `dispose` (without static registry parts).
- Replace `checkPickup` with an overridable hook (`protected onProximity(player, distance)`) or an `onPickup: (player) => void` callback in options.
- Sound key becomes `options.pickupSoundKey?: string` (engine plays it via AudioManager; no FPS vocabulary).
- `_loadBarrels` removed entirely from engine — moves to FPSPickup.

**Moves to `src/games/fps/world/FPSPickup.ts` (`extends Pickup`):**
- `type: "weapon" | "ammo" | "health" | "armor"`, `value`, `amount`, `ammoCount`, `pickupId`.
- Static registry: `allPickups`, `pickupById`, `pendingDeactivations`, plus `deactivateById`, `deactivateByPosition`, `checkDeferredDeactivation`, `triggerUseAction`.
- `nearbyWeaponPickup`, `setNearbyWeapon`, `clearNearbyWeapon`.
- Inventory-aware `checkPickup` override (uses `InventoryManager`).
- `_loadBarrels` (uses `EntityRegistry` + `WeaponBarrels.tags.txt` workflow).
- Calls `super.dispose()` first, then unregisters from static lists.

**Callers to update after the split:**
- `src/games/fps/FPSPlayer.ts` — spawn `FPSPickup` instead of `Pickup`.
- `src/cli/debug-pickup-gravity.ts` — same, or switch to engine generic if the gravity check doesn't need FPS specifics.
- `src/games/fps/client/GameEvents.ts:194` — `Pickup.deactivateById` → `FPSPickup.deactivateById`.
- `src/games/fps/client/DroppedWeaponRenderer.ts` — already imports `PickupPrompt`; after Q5d move, retarget the import.

**Prerequisite tests (Q5a) before any code split:**
- `Pickup.test.ts` — covers spawn, dropToGround mock, in-range proximity callback, respawn timer, dispose unregisters/cleans up observer.
- `FPSPickup.test.ts` — covers inventory-aware checkPickup behavior, weapon-type vs ammo-type branching, static registry lifecycle (`deactivateById`, `deactivateByPosition` with prefix variants, `pendingDeactivations` queue).

**Why this matters for risk:** no Pickup test exists today. Refactoring without one means a silent FPS regression in weapon-pickup flow can ship unnoticed. Always tests-first for this one.
