## Confirmed and fixed

### 1. Background settings uploads raced the first account download

Severity: high; an account's settings could be overwritten during a slow login.

`startSettingsSync` installed a five-second polling interval before awaiting
`requestSettings`. A browser edit during that wait scheduled a save two seconds
later. The reproduction holds the initial response, edits a remembered loadout,
and advances seven seconds: the original implementation sends one premature
save. That save could replace settings the browser has not reconciled yet.

The session now enables change polling only after the initial reconciliation
settles, and collects the latest local values when the download arrives. A new
account still uploads edits made during that wait. Regression: `does not upload
browser edits before the initial account download settles`.

### 2. A stopped account's save response overwrote the next account's sync state

Severity: medium; incorrect local conflict-resolution metadata after switching.

The reproduction holds account A's save response, starts and completes account
B's sync, then releases A's response. Originally `shag_settings_sync.accountId`
becomes A again. The save/error continuations now check session ownership via
the stopped flag before writing state. This finding concerns local sync
metadata; it does not demonstrate a server authorization bypass or settings
being written directly to another account.

Regression: `ignores a save response from the account that was stopped`.
Stopping during the initial download also cancels polling and leaves no owned
timer behind.

### 3. Downloaded cvars missed systems that registered later

Severity: medium; restored preferences silently remained at defaults.

`applySettings` only updated live cvars and localStorage. `Cvar.register` reads
its existing in-memory value, not localStorage again, so a previously unseen
downloaded value was ignored until a page reload. Reproduction: initialize
cvars, download `cl_team_enemy_color = "0 1 0"`, then register it with default
`"1 0 0"`; the original result is the default.

`Cvar.replacePersistedValues` now replaces the synced subset in memory as well
as storage, including values awaiting their subsystem. Actual registration
still owns type validation, numeric bounds and the reset default. Device
preferences remain outside the synced subset. Regression: `uses downloaded
values when a lazy subsystem registers its cvar later`.

### 4. Preloaded cvars disappeared from account uploads and later browser saves

Severity: medium; saved preferences could be lost before their subsystem loaded.

The placeholder for a preloaded cvar used the saved value as its temporary
default. `collectSettings` treated equality with that placeholder default as a
real reset and removed it from the upload. `Cvar.saveToStorage` used the same
comparison, so changing a different registered cvar could erase the saved value
from localStorage too.

Cvars now distinguish declared instances from pending values. Pending values
survive collection and persistence; once declared, normal default elision
applies. Resetting one pending value or all values removes pending preferences
so their owners' declared defaults take effect. Coverage includes uploading a
pending value, saving another cvar, replacing an old account's pending values,
preserving device preferences, clamping on registration, and resetting.

Evidence: the first four tests in `SettingsSyncLifecycle.test.ts` all failed
against the original implementation. The focused five-file check after the
initial fix passed 90 tests; the final suite includes the expanded regressions.

### 5. BSP material tests left a fake browser window in the Node process

Severity: test reliability.

`BspMeshBuilder.test.ts` assigned `globalThis.window` at module scope and never
restored it. Later headless code consequently took browser-only branches. The
baseline full suite failed `MapCommand` while its focused tests passed. The
material tests now stub the window within their test lifecycle and restore it.
The next full run passed `MapCommand`.

### 6. Profile deletion tests leaked open views and Escape listeners

Severity: test reliability.

`ProfileDelete.test.ts` opened a `ProfileView` per test but never destroyed it.
Clearing DOM children does not remove its document-level capture listener.
Temporary event tracing in the DOM test subset caught `ProfileView.onKeyDown`
intercepting Escape in `ChatQuality.test.ts`. Depending on file order, chat
cancellation or texture-browser dismissal failed, while isolated tests passed.

The fixture now destroys every created view in `afterEach` and restores real
timers. The focused profile/chat/texture-browser check passed 12 tests.

## Assumptions, remaining risks and unverified work

- Assumptions: the active FPS module; local curated `washoi_*` assets; the four
  supported modes Duel, Amphi, FFA and S&D; Node 24; Windows; local network;
  development browser client. Existing `package.json` version 0.9.37 is not
  changed merely because the branch is called 1.0.0-alpha.
- `AGENTS.md` and the regression procedure still prescribe retired `wdm2`
  commands. Their actual failures are recorded above; `washoi_dm2` is the
  verified indexed map ID. No ad-hoc BSP path search was introduced.
- Map loading logged 154 unready world meshes at the loading-screen boundary
  for the live DM5 match and 17 for DM2 playback. Later screenshots render
  substantial textured worlds. These warnings need a focused readiness/first
  visible frame investigation; this review does not establish whether they
  cause visible holes, transient shader compilation or a diagnostic mismatch.
- Asset warnings include a missing legacy ammo-model package lookup and GLTF
  skin common-root warnings. The live run also logged projectile texture
  fallback warnings. They are preserved in browser reports and are leads,
  not newly proven rendering defects. No shader compilation error or failed
  HTTP request was captured in the successful standalone demo probe.
- Unverified: Firefox, WebGPU, Apple/Linux/Android/Electron, production build
  browser behavior, audible sound quality, long-session memory, real-world
  latency/loss, human aim/movement feel, full match completion in every mode,
  overtime/ties and S&D plant/defuse balance. Short bot smoke matches cannot
  replace these release playtests.
- Source fixes and tests are uncommitted so they remain reviewable in both
  repositories. A green gate is necessary but does not certify release readiness.
