## Implementation Status (2026-07-09)

All three fixes implemented. Bug 1 took the "formula" approach the user asked about (Option B′ below) rather than the save/restore patch: **animation/effect timelines are now derived from the simulation's own tick axis (input sequence numbers) instead of accumulated wall-clock deltas.**

### Fix 1 — sequence-derived sim clock (replaces accumulated timers)

Design: 1 input sequence = exactly one fixed-dt (8 ms) sim step on both client and server (the fixed-rate tick model consumes one command per tick). So `simTime = sequence × dt` is a pure formula over the input stream: reconciliation replays re-simulate old sequences and recompute the *same* timestamps — timers can no longer double-advance. All movement sub-system timers converted from `elapsed += dt` / countdown style to absolute sim-clock anchors/deadlines:

- [MovementProfile.ts (engine interface)](src/engine/network/systems/movement/MovementProfile.ts) — optional `sequence` field on `MovementInput` (outer repo).
- fps submodule [simulation/MovementProfile.ts](src/games/fps/simulation/MovementProfile.ts) — new `simNowMs` clock: `sequence * dtMs` when a sequence is present, dt-accumulation fallback for offline/bot paths that never replay. `tickCooldown()` plumbing deleted.
- [simulation/Slide.ts](src/games/fps/simulation/Slide.ts) — `slideStartMs` + `cooldownUntilMs` (was `elapsedTime += dtMs` + `cooldownRemaining` countdown). Fixes the reported bug AND the slide cooldown expiring ~3× early client-side.
- [simulation/WallJump.ts](src/games/fps/simulation/WallJump.ts) — `chargeStartMs`, `cooldownUntilMs`, `graceUntilMs`, `groundGraceUntilMs` (was 4 accumulated/countdown timers).
- [simulation/LedgeGrab.ts](src/games/fps/simulation/LedgeGrab.ts) — `stateStartMs` (grab/pull phases) + `cooldownUntilMs`. This is the "player model effects" case the user suspected — ledge pull animation speed was replay-inflated the same way.
- [client/V2NetworkClient.ts](src/games/fps/client/V2NetworkClient.ts) — `toMovementInput`/`storedToMovementInput` pass the seq (fresh prediction and replay use the identical axis).
- [server/systems/FPSMovementSubsystem.ts](src/games/fps/server/systems/FPSMovementSubsystem.ts) — `adaptInput` passes `input.sequence`, so server sim and deterministic demo re-sim share the same timeline as client prediction.

Known accepted quirks: (a) on server input starvation the repeated command keeps its seq, so slide/walljump timelines pause with input time instead of advancing — deterministic and cheat-neutral; (b) tiny per-call cosmetic smoothing (`slidePhase *= 0.85` decay, `crouchViewOffset` lerp) still runs per simulate-call — self-limiting convergent lerps, visually irrelevant during replays.

### Fix 2 — fixed-size trail ribbon (Option A)

[ProjectileManager.ts](src/engine/weapon/ProjectileManager.ts) `updateTrail()`: on the first update the trail is pre-filled with `MAX_TRAIL_POINTS` positions packed 0.01u apart just behind the spawn point (width taper renders them invisible). The ribbon mesh is now created **once** with a constant point count and in-place updated forever after — the 59→60 mismatch cannot occur, and the per-frame dispose/recreate churn during each projectile's first second is gone as a bonus.

**Playtest follow-up (same day): square-cut tail.** First browser round confirmed the ghost was gone but reported the trail tail rendering as a flat square instead of a soft triangle, on all projectile weapons. Cause: the width taper was **index-based** (`width ∝ i/59`), and the pre-fill packs up to 59 points into a ~0.6u cluster behind the spawn — the entire 0→full fade got compressed inside that invisible cluster, so the first *real* trail point already rendered at near-full width. Since the cluster only fully drains after 60 real frames (~1 s, longer than most rocket/plasma flights), the tail looked square for effectively the whole flight. Fixed by switching the taper to **arc-length fraction** (`width ∝ cumulativeLength[i] / totalLength`, cached scratch array, no per-frame alloc): the packed cluster contributes ~zero length, so the triangle spreads over the visible trail regardless of point spacing.

### Fix 3 — constant enabled-light set (Option A) + latent pool-corruption fix

- [PointLightPool.ts](src/engine/weapon/PointLightPool.ts) — pool lights are now **permanently enabled**, parked at intensity 0; `acquire`/`release` touch intensity/range only, never `setEnabled()`. Babylon derives shader defines from the enabled-light set, so the defines are now identical whether a dlight is active or parked → zero mid-game recompiles. `init()` also rebuilds the pool on scene change instead of silently keeping lights from a dead scene.
- **Latent bug found during implementation:** projectile dlights are parented to the projectile node, and `node.dispose()` recurses into children — each projectile despawn was *destroying* a pooled light, silently corrupting the pool (dlights die after ~4 shots). `release()` now unparents the light before the owner node is disposed.
- [WeaponViewManager.ts](src/engine/weapon/WeaponViewManager.ts) — muzzle-flash light created eagerly in `init()` (enabled, intensity 0) instead of lazily on the first shot; the fade path no longer calls `setEnabled(false)` at zero intensity.
- [EffectPreloader.ts](src/engine/weapon/EffectPreloader.ts) — Phase 2 now calls `getPointLightPool().init(scene)` *before* force-compiling materials, so the warmed shader variants are compiled against the exact light set that exists at runtime.

## Bug 1 — Crouch-slide viewport effect runs way faster than the slide

### Symptom

The camera tilt/pitch dip that plays during a crouch slide fades in and out in a fraction of the actual slide. The slide itself (movement) lasts the configured ~800 ms; the viewport effect completes in roughly a quarter of that. Reported as a regression appearing after the server-tick fix.

### How the effect is driven

- [Slide.ts](src/games/fps/simulation/Slide.ts) owns the cosmetic timeline: `elapsedTime += dtMs` each `update()` ([Slide.ts:74](src/games/fps/simulation/Slide.ts#L74)), and computes `slidePhase` (0–1) with a 400 ms smoothstep fade-in/out (`SLIDE_FADE_MS`, [Slide.ts:15](src/games/fps/simulation/Slide.ts#L15)) over `config.slideDuration` (800 ms default).
- `slidePhase` flows: `MovementProfile.simulate()` → `V2NetworkClient.updatePredictedMovement()` ([V2NetworkClient.ts:746](src/games/fps/client/V2NetworkClient.ts#L746)) → `Game.getCurrentMovementState()` → [FPSController.ts:1029](src/engine/camera/controllers/FPSController.ts#L1029) (`slidePitchOffset = slidePhase * -0.22`).
- Client input generation is correctly throttled to real-time 125 Hz by an accumulator ([FPSController.ts:869-905](src/engine/camera/controllers/FPSController.ts#L869-L905)), and each `V2NetworkClient.processInput()` simulates one fixed `dt = 1/125` step. **That path alone is real-time correct.**

### Root cause

`V2NetworkClient.applySnapshot()` replays all unacked inputs through **the same** `FPSMovementProfile` instance on every snapshot ([V2NetworkClient.ts:352-371](src/games/fps/client/V2NetworkClient.ts#L352-L371)). Each replayed input calls `Slide.update()` again, and `resetPhysicsState()` **deliberately does not reset slide state** ([MovementProfile.ts:147-151](src/games/fps/simulation/MovementProfile.ts#L147-L151) — the comment says slide is "purely cosmetic" and must survive reconciliation). So every replayed input adds another 8 ms to `Slide.elapsedTime` for wall-clock time that already elapsed once.

Effective timeline speed ≈ `1 + (unackedCount × snapshotRate / 125)` × real time.

**Why the tick fix made it blatant** (fps submodule commit `1d1d713`, "make physics fixed-rate per tick"):

- Before: the server simulated *every* queued command each tick and acked the last *received* seq → on a good connection the unacked set was ~in-flight only (≈0–2 inputs) → double-advance was negligible.
- After: the server consumes **exactly one** command per tick, buffers up to `MAX_INPUT_BUFFER = 6`, and `SnapshotBroadcaster` acks the last **simulated** seq (`lastProcessedSeq`), not the last received. The steady-state unacked window is now *in-flight + queued* ≈ 4–8 inputs.
- With ~60 Hz snapshots × ~5 replayed inputs, that's ~300 extra `Slide.update()` calls/sec on top of the real 125 → the cosmetic timeline runs ~3–3.5× real time. An 800 ms slide's camera effect completes in ~230–270 ms. Matches the report exactly.

Collateral from the same mechanism (worth fixing in the same pass):

- `Slide.tickCooldown()` is also double-ticked ([MovementProfile.ts:175](src/games/fps/simulation/MovementProfile.ts#L175)) → the 1500 ms slide cooldown expires ~3× early on the client (predicted re-slides the server rejects).
- The *predicted* slide also physically exits early (`slideExpired` fires at ~¼ real time), so client velocity mispredicts during every slide; the server snapshots pull it back, masked by visual-offset smoothing. Likely a source of subtle slide rubber-banding.
- `Slide.reset()` clears `isSliding`/`slidePhase` but not `elapsedTime`/`cooldownRemaining` ([Slide.ts:37-41](src/games/fps/simulation/Slide.ts#L37-L41)) — latent, since re-entry rewrites `elapsedTime`, but sloppy.

### Proposed solutions

> **Outcome:** implemented a variant of Option B ("Option B′") — instead of snapshotting state per input, all timers were converted to formulas over the input sequence axis, which makes replays idempotent without storing anything. See §Implementation Status.

**Option A — save/restore slide state around the replay loop (quick, targeted).**
In `applySnapshot()`, snapshot `Slide`'s fields (`isSliding`, `elapsedTime`, `slidePhase`, `cooldownRemaining`, `crouchViewOffset`) before the replay loop and restore them after. Replay still simulates slide internally for velocity continuity (status quo — the codebase already accepts slide replay divergence per the `resetPhysicsState` comment), but the cosmetic timeline advances only via the real-time 125 Hz `processInput` path. ~10 lines, all in `V2NetworkClient` + a small `getState()/setState()` pair on `Slide`. Recommended as the v0.9.16 fix.

**Option B — make movement-profile state part of the rewind (correct, larger).**
Store a compact movement-state snapshot (slide + walljump + ledge timers) per entry in `InputHistory`; on reconciliation, restore the state as-of `ackedInputSeq` before replaying. This makes replay deterministic and fixes cosmetic *and* physics parity in one move — it is the standard "all sim state participates in rollback" design, and would also let the grab/walljump reconcile-skip hacks ([V2NetworkClient.ts:114-122](src/games/fps/client/V2NetworkClient.ts#L114-L122)) eventually retire. Bigger blast radius; do it as a follow-up work order, not a hotfix.

**Option C — decouple the visual from the sim.**
Drive the camera tilt in `FPSController` from a wall-clock timestamp captured on the `isSliding` rising edge, ignoring the sim's `slidePhase`. Robust for the visuals but leaves the double-advanced timers (cooldown, early exit) unfixed — not sufficient alone.

Also do regardless: make `Slide.reset()` clear `elapsedTime` and `cooldownRemaining`.

- Headless: `npm run cli:game -- -- --exec "sim replay W+CROUCH 60; JUMP 1; W 30; quit"` still green; `npm run test:simulation`, `npm run test:physics`.

## Bug 2 — GL "ghost" trail / triangle after ~1 second of flight

### Symptom

Grenade trail renders fine through the first bounce (two strokes: launch arc, post-bounce arc), then a "3rd trail" appears that seems anchored at the *initial* trail location, making the whole thing read as a triangle.

### How the trail works

Grenades are server-driven visuals only (no local projectile prediction exists — `isLocalPrediction: true` is never passed anywhere). `ProjectileManager.updateTrail()` ([ProjectileManager.ts:959-1064](src/engine/weapon/ProjectileManager.ts#L959-L1064)) pushes `node.position` into `trailPoints` once per render frame, caps the list at `MAX_TRAIL_POINTS = 60`, and renders one camera-facing ribbon (`pathArray = [pathA, pathB]`, DOUBLESIDE, tapered width):

- **Growth phase** (`< 60` points): dispose + recreate the ribbon every frame ("Babylon requires the same vertex count to update in place").
- **Steady state**: `if (proj.trailMesh && proj.trailPoints.length === MAX_TRAIL_POINTS)` → in-place update via `MeshBuilder.CreateRibbon({ instance })` ([ProjectileManager.ts:1022-1028](src/engine/weapon/ProjectileManager.ts#L1022-L1028)).

### Root cause — off-by-one at the growth→steady transition

On the frame where `trailPoints` grows from 59 to 60, the condition flips to the in-place branch — but `proj.trailMesh` was created **last frame from 59 points**. From that frame on, *every* update writes 60-point paths into a mesh whose vertex/index buffers were built for 59-point paths. The mesh is never recreated again (length stays pinned at 60), so the corruption is **persistent**, which matches "the ghost stays for the rest of the flight".

Babylon's ribbon instance update does zero validation of this (checked in `node_modules/@babylonjs/core/Meshes/Builders/ribbonBuilder.js`, `CreateRibbon` → `positionFunction`): it writes `path.length × 3` floats **sequentially** per path per side into the existing positions array. With 60-point paths on a 59-point layout:

- each row overruns its slot by one vertex, shifting every subsequent row's data by an accumulating offset — the index buffer (built for 59-point rows) now stitches triangles across row boundaries → long skewed triangles bridging distant trail positions;
- the back side (DOUBLESIDE doubles the buffer) is shifted further, and the final writes run past the end of the buffer, so the last vertices keep **stale positions from the creation frame** — i.e. points from the *early launch arc*. Geometry connecting the current head to launch-era positions = the reported "3rd trail from the initial location" / triangle.

Timing fits too: 60 points at ~60 fps ≈ 1 s after launch — right around/after the first bounce, exactly when the user sees the ghost appear.

### Proposed solutions

> **Outcome:** Option A implemented. See §Implementation Status.

**Option A — pre-fill the trail to fixed length at spawn (recommended).**
On spawn, fill `trailPoints` with `MAX_TRAIL_POINTS` copies of the spawn position. The ribbon is then created **once** with 60 points and in-place updated every frame after; the growth-phase recreate branch disappears entirely. The width taper (`width = TRAIL_WIDTH * t`, 0 at tail) makes the initial degenerate segment invisible, and it "grows" naturally as real points displace the copies. Bonus: kills the per-frame `dispose()` + `CreateRibbon()` allocation churn during each projectile's first second (~60 mesh creations per grenade), which is also a contributor to bug 3's first-shot hitch.

**Option B — track the built point count.**
Store `trailMeshPointCount` on the projectile when (re)creating the mesh and only take the instance-update branch when `trailPoints.length === trailMeshPointCount`. Minimal diff, keeps the growth-phase recreation cost.

Either way, the fix is entirely inside `updateTrail()` + the spawn initializer ([ProjectileManager.ts:491](src/engine/weapon/ProjectileManager.ts#L491)).

### Validation

- Browser: fire GL across `wdm2`, let it bounce 2-3 times, watch past the 1 s mark — no triangle, trail hugs the arc. Also fire rocket/plasma (same trail path, `trailEffect` defined in their defs) on long flights.
- Cheap regression guard: debug assert in `updateTrail` that `trailMesh.getTotalVertices() === expected(pathLen)` when taking the instance branch (dev builds only).

## Bug 3 — First-shot hitch + walls blinking transparent (the "caching" bug)

### Symptom

The very first projectile fired after a map load causes a visible hitch and 1–2 frames where world geometry (walls) flickers invisible/transparent. Happens for all projectile weapons; after it happens once, every subsequent shot is clean. Suspected "effect cache not caching".

### What the cache actually is

The "effect caching system" is [EffectPreloader.ts](src/engine/weapon/EffectPreloader.ts): during map load it warms shader permutations (BSP lightmap material ± point light, trail/explosion/impact materials) and then force-compiles **every scene material with exactly one temporary `PointLight`** (Phase 2, [EffectPreloader.ts:289-316](src/engine/weapon/EffectPreloader.ts#L289-L316)). [PointLightPool.ts](src/engine/weapon/PointLightPool.ts) pre-creates 4 lights so the scene light *count* "never changes".

### Root cause — the enabled-light **set** still changes on the first shot

Babylon selects shader variants by material defines, and the defines depend on **which enabled lights affect a mesh** — not on how many `PointLight` objects exist. Two things change the enabled-light set on the first shot:

1. **The muzzle-flash light is created lazily on first fire** ([WeaponViewManager.ts:1311-1313](src/engine/weapon/WeaponViewManager.ts#L1311-L1313)): `if (!this.muzzleFlashLight) new PointLight(...)` — a brand-new scene light appears mid-gameplay, then gets `setEnabled(true)` ([:1323](src/engine/weapon/WeaponViewManager.ts#L1323)) / `setEnabled(false)` ([:1359](src/engine/weapon/WeaponViewManager.ts#L1359)) toggled per shot.
2. **Pool lights toggle `setEnabled`** ([PointLightPool.ts:54](src/engine/weapon/PointLightPool.ts#L54), [:91](src/engine/weapon/PointLightPool.ts#L91), [:114](src/engine/weapon/PointLightPool.ts#L114)). A disabled light is excluded from `mesh.lightSources`, so enabling one changes every affected material's define set exactly like adding a light.

So the first shot enables muzzle light **and** a pool light (projectile dlight) at once → lightmapped BSP materials (kept unfrozen by `MapLoader` precisely so dlights work) need a **two-extra-point-lights** shader variant. The preloader only ever compiled the **one**-extra-light variant. Result: on-demand compilation of dozens of BSP material variants in one frame — the hitch — and while each new effect is compiling, Babylon skips rendering that submesh → walls blink invisible. Once compiled, the variants sit in the engine's effect cache forever → all later shots are clean. (Rocket vs plasma both "cure" it because both trigger the same muzzle+dlight combination.)

The preloader isn't failing — it was never warming the permutation the first shot actually uses. Secondary first-shot costs stacking on the same frame: per-projectile `StandardMaterial` creation for the trail (cheap, defines already warmed), trail ribbon growth-phase mesh churn (see bug 2), first `ExplosionEffect` init.

### Proposed solutions

> **Outcome:** Option A implemented, plus a latent pool-corruption fix (pooled lights were being disposed with their parent projectile nodes). See §Implementation Status.

**Option A — keep the light set constant (recommended, kills the class of bug).**

- Pool lights: never `setEnabled(false)`. Keep all 4 permanently enabled with `intensity = 0` (acquire sets intensity/range, release zeroes them). An enabled zero-intensity point light contributes nothing visually but keeps the define set stable — zero recompiles, ever.
- Muzzle flash: create the light once at `WeaponViewManager` init (or take it from the pool), and fade with `intensity`, never `setEnabled`.
- Cost check: 4 pool + 1 muzzle = 5 always-on lights with `maxSimultaneousLights = 4` — Babylon takes the first 4 in stable scene order, so defines stay constant; or bump the cap to 5/expand pool semantics so the muzzle light is pool slot 0. Measure the constant ALU cost on lightmapped surfaces; on desktop GPUs 4 point lights on `StandardMaterial` is negligible.

**Option B — warm the real permutations at load.**
Extend `EffectPreloader` Phase 2 to force-compile each material at 1, 2, 3 and 4 simultaneous enabled point lights (enable pool lights incrementally between `forceCompilation` passes), and create the muzzle-flash light during preload. Keeps runtime toggling, but is a whack-a-mole contract — any new dlight source reintroduces the bug. Reasonable belt-and-braces *addition* to A, weak alone.

**Option C (diagnostic aid).** Log define-triggered compiles in dev (`scene.onNewMaterialAddedObservable` + effect compile hooks) so future "first-time flicker" regressions are caught by log inspection instead of eyeballs.

### Validation

- Browser: fresh load of `wdm2`, stand facing a lightmapped wall, fire one rocket. Frame time graph flat, no invisible geometry. Repeat with plasma first instead. Also verify dlights still illuminate walls (pool light with intensity actually lights BSP surfaces) and the muzzle flash still shows.
- `console` check: no `[EffectPreloader]`-style compile logs / Babylon "compiling" stalls after map load completes.
- Renderer touched → required regression set below.

## Cross-cutting notes

- Bugs 2 and 3 both point at the same hygiene rule: **anything that changes GPU-visible structure (vertex counts, enabled-light sets) mid-gameplay must be fixed-shape from spawn/load time.** Pre-fill and pre-enable; mutate only contents (positions, intensities).
- Bug 1 is the client-prediction mirror of the same rule: **replay must not mutate wall-clock state.** Any timer living inside `MovementProfile` sub-systems is advanced by both real prediction and reconciliation replay unless explicitly rewound (Option B above is the durable answer).
- The projectile spawn path has a related cosmetic quirk (not the reported bug, noting for the backlog): `spawnFromServer` places the visual at the *newest* snapshot position, but `SnapshotBuffer.sample()` renders ~interp-delay in the past, so a fresh projectile can pop slightly forward then snap back for the first ~50 ms ([GameEvents.ts:731-744](src/games/fps/client/GameEvents.ts#L731-L744), [SnapshotBuffer.ts:141-215](src/engine/network/client/SnapshotBuffer.ts#L141-L215)).
