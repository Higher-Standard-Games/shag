# v0.9.16 — Server Authority Review & Hardening

**Status:** Phase A (WO-1..4) **implemented & landed** on `feat/v0.9.16-server-authority-hardening`
(usercmd sanitizer + client parity, action-button decay on starvation, wishspeed invariant test;
1146 tests green, determinism holds). Phases B–D below remain open. Findings + plan follow.
**Scope:** Can a *human* client (not just the bot process we already fixed) escape server
authority the way the bot did? How is packet loss handled, and how gracefully? How does all
this compare to Quake 3 / Warsow (qfusion)?

Follow-up to the v0.9.16 fixed-rate physics fix (`FPSMovementSubsystem`), which closed the
input-**rate** exploit (a client sending fewer/more commands could slow/skip/bank its own
physics). This doc audits the *rest* of the trust boundary.

---

## 0. Where the trust boundary actually is

Real gameplay path (per product):

```
npm run lobby:server        # LobbyServer (matchmaking / redirect)
        │
   client connects to lobby
        │
   lobby redirects client → a spawned GameServer instance
        │
   client ⇄ GameServer  ← THIS is the authority boundary analyzed here
```

The `GameServer` a player ends up on is the same `GameServer` class used by `demo:record` and
`bot:server`, so this audit applies directly to live play. **The `LobbyServer` is a separate
surface** (auth, matchmaking, redirect, DoS) that this doc does *not* deep-review — flagged as
matrix #14 / Phase D, its own follow-up.

### The only thing a client can send that touches the sim: the usercmd

`BinaryProtocol.decodeCommand` (the wire format) carries **exactly**:

| Field | Type | Meaning |
|-------|------|---------|
| `playerId` | string | identity (from connection, not trusted for routing) |
| `sequence` | uint32 | ordering / reconciliation |
| `direction` | 3×float32 | **world-space wish dir**, already yaw-rotated client-side |
| `pitch`, `yaw` | 2×float32 | view angles (radians) |
| `buttons` | uint16 | button bitmask |
| `tick` | uint32 | client tick (advisory) |
| `weaponSlot` | uint8 | desired weapon slot |

**Critically, the client sends NO position, velocity, health, ammo, or "I hit X" claims.**
This is the correct Q3/Warsow model: the client transmits *intent* (a usercmd), and the server
simulates everything else. That is a strong foundation — most of the classic "trust the client"
disasters are structurally impossible here.

## 1. What the server is already authoritative over ✅

Verified in code (`GameServer.handleInput`, `FPSMovementSubsystem`, `WeaponSystem`,
`CombatSystem`, `MovementProfile`):

- **Position / velocity** — computed server-side by `MovementProfile.simulate`. Client-sent
  position does not exist on the wire; it can never be read. ✅
- **Physics rate** — fixed one `dt` per server tick, `MAX_INPUT_BUFFER = 6`, `lastInput` repeat
  on starvation. Input *rate* cannot affect physics (the v0.9.16 fix). ✅
- **Wish-direction magnitude** — `MovementProfile.ts:298-301` normalizes `direction` to unit
  length (`normalizedWish = wishDir / wishLen`) and derives `wishspeed` from **server config**
  (`config.maxSpeed`/`runSpeed` + server-set `speedBonus`). A client sending
  `direction = (1000,0,0)` gains **nothing** — the magnitude is discarded. The single most
  dangerous speed-hack vector is **already closed by design.** ✅ *(This is stronger than it
  looks — see H2 below for the one caveat.)*
- **Fire rate / refire** — server-enforced via `fireIntervalTicks` vs `lastFireTick`. Buttons
  express intent only. ✅
- **Ammo & reload** — `consumeShot`, reload timing quantized to server ticks. ✅
- **Weapon switch** — edge-detected, clamped to owned weapons
  (`weaponSlot > 0 && weaponSlot <= weapons.length`, then `weapons[slot-1]`). A client cannot
  select a weapon it does not own. ✅
- **Hit detection** — server-side ray / sphere / cone traces from **server-side** positions
  (`traceHitscanRay`, `fireMelee`, splash). The client never asserts a hit. No "trust the
  client's hit" path exists. ✅
- **Damage / armor / knockback / kills** — entirely server-side (`CombatSystem`). ✅
- **Anti-warp** — `MovementValidator` (rate cap + real-time budget, silent drop). ✅ *(but see
  H6 — it now partially overlaps the fixed-rate model)*
- **Wallhack mitigation (partial)** — `SnapshotBroadcaster.filterStateForClient` PVS-culls
  entities the client can't potentially see, so ESP can't reveal what isn't sent. ✅ *(genuine
  structural anti-wallhack — see §5)*

**Bottom line:** the movement/speed/firerate/ammo/damage cheat classes are structurally
prevented or nearly so. The bot's "escape" was a *rate* bug, now fixed; a human using the same
trick gains nothing today.

## 2. Remaining holes — where client input is still trusted

Ordered by risk. These are the ways a *malicious human* could still poke the matrix.

### H1 — View angles (`pitch`/`yaw`) are trusted raw, with no sanitization ⚠️ (P0)
`decodeCommand` reads `pitch`/`yaw` as raw float32; nothing clamps or validates them.

- **Aim is *intended* to be client-authoritative** (the server can't know true intent) — this
  matches Q3/Warsow, and aimbots are not preventable by authority alone (§5).
- **But there is no NaN/Infinity guard and no pitch clamp.** `pitch`/`yaw` feed:
  1. `transform.rotation` (visual), and
  2. **`WeaponSystem` fire rays and projectile velocities** (`fireHitscan`, `fireProjectile`).

  A `NaN`/`Inf` yaw ⇒ `NaN` fire direction ⇒ `NaN` projectile velocity ⇒ a projectile entity
  with `NaN` position injected into the sim and broadcast to everyone. A pitch beyond ±90°
  produces a nonsense but "legal" ray.
- Note: movement math is **protected** from NaN here, because `direction` NaN ⇒ `wishLen = NaN`
  ⇒ `hasInput = (NaN > 0.001) = false` ⇒ `normalizedWish = ZERO`. So this is a *combat/entity*
  corruption vector, not a movement one.
- **Q3/Warsow parity:** both clamp view angles server-side (`PM_UpdateViewAngles`).

**Fix:** sanitize on ingest — reject NaN/Inf commands; clamp pitch to `[-π/2, π/2]`; wrap yaw.

### H2 — Wish-direction magnitude: closed, but relying on one call site ⚠️ (P0, defense-in-depth)
The normalize in `MovementProfile.ts:301` is what saves us. It is currently the *only* thing
between a client-supplied float vector and the accel functions. If a future refactor moves,
guards, or bypasses that normalize (e.g. a new movement mode that reads `input.direction`
directly), the speed hack silently reopens.

**Fix:** normalize/clamp `direction` to unit length **at the ingest choke point** (§4) as well,
so the invariant holds regardless of any single downstream call site. Belt *and* suspenders.

### H3 — `buttons` bitmask trusted raw (P3, effectively closed)
Uint16, any bits. The wire codec already bounds it (`readUint16` → 0..0xFFFF), and **all 16 bits
are assigned** in `InputButtons` (movement 0–7, actions 8–11, `ACTION1..4` 12–15), so there are
no "junk" bits to mask — a `KNOWN_BUTTON_MASK` would be `0xFFFF`, a no-op today. Consumers mask
the specific bits they care about anyway. **No action needed** beyond keeping the mask constant in
the sanitizer as future-proofing *if* a bit is ever freed. Downgraded from P2 → P3.

### H4 — No weapon-switch time gate (P1)
Switch is edge-detected (fires only on change) **and cancels reload + charge**. A client
alternating `weaponSlot` 1→2→1→2 every command can **permanently reset an opponent-facing…**
no — it only affects *its own* weapon, but it can perpetually cancel *its own* reload/charge, or
spam switch animations/events at other clients (`pendingFireEvents`/state churn). Warsow gates
weapon switching by a switch time.

**Fix:** minimum ticks between accepted weapon switches per entity.

### H5 — `sequence` monotonic only via dedup (P2, self-harm)
`handleInput` drops `seq <= lastInputSeq`. A client that jumps `seq` to `0xFFFFFFFF` then sends
normal (smaller) seqs soft-locks *itself* (all future inputs dropped). No effect on others.
Low priority; a sanity check ("seq must be within a window of the last accepted") is nice hygiene.

### H6 — `MovementValidator` now overlaps the fixed-rate model (P1)
Before the fixed-rate fix, flooding inputs bought extra movement, and `MovementValidator`'s
time-budget layer was the defense. **Now** the buffer cap (6) + one-command-per-tick already
neutralizes the *physics reward* of flooding — a flooder's excess commands are simply dropped by
`queue.splice`. Meanwhile `MovementValidator` still **silently drops** inputs that exceed its
budget, which under the new model can drop *legitimate* buffered commands on a bursty/jittery
connection (false positives → the player's own reconciliation snaps).

**Fix:** keep the rate cap (cheap DoS guard) but relax/remove the real-time *budget* layer — the
fixed-rate consumption is the authoritative anti-warp now. Re-tune so the two mechanisms compose
instead of double-jeopardy.

### H7 — `lastInput` repeat re-applies *action* buttons during starvation ⚠️ (P0)
When no fresh command arrives, `FPSMovementSubsystem` repeats `lastInput` so gravity/momentum
keep advancing — correct for *movement*. But the repeated command still carries the old
**buttons**, so a client that sends one `FIRE`-held command then goes silent (rage-quit freeze,
throttled connection, deliberate) keeps "holding fire": `WeaponSystem` re-reads `buttons & FIRE`
every tick and keeps firing at the refire cadence (bounded by ammo, but still auto-firing a
frozen player). Same for held movement/jump.

**Q3 parity:** Q3 does not invent *new* button presses from a stale cmd; a frozen client stops
acting.

**Fix:** on `lastInput` *repeat* (not fresh), zero the action/edge buttons (FIRE/ALT/RELOAD/JUMP)
after K starvation ticks, or clear action bits on any repeat. Keep the movement axes so physics
still advances smoothly. No auto-fire / auto-jump from a silent client.

### H8 — Respawn / join / spectate / team spam (P1)
- `handleRequestSpawn` sets `wantsRespawn` with no rate limit.
- `JoinGame`/`Spectate` toggling each removes/adds the entity, **resets scores**, and
  **re-registers the anti-warp client with a full fresh budget** (`addClient` starts at
  `maxBudgetMs`) — a rapid toggler could bank grace and thrash gametype/spawn state.

**Fix:** minimum interval between team/spectate switches and between respawn requests (Warsow has
a team-switch delay). Don't reset anti-warp grace on re-join within a window.

### H9 — No defense-in-depth position sanity clamp (P1)
Movement is server-computed, so this isn't strictly required — but there is no backstop that
asserts "an entity did not move more than physically possible this tick." A collision/NaN/logic
bug that produces an impossible delta would propagate silently. A per-tick delta clamp
(`|Δpos| ≤ maxSpeed·dt·margin`, else log + clamp) enforces the "no way out of the matrix"
invariant as a tripwire even for *our own* bugs, not just cheaters.

## 3. Packet-loss handling — current state & gaps

### What we do today (and it's mostly good)
- **Command redundancy** — the client packs the last **3** commands per packet; the server dedups
  by `seq` (`handleInput: seq <= lastInputSeq → drop`). A single lost input packet is covered by
  the next packet's backups. ✅ This is exactly Q3's backup-cmd scheme.
- **Ack = last *simulated* seq** — `SnapshotBroadcaster` acks `input.lastProcessedSeq` (the command
  actually consumed into physics under one-per-tick), not the last *received* seq. The client
  replays `getUnacked(ackedSeq)`. ✅ Correct under the fixed-rate model.
- **Delta baselines degrade gracefully** — 64-snapshot server history; if the client's acked
  baseline has aged out or was lost, the broadcaster falls back to a **full** snapshot
  (`baseline = undefined`). ✅ No stall.
- **Snapshot loss self-heals** — the client processes only the *latest* buffered snapshot and
  reconciliation is absolute (reset to server pos + replay unacked). A dropped snapshot = one
  skipped correction, healed next snapshot. ✅
- **Bounded client memory** — `InputHistory` caps at 256 and prunes oldest. ✅

### Gaps
- **G1 — No adaptive jitter buffer on the server.** The server drains toward 0 each tick
  (consume one, cap at 6). Under jitter a late packet ⇒ buffer underflow ⇒ `lastInput` repeat
  (a 1-tick extrapolation hitch); under burst, >6 buffered are dropped. Reasonable, but *fixed*.
  Consider a small target occupancy (hold ~2–3, don't drain to 0) to smooth jitter at the cost
  of ~1–2 ticks latency. Document the latency/smoothness trade-off explicitly.
- **G2 — Redundancy depth fixed at 3.** Beyond 3 consecutive lost packets, inputs are gone for
  good ⇒ server repeats `lastInput` ⇒ client replays inputs the server never simulated ⇒
  correction snap. Warsow scales redundancy (`cl_packetdup`). Consider adaptive depth under
  measured loss.
- **G3 — Client-acked tick is trusted into the encoder.** A client can `Ack` a tick it never
  received; the server will try to delta against that history entry (or fall back). Low risk, but
  it's client-controlled input into server CPU/encoding. Clamp acked tick to the set of snapshots
  actually sent to that client.
- **G4 — No per-client loss/jitter telemetry** to drive adaptive behavior or flag anomalies.

## 4. Exact implementation spec

Everything below is written against the current code. New files live in `shared/` when they must
be reused by both the sim and (later) the client; server-only gates live next to their subsystem.
Repo column: **fps** = `src/games/fps` submodule, **eng** = parent (`src/engine`, `src/shared`).

### 4.1 — `sanitizeCommand` ingest choke point (H1, H2, H3) — repo: **fps + eng**

Almost every H-item is "raw client field trusted downstream." One ingest function every command
passes through *before* it enters `inputQueue` makes the trust boundary a single auditable place.

**New file** `src/shared/server/simulation/InputSanitizer.ts` (shared so client-side prediction can
apply the identical clamp and stay in sync — important, or prediction diverges from the server):

```ts
import type { NetworkCommand } from "@engine/network/protocol/BinaryProtocol";

/** All 16 button bits are currently assigned; 0xFFFF today. Kept explicit so a freed bit
 *  is masked automatically. */
export const KNOWN_BUTTON_MASK = 0xffff;

/** Max weapon slots (blade + 2 pickables today → index 1..3). Bound the index defensively. */
const MAX_WEAPON_SLOT = 9;

export interface SanitizedCommand {
  direction: { x: number; y: number; z: number };
  pitch: number;
  yaw: number;
  buttons: number;
  weaponSlot: number;
  sequence: number;
}

const HALF_PI = Math.PI / 2;

function wrapAngle(a: number): number {
  // Normalize to (-π, π]. Assumes finite (checked by caller).
  const twoPi = Math.PI * 2;
  let r = a % twoPi;
  if (r > Math.PI) r -= twoPi;
  else if (r <= -Math.PI) r += twoPi;
  return r;
}

/**
 * Clamp/validate a raw client usercmd. Returns null to REJECT the whole packet
 * (non-finite anything) — a NaN/Inf must never reach the sim.
 *
 * NOTE: direction magnitude carries no information (MovementProfile normalizes it),
 * so we clamp |dir_xz| ≤ 1 here as defense-in-depth (H2) in case a future movement
 * path reads input.direction without normalizing.
 */
export function sanitizeCommand(cmd: NetworkCommand): SanitizedCommand | null {
  const dx = cmd.direction?.x ?? 0;
  const dz = cmd.direction?.z ?? 0;
  const pitch = cmd.pitch ?? 0;
  const yaw = cmd.yaw ?? 0;

  if (!(Number.isFinite(dx) && Number.isFinite(dz) && Number.isFinite(pitch) && Number.isFinite(yaw))) {
    return null; // H1: reject NaN/Inf outright
  }

  const len = Math.hypot(dx, dz);
  const scale = len > 1 ? 1 / len : 1; // H2: clamp to unit; leave sub-unit (analog) dirs intact

  return {
    direction: { x: dx * scale, y: 0, z: dz * scale },
    pitch: Math.max(-HALF_PI, Math.min(HALF_PI, pitch)), // H1: clamp look pitch
    yaw: wrapAngle(yaw),                                 // H1: bound yaw
    buttons: (cmd.buttons ?? 0) & KNOWN_BUTTON_MASK,     // H3: no-op today, future-proof
    weaponSlot: Math.max(0, Math.min(MAX_WEAPON_SLOT, (cmd.weaponSlot ?? 0) | 0)),
    sequence: cmd.seq ?? 0,
  };
}
```

**Wire in** at `GameServer.handleInput` (`GameServer.ts:977`). After the dedup + anti-warp checks,
replace the raw `inputQueue.push({...})` with the sanitized command; drop the packet if `null`:

```ts
const { command } = MessageCodec.decodeCommand(data);
const seq = command.seq || 0;
if (seq <= client.lastInputSeq) return;
if (!this.movementValidator.validateInput(client.playerId)) return;

const clean = sanitizeCommand(command);          // ← NEW
if (!clean) { client.lastInputSeq = seq; return; } // reject bad packet, still advance dedup

const mutEntity = state.getEntityMut(client.entityId);
if (mutEntity?.input) {
  mutEntity.input.inputQueue.push({
    forward: clean.direction.z,
    right: clean.direction.x,
    pitch: clean.pitch,
    yaw: clean.yaw,
    buttons: clean.buttons,
    sequence: seq,
    weaponSlot: clean.weaponSlot,
  });
  client.lastInputSeq = seq;
}
```

**Client parity (later, same branch):** call `sanitizeCommand` in `V2NetworkClient.processInput`
before local prediction so predicted and server states apply the identical clamp. Without this,
a legitimately steep pitch predicts differently than the server simulates → a reconciliation snap
on every frame you look near vertical.

**Tests** (`InputSanitizer.test.ts`, eng): NaN/Inf in any of dir/pitch/yaw → `null`; `|dir|=1000`
→ unit length; pitch `±π` → clamped to `±π/2`; sub-unit analog dir (0.3,0,0.3) passes unchanged;
finite passthrough round-trips.

### 4.2 — Decay action buttons on `lastInput` repeat (H7) — repo: **fps**

`FPSMovementSubsystem.update` (`:321`) does `const cmd = queue.shift() ?? this.lastInput.get(eid)`.
When it falls back to `lastInput` (no fresh command), the repeated command still carries the old
FIRE/JUMP/etc., so a frozen client keeps acting. Fix: track *starvation* per entity and strip the
**action** bits from the repeated command after a short grace, keeping the movement axes so
physics still advances smoothly.

```ts
// class fields
private starvationTicks: Map<number, number> = new Map();
private static readonly BUTTON_HOLD_GRACE_TICKS = 3; // ~24ms @125Hz: cover one dropped packet
private static readonly ACTION_BUTTON_MASK =
  InputButtons.FIRE | InputButtons.ALT_FIRE | InputButtons.RELOAD | InputButtons.USE | InputButtons.JUMP;

// in update(), replacing the `const cmd = ...` block:
const fresh = queue.shift();
let cmd = fresh ?? this.lastInput.get(eid);
if (fresh) {
  this.starvationTicks.set(eid, 0);
} else if (cmd) {
  const starved = (this.starvationTicks.get(eid) ?? 0) + 1;
  this.starvationTicks.set(eid, starved);
  if (starved > FPSMovementSubsystem.BUTTON_HOLD_GRACE_TICKS) {
    // Repeat movement/aim, but stop inventing action presses from a silent client.
    cmd = { ...cmd, buttons: cmd.buttons & ~FPSMovementSubsystem.ACTION_BUTTON_MASK };
  }
}
```

Clear `starvationTicks` in `removeEntity`. **Test** (extend `FixedRatePhysics.test.ts`): send one
`FIRE|JUMP` command, then tick N>grace times with an empty queue; assert the consumed `buttons`
has FIRE/JUMP cleared after grace while `forward`/`yaw` persist (movement still advances under
gravity). A companion `WeaponSystem` test: one FIRE then silence → exactly one shot, not a stream.

### 4.3 — Weapon-switch time gate (H4) — repo: **fps**

`WeaponSystem.update` (`:567`) switches on slot edge. Add a per-entity min interval:

```ts
private lastSwitchTick: Map<EntityId, number> = new Map();
private static readonly SWITCH_INTERVAL_TICKS = 25; // ~200ms @125Hz (Warsow-ish)

// where the switch is applied:
if (weaponSlot !== prevSlot && weaponSlot > 0 && weaponSlot <= weaponState.weapons.length) {
  const last = this.lastSwitchTick.get(entity.id) ?? -Infinity;
  if (tickNum - last >= WeaponSystem.SWITCH_INTERVAL_TICKS) {
    const newWeapon = weaponState.weapons[weaponSlot - 1];
    if (newWeapon && newWeapon !== weaponState.currentWeapon) {
      weaponState.currentWeapon = newWeapon;
      weaponState.reloading = false; weaponState.reloadEndTick = 0; weaponState.chargeStartTick = 0;
      this.lastSwitchTick.set(entity.id, tickNum);
    }
  }
}
```

Note the pickup **auto-switch** path (`addWeapon`) should bypass the gate (it's server-initiated).
**Test:** two switches within the interval → only the first applies; after interval → second applies.

### 4.4 — Rate-gate respawn / team / spectate (H8) — repo: **fps**

Per-connection timestamps on `ClientInfo`; reject actions inside the window. `Client.ts` gains
`lastRespawnReqMs`, `lastTeamSwitchMs` (default 0).

```ts
// GameServer.handleRequestSpawn
const now = performance.now();
if (now - (client.lastRespawnReqMs ?? 0) < 500) return; // 2/s cap
client.lastRespawnReqMs = now;

// GameServer.handleJoinGame / handleSpectate (top, after client lookup)
if (now - (client.lastTeamSwitchMs ?? 0) < 3000) { /* optional: notify "wait N s" */ return; }
client.lastTeamSwitchMs = now;
```

Also **don't reset anti-warp grace on rapid re-join**: in `handleJoinGame`, only
`movementValidator.addClient` if not already tracked within a window (or have `addClient` no-op /
preserve budget if the player id is re-added quickly). **Test:** two `RequestSpawn` 100ms apart →
one honored; two `JoinGame`/`Spectate` toggles inside 3s → second rejected.

### 4.5 — Clamp client-acked tick to the sent window (G3) — repo: **fps**

`GameServer.handleDatagram` Ack branch (`:724`) stores `client.lastAckedTick = tick` if greater.
A client can ack a tick it never received. Clamp to the current server tick (a client can't have
seen the future) and let `SnapshotBroadcaster`'s existing `snapshotHistory.get(...) ?? undefined`
fall back safely for unknown-but-past ticks:

```ts
const serverTick = Number(this.simulation.currentTick);
if (tick > client.lastAckedTick && tick <= serverTick) {
  client.lastAckedTick = tick;
}
```

**Test:** ack of `serverTick + 1000` is ignored; ack of a valid past tick is accepted.

### 4.6 — Reconcile `MovementValidator` with fixed-rate (H6) — repo: **fps**

The buffer cap + one-cmd-per-tick already removes the *physics reward* for flooding, so the
time-**budget** layer now mostly causes false drops on bursty links. Keep the **rate cap** (cheap
per-tick DoS guard) and make the time budget advisory:

- Raise `maxBudgetMs` (e.g. 200 → 500) and only *count strikes* on budget violation, **don't drop**
  the input for budget (still drop on rate-cap). Movement can no longer be gained by flooding, so a
  budget overshoot is now a *signal*, not something we must physically prevent.
- Keep `getStrikes()` feeding the future statistical layer (§5.2).

**Test:** a burst of 12 commands in one tick → rate cap drops the excess beyond
`maxInputsPerTick`, budget layer records strikes but the accepted commands still enqueue.

### 4.7 — Post-simulate position-delta tripwire (H9) — repo: **fps**

Defense-in-depth against *our own* bugs (bad collision/NaN), not just cheaters. After
`applyResult` in `FPSMovementSubsystem`, compare to the pre-simulate position:

```ts
const maxStep = (this.profileMaxSpeed(profile) * dt * 2) + 64; // 2× wishspeed + slop for KB/teleport
const moved = dist(prevPos, transform.position);
if (moved > maxStep) {
  console.warn(`[Authority] entity ${eid} moved ${moved.toFixed(0)}u in one tick (max ${maxStep.toFixed(0)}) — clamping`);
  // Option A (strict): clamp back toward prevPos along the move dir to maxStep.
  // Option B (log-only first): ship as telemetry, enable clamp after we confirm no false positives.
}
```

Ship **log-only first** (Option B) so legitimate KB launches / teleports don't get clipped;
promote to clamp once telemetry is clean. **Test:** synthetic impossible delta triggers the warn;
a normal sprint/jump/KB does not.

### 4.8 — Packet-loss quality (G1, G2) — repo: **fps + eng** — *P2, separate sub-effort*

- **G1 jitter buffer:** change `FPSMovementSubsystem` to target a small held occupancy instead of
  draining to 0 — e.g. only consume when `queue.length >= 1` *and* don't consume the last buffered
  command if it arrived this same tick, holding ~1–2 as a cushion. Adds ≤2 ticks latency for
  smoother jitter. Gate behind a cvar so it's tunable/measurable.
- **G2 adaptive redundancy:** client tracks ack gaps; when loss is detected, raise backup-cmd depth
  (3 → 5). Wire format already carries per-packet backups; only the count changes. Needs a client
  change (`V2NetworkClient` send loop) + no server change (dedup already handles any depth).

These are netcode-quality, not authority; keep them in a later phase so P0/P1 land clean.

## 5. Comparison to Quake 3 / Warsow (qfusion)

| Concern | Q3 / Warsow | SHAG today | Verdict |
|---|---|---|---|
| Client sends intent, not state | usercmd (forward/right/up as ±127 bytes, angles, buttons) | usercmd (dir vec, angles, buttons) — **no** position/hp/hits | ✅ parity |
| Movement authority | `pmove` on server-owned playerState | `MovementProfile.simulate` on server WorldState | ✅ parity |
| Speed from input magnitude | implicitly bounded — cmd components are ±127 bytes, then `VectorNormalize` + clamp to `ps->speed` | float vector, **normalized** + server `wishspeed` | ✅ (but see H2 — enforce at ingest too) |
| View-angle clamp | `PM_UpdateViewAngles` clamps server-side | **none** | ❌ **H1** |
| Time-step trust | server clamps `cmd.msec` (1..200) & `serverTime` | **not trusted at all** — fixed server `dt` | ✅ **stronger** |
| Flood → extra movement | bounded by msec clamp | bounded by one-cmd-per-tick + buffer cap | ✅ parity (our v0.9.16 fix) |
| Frozen client keeps acting | stale cmd doesn't invent presses | `lastInput` repeat re-applies buttons | ❌ **H7** |
| Weapon switch gate | switch time | none | ❌ **H4** |
| Packet loss | backup cmds (`cl_packetdup`), full-snapshot fallback | 3 backups, full-snapshot fallback | ✅ parity (G1/G2 to improve) |
| Wallhack | PVS in snapshot | PVS cull in `SnapshotBroadcaster` | ✅ parity |
| Aimbot | not preventable by authority; relies on detection | same | — (see below) |

**Our fixed-`dt` model is actually *more* robust than Q3's `msec`-clamp model** for the flooding
case: Q3 still trusts a (clamped) client time-step; we trust *no* client timing at all. Good.
The parity gaps that remain are H1 (angle clamp), H7 (stale-button), H4 (switch gate) — all small.

### The honest limit: aimbot & ESP
No amount of server authority stops **aim** cheats (aimbot/triggerbot) or **ESP** where data is
sent, because the client must render what it's allowed to see. The durable answers, in order of
what we already have:

1. **PVS culling (have it)** — don't send entities the player can't potentially see. Structurally
   defeats most wallhack/ESP. *Action:* ensure PVS is **enabled in production** and audit the
   "always send" fallbacks (players' scoreboard state is global, but their *entities* are
   PVS-gated — correct).
2. **Server-side statistical detection (build it)** — impossible-flick / angular-snap detection,
   hit-ratio and headshot-ratio outliers, reaction-time distributions. Runs on the usercmd stream
   the server already owns.
3. **Replay review (we just built the substrate!)** — the v0.9.16 demo pipeline doubles as an
   **anti-cheat evidence store**: record suspect matches, review angle traces offline, auto-flag.
   This is the highest-leverage tie-in — the demo work and the anti-cheat work reinforce each other.
4. **Account / trust / matchmaking** (lobby layer) — segregate low-trust accounts, rate-limit new
   accounts. Belongs with the LobbyServer review (§6).

**"Cheaters overpopulating honest players"** is fundamentally a detect-and-segregate problem, not
a pure-authority one: authority makes speed/damage/firerate/ammo cheats *impossible* (mostly done
here), and detection + replay + trust handle the aim/ESP residue.
