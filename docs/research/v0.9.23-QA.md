### N01 — Lost PVS snapshot can leave position permanently stale

**Source:** [SnapshotBroadcaster.ts](../../src/games/fps/server/SnapshotBroadcaster.ts),
lines 98–117; [BinaryProtocol.ts](../../src/shared/net/BinaryProtocol.ts),
`encodeSnapshot`, `encodeEntities`, `decodeEntities`;
[NetworkGameHost.ts](../../src/engine/network/client/hosts/NetworkGameHost.ts),
lines 473–475 and 624–629.

The PVS sender deltas against `client.lastSentState`, regardless of its ACK.
The receiver decodes against its last received snapshot. No baseline identity
is transmitted, so it cannot detect a missing dependency. The sender also
updates `lastSentState` before attempting `sendDatagram`.

**Reproduction:** receive tick 1 at x=0; drop tick 2 at x=100; receive ticks 3–8,
all authoritative x=100. Decoded x remains **0 through tick 8**. Subsequent
unchanged snapshots keep omitting position, so the incorrect state can persist
until that component changes or a full resynchronization occurs. Static weapon
metadata/player fields have the same class of risk.

**Scope:** ordinary datagram loss on WebTransport; also failed sends after the
baseline has advanced. Reliable ordered WebSocket does not normally lose an
individual delivered frame, so do not attribute ordinary WS loss to this case.

**Fix direction:** identify each baseline on the wire, retain per-client
filtered history by tick, and encode only against an acknowledged retained
baseline. Unknown baseline must request/await a full state without ACKing
corrupt reconstruction. Add periodic full-state recovery. Preserve PVS privacy.
Test loss, multiple losses, new entities, component changes followed by rest,
PVS enter/exit, and send failure before recording the baseline.

### N02 — ACK delay alone breaks non-PVS reconstruction

Same source locations as N01, but a distinct trigger. The server uses
`snapshotHistory.get(client.lastAckedTick)` while `sendAck()` immediately
replaces the client's single decode baseline. ACK delivery is asynchronous:
reliable delivery does not mean the sender has received the newest ACK.

| Step | Authoritative x | Sender baseline | Receiver baseline | Decoded x |
| --- | --- | --- | --- | --- |
| Tick 1, full received and ACK delivered | 0 | None | None | 0 |
| Tick 2, received; ACK still in flight | 100 | Tick 1 | Tick 1 | 100 |
| Tick 3, player returns to x=0 | 0 | Tick 1, so position omitted | Tick 2 | **100** |

**Reproduction:** actual broadcaster + codec, all three packets delivered in
order, **zero dropped packets**. Same mismatch can affect grounded transitions,
velocity, rotation and player metadata. Movement flags already being sent every
snapshot does not repair other delta-compressed fields.

**Fix direction:** shared protocol/history work with N01. A reliable ACK channel
alone cannot fix this. Add delayed-ACK tests over the actual host and server,
including A→B→A component changes and several snapshots per RTT.

### N03 — Knockback replay is not idempotent

**Source:** [V2NetworkClient.ts](../../src/games/fps/client/V2NetworkClient.ts),
`processInput`, `applySnapshot` replay loop, `applyKnockback`, `applyKBDrag`;
[FPSMovementSubsystem.ts](../../src/games/fps/server/systems/FPSMovementSubsystem.ts),
lines 617–653.

Client `kbTickCounter` is incremented by every fresh input **and every replayed
input**, without rewinding to authoritative KB age. Snapshot state includes
position/velocity/grounded, not KB activation/age. Server derives age from
`serverTick - lastKBTick` instead.

**Reproduction:** apply KB, predict 30 inputs, then apply the same authoritative
snapshot twice with those same 30 inputs unacked and no new input. KB age changes
**30→60→90**. First replay gives `(95.98124, 5066.23437, 0)`; second gives
`(91.61067, 5064.86903, 0)`. This is physical state divergence, not visual smoothing.
The duplicate snapshot isolates replay dependence; repeated replay of overlapping
unacked inputs also happens across normal successive snapshots.

**Additional source mismatch:** server applies KB drag before movement while
client applies it after movement. Starting/cancelling age also uses different
step conventions. These need parity checks, not just a counter decrement fix.

**Fix direction:** replicate authoritative KB state/activation tick and restore
it during replay; make the shared simulation own identical KB ordering and
elapsed-time rules. Test remote damage and predicted self-damage, landing,
multiple impulses, repeated reconciliation and delay/ramp boundaries.

### N04 — Fixed-rate physics and sequence-derived effect time disagree

**Source:** `FPSMovementSubsystem.ts`, lines 720–772;
[MovementProfile.ts](../../src/games/fps/simulation/MovementProfile.ts),
lines 446–452 and consumers of `simNowMs`;
[WallJump.ts](../../src/games/fps/simulation/WallJump.ts), absolute deadlines.

The server repeats `lastInput` when starved, including the same sequence.
Movement sets `simNowMs = sequence * dtMs`. Gravity advances every tick, but
walljump/slide/ledge deadlines, ladder detach cooldown and water-jump timing
share an effect clock that stops during those repeated commands. Dropping
queued inputs creates the opposite problem: sequence gaps jump effect time
forward without the corresponding physics steps.

**Reproduction:** one command with sequence 1, then 20 total server ticks.
Physics has advanced **160ms** and y falls from 5000 to **4983.52**, but the
profile clock is still **8ms**. The repeat sequence is intentional for input ACK
correctness; changing the ACK on repeated input would introduce a different bug.

**Fix direction:** separate command identity from simulation time. Design the
mapping between authoritative tick, replay step and movement deadlines before
changing either counter. The command ACK alone cannot represent how many
server repeat steps occurred. Replicate enough timing/state for exact replay.
Test starvation and burst recovery during every timed movement mechanic.
The precise magnitude of each mechanic's gameplay failure is unmeasured.

### N05 — Reconciliation suppression is unbounded while eligibility persists

**Source:** `V2NetworkClient.ts`, lines 330–367.

`wallJumpState !== "none"` includes **available**, not just charging. Each such
snapshot resets a ten-snapshot skip counter. Ledge state behaves similarly.
The skip branch prunes ACKed inputs and returns before adopting authoritative
position/velocity, irrespective of the correction magnitude. A stream of eligible
states has no overall timeout. This is a workaround for replay disagreement,
not resolution of that disagreement.

**Reproduction limit:** seed `wallJumpState="available"` after a first snapshot,
then submit 100 fresh authoritative snapshots at x=1000. Client x stays **0**.
This proves the correction gate; it does **not** prove a real player can remain
eligible for 100 snapshots on a particular BSP. Local input normally recomputes
eligibility each tick. Ten snapshots also means different real durations at
different snapshot rates (160ms at 62.5Hz; about 333ms at 30Hz).

**Fix direction:** restore complete movement state and remove/bound suppression;
hard authoritative discontinuities must override it. Capture correction debt,
skip reason, duration and maximum divergence. Add actual wall/ledge fixture
tests before removing a workaround that currently protects visual stability.

### N06 — Snapshot arrival order is treated as server chronology

**Source:** `NetworkGameHost.ts`, `handleSnapshot` and `sendAck`;
`V2NetworkClient.ts`, `bufferSnapshot`/`processBufferedSnapshots`;
[SnapshotBuffer.ts](../../src/engine/network/client/SnapshotBuffer.ts), `push`.

Host decodes every snapshot against its current baseline, sets `currentTick`,
sends an ACK and invokes game callbacks without rejecting stale/duplicate ticks.
V2 selects the last **arrival**, not the highest tick. Remote buffer also appends
without sorting/rejecting stale samples. Server ACK monotonicity guards do exist;
they do not protect client state.

**Reproduction:** apply tick 20 at x=200, then tick 18 at x=100: predicted x
regresses to **100**. No newer input is involved. Full WebTransport reordered
delivery through the browser has not been exercised. WebSocket's ordered frames
normally mask this trigger.

**Fix direction:** baseline-aware decode first, monotonic accepted world state
per connection/map epoch, event deduplication, and a consistent ordering policy
for interpolation. Retain older decoded states only when needed as baselines;
do not run lifecycle callbacks for them. Test duplicates, reorder, map resets,
and tick wrap separately.

### N07 — Per-entity input state survives cleanup

**Source:** `FPSMovementSubsystem.ts`, `lastInput`, `removeEntity` (lines 977–991);
[GameServer.ts](../../src/games/fps/server/GameServer.ts),
`handleDisconnect`/`handleSpectate`;
[WorldState.ts](../../src/engine/server/core/WorldState.ts), `generateEntityId`.

`removeEntity()` deletes profiles and several timers but does not delete
`lastInput`. The inspected active disconnect/spectate paths remove the ECS
entity without calling movement `removeEntity` at all. Gametype callbacks clean
their own roster/spawn maps, not these movement caches.

**Reproduction:** command seq=77, forward=1, yaw=0.75; explicitly call movement
cleanup and remove the ECS entity; install a fresh player at the same ID and
tick with no commands. New player inherits **forward=1, yaw=0.75, ACK=77**.

**Limits:** normal `WorldState.generateEntityId()` is monotonic, and spectate
reserves a fresh ID. Cross-player inheritance is therefore conditional on ID
reuse, not established for an ordinary rejoin. Retained cache entries across
disconnects are a separate source-confirmed long-session concern; memory growth
has not been profiled. Match reset does clear `lastInput` globally.

**Fix direction:** one explicit movement lifecycle cleanup contract, invoked by
every removal path, clearing all maps/queued effects. Test disconnect/spectate
cache sizes and deliberate ID reuse; audit respawn of the same entity separately.

### N08 — Replay cap creates a noncontiguous simulation history

**Source:** `V2NetworkClient.ts`, lines 395–410;
[InputHistory.ts](../../src/games/fps/client/InputHistory.ts), 256-entry cap.

When more than 32 commands are unacked, client starts at the authoritative
snapshot but replays only the **last** 32. Those inputs assume the missing
prefix already happened. Their sequence-derived clocks advance while their
position/velocity history does not. This is a deliberate CPU cap with an
incorrectly specified fallback, not an argument for unlimited replay.

**Reproduction:** free fall with identical baseline and input history. At 32
inputs, reconciliation preserves y=**4958.272**. At 33, it moves y from
**4955.648 to 4958.272** (2.624 units) even though authority has not disagreed.
Threshold is 256ms worth of 125Hz commands, including transit, queueing and
unprocessed snapshots; it is not a direct RTT threshold. Direction changes,
triggers and movement timers can make the skipped prefix more consequential.

**Fix direction:** explicitly define a bounded resynchronization mode and the
next sequence/time anchor; never silently replay a suffix as though it followed
the snapshot. Test 31/32/33 inputs, more than 256, burst ACK recovery, and moving
lifts during overload.

### N09 — Advertised server rate does not configure active client prediction

**Source:** [FPSController.ts](../../src/engine/camera/controllers/FPSController.ts),
lines 915–925; [Game.ts](../../src/games/fps/Game.ts), lines 785–791,
server-info callback and line 972; `NetworkGameHost.ts`, Welcome handling;
`GameServer.ts`, `sendWelcome`; [ServerTiming.ts](../../src/games/fps/server/ServerTiming.ts).

Server supports a configured tick rate and includes it in Welcome. Client
prediction is constructed using `config.tickRate ?? 125`, and the controller
sends/simulates at a literal 125Hz. The Welcome callback loads the map but does
not renegotiate those values. Even passing a custom client config leaves the
controller rate hardcoded. Server-only rate tests cannot verify this path.

**Impact:** nondefault-rate sessions cannot share a consistent dt/input cadence;
queue dropping/repeats and prediction drift follow. Default 125Hz masks it.
Live custom-rate client/server testing is still required. Weapon/pickup/KB
constants also contain 125Hz assumptions; this pass did not prove all of those
are runtime-correct at other rates.

**Fix direction:** consume an immutable negotiated timing contract before
enabling prediction/input, or explicitly reject unsupported rates. Validate
end-to-end 60/125/250Hz with legal snapshot rates, not only server tick counts.

### N10 — Low-FPS catch-up loses one-shot input before simulation

**Source:** `FPSController.ts`, lines 920–949 (`_pendingWeaponSlot` cleared on
first catch-up command); `NetworkGameHost.ts`, redundant command transmission;
`FPSMovementSubsystem.ts`, queue cap then `shift` at lines 726–758.

A frame hitch can accumulate 100ms and generate twelve commands. The pending
weapon slot appears only in the first. If those commands reach one server tick
together, the six-entry server buffer drops the oldest six, including the
switch. Redundant retransmission does not rescue a command the server already
accepted then discarded; sequence deduplication rejects its older copies.

**Reproduction:** enqueue seq 1–12, slot=3 only on seq 1. Across six server ticks,
processed sequences are **7,8,9,10,11,12**, and the input weapon slot stays **1**.
No simulated packet loss is needed. The harness reproduces queue consumption;

### N12 — Freshness gate needs projectile timeline resets too

**Introduced by:** root `c28ef24c`; FPS `c088ce6` resets the remote-player
renderer but misses the other `SnapshotBuffer` owners.

**Source:** `SnapshotBuffer.push` lines 163–165; `Game.projectileBuffer` line
166 and connect line 977; `GameEvents.processProjectileEntities` line 1171;
`DemoService._clearDemoProjectiles` line 1128. `Game` keeps its buffer for the
singleton's lifetime; its only explicit operation outside sampling/pushing is
the tab-return `flush`. Demo seek calls `_clearDemoProjectiles`, which also
flushes. A flush keeps the latest sample and `lastTick`; it is not a reset.

**Counterexample:** accept tick 10000, flush, push tick 10: rejected. Calling
`reset()` first accepts tick 10. A reconnect to a younger server or backward
demo seek therefore rejects subsequent projectile samples until they exceed
the old maximum. This affects even a previous session whose last sample had
no projectiles. New projectile IDs have no sample; reused IDs can sample the
old session. Server-driven projectiles do not advance their own positions, so
their visuals can remain at spawn or use stale motion until despawn/recovery.

**Fix direction:** reset projectile interpolation and associated lifecycle
collections on connection and demo timeline changes. Keep ordinary tab-return
flush semantics. Test the real owners, not only calling `SnapshotBuffer.reset`
directly. Buffer mechanism reproduced; rendered reconnect/seek not exercised.

### N13 — Historical landing cancels an impulse that has not happened yet

**Introduced by:** FPS `ef76612`, the N03 replacement landing latch.
**Source:** `V2NetworkClient.applyKBDrag` lines 915–932, and `applySnapshot`
lines 492–493.

Landing is checked before computing `step - kbStartSeq`. An unacked replay
window can include grounded commands from before the locally predicted
knockback. Those commands set `kbCancelSeq` even though their step precedes
the impulse, and every later drag step is then skipped.

**Counterexample:** stand on the floor, issue ten idle commands, apply KB
(anchor seq 11), predict ten more, then reconcile a grounded pre-impulse
snapshot (ACK 0). Real V2 replay, under the 32-command budget, records
`kbCancelSeq = 1`. A later airborne authoritative snapshot with ACK 11 retains
that cancellation because it is already below the ACK. At seq 111, a diagnostic
drag step leaves velocity `(1000, 0, 0)` unchanged; the same anchor without the
invalid cancellation produces `(982.22222, -2.13333, 0)`.

**Fix direction:** pre-activation steps must have no effect on this impulse,
including its landing latch. Add this crossing-window case to the permanent
replay suite. Multiple impulses, authoritative remote KB and impulse replay
remain separate state-restoration questions; this probe does not resolve them.

## Implementation order and acceptance criteria

### W01 complete — 2026-09-14

Every regression below was first run against unchanged production and observed
to fail with the recorded wrong value, then re-run after the fix.

- N01/N02: **2 failed** with exactly the recorded wrong positions (expected
  100/0, received 0/100). N11: **3/3 failed**, including yaw expected 0,
  received 1.
- Shipped: explicit network baseline identity on the wire, bounded per-client
  ACKed history on the sender (64), bounded decode history on every receiver
  (128), periodic full-state recovery every 64 emissions, and baseline
  component ownership isolation.
- The receiver never ACKs state it could not reconstruct, so a missing
  dependency can no longer become the sender's next baseline. PVS filtering is
  preserved because the retained baseline *is* the filtered state that was sent.
- Raw `BinaryProtocol` demo frame layout is unchanged; existing demos still
  decode. The network envelope uses a distinct message type (`Snapshot = 0x0b`,
  old `0x04` retained as `LegacySnapshot` and rejected), so old peers cannot
  silently misinterpret the header — server, browser and bots ship together.
- N11 root cause: `decodeEntities` borrowed `baselineTransform` when position
  was unchanged, then wrote its rotation for flag 0x08, corrupting a retained
  baseline even at the correct tick. Position, transform and weaponMeta
  carry-forward now clone. The player and velocity/movement carry-forward paths
  were audited and copy scalars, so they were already safe.
- Sender history retains entities and players only: events, match and pickup
  payloads are encoded in full every snapshot and are never delta inputs.
- **Bounds check:** the receiver's 128 entries always cover the sender's 64, so
  the sender cannot name a baseline the receiver has already evicted.
- Server tick is monotonic for the process lifetime (`Simulation.reset()` has no
  production caller and there is no in-process map change), so the new freshness
  gate cannot stall a live session. ACK monotonicity is already guarded by
  `nextAckedTick`.
- **Cost:** the sender now retains ~1s of per-client snapshots instead of one.
  With PVS off the entity map is shared across clients; with PVS on each client
  holds its own filtered map over shared entity objects.

### W02 progress — 2026-09-14

N06's ordering half is implemented. Arrival order is no longer read as server
chronology at any of the three layers the finding named.

- `SnapshotReceiver` (W01) already refuses to publish or ACK a tick that is not
  newer than the newest accepted one, so the host's `currentTick`, ACK and
  lifecycle callbacks cannot move backwards.
- `V2NetworkClient.processBufferedSnapshots` selected the last **arrival**; it
  now selects the highest **tick**. Regression fails without the fix with
  exactly the recorded counterexample (expected 200, received 100).
- `SnapshotBuffer.push` appended any tick; it now rejects one that is not newer
  and reports whether it was accepted, so `RemotePlayerRenderer.pushSnapshot`
  no longer applies roster or respawn bookkeeping from a stale snapshot either.
- **Session epoch:** `Game` creates a fresh `V2NetworkClient` per connect but
  lazily creates `RemotePlayerRenderer` once and reuses it for the process
  lifetime, so a reconnect inherited the previous session's interpolation
  buffer, jitter window, teams and death state — entity ids are only meaningful
  inside one session, so a reused id could be bracketed against whoever last
  held it. `SnapshotBuffer.reset()` and `RemotePlayerRenderer.resetSession()`
  now run at the connect boundary. Bodies need no explicit removal: `render()`
  drops every hitbox missing from the now-empty buffer on the next frame.

**Still open in W02:** T06 (one-shot event loss/duplication) and T08
(WebTransport cross-stream ordering) are untouched, and the projectile/event
state held in the `GameEvents` context is not yet part of the session reset.
The session-epoch path is source-reasoned and unit-tested; no browser reconnect
was exercised.

### W03 progress — 2026-09-14

N04 and N03 are implemented. Both were replay/step-accounting bugs: something
that should have been a function of *which* simulation step this is was instead
counted per call. Each regression was first run against unchanged production
and observed to fail with the recorded wrong value.

**N04 — the effect clock counts steps, not command identity.** `MovementInput`
now carries `simStep` alongside `sequence`, and the profile derives `simNowMs`
from it. The client supplies the command sequence, which is a valid step index
there: one command is one client step, and a replay re-simulates the same
command, so replays still recompute identical slide/walljump/ledge timelines.
The server cannot use the sequence — it repeats the last command when a client
starves it and drops commands when one floods it — so it supplies the server
tick, which advances once per physics step by construction.

Observed against the unfixed clock, in `FixedRatePhysics.test.ts`:

| Case | Effect clock advanced | Should have been |
| --- | --- | --- |
| 19 starved ticks repeating one command | **0ms**, while the body kept falling | 152ms |
| Sequence jumping 1 → 500 in one tick | **3992ms** | 8ms |
| 6 ticks draining a 12-command burst | 40ms | 48ms |

The command ACK is deliberately untouched: `input.sequence` still reports the
last command actually simulated, so reconciliation still replays the right set.

**N03 — knockback age is an anchor, not a counter.** The client held
`kbTickCounter`, incremented once per simulated step, so every reconciliation
aged the same impulse again (30 → 60 → 90) and eventually crossed the drag
delay the server had not reached. It now holds two step indices: `kbStartSeq`,
the step the impulse takes effect on, and `kbCancelSeq`, the step a landing
cancelled it on. Age is `step - kbStartSeq`, so a replay recomputes it.

- Expiry needs no latch — it is a pure function of the anchor. The anchor is
  therefore never cleared on expiry, which would make a replay of an earlier
  step skip an impulse that was live then.
- A landing is latched, because leaving the ground again does not revive the
  impulse. At reconciliation a latch recorded *after* the acked sequence is
  discarded: those steps are about to be re-simulated from the server's state,
  which may not put the player on the ground at all. A latch from an acked step
  is kept — the server has already agreed to it.
- **Parity, not just idempotence:** the client applied drag *after* movement and
  aged the impulse from 1; the server applies it *before* movement, reading the
  grounded state the tick starts from, and ages from 0. The client now matches
  on both counts. This changes knockback feel slightly — towards the
  authoritative behaviour, so it should reduce correction — and is worth a
  playtest of rocket jumps and landings specifically.

**N06 addendum.** Selecting the newest of one frame's arrivals (W02) did not
cover a stale datagram arriving a frame later; the standing probe caught it.
`V2NetworkClient` now tracks the newest tick it has reconciled against and
refuses anything not newer, so replay, ACK pruning and lift restore cannot run
for a stale snapshot. `applySnapshot`/`processBufferedSnapshots` now report
whether anything was applied.

**N05 — suppression is bounded, deliberately not removed.** The ledger's own
fix direction warns against removing a workaround that currently protects
visual stability before there are wall and ledge fixture tests, and the
suppression only exists because replay disagrees (T01). So the trigger
condition is untouched — `wallJumpState !== "none"` still includes *available*,
and that narrowing still needs fixtures — and what changed is that the skip can
no longer run forever:

- The skip branch returned *before* measuring anything, so it could not tell a
  sub-unit trace disagreement from a teleport. Divergence is now measured
  first, and the same value feeds the existing `preError` diagnostic.
- **Divergence bound (400 units).** Past this, the snapshot is a discontinuity
  and is adopted whatever the player's wall state says. Set far above ordinary
  prediction lead on purpose — a strafe-jumping player on a 300ms link is
  legitimately a few hundred units ahead of authority — so it catches an
  unpredicted teleport and nothing suppression is there to smooth.
- **Time bound (500ms of continuous suppression).** In milliseconds, not
  snapshots, because the ten-snapshot window means 160ms at 62.5Hz and about
  333ms at 30Hz. Well past the window suppression is meant to cover.
- Releasing clears the skip counters as well as taking the correction.
  Leaving them armed would suppress the very next snapshot, so the bound would
  have delayed one correction rather than ended the run. Eligibility that
  genuinely persists re-arms them on the next snapshot, which turns unbounded
  suppression into a **duty cycle**: at most 500ms suppressed between forced
  corrections. That is the honest description of this fix — not "suppression is
  correct now", but "suppression can no longer ignore authority indefinitely".
- `getDebugInfo()` now reports the capture list the ledger asked for: skip
  count, duration, maximum divergence while suppressed, and what released the
  run (`divergence`, `timeout` or `eligibility-ended`). A release also logs.

A control regression asserts a small correction inside the window is **still**
suppressed, and it keeps passing with both bounds disabled — so the tests prove
the limits were added without the workaround being quietly switched off.

### W04 progress — 2026-09-14

**N10 — queue compaction drops physics, not intent.** The six-entry input queue
discards the oldest commands when a client's frame hitch delivers a burst, which
is exactly what stops a flooding client banking physics time. But a weapon
switch rides only the *first* command of a burst, so the cap silently threw the
switch away and the player kept firing the old gun. Compaction now carries the
newest weapon request from the dropped commands onto the oldest surviving one.
It rides an existing command rather than adding one, so no extra physics step is
granted and the anti-speedhack invariant is untouched — the regression asserts
the processed sequences are still exactly 7-12. A newer explicit request still
wins, and a burst that asked for nothing still changes nothing.

**N08 — a suffix replay is replaced by an explicit resynchronisation.** Past the
32-command replay budget the client replayed the newest 32 from a server state
that precedes *all* the unacked commands, so it resumed at a position its own
history never passed through and its sequence-derived clocks ran ahead of the
steps that actually moved it. At the boundary that showed as free fall gaining
2.624 units with authority in perfect agreement.

A suffix cannot be made correct — the intermediate state it needs was never
kept. So the budget now triggers a defined resynchronisation: adopt authority,
discard the commands that can no longer be honoured, and predict forward from
the next one. The player loses input in that window, which is visible and
truthful, rather than being left somewhere neither side simulated.
`getDebugInfo()` counts resyncs.

**A test that the fix caught.** The N03 knockback regressions predicted 90
commands with none acked, which is past the new budget — so after the N08 change
they would have resynchronised, replayed nothing, and passed trivially. They now
ack down to 30 unacked and assert `resyncCount === 0`, so they keep proving what
they were written to prove. Both fixes were re-verified by injection afterwards:
the old knockback counter still diverges the position across replays, and the
old suffix replay still produces **exactly the recorded 4958.272**.

**Still open in W04:** T07 (three independent sequence counters) is untouched.

**Carried risks, not defects:**

- Client and server effect clocks now share a *rate* but not a *base* — the
  client counts commands, the server counts ticks. Every deadline is set and
  compared against the same clock, so this is sound, but any future code that
  compares one side's `simNowMs` to the other's would be wrong.
- The four KB drag constants are duplicated between `V2NetworkClient` and
  `FPSMovementSubsystem` under a "must match" comment. They do match today. A
  shared module would be the real fix; this pass did not take it.
- Re-sim bundles recorded before N04 encode the old frozen-clock timing and
  will not reconcile. No bundle is committed, and `buildReSimBundle` generates
  its golden checksums from `resimulate` at record time, so bundles made after
  the change verify normally. `server:tick` and `server:fuzz` are unaffected:
  they drive `CharacterPhysicsSystem`, not `FPSMovementSubsystem`.

## Assumptions and limits

- Active game is `src/games/fps`, multiplayer; baseline map `wdm2` where needed.
- WebSocket and WebTransport paths are audited separately; datagram loss is not
  assumed for WebSocket.
- No browser or WAN symptom reproduction yet; no claim that all networking has
  been audited or that any listed cause explains the reported random behavior.
- Prior research is context, not proof of current source behavior.
- W01, W02's ordering half and W03's N03/N04 are implemented, headless-validated
  and covered by permanent regressions. No browser/QUIC session, browser
  reconnect, custom-rate client session, or field-frequency measurement is
  claimed. N08/N10 are also implemented; N05 is bounded, not resolved;
  N09 and T07 are untouched. N12 and N14's cooldown are patched and T11 is
  implemented; broader T01 remains open. The knockback ordering change
  (W03) was playtested and reported solid; W04 has not been playtested. The N05 bounds have not been observed firing in a live
  session — no capture yet shows how often a real player holds wall eligibility. The raw probes use synthetic free-fall
  worlds, seeded eligibility and deliberate queue schedules; these isolate
  mechanisms and do not substitute for BSP gameplay reproductions.
