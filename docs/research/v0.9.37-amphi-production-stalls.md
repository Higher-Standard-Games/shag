# Amphi production match: intermittent frame-time stalls

Date: 2026-10-19. Branch: `v0.9.37-papercuts`.
Status: three renderer defects fixed and locally validated; the user's severe
live FPS drop has not been reproduced or conclusively attributed.

## Findings

1. Player color materials retained cloned texture wrappers after bodies were
   removed. Across the complete match, the control ended with **721** scene
   textures and the fixed replay with **349**. The difference is 372 wrappers,
   matching four wrappers per 93 recorded deaths. These wrappers share GPU pixel
   storage; this is not evidence of 372 additional pixel allocations.
2. Blade slash ribbons destroyed and rebuilt their mesh every swing frame.
   Babylon 9.17 releases a shader when its final drawing submesh is disposed,
   even if its material survives. Runtime attribution identified the same
   `slashTrailMat` program repeatedly compiled. Keeping its mesh/submesh alive
   reduced shader work without changing ribbon geometry.
3. Different Quake material plugin combinations reused incompatible shaders.
   An Amphi sprite had a **1,216-byte** material buffer but shared a program
   requiring **1,296 bytes**. WebGL rejected its draws. Distinct plugin identities
   and feature markers remove this cache collision. The real-GPU diagnostic
   captures zero invalid draws after the fix; the buffer-size warnings disappear.

These are confirmed defects, not proof they caused the original report. A short
combined-fix replay does **not** establish an overall FPS gain. Firefox combat
stalls and a separate Babylon clustered-proxy warning remain open.

## Repairs and evidence

### Player texture ownership

`PlayerModelManager` records texture wrappers introduced by each visibility
material clone, excluding the source's texture objects. Disposing that material
releases those owned wrappers. Source objects and surviving players retain their
ownership. This covers ordinary removal, ragdoll expiry and scene teardown
without forcing shared texture disposal.

The NullEngine regression simulates 100 respawns, checks the original texture
count after each disposal, and preserves another player's textures. It fails on
the original source and passes after repair.

The complete fixed replay reaches tick 90,250, all 42,375 frames and **zero
skipped frames**. After tick 15,000, textures stay within **330-370**, ending at
349 instead of 721. The lifetime runs overlap diagnostic work and brief test
execution, so their wall times are not an A/B performance benchmark.

### Blade draw ownership

The ribbon uses Babylon's original vertex generator and retains its existing
mesh and submesh as the paths grow. Vertex/index ranges and bounds are updated;
no sample cap or visual simplification is introduced. Buffer allocation and
ribbon-data generation remain possible follow-ups.

A 50-frame curved-ribbon regression checks positions, normals, UVs, indices and
bounds against fresh Babylon ribbons, while asserting mesh/submesh identity and
cleanup. It fails on the original source and passes after repair.

One runtime attribution interval identifies 166 of 182 new effects as
`slashTrailMat` / `slashTrail`; a longer later interval identifies 340 of them.
Observed full-soak shader compilations fall from 1,599 to 424 with the two
lifetime fixes. This is resource-work evidence, not a measured FPS gain.

### Quake plugin shader identity

The failing `bsp_sprite_53_49` / `bsp_sprite_mat_53_49` has Q3DistanceRamp only.
`bsp_tex_73` has Q3DistanceRamp plus Q3SoftParticle. Their actual submeshes share
one effect, containing `q3SoftView` and `q3SoftZ` even for the sprite without
that plugin. Its Scene buffer matches at 272 bytes; its Material buffer is
80 bytes short. The bounded diagnostic captures 12 repeated error-1282 draws.

Five custom plugins inherited `MaterialPluginBase.getClassName()`. They also
lacked persistent feature markers for all code/layout combinations. Each now
has its own class name and markers for distance ramps, soft particles, stage
color (including vertex RGB), environment mapping (including surround versus
reflection), and vertex lighting. The existing fog and baked-lighting plugins
already have distinct class names. Quality settings remain unchanged.

The regression constructs eight real Babylon plugin combinations with otherwise
identical settings. Released code collapses them into two cached effects;
repaired code produces eight. The released-code-plus-plugin-fix GPU diagnostic
captures **zero invalid draws**, no buffer-size warnings and no shader compile
errors. A separate clustered-proxy `glGetProgramiv` warning remains.

## Timing observations and limits

Same 35-second dense-plasma fixture, one warmup and one measured replay each:

| Local code | Wall p50 / p95 / p99, ms | Scene CPU p95, ms | GPU p95, ms | Measured shader compilations |
| --- | --- | --- | --- | --- |
| Released v0.9.36 | 7.60 / 9.10 / 16.83 | 6.80 | 6.46 | 61 |
| Branch control | 7.60 / 8.90 / 15.09 | 6.90 | 6.52 | 154 |
| Two lifetime fixes | 7.60 / 8.70 / 15.58 | 6.30 | 6.40 | 54 |
| All three fixes | 7.60 / 10.60 / 19.03 | 7.70 | 6.49 | 63 |

These exploratory single trials do not establish a statistically reliable speed
change. The final combined trial has worse tail/CPU values, so it must not be
advertised as faster. Repairing invalid draws also restores rendering work;
the old control is not a visually correct performance target. GPU samples are
asynchronous and cannot be assigned to individual impact events. The final
Brave run is workload-valid and has no UBO-size or shader compilation errors.

Timedemo's validity flag checks workload/profile coverage, not GPU correctness.
The branch control is workload-valid while issuing invalid draws. Browser
errors therefore remain a separate acceptance check.

Both Brave and Firefox load/render all five shipped maps for 90 frames each
with the combined fixes and zero polled GL errors: Amphi1, DM2, DM5, DM11 and
SND1. Brave records zero failed HTTP responses and no shader compile errors.

Firefox's 1080p combat compatibility replay completes without UBO-size or shader
compile errors, but **is workload-invalid**: a stall skips 121 recorded frames.
The worst measured interval is 1,445 ms near clip second 1.8. Both player bodies
are loaded, while the POV weapon is still loading. This does not attribute the
stall to that weapon or prove a GPU cause. Its timing results are not accepted
as a benchmark or a Firefox improvement claim.

## Remaining investigation

- Reproduce the user's severe drop during interactive Brave fullscreen play,
  with a client performance trace. A server demo cannot recover original packet
  arrivals, client frame timings or input events. No networking behavior changed.
- Attribute the remaining clustered-proxy `glGetProgramiv: Program object
  expected` warning. It is also recorded in
  `v0.9.30-qfusion-lighting-parity.md`; it is separate from the fixed UBO draw.
- Repeated dropped-plasma-barrel loads use a loose `/data/models/...` URL and
  fail to load the GLB in this packaged-data setup. Follow up on the barrel
  loader's PK3 resolution and failure caching; no model/media changes here.
- Effect warmup creates and disposes fixtures. Babylon's effect reference
  counting means compile-and-dispose is not proof of retained warm programs.
  Measure a bounded owner lifetime before proposing a retained shader cache;
  do not enable a global permanent cache as an unmeasured fix.
- Firefox cold combat/model stalls remain open. Static-map GPU checks do not
  certify smooth combat, and the invalid replay cannot support an FPS claim.
- Other GPUs, native Linux, WebGPU and production-bundle gameplay remain
  unverified by this investigation.
