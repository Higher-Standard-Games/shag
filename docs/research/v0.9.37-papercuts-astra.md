## Implementation follow-up

Implemented the three primary candidates. The parallel agent owns server/demo

[its investigation](v0.9.37-papercuts-claude.md); those files were not edited here.

### Package ownership

`PK3Loader.ensurePK3` / `ensurePK3FromUrl` share in-flight work and skip already
mounted sources. Filename and equivalent URL consumers converge; different
origins/paths/query revisions do not merge merely because basenames match.
Filename ensures also reuse explicitly ingested local archives. Failures release
pending entries. Unload and newer explicit loads invalidate late responses.
`loadPK3` / `loadPK3FromUrl` retain intentional refresh semantics and alphabetical
package override order is unchanged.

Migrated map dependency phases, model/config reads, player/ghost imports, ammo
icons, weapon setup, audio and cartoon-hit media. Removed the separate player,
model and Audio V2 package-promise maps. Entity-model dependency lookups strip the
local `/data/` URL prefix before asking the virtual filesystem for ownership.

Tests prove one fetch/parse for eight concurrent filename consumers plus an
equivalent URL consumer, no fetch for mounted reuse, deliberate refresh, revision
queries, search-path fallback, retry, local byte ingestion, unload during a
pending response, refresh racing an older response, and override ordering.
The real five-map Firefox run mounted the texture bank and weapon bank **once
each**, with no archive-loading errors. This is reuse within a page session;
no persistent browser cache or production cache-header policy was added.

### Map lifecycle

Loads run sequentially, with a newer request cancelling its predecessor. A
queued request superseded before starting returns a failure without emitting
loading events. Every started operation emits one completion. Scene disposal
and `disposeCurrentMap()` cancel active waits; disposal is serialized with new
loads. Temporary visibility listeners and readiness deadlines are released on
all terminal paths. Background recovery waits are cancellable, and map loads
can stop waiting for shared archive work without cancelling other consumers.

Partial-map failure invokes the existing map disposal path. Completion is owned
by the outer operation, removing the second success event. Overlay fade
scheduling clears its previous timer before installing another one.
Clearing a map also unsubscribes its pending loading-screen readiness check.

Fault-injection tests cover repeated archive failure and retry, null BSP,
material preparation exceptions, one completion on success, overlapping loads
with a late old operation, leaving during a hidden-tab wait, leaving during a
shared archive download, and all readiness timer outcomes.

## Recommendation

Pursue these three bounded changes, separately. The first offers the clearest
route to steady frame-time savings; the others address reproduced loading bugs
and unnecessary work. No percentage improvement in production FPS is established.

| Order | Work | Evidence | Expected benefit | Risk |
| --- | --- | --- | --- | --- |
| 1 | Validate and enable early mesh filtering for the first-person weapon camera | Actual Babylon evaluation: 1,001 readiness and world-matrix calls become 1 each in a synthetic scene; same active mesh and 36 indices | Less CPU work every rendered first-person frame, potentially especially useful in Firefox | Medium: renderer semantics and visual acceptance |
| 2 | Give package loading one shared in-flight/mounted ownership policy | Eight concurrent loads cause eight fetches; another load after mounting causes a ninth | Avoid repeated transfer/body reads, ZIP parsing and full index rebuilds; clearer progress; simpler callers | Medium: refresh, replacement and unload semantics |
| 3 | Make map loading release resources on every exit and emit one completion | Three injected archive failures leave three visibility listeners and `isLoadingMap=true`; success has two completion emit sites | Reliable retry/return-to-menu behavior and bounded listener/timer lifetimes | Medium: asynchronous lifecycle |

For an immediate correctness patch, do #3 first. For the next performance
experiment, do #1. Do not combine renderer changes with a networking change.

## 1. Stop evaluating world meshes for the weapon camera

### Verified mechanism

- `src/engine/rendering/WeaponCameraCandidates.ts` already implements the
  experiment. `r_weapon_candidates` defaults to **0** and is not persisted.
- `src/engine/weapon/WeaponViewManager.ts` installs it for its weapon camera.
- Installed Babylon source, `node_modules/@babylonjs/core/scene.pure.js`,
  `_evaluateActiveMeshes`, does `mesh.isReady()`, `computeWorldMatrix()` and LOD
  work **before** rejecting a mesh by camera layer. Freezing world matrices
  reduces matrix computation; it does not remove this evaluation path.
- The provider filters candidates by the active registered camera's layer. It
  preserves meshes with action managers and falls back for custom LOD selectors.
  It still scans candidate masks; this is not an O(1) candidate lookup.

Headless probe: one weapon-layer box plus 1,000 world-layer boxes, one weapon
camera, native `Scene.render()`, shader readiness awaited, off/on/off:

| Filter | `isReady` calls/frame | `computeWorldMatrix` calls/frame | Active meshes | Active indices |
| --- | ---: | ---: | --- | ---: |
| Off | 1,001 | 1,001 | `gun` | 36 |
| On | 1 | 1 | `gun` | 36 |
| Off again | 1,001 | 1,001 | `gun` | 36 |

These are method-call counts in NullEngine, **not GPU timings or pixel checks**.
The fixture deliberately isolates the second camera's wasted work; it does not
represent a measured production map mesh count or total-frame saving.

Prior evidence is consistent but insufficient to ship a default:
[v0.9.36 profiling](firefox_performance_v0.9.36.md) attributed about 3.956 ms/frame
in Firefox to inclusive active-mesh evaluation. That includes more than the
weapon camera, so it is not a recoverable budget estimate. The
[earlier experiment](firefox_performance.md) changed median time from 31 to 23 ms
in one valid repeat, but also improved freefly, outside this filter's intended
scope. That confounding improvement is why the old experiment is not proof.

### Smallest acceptable implementation

Retain the existing provider and ownership tests. First validate it in paused
real-map views and then the fixed combat fixture. If only Firefox has convincing
benefit/coverage, enable by default only for Firefox WebGL. There is no reason
to remove outlines, change resolution, change player animation cadence or alter
network/input timing to test this optimization.

Acceptance:

1. Compare off/on/off active meshes, indices and pixels for DM2, DM5, DM11, S&D
   and Amphi. Include animated weapons, pickups, transparency, sky portals,
   death/spectator transitions, demo playback, map changes and late imports.
2. Fresh-session alternating A/B runs in Firefox and Chromium; identical
   resolution, fixture, camera route and settings. Record frame median/p95/p99
   and weapon-camera CPU time. Reject playback runs with skipped events/frames
   as performance scores. Keep function-wrapper attribution separate from FPS.
3. Existing `WeaponCameraCandidates.test.ts` checks layers, action managers,
   LOD fallback, changing active sets and shared lease cleanup. It passes, but
   does not replace real GPU visual checks.
4. Run all renderer gates before changing the default. Keep the cvar available
   for diagnostics and straightforward rollback.

## 2. Centralize package reuse before adding another persistent cache

### Reproduced within a page session

`src/engine/loader/pk3/PK3Loader.ts`:

- `loadPK3` and `loadPK3FromUrl` fetch and parse on every call. Neither consults
  mounted packages or a loader-owned in-flight promise map.
- `processPK3` replaces the package entry and runs `rebuildFileIndex`, scanning
  all mounted package entries again. One final map entry does not mean only
  one download/parse happened.

A valid tiny ZIP fixture, delayed successful fetch stub, and a fresh transient
loader produced:

```text
Promise.all(8 calls to loadPK3("probe.pk3")) -> 8 fetch calls
loadPK3("probe.pk3") after those finish     -> 1 additional fetch
Final mounted package count                -> 1
```

This proves duplicate application requests and parsing. A real browser may
serve a request from HTTP cache or coalesce network work; the count is not proof
that eight full archive bodies crossed the network.

Concrete callers:

- `src/games/fps/world/pickups/AmmoIconTexture.ts` always calls `loadPK3(owner)`
  before resolving an icon, even if the package is mounted. Procedural icon
  creation and the authored pickup path both use it. The local gfx archive is
  only **43,606 bytes**; this case alone is not a 100 MB texture-download bug.
- `src/engine/loader/model/ModelAsset.ts` and
  `src/engine/animation/PlayerModelAssets.ts` each have their own weak-map of
  pending package loads. `AudioV2Sfx` has another package-promise map. They solve
  similar problems independently and cannot coordinate across consumers.
- `MapLoader.loadBspMap` captures `loadedPk3s` once. Its map/texture phases do
  not add their new entries; model/weapon phases do. This is inconsistent when
  an archive serves multiple dependency roles. **Do not claim that every
  texture pack is downloaded twice:** the sky resolver independently takes a
  fresh mounted-package snapshot and excludes already mounted owners.

A read-only scan using the real BSP parser and dependency methods found
`washoi_textures.pk3` as the texture bank for all five local production maps.
The model-dependency method returned no indexed owners and logged misses for
URL-prefixed GLB paths such as `/data/models/weapons/rlauncher/rlauncher.glb`;
the later explicit weapon-bank load and indexed model loader provide separate
paths. Treat that as dependency-resolution cleanup, not proof that weapon models
are missing. This scan did **not** demonstrate repeated texture-bank downloads.

### Why this can matter beyond small icons

Local archive sizes, not estimates:

| Archive | Bytes | Decimal MB |
| --- | ---: | ---: |
| `washoi_textures.pk3` | 122,191,156 | 122.19 |
| `washoi_weapons.pk3` | 85,923,291 | 85.92 |
| `washoi_player_model.pk3` | 4,259,832 | 4.26 |

`AssetRequest.readAssetBuffer` retains chunks and then copies into one contiguous
buffer. During assembly, roughly two archive-sized byte payloads can coexist,
before considering ZIP objects, extracted assets or browser-internal buffers.
This is a source-derived allocation observation, not measured peak heap. Avoiding
duplicate loads is preferable to merely making that repeated work faster.

### Proposed contract

Introduce a loader-owned **ensure-mounted** operation for ordinary consumers.
Keep intentional reload/refresh explicit rather than silently changing all
existing `loadPK3` calls to permanent no-ops.

- Concurrent requests for the same resolved source/revision share a promise;
  already-mounted requests return without reading bytes again.
- Normalize package identity consistently across filename and full-URL callers.
  Do not merge unrelated URLs merely because their basenames match.
- Failed requests release the pending entry so retry works. Unload/refresh uses
  a generation or equivalent ownership check so late work cannot remount stale
  contents. Honor explicit editor rebuilds and replacement package precedence.
- Keep mirror validation, deadlines, retry rules and index override ordering.
  Remove caller-specific promise maps only after migrating their semantics.
- Normalize virtual model paths at the lookup boundary using the existing
  `ModelAsset` behavior as the reference; distinguish custom external URLs.

Acceptance: one request/parse/index rebuild for concurrent ensures; zero for a
mounted ensure; a new request for explicit refresh; failure followed by retry;
unload during a pending request; same basename from different sources; package
override order; editor Playtest refresh; map cycling and ammo icons. Then capture
real cold/warm session package counts and loading wall time in both browsers.

### Browser-cache follow-up, kept separate

The loader uses ordinary fetch caching and in-memory archives, not a dedicated
persistent PK3 cache. Local Vite `liveGameData` sends `Cache-Control: no-cache`
with no ETag/Last-Modified conditional-response handling. Adding validators and
304 handling is a worthwhile local developer-experience fix, preserving immediate
recognition of edited assets. It is not a production rendering optimization.

`PackageDownload.response` labels every successful body read `Downloading`,
including HTTP cache responses. Prefer neutral loading/reading language unless
cache/network origin is known; do not infer actual network speed from fast
cached-body consumption. Persistent storage would need its own eviction and
revision policy. Production response headers were not investigated in this task.

## 3. Make map loading a bounded operation, including failures

### Confirmed failure cleanup gap

`MapLoader.loadBspMap` sets `isLoadingMap=true` and adds a document
`visibilitychange` listener before loading the archive. It clears the flag and
removes the listener near the successful end, without an encompassing `finally`.
The outer `loadMap` catches failures and returns a failure result; it does not
perform that cleanup. A missing BSP can also return before cleanup.

Headless fault injection used the real public `loadMap` method with a throwing
archive boundary and a document-listener ledger:

| Failed attempt | Retained visibility listeners | `isLoadingMap` after return |
| --- | ---: | --- |
| 1 | 1 | true |
| 2 | 2 | true |
| 3 | 3 | true |

The probe supplies dependencies rather than loading a real failed network map.
It confirms the cleanup defect; it does not establish a production memory size
or explain all historical tab-switch/brightness reports.

Related source findings to address in the same lifecycle patch:

- Successful BSP loads emit `LOADING_EVENTS.COMPLETE` inside `loadBspMap`, then
  again in `loadMap` (the inner duration is zero). Give completion one owner.
- `MapLoadingOverlay.onLoadingComplete` ignores idle/fading states, but not
  `completing`; repeated completion can call `scheduleFadeOut` again and replace
  its stored timer handle. This is a reachable duplicate-timer risk from source,
  not a reproduced visible flicker.
- The post-background visibility wait has no cancellation tied to abandoning
  the load. The readiness `Promise.race` also leaves its timeout alive when
  readiness wins. Clean up owned listeners/timers without pretending that an
  arbitrary Promise becomes cancelled by losing a race.

### Proposed patch boundary

Use a per-load ownership token and `try/finally` around temporary listeners and
flags. Let the outer load operation emit one terminal result with its real
duration. Prevent abandoned asynchronous work from completing a newer load or
modifying a disposed scene. Release only resources owned by that load; do not
clear shared package/model caches as a blanket failure response.

Acceptance: archive failure, null BSP, geometry/material exception, success,
hidden-tab wait cancelled by leaving, successful retry, and overlapping loads
where the older operation finishes last. Assert listener/timer counts return to
baseline, loading state resets, exactly one completion per operation, and no old
completion dismisses the next map's loading overlay. Follow with normal map
cycling and all loader/renderer regressions.

## Networking: measure first, preserve the v0.9.36 behavior

The recent upload-queue/stall work is already present. See
[v0.9.36 network investigation](v0.9.36-netcode-jitter-round2.md). Do not repeat
it as a new finding or adjust prediction/tick policy while evaluating these three
changes.

One bounded investigation remains useful: **server outbound queue age under a
slow reader**. `WebSocketClientConnection.canSend` permits queued output until
the next message would exceed 8 MiB, then terminates that connection. This bounds
memory, but does not itself enforce a latency target below that threshold.
This is not evidence that production clients are hitting it.

First measure per-client queued bytes, ACK lag, encoded bytes/s, queue drain
after a controlled downstream stall, and healthy-client tick/latency behavior.
Distinguish delayed network delivery from a browser main-thread pause. Existing
tests already cover saturated-client isolation and exact acknowledged snapshot
baselines; both suites passed here.

Do **not** implement “drop old snapshots” at the transport layer: the WebSocket
path shares a reliable ordered stream with other messages, and snapshots carry
one-shot events as well as state. Skipping application sends requires explicit
event delivery and baseline/ACK semantics. Any remedy needs a separate measured
proposal, lossy/delayed/resume convergence tests, unchanged healthy-client golden
bytes where applicable, admission/privacy checks, and the full networking gates.
No transport replacement, protocol change or new rate cap is recommended yet.

## Secondary candidate, after the three above

`Q3SoftParticleDepth.prepare` scans scene meshes for a visible soft-particle
material and, when needed, renders a separate depth pass. Its custom list uses
`slice(...).filter(...)` each pass. Reusing a scratch list is a small allocation
cleanup; it does not remove the main cost of rendering depth. Previous profiling
attributed about 1.891 ms/frame in Firefox to this pass, inclusively.

Investigate compatible depth reuse or tighter contributor selection only after
the higher-confidence candidate filter. Water/outline depth encodings and
camera ownership differ. Validate alpha-tested edges, animated actors, camera
switches, portals and particle intersections; disabling authored fading is not
an equivalent optimization. No new depth benchmark was run here.
