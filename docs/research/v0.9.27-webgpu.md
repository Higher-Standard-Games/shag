# v0.9.27: WebGPU parity and rendering performance

**Investigated:** 2026-10-09. **Status:** source/evidence audit; implementation proposals, not measured speedups.

## Conclusions

We are substantially closer to WebGL2 parity than the September research suggests, but cannot yet call WebGPU fully accepted. Clustered lighting and the normal Standard/PBR light budgets are restored on capable WebGPU engines. Paired GPU fixture reports exist for multiple clusters and environment lighting. Weather still uses CPU simulation on WebGPU, normal startup still forces WebGL unless a URL override is supplied, and a complete gameplay/effects/lifecycle parity run is not recorded in the evidence inspected here.

For crowded FFA, the strongest next experiments work on **both renderers**: conservative actor frustum culling, measuring and reducing outline passes, geometry LOD, and better animation scheduling. Changing the graphics API alone leaves the JavaScript animation/controller work and model geometry in place. WebGPU bundle reuse is a separate, worthwhile submission experiment after the shared model costs are understood.

The installed Vanguard body has **27,843 vertices, 11,376 triangles, two indexed primitives and a 65-joint rig**. With outlines enabled, Babylon's opaque/depth-writing outline path can submit each primitive three times in the main view. Players in PVS currently bypass ordinary mesh frustum rejection. These are source/asset observations; none establishes the dominant bottleneck on the user's GPU without a controlled capture.

**Answer to “are we good already?”:** fixture-level lighting parity has concrete positive evidence. Full supported-gameplay parity and the performance comparison remain open. The concrete retained backend differences are weather acceleration, the unsupported-capability lighting fallback, normal renderer selection, and WebGPU shader hot-swapping being disabled for safe layout transitions. The last can skip draws during a variant compile; it should be exercised under combat rather than removed casually.

Q3 parsing limitations such as skipped `deformVertexes wave/bulge/move` are **shared content-compatibility limitations**, not WebGPU/WebGL2 parity gaps. Likewise, neither an engine-init success nor the absence of `window.rendererRuntimeReport` proves all shader families rendered successfully.

### Weather: the installed dependency already has the missing machinery

Babylon 9.17's `Particles/gpuParticleSystem.pure.js` checks `supportComputeShaders` and constructs a registered `BABYLON.ComputeShaderParticleSystem`; otherwise it uses the WebGL2 implementation. `Particles/computeShaderParticleSystem.js` is present locally. SHAG's current WebGPU exclusion is therefore more conservative than the installed capability.

A bounded experiment should import/register the compute platform, check the **active engine's** caps, keep a CPU fallback, and compare rain/snow counts, wind/emitter movement, lifecycle and frame time. Do not blindly change the boolean: modular registration and feature compatibility must be verified. The current public [GPU-particles guide](https://doc.babylonjs.com/features/featuresDeepDive/particles/particle_system/gpu_particles/) still describes the older WebGL2-only boundary; installed version-specific source is the stronger evidence for this proposal.

## What crowded player models cost

### Asset inventory, measured from the installed GLB

Audited `public/games/default/animations/vanguard.glb` directly, including accessors, index buffers, skins and embedded PNG headers. This loose asset is local content, not a guaranteed tracked artifact.

SHA-256: `423cbe9717c91509d61d9987f1e015ad3637e0fe071aada6045eda2f1054ae73`; file size **4,914,628 bytes**.

| Primitive | Vertices | Indices | Triangles | Material |
| --- | ---: | ---: | ---: | --- |
| `vanguard_visor` | 386 | 570 | 190 | `Vanguard_VisorMat` |
| `vanguard_Mesh` | 27,457 | 33,558 | 11,186 | `VanguardBodyMat` |
| Total per body | **27,843** | **34,128** | **11,376** | Two opaque, single-sided PBR materials with base-colour and normal maps |

- Three skin records each describe the same 65 joint indices; two nodes reference skins. [PlayerModelManager.createInstance](../../src/engine/animation/PlayerModelManager.ts) already verifies equivalent cloned rigs, rebinds meshes to one skeleton and disposes redundant skeletons. Do not propose that same repair again.
- Both primitives have POSITION, NORMAL, TANGENT, TEXCOORD_0/1, JOINTS_0 and WEIGHTS_0; no morph targets or second weight/joint set were found. Rendering still combines CPU pose evaluation/matrix preparation with GPU vertex skinning.
- Every indexed vertex is used; no index-degenerate triangles were found. The body has 5,781 unique position byte-tuples but **27,447 unique complete attribute tuples** out of 27,457. Only ten vertices are exact full-attribute duplicates. Welding positions alone would damage seams/normals/UVs/weights; a lossless full-attribute weld is not a meaningful geometry reduction here.
- Four image descriptors alias **two bufferViews**, containing two distinct 1024×1024 PNG payloads. This is not four copies in the GLB. Whether duplicate descriptors produce distinct runtime GPU textures needs inspection of Babylon InternalTexture identity. At RGBA8 with a full mip chain, two distinct textures would be about **10.7 MiB** before other resources; that is a format-based estimate, not a VRAM measurement or per-player allocation.
- Shared cloned geometry/textures save storage, not per-player draw/skin work. Inspect runtime sharing before assuming memory grows by a whole GLB for each player.

For **10 rendered bodies**, matching the user's stated maximum realistic match size of 5v5, a single body pass represents 278,430 vertices and 113,760 triangles. These are geometry inventory multiples, not measured vertex-shader invocations: indexing/cache behavior and each extra pass affect actual work. A freefly observer can see all ten bodies; player POV generally excludes the viewer's own body. Weapons, ragdolls and effects are additional.

### Existing improvements that are already present

The [B12 research/status](../../src/games/fps/docs/research/v0.9.26-remote-renderer.md) and current [RemotePlayerRenderer](../../src/games/fps/client/RemotePlayerRenderer.ts) show:

- root-motion nodes and body-part arrays cached rather than rediscovered every frame;
- frame-level cvar/style reads, reused sampling results and bracketing snapshots;
- PVS visibility decided before switching body/weapon state;
- three body probes for conservative doorway/stair PVS visibility;
- off-PVS bodies disabled and locomotion groups paused;
- animation paused below a 24-pixel projected-height approximation;
- weapon visibility restored after PVS re-entry and weapon loader leftovers released with the weapon;
- independent player skeletons with proven ownership and redundant skins collapsed.

These improvements have CPU regression coverage. They do not include a current FFA GPU benchmark. Older descriptions of full per-frame root-node scans, duplicate skeletons surviving per player, repeated PVS on/off walks or unbounded remote weapon-root leaks are not the present baseline.

## Shared-renderer performance priorities

### 1. Measure actor visibility and pass costs before choosing the fix

Use the existing `perf capture 10` command, supplemented by scoped timers/counters in a diagnostic experiment. Separate connected/alive actors, PVS-visible actors, camera-visible actors, animation-active actors, body/weapon primitives and actor draws by pass. The existing report only labels backend/map/KTX2 and aggregates scene work; it does not distinguish these groups.

The important timing distinction is **CPU pose evaluation versus GPU skinning versus submission**. If offscreen actors dominate CPU animation and draws, culling can address both. If a packed on-screen crowd is slow, geometry/outline/animation budgets remain necessary. If reducing render resolution helps much more than hiding bodies, investigate pixel/pass cost first.

This first experiment should preserve the normal model path and compare outline off/on and ordinary/all-on-screen camera poses. It supplies the evidence for the following order; no FPS gain is promised in advance.

### 2. Add conservative actor frustum bounds

Keep the PVS test, then reject actors outside the current world's frustum using an actor-level conservative sphere/AABB that follows network position, standing/crouched/swimming poses and weapon reach. Precompute clip envelopes or use a deliberately padded hull; account for crouch offsets, jumps and hand attachments. Do not simply remove `alwaysSelectAsActiveMesh` and reuse the known-unreliable imported bounds.

Keep pose scheduling and visibility separate. Main-view culling must not globally disable a body required by a water mirror, shadow or another camera. Water actor reflection already builds its own view/list; integrate pass-specific eligibility, and test local reflection-only bodies. Gameplay, snapshots, hitboxes, audio and effects continue independently of visual eligibility.

Start with a cheap CPU hull test. Babylon's installed `Culling/Helper/boundingInfoHelper.js` supports compute on WebGPU and transform feedback on WebGL2, but involves result fetching and is not automatically cheaper. Avoid per-frame vertex scans or synchronous GPU readback for every player. The official [skeleton guide](https://doc.babylonjs.com/features/featuresDeepDive/mesh/bonesSkeletons) describes these alternatives; the fixed-hull proposal is our inference for these small player rigs.

**Acceptance:** no popping at doorways/screen edges, crouch/slide/swim and weapons; spectator/demo camera switches and reflected actors remain correct. Off-camera actor draw and locomotion counts decrease, with measured p95 CPU/GPU benefit.

### 3. Treat outline cost as a first-class actor budget

First capture `cl_player_outline 0` versus `1` while keeping tint/fullbright and all other settings fixed. Turning the outline off is a diagnostic/quality tradeoff, not a parity fix or a proposed silent default change.

If outlines explain a material share of crowded-frame cost, prototype a cheaper outline proxy or a lower-detail mesh used only for the outline, retaining close-range silhouette/readability. A screen-space actor-ID outline is a larger alternative: it still needs mask/depth work and must preserve actor colours, occlusion and first-person exclusions. Existing cel outlines detect different scene edges and are not an appearance-equivalent replacement.

Check total draws, actor vertex cost and overlapping-crowd clarity. Ragdoll, quad/powerup and accessibility outline behavior must remain explicit in the quality policy.

### 4. Add actual geometry LOD and audit the source export

Build lower-detail player meshes with the same rig and material contract, selected by projected size with hysteresis. Begin with two reduced tiers; choose vertex/triangle targets from captures and silhouette checks, not a universal triangle budget. Keep near/spectated actors at full quality; preserve weapon sockets and animation mapping across transitions. Bone reduction is separate work because the current manager verifies the source rig and channel ownership.

Try index/cache/fetch optimization and texture/image deduplication on a **copy** of the asset before simplification. Only ten complete vertex records are duplicates, so ordinary welding alone will not solve this asset. Reducing unnecessary exported UV/tangent data requires a material audit; position-only merging is unsafe.

`npm run tools:optimize` is verified in `package.json` and invokes glTF Transform with WebP textures and meshopt compression. Those primarily change loading/storage; meshopt compression is not a runtime draw-call reducer, and WebP is not GPU block compression. Do not assume `npm run tools:textures` compresses the embedded player PNGs: [convert-ktx2.js](../../scripts/convert-ktx2.js) builds a PK3-sidecar texture cache. A GLB KTX2/Basis path needs its own conversion/load validation for colour/normal maps and backend format fallbacks.

**Acceptance:** lower submitted body vertices/indices at medium/far distance, stable transitions and hand weapons, no visible lost silhouettes or corrupt normals, correct animated poses on both backends. Measure memory/loading separately from frame time.

### 5. Improve animation scheduling without reducing movement updates

Keep position/yaw interpolation at render cadence. Make near readable actors fully animated; test a lower pose-update cadence for medium actors and paused/unseen actors, with hysteresis. Suggested 30/60 Hz tiers are experiments, not accepted defaults. Maintain elapsed clip phase, backward playback, swim/climb, one-shots and demo time scaling; do not change playback speed merely to update less often.

Pausing an AnimationGroup does not itself implement sampling at an arbitrary frequency. A scheduler must avoid Babylon's ordinary per-frame track evaluation between scheduled samples, and advance/sample phase correctly. Include the separately owned one-shot groups and ensure re-entry does not show bind-pose or jump in motion.

After tracing scoped CPU costs, skip redundant static scale/rotation/visibility writes or defer cosmetic weapon acquisition for invisible actors while preserving their latest desired state. Current B12 caches already removed the large repeated hierarchy/allocation work; optimizing that again would misstate the baseline.

### 6. Crowd animation/instancing is a later architectural option

The name `createInstance` in PlayerModelManager does not mean hardware instancing: it calls `instantiateModelsToScene(..., false, { doNotInstantiate: true })` and builds independent skeletons/retargeted playback. The generic [InstancedMeshManager](../../src/engine/rendering/InstancedMeshManager.ts) is useful for repeated rigid meshes, but cannot give each ordinary skinned instance a different animation pose automatically.

If captures show CPU pose/submission still dominating at the required player count, prototype a medium/far crowd path using Babylon's `BakedVertexAnimationManager`/`VertexAnimationBaker` or a custom bone-palette atlas with instance clip/phase/tint. The installed baker stores **bone matrices per frame**, not an entire copy of every vertex position. With 65 bones plus the identity matrix, 1,000 frames of float32 matrices are approximately **4.0 MiB**, before texture packing and other data; frame count is illustrative, not our measured clip corpus.

This moves pose work and can support batched draws on both APIs, but still skins vertices and needs clip-transition, per-actor colour/powerup, weapon socket and ragdoll handling. The current glTF clips target linked TransformNodes; verify baking produces the actual current pose rather than assuming a skeleton-only example transfers directly. Keep the existing path for nearby actors and ragdolls during a spike.

### WebGPU-specific submission experiment

SHAG currently makes no application assignment to `compatibilityMode` or `snapshotRendering` in the source inspected. Installed `abstractEngine.pure.js` initializes compatibility mode to true. Our factory therefore leaves WebGPU on Babylon's compatibility path.

Prototype **non-compatibility mode** behind a new opt-in setting, with fallback to the current path. It caches per-submesh/context render bundles and primarily addresses JavaScript submission, not animation-track evaluation or fewer skinning vertices. The existing perf report already exposes created/reused bundle counts. After warmup, seek stable reuse and improved p95 CPU time; if bundles rebuild continuously, the experiment can lose performance. [Babylon NCM documentation](https://doc.babylonjs.com/setup/support/webGPU/webGPUOptimization/webGPUNonCompatibilityMode/)

Do not undermine this experiment by indiscriminately sharing materials: the official NCM guidance warns about sharing a material across different skeletons. Current per-actor material clones help separate those bindings. Uniform values can vary without changing the material object; render-state/sample-count changes may need `resetDrawCache`. Check camera/RTT pass identities, outlines, mirrors, alpha, live quality changes and dynamic vertex uploads. Occlusion queries and `separateCullingPass` are documented constraints, so audit them before combining future experiments. Existing thin-instance weapon effects update buffers with `thinInstanceBufferUpdated`, a useful reuse pattern.

**Snapshot rendering is not the first FFA experiment.** It replays a recorded draw list; PVS changes, spawning/despawning, weapon switches, particles and multiple captures require correct invalidation and updates. Babylon's helper supports some animated cases, so “animation is impossible” would be inaccurate. Its value here is unproven, and repeated rerecording or disabling culling can erase the benefit. Consider it later for stable menu/background scenes or a deliberately isolated static path. [Babylon snapshot documentation](https://github.com/BabylonJS/Documentation/blob/master/content/setup/support/webGPU/webGPUOptimization/webGPUSnapshotRendering.md)

Compute-driven crowd culling/indirect submission is another later WebGPU option, after the shared CPU-culling/LOD design exists. It requires batchable actor data and pass visibility; introducing it before understanding independent skeleton/weapon/material behavior is a much larger change than the present optimization targets.

## Reproducible performance and parity plan

### Capture protocol

1. Run headless checks first. Start the app with `npm run dev`, then use `?renderer=webgl2` and `?renderer=webgpu`. Record the **actual** backend and fallback reason. A requested WebGPU session that fell back is not a WebGPU result.
2. Use the same recorded match/camera path on both backends where possible. Use ten-player FFA for the first scripted-camera rendering benchmark; ten is the player-count budget drawn from a realistic 5v5 match, not a requirement that this fixture use teams. Verify `demo:record` options in the headless guide; e.g. `npm run demo:record -- --map wdm2 --gametype ffa --bots 10 --seconds 60` is a proposed fixture creation command, not a benchmark run made here. Record the output bundle and asset/build identity. Headless bot creation records simulation, not GPU rendering.
3. Capture 0/2/5/10 **rendered bodies** in controlled cases, separating connected count from bodies actually visible. Include all-on-screen crowd, same-PVS actors behind the camera, actors in other rooms, camera motion, sustained combat, deaths and water. A bot count is not automatically a visible-body count. Record model/weapon choices, map, render dimensions, FOV, adapter/browser, power mode, cvars (`render export` plus player-style cvars), and active passes.

### Limits of `perf capture`

[RendererPerformanceCapture](../../src/engine/rendering/RendererPerformanceCapture.ts) uses Babylon Scene/EngineInstrumentation, samples on `onAfterRender`, and formats percentiles. It is a useful starting point, with these interpretation limits:

- `frameTimeMs` is Babylon scene-frame work, not necessarily the wall time between presented frames or all work outside `scene.render`. `cpuRenderMs` covers the rendering interval and is not a dedicated remote-model timer. Add a wall-frame metric and use a browser CPU profile/scoped model timer for attribution.
- The GPU counter can be unavailable or delayed/repeated between fresh query results. Current collection takes any positive `current` value each scene frame without a freshness check. Do not turn unavailable timing into zero or assume one independent GPU sample per CPU sample.
- Active meshes and `getActiveIndices()/3` are not a complete actor/pass/vertex-invocation census; mesh outline/depth/mirror work needs explicit attribution. Scene counters should not be added together as if independent CPU/GPU times cannot overlap.
- WebGPU bundle counters are `countersLastFrame`, sampled after scene render. Verify alignment with engine frame boundaries before interpreting totals as exact for this capture. Zero created/reused counters in compatibility mode do not prove perfect caching.
- It records no GPU-memory measurement or adapter identity. `backend` labels every non-WebGPU engine `webgl2`; this utility alone cannot distinguish NullEngine or a WebGL1 fallback. Use factory/QA actual-backend diagnostics.
- Existing tests verify formatting and percentiles, not hardware timing correctness. Instrumentation itself has overhead; record an uncaptured control.

### Clock design: two different questions, two labelled modes

**Mode 1 — real-time replay, implement first.** Play the frozen interval at 1× with the camera sampled from the same fractional demo playhead. Faster renderers display more samples of the same time interval; actors and camera have the same intended state at each recorded time. Measure frame pacing and CPU/GPU work. Use time bins/named phases to compare matching parts of the route rather than assuming sample #100 occurs at the same game time on both runs.

Count delivered/skipped demo frames and transient events. A stall that causes presentation skipping is a measured failure symptom; flag that repetition as workload-incomplete for strict A/B ranking, retain its stall metrics, and rerun. Do not silently drop that repetition from the report or call it a speedup because less combat was drawn. Loading/readiness stalls should be excluded by preparation, not concealed by clamping the measured wall-frame interval.

**Mode 2 — fixed-work timedemo, implement after clock auditing.** Advance by a fixed logical step per rendered sample, regardless of wall time, and render a fixed number of samples. For example, a 45-second interval at 60 logical samples/second is 2,700 renders of the same intended scene trajectory. Camera, demo state, skeletal phase, event delivery and effect lifetime must follow that logical clock. Do not implement this by `seekToTick` every frame: seeking suppresses/rebuilds presentation and clears transient state, which produces a different workload.

This second mode measures cost for fixed work; its animation speed in wall time is not a gameplay pacing result. Babylon animation/particle deltas, asynchronous assets, random effects, wall-clock muzzle effects and other presentation timers need an explicit strategy before claiming determinism. Existing DemoService presentation clocks help, but some effects still use `performance.now` or random sources. Seed applicable cosmetic randomness locally or mark those channels nondeterministic; do not globally monkey-patch browser clocks/RNG. Start with a controlled actor fixture if whole-combat clock ownership is not ready.

Both modes may remain refresh-limited in an ordinary browser. `requestAnimationFrame` generally follows display refresh and is commonly paused in background tabs. Equal 60 FPS results on a 60 Hz display do not establish equal rendering capacity; compare CPU/GPU costs and available headroom and label saturation. Fixed logical stepping does not remove display pacing. An uncapped/offscreen throughput mode would need its own queue/backpressure design and separate interpretation. [MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

### Runner lifecycle and frame order

Proposed session lifecycle:

```text
validate fixture/settings/backend
  -> load map + demo + actor/weapon assets
  -> untimed route rehearsal + shader readiness
  -> reset presentation, replay untimed pre-roll
  -> measure the exact interval
  -> finish pending timing samples outside measured work
  -> save report, stop, dispose/restore
```

- Require the requested renderer to be the actual renderer. WebGPU fallback, NullEngine, invalid content/hash, missing expected bodies or runtime validation/device errors produces a failed benchmark report; retain diagnostics. Do not score a black or incomplete scene.
- Use an explicit temporary render profile including actor outlines, PVS, material features, water/post settings, FOV and render dimensions. Snapshot/restore user settings and do not save benchmark quality overrides to their normal config. Precompute profiles outside measurement; actual render dimensions must match the requested preset.
- Wait for the expected models, weapons, textures and shader effects to settle with bounded deadlines. A scene-level readiness signal alone may precede later asynchronous actor/weapon acquisition. Capture readiness failures; do not proceed with invisible placeholders. Warm the whole selected route once and label the result **warm**. A separate cold-load/first-use test is valuable but must not mix with the warmed score.
- Reset logical state/effects, then replay an untimed pre-roll into the selected interval to reconstruct active projectiles/one-shots. Pre-roll must cover audited effect lifetimes or begin from recording start. A seek directly to the measurement start cannot reconstruct every transient effect. Clear warmup corpses/projectiles and restore clock/RNG state deliberately; avoid accumulated leftovers across repetitions.
- In benchmark mode, order each update as: advance benchmark/demo clock and deliver snapshots/events; apply camera pose/FOV and refresh its matrices; update remote models/effects; run PVS/scene evaluation and `scene.render`; collect counters/timing. Integrate through existing composition hooks and ensure the normal DemoService RAF is not also ticking. Avoid camera/input/controller updates overwriting the route. No mouse/pointer lock is required; an abort control remains available.
- Runs are bounded and abortable. Tab becoming hidden, viewport/quality/backend changes, user intervention or device loss invalidates the repetition with a reason. Preserve slow frames; visibility changes are an environmental interruption, not a low-FPS data point.
- Dispose observers/timers/export resources and release benchmark-owned scene/presentation state. Restore prior camera/settings on completion/cancel/failure. Do not resume a live multiplayer session automatically after its teardown.

`timedemo report/export` now includes raw `samples[].bundles` and aggregated
`summary.bundles` / `phases[<name>].bundles` under the existing schema 1. Metrics:
created/reused bundle totals, counts per sampled frame, weighted creation share,
frames with any creation and complete counter coverage. Creation share means
`sum(created) / (sum(created) + sum(reused))`; frames-with-creation means the fraction
of sampled frames whose creation count is nonzero. These are not GPU-time shares,
and raw totals alone should not be compared across different rendered frame counts.

Installed Babylon 9.17's `WebGPUEngine.endFrame()` copies its public
`countersLastFrame` totals and only then calls the base engine, which notifies
`onEndFrameObservable`. At scene `onAfterRender`, those totals still describe the
preceding engine frame. Timedemo therefore holds the just-rendered measured sample
until engine end-of-frame, then assigns a copied counter pair to that sample's
original phase. This prevents stale observations and boundary misattribution.
Warmup/pre-roll and the first frame outside measurement do not enter these totals.

Collection applies only to actual WebGPU non-compatibility mode. WebGL2 and normal
WebGPU samples keep `bundles: null` (not applicable). Missing, negative, fractional
or nonfinite NCM counter values stay null and invalidate coverage; genuine zeros
remain zeros. Rendering another measured scene before engine end-of-frame fails
explicitly because whole-frame totals cannot be assigned to a single camera phase.
End-of-frame observers are removed on success, timeout, abort and other failures.
Totals include all enabled passes in that engine frame, including the POV weapon,
and cannot yet identify which particular body/material/particle rebuilt a bundle.

### WG27-6: WebGPU non-compatibility mode (render bundles)

What changed:

- **Opt-in:** `?renderer=webgpu&ncm=1` for one session, the same model as `?renderer=`. ### WG27-1: conservative actor frustum culling

What changed:

- [PlayerModelManager](../../src/engine/animation/PlayerModelManager.ts): `PLAYER_POSE_BOUNDS` (anchor-space cylinder, radius 64u, height −32…96u) and `useConservativeBounds(instance)`. That method gives every body part, and its submeshes, a local bounding box that contains the cylinder, then clears `alwaysSelectAsActiveMesh`. The parts hang rigidly off the anchor (root motion is cancelled each frame), so one box computed per instance holds wherever the anchor moves or turns. `selectAlways(instance)` restores the old behaviour.
- [RemotePlayerRenderer](../../src/games/fps/client/RemotePlayerRenderer.ts) (fps repo) applies the bounds once per remote body in `updateModel` and no longer forces always-select every frame. Bodies stay **enabled**, so the main camera, the water actor mirror (which selects actors by `isEnabled()` and world bounds, and culls against its own reflected frustum) and any other pass each decide independently. Culled bodies also skip Babylon's per-mesh skeleton preparation. `detachModel` calls `selectAlways` before handing a body to the ragdoll, because physics carries bones off the anchor.
- Pose eligibility: `applyAnimationLod` also pauses the locomotion group of a player whose pose sphere (radius ≈ 90u around the cylinder) is wholly outside the main camera frustum, using `sphereInFrustum` in [RemotePlayerLogic](../../src/games/fps/client/RemotePlayerLogic.ts). It is disabled while `waterNeedsLocalReflection` reports a nearby pool, and whenever more than one active camera exists, because a frozen stride in a mirror is the visible kind of wrong. ### WG27-4: pose-rate tiers

What changed:

- [PlayerModelManager](../../src/engine/animation/PlayerModelManager.ts) `stepAnimation(instance, dtSeconds, stepSeconds)`. Babylon has no per-group update rate, so the locomotion group is paused and its clip phase kept by hand. The phase advances every frame by Babylon's own animation clock (`animationDeltaSeconds`: clamped engine delta × `scene.animationTimeScale`) times the group's live speed ratio, which already carries walking backwards, crouch-idle freezes and demo playback speed. The pose is written with `goToFrame` only when a step is due; the step timer carries its remainder but never banks more than one step, so a hitch is followed by one pose, not a burst. Root motion is cancelled again after each write. A one-shot (blade swing etc.) owns the bones while it plays and is never stepped. `setAnimationActive` hands a stepped clip back to Babylon at the phase it reached, so going back to full rate does not jump.
- **Babylon detail that would have cancelled the saving:** after a `goToFrame`, Babylon remembers the jump until the group next animates. While it remembers, every `speedRatio` change re-poses the whole skeleton. The renderer sets the speed ratio every frame and a paused group never animates, so stepped players were being re-posed every frame anyway. `forgetPendingJump` clears Babylon's internal `_goToFrame` after each stepped write; `PlayerModelPoseStepping.test.ts` fails without it (verified by removing the call).
- [RemotePlayerRenderer](../../src/games/fps/client/RemotePlayerRenderer.ts) tiers each drawn, on-screen player: **full rate** while taller than 72 px on screen, **stepped** once shorter than 56 px (the gap is hysteresis), **paused** under the existing rules (outside PVS, under 24 px, outside the main frustum). Pixel size uses the same projection helper as the 24 px rule. New console cvar `cl_player_pose_hz` (default 30, 0 = every player posed every frame) exists for timedemo A/B, not as a settings-menu option.

Tests: `PlayerModelPoseStepping.test.ts` (new): wrap-around both directions; 30 Hz stepping on a 62.5 Hz clock writes 7–9 times in 16 frames and stays within one step of the true phase; backwards speed ratio; resume continues from the stepped phase; speed changes do not re-pose; one-shots are left alone. The B12 parity recording was regenerated against the WG27-1 version: its **only** difference is the play flag (`1`→`0`) on 405 lines where a player is now stepped; positions, clips, speed ratios, styles and root-motion fields are identical.

### WebGPU first-person stall: root cause (BM-W1, 2026-10-09)

CPU profiles (CDP sampling profiler, 12 s, visible Edge, `demoplay` of `wdm5_ffa_20261009_134832.shagdemo` in first-person view) put Babylon's `_markAllSubMeshesAsDirty` at **13.5%** of the main thread on WebGPU (plus 4.8% `_markAllSubMeshesAsLightsDirty`, 1.5% `markDirty`) against 1.6% on WebGL2. The callers were all one path: the glTF loader's `onReady` → `SceneRendererPolicy` → `applySafeSceneLightCaps` → `maxSimultaneousLights` setter, plus Babylon's own write just before it.

Mechanism: at the end of **every** glTF import, Babylon 9.17's loader raises the light cap of every scene material to `scene.lights.length`. On WebGPU our policy then set every material back to its budget. Each import therefore changed every material's cap twice, and each change marks all its submeshes light-dirty, forcing defines, effects and bind groups to be prepared again; frozen materials got a full `markDirty(true)`. The pass also raised the view weapon's deliberately lowered cap (2) back to the PBR budget (4) on every import. In first-person spectating, weapon and effect models keep loading, so this ran continuously. WebGL2 was spared because its policy only raises: after Babylon's first raise the values stay equal and Babylon's setter skips them.

Fix ([DynamicLightSafety](../../src/engine/lighting/DynamicLightSafety.ts), [SceneRendererPolicy](../../src/engine/rendering/SceneRendererPolicy.ts)):

- On WebGPU, a material that has passed through the light policy gets an instance-level `maxSimultaneousLights` accessor: **only the policy can raise it; other writes may only lower it**. Babylon's import-time raise is ignored, the value stays equal, and nothing goes dirty. The view weapon can still lower its own cap.
- The post-import hook now calls `clampSceneLightCaps`: it guards every material and **only lowers** caps above budget; it never raises.
- Test: `SceneRendererPolicy.test.ts` "leaves existing WebGPU materials clean across glTF imports, and keeps lowered caps". Three real glTF imports on a WebGPU-flagged NullEngine with 11 lights cause no light-dirty calls on a world or view-weapon material, and a lowered cap stays lowered. It fails with the guard disabled (verified).

Effect in the same profile setup: `_markAllSubMeshesAsDirty` **13.5% → 1.9%**, the light-dirty and markDirty entries drop out of the top list, and Babylon's FPS reading in the first-person view went from 52 to 72. The headed timedemo series below this section predates the fix.

### Where the frame goes: CPU profiles WebGL2 vs WebGPU (2026-10-09)

Method: CDP sampling profiler (250 µs), visible Edge, 15 s of first-person `demoplay` of `wdm5_ffa_20261009_134832.shagdemo` after a 50 s warm-up, two captures per backend, alternating. Self and inclusive time per function, divided by frames rendered (engine FPS × duration). Profiles are main-thread only; frame counts differ between captures because the demo shows different combat at the same offset, so treat the numbers as attribution, not as the benchmark.

**Finding 1 — gib bounces were ~15% of the main thread on both backends.** `GibSystem.update` took 2.1–2.5 s of each 16 s capture. Each death spawns five "hero" gibs, and every frame until it bounces each one called `scene.pickWithRay`. That tests the ray against the render triangles of every large BSP mesh whose bounds it crosses (`intersectsTriangle` ≈ 2.2–2.4 ms per frame). Fixed in [GibSystem](../../src/games/fps/client/GibSystem.ts): hero gibs trace the BSP collision world (`CollisionManager.trace`, `CollisionMasks.SHOT`, ray), a few plane tests, and fall back to the scene pick only when no collision world is loaded. The collision world is loaded during demo playback, confirmed by the profile. After the fix `GibSystem.update` is **64–81 ms per 16 s** (from 2,100–2,500 ms), and WebGL2 frame time in the profiled view fell from 20.7 to 13.3 ms. New test `GibSystemTrace.test.ts`: bounce off the trace's surface without any scene pick, keep flying on a miss, fall back without collision.

**Finding 2 — the WebGPU gap is per-draw submission plus slower generic paths.** After both fixes, per rendered frame (WebGL2 / WebGPU):

### Reproduce the basic asset inventory

```powershell
@'
import fs from 'node:fs';
import crypto from 'node:crypto';
const b = fs.readFileSync('public/games/default/animations/vanguard.glb');
const g = JSON.parse(b.subarray(20, 20 + b.readUInt32LE(12)).toString());
const primitives = g.meshes.flatMap(m => m.primitives.map(p => ({
  mesh: m.name, mode: p.mode ?? 4,
  vertices: g.accessors[p.attributes.POSITION].count,
  indices: g.accessors[p.indices].count
})));
console.log(JSON.stringify({
  sha256: crypto.createHash('sha256').update(b).digest('hex'),
  bytes: b.length, primitives,
  vertices: primitives.reduce((n, p) => n + p.vertices, 0),
  triangles: primitives.reduce((n, p) => n + p.indices / 3, 0),
```
