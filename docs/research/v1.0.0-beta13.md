# v1.0.0-beta.13 release checklist

What has to happen, and which files change, to take beta.13 from `staging` to
production. The file lists compare production (`origin/main`, the beta.12.2
release: outer `4a475b4b`, fps `c3d876b`) with local `staging` (outer
`b1eaad0e`, fps `8c9f6fe`) as of 2026-11-17.

## State on 2026-11-17

- Everything is committed on `staging` in both repositories, and outer
  `staging` pins fps `8c9f6fe`.
- **Not pushed yet.** Local `staging` is ahead of `origin/staging` by 37 outer
  and 45 fps commits. Push fps `staging` first, then outer `staging`.
- `main` is untouched. Promote `staging` to `main` only when the release is
  approved (the `merge-and-release` skill).

## Release order

1. Push fps `staging`, then outer `staging`.
2. Check `washoi-lobby`'s limits on both hosts (operator step 1 below).
3. Upload the media below to `/srv/washoi/assets/data` on EU and US, backing
   up what it replaces into `/srv/washoi/backups/media-v1.0.0-beta.13/`.
4. Merge `staging` into `main` (fps first, re-pin, outer), push fps `main`,
   then outer `main`. The deploy timers build and activate.
5. Verify, install the new activation scripts, retire `washoi-bots`
   (operator steps 3–5).
6. Finalize `docs/changelog/v1.0.0-beta.13.md`, tag `v1.0.0-beta.13`.

## Server changes

Bots move out of `washoi-bots` into the lobby: the lobby seats bots and plays
each match's bots in a match runner, a child process of about 175 MB that
exits with its match. The full steps are in the fps
`scripts/deployment/README.md`, "v1.0.0-beta.13 operator steps":

1. **Before publishing**, on each host:
   `systemctl show washoi-lobby -p MemoryMax -p MemoryHigh -p TasksMax` must
   leave room for one runner per bot match on top of the match servers (about
   120 MB each). If the units are sandboxed, give `washoi-lobby` the write
   paths `washoi-bots` had, for the bots' navigation caches.
2. **Publish** as usual; the installed activation script still restarts both
   services, and the bot server starts and stays idle.
3. **Verify** in `journalctl -u washoi-lobby`:
   `Bots: seated by the lobby, matches in match runners`, and from a bot
   match's runner `[HeadlessBSPCollisionWorld] World trace: compiled (WebAssembly)`.
   `pgrep -af bot-runner` shows a runner while the match plays and none after.
   Play a campaign mission and a quick play with bots.
4. **Install** the new `scripts/deployment/activate-eu.sh` /
   `activate-us.sh` as `/usr/local/sbin/washoi-activate`.
5. **Retire** the bot server: `systemctl disable --now washoi-bots`.

Rollback to beta.12: `systemctl enable --now washoi-bots` first.

New files the servers make or need:

| Path | What |
| --- | --- |
| `dist-server/bot-runner.mjs` | New bundle: one match's bots (built by `build:server`) |
| `dist-server/bot-nav-worker.mjs` | New bundle: the nav graph build in a worker thread |
| `dist-server/WorldTrace.wasm` | The compiled collision trace, copied beside the bundles |
| `<data-dir>/campaign.db` | New database: campaign clears per account, beside `players.db` |
| `<data-dir>/bot-intel.db` | The bots' match reports, now written by the lobby |
| `.cache/bots/maps/` (working dir) | Bot navigation caches; rebuilt each match if not writable |
| `config/campaign.json` | The campaign's missions, rosters and rules (in git) |

Behaviour changes worth knowing on the server side:

- Team Deathmatch plays a tie at the time limit on in 60 s of overtime;
  Survival does not.
- A new Survival gametype and body scale (`HitScale`, `BodyScale`) are used by
  campaign missions.
- `@tensorflow/tfjs-node` is no longer a dependency (bot training was
  removed); `npm ci` on the hosts drops it.
- No ratings or ranking schema re-rate is needed: `players.db` keeps its
  schema; the campaign's clears live in their own `campaign.db`.
