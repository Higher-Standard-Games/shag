# Server memory investigation results

Measured on Windows x64 with Node 24.21.0 and experimental Bun 1.4.3.
Node remains the default for the first public release. Bun is optional through
`lobby:server:bun` and `net:server:bun`; spawned matches inherit the lobby runtime.

## Repeated idle comparison

Both runtimes execute the same production bundle. Each map/runtime has three
trials, ten seconds warmup and fifteen seconds sampling, without forced GC.
Values below are medians across trial medians, in MiB. Private commit is sampled
once per trial after warmup; it is not peak commit or resident RAM.

| Map | Node RSS | Bun RSS | Node private commit | Bun private commit |
| --- | ---: | ---: | ---: | ---: |
| wdm2 | 89.0 | 79.2 | 90.2 | 212.1 |
| wfdm5 | 83.2 | 80.1 | 82.5 | 265.7 |
| wfdm11 | 78.3 | 74.7 | 78.5 | 230.7 |

Concurrent recording soaks ran during these measurements. These are memory
comparisons, not isolated CPU or latency benchmarks. RSS includes shared pages.
On Windows, Bun's lower RSS does not imply lower committed-memory demand.

The first short wdm2 baseline measured 354 MiB RSS through Node/Vite, 213 MiB
through bundled Node, and 138 MiB through bundled Bun. Those preliminary trials
had shorter warmup and sampling and should not be treated as a controlled
percentage improvement against the repeated final matrix.

## Capacity and recording soaks

Ten idle wfdm11 processes completed and exited cleanly for each runtime:

| Runtime | Summed RSS MiB | Private resident MiB | Private commit MiB |
| --- | ---: | ---: | ---: |
| Node | 794.3 | 398.5 | 792.4 |
| Bun | 735.3 | 473.1 | 2076.8 |

Summed RSS counts shared pages repeatedly; private resident pages do not. This
Windows result supports keeping Node as the default despite Bun's lower RSS.

Both final thirty-minute wfdm11 runs completed with eight network clients and
recording enabled: 22 finalized recordings each, over 907000 snapshots each,
and zero socket/decode errors. Median server RSS was 196.1 MiB on Node and
109.7 MiB on Bun. These include active play, recording buffers and runtime GC
headroom, so they are distinct from the idle matrix. Trials were concurrent;
client command counts differ with scheduler timing. They establish successful
extended operation, not identical CPU workloads or proof of absence of leaks.

## What changed

- Dedicated and lobby servers use production bundles instead of keeping Vite
  in every production process. Development commands retain Vite.
- The dedicated BSP parser retains authoritative collision, entity and
  visibility data, with sparse patch control positions. It skips rendering
  vertex attributes, lightmaps, lightgrid and mesh indices.
- PVS bytes own a compact copy instead of retaining the raw BSP backing buffer.
- Indexed PK3 extraction uses temporary archive ownership. Unrelated fallback
  archives are released between attempts rather than retained globally.
- Owned child servers accept a graceful stdin shutdown so recordings can finish
  before the existing forced-kill fallback, including on Windows.

No collision precision or trace rules changed. Map lookup still uses the
canonical PK3 index. Player meshes, bones and animation clips are not required
by authoritative gameplay: hit capsules, view origins and weapon timing use
simulation values; client rendering resolves animation and muzzle tags.

Separate Node heap diagnostics after forced GC measured wdm2 heapUsed falling
from 72.4 to 23.7 MiB. Reachable vertex allocations fell from 47.76 to 0.17 MiB;
PVS reachability fell from 8.98 to 0.17 MiB. These are reachable shallow allocation
inventories, not dominator-retained sizes; shared backing buffers must not be
summed across owners. Heap snapshots were separate from normal timing trials.

## Reproduce

```bash
npm run build:server
npm run benchmark:server-memory -- --maps wdm2,wfdm5,wfdm11 --runtimes node,bun --warmup 10 --seconds 15 --repeats 3 --out .cache/server-memory/report.json
npm run benchmark:server-memory -- --maps wfdm11 --runtimes node,bun --clients 8 --recording --warmup 15 --seconds 1800 --repeats 1 --out .cache/server-soak/report.json
node scripts/benchmarks/server-capacity.mjs --runtime node --instances 10 --map wfdm11 --out .cache/server-capacity-node/report.json
node scripts/benchmarks/server-capacity.mjs --runtime bun --instances 10 --map wfdm11 --out .cache/server-capacity-bun/report.json
```

Full local logs, JSONL samples and heap snapshots are ignored under `.cache/`.
The adjacent `v0.9.31-server-memory-measurements.json` preserves compact results,
artifact/map hashes and workload details without machine-specific paths.

The physics position warning is expected on a passing run. Initial validation
found a ZIP fixture Buffer typing mismatch; the fixture now uses an ArrayBuffer
converted to Uint8Array, and typecheck/build passed after correction.

Linux deployment, remote TLS, adverse network conditions and manual browser
gameplay on Bun remain unverified. New CI runtime checks have not yet run on the
remote runner. Ten idle instances do not establish ten active-match CPU capacity.
Bun's generic WebSocket publish benchmark does not model personalized snapshots:
our visibility, acknowledgement, privacy and delta baselines differ per client.
