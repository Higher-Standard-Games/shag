# Qfusion lighting parity: dark walls and excessive shine

**Date:** 2026-10-15. Research and isolated browser diagnostics; no permanent
lighting/material changes in this follow-up.

## Result

The difference is a collection of identifiable translation gaps, not a hidden
brightness setting. The strongest confirmed issues are (1) multiplying baked
vertex lighting into surfaces that already have lightmaps, (2) treating a Qfusion
specular-strength texture as Babylon roughness, and (3) approximating Qfusion's
map-dependent directional lighting with fixed global scene lights and a clipped
lightmap transfer. Worldspawn does contain runtime lighting controls we omit.

Use the upstream wfdm11 now installed as the common data baseline. The user's
middle screenshot is the Qfusion appearance reference. Its exact camera,
renderer backend, cvars and BSP revision are unknown, so these findings explain
mechanisms and demonstrate SHAG A/B changes; they do not prove a pixel match to
that screenshot or establish Qfusion's active settings from its appearance.

## Differences ranked for implementation

| Priority | Difference | Evidence | Consequence |
| --- | --- | --- | --- |

| 1 | Qfusion gloss strength becomes PBR roughness | Actual Babylon GLSL/WGSL, source gloss statistics, isolated material A/B | Weakly specular authored brick becomes smooth/shiny |

## What Qfusion reads from worldspawn

The shared renderer BSP loader at
`C:/Users/sundf/Desktop/warfork-qfusion/source/ref_base/r_q3bsp.c`,
`Mod_LoadEntities`, performs case-insensitive lookup. The relevant runtime keys:

| Key | Qfusion runtime use | Installed wfdm11 | SHAG status |
| --- | --- | --- | --- |
| `_lightmapImageSize` | Page extent; absent means format default 512 | 2048 | Implemented in the preceding loader fix |
| `_lightingIntensity` | Non-power-of-two baked lighting gain; affects lightstyle uniforms and map light scale | 3.0 | Ignored by our BSP lighting setup |
| `_ambient`, or `ambient` fallback | Ambient compensation for material/deluxe shading | 6 | Ignored as a map lighting input |
| `_color`, or `color` fallback | Tints the map ambient value | 0.882353, 0.490196, 0.164706 | Ignored as a map ambient lighting input |
| `gridsize` | Model/entity light-grid spacing | 64 64 64 | Parsed, but FBSP grid representation/spatial sampling still wrong |
| `fog*` / `_fog*` family | Atmospheric fog | Warm map fog | Separate supported fog path; not a replacement for lighting metadata |

For default Qfusion `r_mapoverbrightbits=2`, the authored intensity path subtracts
the default overbright setting, leaving texture-side overbright exponent zero
for this map and applying intensity 3 in lightstyle uniforms. Its map ambient is
`ambient * _color * mapLightColorScale / 255`, approximately
`(0.06228, 0.03460, 0.01163)` here. In the deluxe material shader that contributes
as `(1 - max(dot(normal, bakedLightDirection), 0)) * ambient`.
It is not equivalent to adding a white hemispheric light of intensity 6.
Changing gamma or multiplying all lightmaps by 3 alone would not reproduce this.

Relevant Qfusion functions also include `Mod_LoadLighting`, `Mod_Finish`,
`R_FinishMapConfig`, `RP_UpdateDynamicLightsUniforms`, and
`RB_RenderMeshGLSL_Material`. Both `source/ref_gl/r_model.c` and
`source/ref_nri/r_model.c` finish the ambient scaling. GL and NRI registration
sources default map overbright to 2, gloss intensity to 1.5, gloss exponent to
24 and gamma to 1.0. These are source defaults, not measured values from the
user's running Qfusion instance.

`shading "halflambert"`, `saturation`, `_lightmapbits` and `grid_*` values also
appear in the BSP. No corresponding key handling was found in the examined
runtime renderer entity parser for these. Do not blindly convert compiler/bake
settings into new runtime lighting. Qfusion's half-Lambert material branch is
selected under a compile-time `HALFLAMBERTLIGHTING` condition in the examined GL
backend, not by a `shading` worldspawn branch there. `_lightintensity` is also
not the same spelling as `_lightingIntensity`; do not invent aliases merely
because an older map stores compiler metadata under that name.

## Darkness: applying baked light more than once

SHAG's `mesh/vertices.ts` takes FBSP color slot 0 and normalizes it into the mesh
color attribute. `BspMeshBuilder.applyLightmaps()` then attaches a lightmap,
leaving `mesh.useVertexColors=true`. Babylon's Standard fragment shader first
multiplies base RGB by vertex RGB, computes ordinary scene illumination/specular,
and then multiplies the resulting color by the shadowmap-style lightmap.

The simplified current relationship for ordinary Standard surfaces is thus
closer to:

```text
albedo × baked_vertex_RGB × synthetic_scene_diffuse × converted_lightmap
  + a synthetic specular contribution also modulated by the lightmap
```

Qfusion's lightmapped material branch derives lighting from the lightmap and
its baked direction, with authored RGB modulation only when selected by the
shader's rgbGen semantics. It has a separate vertex-lighting branch for surfaces
without a lightmap. Its `defaultMaterial.frag.glsl` does not unconditionally
multiply every lightmapped surface by baked vertex RGB. The NRI shader contains
the same relevant conditional structure.

We already demonstrated a real crate triangle whose baked vertex RGB is exactly
zero, despite valid textures and a lightmap. The new probe repeats the
no-vertex-color comparison on the installed upstream BSP and both renderers.
Wall/wood/roof detail visibly returns. Some areas become too bright: that is
expected evidence of additional gain/scene-light discrepancies, not a reason
to retain the extra dark factor.

Implementation must preserve intentional `rgbGen vertex`, `exactVertex`, alpha
channels, unlightmapped/vertex-lit surfaces and custom liquid/decal shaders.
The diagnostic all-mesh `useVertexColors=false` toggle is not a complete patch.
An appropriate policy can neutralize only the fallback baked RGB factor on
eligible lightmapped surfaces while retaining authored alpha and modulation.

## Shininess: the gloss channel has the wrong meaning

A particularly clear example actually used in wfdm11:

```text
textures/refly_bricks/bricksdark1
  glossExponent 100
  glossIntensity 0.2
  material textures/bricks/bricks_05_bricksdark1
           textures/bricks/bricks_05_norm
           textures/bricks/bricks_05_gloss
```

This is `assets/data0_21pure/scripts/legacy.shader`, not an invented material.
Qfusion's `Shader_GlossIntensity` / `Shader_GlossExponent` parse the factors,
`RB_RenderMeshGLSL_Material` selects them, and `RP_UpdateMaterialUniforms` uploads
them. `glsl/defaultMaterial.frag.glsl` uses:

```text
specular = gloss_RGB × glossIntensity × max(dot(surfaceNormal, halfVector), 0)^glossExponent
```

This term is added to the lighting and then multiplied by the base texture in
the examined Qfusion shader. Its direction comes from the baked light direction
for a lightmapped world material. No gloss map means that material backend does
not enable its `APPLY_SPECULAR` branch. This is not Babylon metallic/roughness
PBR, and a global roughness tweak cannot preserve that complete contract.

SHAG does not preserve the authored two scalar directives. Its generated PBR
material sets `metallic=0`, `roughness=0.78`, `microSurface=0.9`, and assigns the
old gloss image to `microSurfaceTexture`. Because setting metallic/roughness
selects Babylon's **metallic workflow**, both its GLSL and WGSL
`pbrBlockReflectivity` shaders execute:

```text
roughness *= microSurfaceTexture.r
```

The comment in our material factory describes a spec/gloss workflow, but the
actual properties select a different one. This is not merely a question of
whether to invert a glossiness map: the Qfusion map controls RGB specular
strength, and the separate exponent controls the lobe.

Actual source PNG measurement through the browser:

- `bricks_05_gloss.png`: 1024×1024.
- Red minimum 0, maximum 33, mean 31.3584 / 255.
- Our source-value approximation is `0.78 × 31.3584 / 255 = 0.09592` roughness.
- Qfusion's authored multiplier at the same mean is
  `0.2 × 31.3584 / 255 = 0.02460` before the exponent and albedo.

The roughness calculation uses source channel values for illustration, not a
measured uniform effective roughness across all rendered pixels; filtering,
color-space and BRDF processing may also matter.

An isolated sphere using the actual runtime brick material demonstrates sharp
bright highlights. Removing **only** `microSurfaceTexture` removes those sharp
highlights while retaining the same textures, camera, lights and roughness
scalar. Screenshots `.cache/qf-gloss-original.png` and
`.cache/qf-gloss-without-roughness-map.png` were inspected. The sphere deliberately
has no baked lightmap or vertex lighting: this isolates the material-channel
problem, not Qfusion scene parity.

The StandardMaterial fallback also differs: it boosts specular texture levels
to 1.2/1.4, specular colors to 0.5/0.65 and uses powers 32/24. A normal map with
**no gloss map** still gets specular color 0.18 and power 48. Qfusion's material
branch would have no gloss-specular term in that case. These invented boosts
are another cause of shiny highlights on otherwise matte authored surfaces.

## Synthetic lights and unused baked directions

The live probe found the same lighting inventory on WebGL2 and WebGPU:

| Light | Intensity | Specular RGB |
| --- | ---: | --- |
| worldFillLight (hemispheric) | 1.2 | 1, 1, 1 |
| sunLight (directional) | 1.15 | 0.16, 0.16, 0.16 |
| moonLight (off) | 0 | 0.05, 0.05, 0.08 |
| ambientLight (hemispheric) | 0.35 | 0, 0, 0 |

`createWorldFillLight()` sets no specular override, so the default white
specular remains. Its render priority is 1000. `setBspMode()` adjusts the sun
and ambient but leaves this fill active. This means our nominal fill light also
produces highlights. The sun uses a fixed direction unrelated to the baked
illumination for a particular wall. Removing specular is a useful control, but
removing every light would also remove the diffuse path our current materials
expect; that is not itself a compatibility fix.

Qfusion's `glsl/include/material_lightmaps.frag.glsl` reads the paired deluxe
page, decodes `normalize(rgb - 0.5)` and uses the resulting local light direction
with the surface normal and specular half-vector. SHAG's `r_deluxe` selects
shader condition branches; no equivalent paired-direction texture sampling was
found in the examined mesh/material/lighting code. Applying ordinary Babylon
normal/specular shading with a fixed sun cannot reproduce this spatially varying
lighting. Qfusion falls back to its plain Q3A world shader when deluxe mapping
is unavailable; it does not replace the missing direction with an arbitrary sun.

The upstream map's four raw pages consist of two diffuse/direction pairs, with
world surfaces referencing pages 0 and 2. We upload all four through the same
RGB gamma/gain helper even though the two direction pages are not used. Any
future direction sampler must preserve those direction bytes as data, without
gamma, overbright, sRGB conversion or color clamping.

## Lightmap transfer and shared gain state

SHAG's helper transforms each raw channel before upload:

```text
convertedByte = min(255, (rawByte / 255)^0.7 × 255 × 2)
```

Values around 95 and above saturate to 255. For example, the gable's raw sample
`(153,139,110)` becomes `(255,255,255)`, losing its warm color ratio before the
base texture is multiplied in. The map loader then asks for format gain 2.
Qfusion's authored wfdm11 path, at source defaults, instead preserves raw
lightmap bytes through upload and applies the authored gain 3 in its lighting
uniforms. It does not use our arbitrary `pow(0.7)` transform. Other overbright
settings use Qfusion's color normalization, not independent channel clipping.
This mismatch can produce simultaneously dark material factors and overbright,
desaturated highlights. Matching mean frame brightness would conceal the issue.

Our material-specific gain attempt has another problem: PBR requests
`intensity * 0.6` while Standard requests `intensity`, but `Texture.level` lives
on the **shared lightmap texture**, not on each material. The browser inventory
shows PBR lightmap level 2, despite its branch requesting 1.2. Source inspection
shows all users of a page share that texture. Thus the requested per-material
gains are not independent; later assignments can overwrite earlier ones.
A real per-material factor needs a material uniform/plugin or intentionally
separate texture wrappers, not mutation of a shared Texture's level.

## Implementation order and acceptance

1. **Correct material gloss semantics.** Preserve authored intensity/exponent
   in the parser/resolver. Stop feeding strength RGB into metallic-workflow
   roughness. A classic specular-material path is a better initial compatibility
   target than trying to infer PBR roughness from an unrelated channel. Honor
   absent gloss and existing explicit blank channel markers. Preserve glTF
   weapons/player PBR; this concerns translated BSP materials only.
2. **Choose baked lighting once.** Separate fallback baked vertex RGB from
   intentional shader vertex/alpha semantics. Correct ordinary lightmapped
   surfaces while retaining vertex-lit and custom material cases. Test inline
   movers and classic Q3 maps too.
3. **Represent authored world lighting.** Parse `_lightingIntensity` and ambient/
   color into one engine-owned map-lighting profile. Preserve missing-key legacy
   behavior; reset on map changes. Do not reinterpret every compiler key.
4. **Establish a direct baked-light baseline.** Replace the clipped/gamma-baked
   transfer with a source-backed path, apply gain at the correct shader stage,
   fix shared-factor ownership, and avoid an additional directional diffuse
   lighting multiplier on already-baked surfaces. Retain dynamic game lights
   and authored emissive/glow behavior.
5. **Implement paired deluxe directions and matching specular.** Preserve the
   direction data, sample it in the same UV2 space and use it for normal-map
   relief/half-vector lighting, with map ambient compensation. Fall back to
   classic lightmapped behavior when unavailable. Then fix the separate FBSP
   light grid for model/entity lighting.

Start with synthetic material/lighting fixtures plus wfdm11, wfdm1 and wdm2,
then fixed-camera WebGL2/WebGPU captures. Compare the user's Qfusion view after
obtaining/matching camera and render settings; do not declare parity from
matching overall brightness. Check dark walls, weak-gloss brick, genuine metal,
no-gloss normal-mapped surfaces, fullbright lamps, decals and moving brushes.
Use release gates and the renderer regression set for implementation, followed
by timedemo checks for any added shader work. No extra player-facing cvar is
required to justify a better compatibility default.
