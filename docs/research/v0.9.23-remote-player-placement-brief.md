# Investigation brief: remote players render inside walls and floors

**2026-09-13 follow-up:** [Measured model defects and fix](v0.9.23-remote-player-placement-findings.md)
documents a reproduced cross-player animation/placement defect, the patch and
regressions, and two corrections to this brief's wireframe/hull assumptions.
The intermittent live wall case is still unverified. The original investigation
context below is preserved as written.

**For:** an engineer or agent picking this up cold.
**Repo:** SHAG (Babylon.js Quake3/Warsow-style FPS), branch
`feature/v0.9.23-gfx-investigation`.
**Companion:** [v0.9.23-bughunt.md](v0.9.23-bughunt.md) holds the wider defect
ledger; this file is the deep context for one unresolved item.

---

## 1. The symptom

Other players — in practice bots, since testing is single-player with bots —
are **drawn inside solid geometry**. Reported across several sessions:

- A bot walking into a wall on `wdm2` and ending up visibly inside it, on flat
  ground, not crouching, not jumping.
- A bot partly sunk into the floor on `wdm7`.
- A player floating *above* the floor on `wdm2`, in an earlier session.
- Accompanying "warping" — bodies jumping position.

**Intermittent.** Reloading the same map has produced a correct-looking session.
No reliable reproduction exists yet.

**The local player is never affected.** The reporter cannot walk into walls
themselves. This asymmetry is the single most important clue and is explained in
§3.

---

## 2. Architecture you need before forming a theory

**The local player and remote players reach the screen by completely different
routes.** Getting this wrong wastes hours.

**Local player:** client-predicted. `MovementProfile.simulate()` runs the same
fixed-step movement code as the server, against the real client-side collision
world, and reconciles against server snapshots. Its position is
collision-correct *by construction* — it physically cannot be inside a wall,
because a swept collision solve produced it.

**Remote players:** *not* simulated on the client at all. Their positions come
from `SnapshotBuffer`, which interpolates between the two snapshots bracketing
`renderTime = now - interpDelay`, or extrapolates from the newest one when the
buffer has run dry. **Neither path performs any collision test.** Whatever
position comes out is drawn.

**Bots** are real clients: they connect, send inputs, and are simulated
server-side through the same movement and collision path as human players. They
are not a special case with their own physics.

So a remote player may be drawn inside a wall while every authoritative position
involved is perfectly legal — and the local player would never show the same
defect, because their position never passes through the interpolation path.

## 3. What has been ruled out, and on what evidence

Do not re-investigate these without new evidence. Each was eliminated by
mechanism or measurement, not by intuition.

| Suspect | Why it is out |
| --- | --- |
| PVS entity culling (added this cycle) | Only calls `setEnabled`. It never writes a transform, so it cannot move a body. It also disables whole meshes, so it cannot sink one halfway. |
| Facet-bevel collision change (added this cycle) | Alters trace results only. Cannot move a render anchor, and the local player — who *does* use collision — is unaffected. |
| Server-side collision on `wdm2` | `npm run audit:stuck -- wdm2` walks a real player hull into every surface: **0 penetrations** across 169 faces / 10,038 triangles. The server is not putting bodies into `wdm2` geometry. |
| Client-side position smoothing | `RemotePlayerRenderer.updatePosition` (~line 1296) sets `smoothedPos` **directly** from the interpolated value. The name is a misnomer; there is no filter to lag or overshoot. |
| Missing animation clips | `PlayerModelManager.playAnimationOn` now warns once per missing clip. It stayed **silent** for a full session, so every requested clip was loaded. |
| Distance-based animation LOD | Pauses skeletons beyond a screen-size threshold; it cannot move anything. (It was separately implicated in a *different* symptom and cleared — see §6.) |

**Partially addressed, did not resolve the symptom:** extrapolation was capped
from 200ms to 60ms (`MAX_EXTRAPOLATION_SEC` in `SnapshotBuffer.ts`). At 320 u/s
that reduced blind travel from 64 units to 19. Bodies still appear inside walls.

## 4. Hypotheses, ranked

### H1 — The visual model is larger than the collision hull *(currently favoured)*

The collision hull is **32 units wide, 64 tall** (`PLAYER_RADIUS` 16,
`PLAYER_MINS_Z` -24, `PLAYER_MAXS_Z` +40, in
`src/engine/physics/PlayerPhysicsConstants.ts`). The rendered character
(`vanguard.glb`) has shoulders, arms and a held weapon that are very unlikely to
fit inside that box.

If so, a bot standing **legally** flush against a wall — hull entirely outside —
has its shoulder geometrically *inside* the wall. Nothing is wrong with any
position; the model is simply wider than the box the position guarantees.

This fits every observation, including the two that defeated other theories:

- **Why only bots:** you never see your own model in first person. The defect
  would affect the local player identically and be invisible.
- **Why intermittent:** it depends on approach angle and how flush the bot ends
  up, not on timing.
- **Why the floor cases too:** `RemotePlayerRenderer.updateModel` applies
  `MODEL_Y_OFFSET` plus a **-10 crouch / -20 slide** anchor drop (~lines
  1332-1336) to compensate for Mixamo clips not lowering the skeleton. Any
  mismatch between that compensation and the pose actually playing sinks the
  model.

**This hypothesis has not been tested. §5 test 1 settles it in one round.**

### H2 — Interpolation cuts corners

`SnapshotBuffer` lerps **linearly** between two snapshot positions. A body
rounding a corner, or sliding along a wall on a curved path, follows a straight
chord between endpoints — which can pass through geometry neither endpoint
touches. At 30Hz and 320 u/s consecutive snapshots are ~10.6 units apart, so the
chord error is small but non-zero near sharp corners.

Weakness: probably too small to place a body clearly *inside* a wall.

### H3 — Extrapolation fires far more often than assumed

`interpDelay` adapts to `avg + stddev` of snapshot arrival intervals, clamped to
[16, 150]ms (`SnapshotBuffer.ts` ~line 381). At a steady 30Hz that is ~35-40ms,
which should almost always leave a newer snapshot bracketing `renderTime`, making
extrapolation rare.

**This has never been measured.** If the real snapshot rate is lower or more
irregular than assumed, the buffer could be running dry routinely, making blind
dead-reckoning the *normal* path rather than the exception. 60ms still permits 19
units at run speed — more than a hull radius.

### H4 — Crouch/slide anchor offset decoupled from the pose *(explains sinking only)*

`updateModel` chooses the -10/-20 anchor drop from the raw `interp.crouching` /
`interp.sliding` flags. `deriveAnimation` chooses the pose from a **different**
order of conditions, and returns `"jump"` for anything not grounded *before* it
ever examines crouching.

So a **crouching airborne** bot gets the jump pose *and* a 10-unit drop — the
compensation applied without the animation it exists to compensate for.

The reporter rejected this as the cause of the *wall* cases (correctly: it is
purely vertical), but it remains a genuine defect for floor cases.

### H5 — `grounded` is wrong on remote players *(explains a second symptom)*

`deriveAnimation` returns `"jump"` whenever `!grounded`, before any strafe or
run check, and the jump clip **freezes** (`speedRatio = 0`) when `|vy| < 10`.

A bot moving horizontally while `grounded` is false therefore renders as a
**frozen pose sliding sideways** — which matches a separate report of "bot
standing and sliding with no animation". If `grounded` flickers on remote players
this is one bug producing two symptoms, and it may share a root with the
placement problem.

## 5. Tests, in the order they should be run

### Test 1 — Split "render offset" from "network position" *(do this first)*

In the game console:

```
cl_remotehitbox 1
```

This draws the wireframe collision hull around remote players. Watch a bot walk
into a wall.

- **Wireframe stays outside the wall, model clips in** → **H1 confirmed.** The
  transported position is fine and this is not a networking bug at all. Move to
  model scale/anchor work.
- **Wireframe itself enters the wall** → the position really is wrong. H1 is
  dead; proceed to test 2.

This is one cvar and one round, and it eliminates either half of the search
space. Everything else is more expensive.

*(The cvar is registered with default 0 in `RemotePlayerRenderer.ts`. A recent
fix made an absent value mean off, so the toggle is trustworthy.)*

### Test 2 — Is the drawn position the server's position?

Only if test 1 says the hull is inside the wall.

In `RemotePlayerRenderer.render()`, for one entity id, log per frame:

- the interpolated position actually drawn,
- the raw position of the newest snapshot in the buffer,
- whether the sample came from the interpolate or the extrapolate branch
  (`SnapshotBuffer.sample`, cases 1 and 2 around lines 209-235).

- **Raw snapshot already inside the wall** → server-side. Given the clean
  `audit:stuck` result this would be surprising and worth re-running the audit
  against the exact coordinates.
- **Raw fine, drawn position inside** → confirms H2 or H3, and the branch flag
  says which.

### Test 3 — Measure how often the buffer runs dry

Count extrapolate-branch hits per second across a normal round, alongside the
live `interpDelay` and observed snapshot interval.

If extrapolation is common, H3 is the answer and the fix is **collision-aware
extrapolation**: sweep the dead-reckoned path against the client collision world
(the client has one — `getCollisionManager()`) and clamp at the first hit. That
makes penetration impossible at any cap and is the correct fix regardless.

If extrapolation is rare, H3 is out and H2 is the remaining position-side
candidate.

### Test 4 — `grounded` and pose, for H4/H5

Log `interp.grounded`, `interp.crouching`, `interp.sliding` and the string
returned by `deriveAnimation` for one bot over a few seconds of normal movement.

Look for `grounded === false` while the bot is plainly running on a floor. That
would confirm H5 and make `grounded` a shared root cause worth chasing on the
server side.

## 6. Notes on prior reasoning, so it is not repeated

Two earlier diagnoses in this investigation were **wrong**, and both failed the
same way — a plausible mechanism accepted without doing the arithmetic:

1. **Distance LOD blamed for frozen animations.** The threshold was 2500 units,
   justified as "limb motion is sub-pixel there". Working it out: a 64-unit body
   at 1080p under a 59° vertical FOV covers 24 pixels at **2545 units** — within
   2% of the value under suspicion. The threshold only ever fired where a player
   really is a thumbnail. (The LOD was rebuilt to gate on projected screen height
   regardless, since one distance constant meant 1946 units at 73° FOV and 3394
   at 1440p.)

2. **Extrapolation as prime suspect for placement.** Weakened by the
   `interpDelay` arithmetic in H3 — it should rarely fire. Not eliminated,
   because it has never been measured.

**Method note for whoever continues:** the useful moves in this investigation
have all been measurements that *eliminated* things — the `audit:stuck` run, the
missing-clip warning that stayed silent, the pixel arithmetic. The unhelpful ones
were mechanism stories that sounded right. Prefer the cheap discriminating
observation over the plausible explanation.

**Tools**

- `npm run audit:stuck -- <map>` — penetration scan. `--ladders` narrows to
  ladder regions; `--at x y z` dumps every surface a trace reports from one
  point. Babylon coordinates (y up).
- `npm run net:viewlag` — view lag and ping under injected latency.
- `cl_remotehitbox 1` — remote player collision wireframe.

**Verification expected of any change**

`npx tsc --noEmit`, `npx vitest run` (2610 tests at time of writing),
`npm run gate:biome` (lint baseline — do not raise it), and for anything
touching simulation, `npm run server:tick` and
`npm run server:fuzz -- --ticks 1000` for determinism.
