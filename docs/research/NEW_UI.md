After review, two more gaps closed the same day. The rail's page keys looked flat because they are the panel's tab buttons raised into keys, and `.game-panel__tab` still clipped them (its own parallelogram cut the key's side and shadow away); a raised tab now drops the tab frame. A lobby-completion pass (2026-09-28) compared every view with real data against its prototype state — rooms of every mode filled with bots through a scratch bot server, the lobby server down, `public/data` blocked, keyboard only, reduced motion. Found and fixed: a room never said it could start before it was full (the server's `minPlayers` now travels in the room config, so a two-player S&D start reads "Ready when you are · 3 / 4 ready"); room chat did not say who came and went; the lobby chat was blank when empty and never noted a match starting; Tab from the top of the page was trapped in the closed debug console (now `inert` while closed); reduced motion left the panel sliding and drifting; the leaderboard called an offline lobby "unsupported"; a keyless Profile showed the key warning alone. ## Source and intent

`public/ui-proto/lobby-3d.html` is the visual and interaction reference for the main UI. Its companion pages are `welcome.html`, `lobby-room.html`, `leaderboard.html`, `demos.html`, and `settings.html`. These six pages are currently untracked local files; preserve them as references and add them to the feature branch before review. The tracked `public/ui-proto/lobby.html` is an earlier exploration, not the target.

The old `GamePanel` reserves 10% of the viewport at both top and bottom for blurred strips. The current FPS `LobbyPanel` puts five tabs across the top and three tall match tickets beside social and chat columns. The new shell should fill the viewport. A gold, slanted left rail holds the logo, primary navigation, contextual list, identity, and utilities. The remaining stage holds one task at a time. The Play stage uses selectable raised mode keys, a single selected-mode description and CTA, and lobby chat. This keeps the prototype's depth, diagonal edge, ink/cream contrast, and per-mode accents while removing the repeated text and empty space in the tickets.

S0a wire contract: clients send `{ type: "lobby:chat_send", lobbyId, text }`; the server accepts only the current room's members, trims text to 500 characters, and broadcasts `{ type: "lobby:chat_message", lobbyId, from, fromId, text, ts }` to that room including the sender. `MatchLobbyInfo.chatHistory` carries its last 50 messages on create/join and during the return-trip reconnect window. Global `chat:send`/`chat:message` and its history remain separate. Room history is in memory and ends when the room is destroyed.
The `chatHistory` field is optional at the type boundary for older lobby servers. If it is absent, the room view disables sending and says that room chat is unavailable on that server rather than offering a silent no-op.

S1 wire contract: create sends `{ type: "lobby:create", gametype, visibility: "private" }`; join sends `{ type: "lobby:join", lobbyId, inviteToken }`. The server generates a separate 192-bit random token and returns `MatchLobbyInfo.visibility` and a relative `shareUrl` containing `?lobby=<id>&invite=<token>` only to room members. The token is required on every private join, including reconnect. A missing/wrong token gets the same generic error as an absent room, before capacity or membership is exposed. Private rooms stay out of `welcome.liveMatches`, `matches:update`, queue discovery and public player `lobbyId` snapshots, including while playing. All members receive the same invite URL so they can invite another player. The client keeps its token in same-tab `sessionStorage` to make Return to Lobby work after a match; a direct invite link also carries it. An invite lasts only as long as the in-memory room: an empty waiting room is destroyed immediately, while the existing post-match return window can keep a room alive briefly. Room visibility cannot change in place. There is no individual-token revocation yet; destroying the room revokes its link. Private rooms do not survive a lobby-server restart. Treat the invite URL as a bearer secret and share it only with intended players.

S2 rules chosen from the prototype's 1v1/three-minute/kit/first-to-three outline: each round has a five-second freeze and no respawn until the next round; the first player to win three rounds wins the match with no extra lead requirement. The first kit choice applies to the first spawn; a later change applies next round. Bots use the default kit. ## Key implementation decisions

- Start with a rail around 26–28% of desktop width, bounded by usable minimum/maximum widths. The prototype's 33% idea is a comparison point, not a fixed requirement. Give the stage the larger share. At narrower widths, reduce key height and rail width; at phone width, stack or replace the rail with a compact navigation treatment rather than clipping the stage.
- Keep native `button`/`input` semantics. Mark the active nav page and selected mode (`aria-current` / `aria-pressed`), preserve visible focus, and make every action reachable by keyboard. The prototype removes outlines on its keys, which must be corrected in production.
- Use the existing Orbitron/Rajdhani assets and theme colors. Prefer transforms/opacity for movement, support reduced motion, and avoid permanently animating large blurred fields on low-end hardware unless profiling shows it is safe.
- Build DOM nodes or use safe text assignment for server-provided names, chat, and map labels. The existing lobby view has some `innerHTML` interpolation; the redesign is an opportunity to remove that exposure from touched UI.
- Do not make media under `public/data` a build dependency. The logo and map art may be missing in a clean checkout; provide a text/gradient fallback. The prototype notes only `acidwdm2` has an installed levelshot.
- Keep the UI state separate from lobby state: selected mode/tab/filter can be local; queue, room membership, ready, roster, map vote, chat, and match status must come from the server.

### The post-match return, and the stats surfaces (2026-09-22)

The return trip finally ran in a browser, and it took the spawn fix to get there. `GameServerSpawner` now bounds its readiness wait by `SHAG_SPAWN_TIMEOUT_MS` (default 45s, clamped to 5s–5min) and `abandonSpawnedChild()` sends the child SIGTERM, then SIGKILL five seconds later, so a server the lobby gave up on no longer holds its port. With a 120-second deadline on this machine, a private Amphi room spawned `wamphi1`, a bot took the other seat and decided the match, and the post-game scoreboard appeared — the first time any of this was seen on screen.

**The defect the return exposed: "Lobby is full."** RETURN TO LOBBY reloads the page, so the player comes back on a *new* lobby socket while the socket that carried them into the game is not yet known to be gone. Their old seat still counted, so a two-seat room turned its own member away. A room now hands a seat to the newest connection of the same account: the older connection is told it left (`lobby:kicked`, "you joined from another window"), the room hears one `lobby:player_left` for the old id, and the returning player keeps the side it was playing on but comes back unready. Bots have no account and never share a seat, so a room full of bots still fills seat by seat. `src/lobby/__tests__/SeatTakeover.test.ts` pins all of it (7 tests), and the browser flow now passes: back in the same private room, invite intact, no invite token left in the address bar.

A second thing the return showed: a room whose match is still running said **"Match starting — everyone is ready"**, with stale ready chips from the match being played. A room that was already mid-match when the player walked in now says "Match in progress", points at the rejoin key, shows every seat as "In match", and returns to the ready-up screen on `match:ended`.

**Stats surfaces.** The Profile has a record card: one line per mode the lobby ranks the account in — rank, W, L, D — with a summary line ("5 ranked matches · best #2 in AMPHI"). It reads the account's own row straight from the leaderboard query, so it is honest about a lobby that is offline, one that does not rank, a mode with no finished match, and a query that fails for one mode but not another (`ProfileRecord.test.ts`, 7 tests).

The leaderboard was finally seen with rows in it, against results seeded into the QA lobby's own database. Still unproven on screen: a positive ranked row from a match between two humans (idle browsers cannot decide one), spectating, disconnect/reconnect, switch and shuffle, and a wrong or missing invite token.
