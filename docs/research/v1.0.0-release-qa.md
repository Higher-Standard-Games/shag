# v1.0.0 release QA

A final quality pass before the stable release, on branch `review/v1-qa` in
both repositories (from `staging`, 2026-11-18), across client, server and
bots: performance, data flows, security and anti-cheat, bugs, comment
quality, platform problems and the big picture. It follows the release review,
the papercuts pass and the security review
([v1.0.0-security-anticheat.md](./v1.0.0-security-anticheat.md)), so it
concentrates on what changed since beta.12.2 (about 33,000 lines added across
both repositories) and on the anticheat work merged since.

How it was checked:

- **Measured.** A CPU profile of a two-minute 8-bot S&D match (game server and
  bots in one process); CPU profiles of S&D demo playback in headless Edge on
  WebGPU and WebGL2.
- **Driven in a browser.** Every lobby screen (Play, Campaign, Leaderboard,
  Demos and each settings page) in both renderers, collecting exceptions,
  console errors and failed requests; boot with WebGPU missing and with no
  adapter; the lobby on an emulated touch phone, portrait and landscape.
- **Read.** The anticheat changes (per-client event filtering, spectator
  delay, the backtrack bound, the signed fair-play report) for what a client
  can still learn or claim; comments added since beta.12.2 for history,
  provenance and tracking codes.

## Checked and sound

| Area | Category | Finding |
| --- | --- | --- |
| Server | Performance | The game server's tick (simulation, per-client event filtering, snapshot encode) used about 2% of one core through a 2-minute 8-bot S&D match; the process was 82% idle. Most busy time was the 8 bots decoding snapshots, which in production run in separate match runners. Bot snapshot handling: p50 0.15 ms, p99 0.86 ms. |
| Client | Performance | S&D demo playback held 148–166 fps on WebGPU and 154–165 on WebGL2 (the 165 Hz cap). No new hotspot from this cycle's client work (hit spatter, reel effects, bomb, campaign). The top JavaScript costs are the snapshot replay check (5.6%, trimmed earlier) and Babylon's matrices and binding. `SkinPreparationGate.compare` (1.1%) is an optimisation that skips unchanged bone rebuilds. |
| Server | Data flows / anti-cheat | Spectator delay: one delayed frame per broadcast shared by every spectator; a player who starts spectating sees nothing newer than what they had. |
| Lobby | Security | Fair-play reports: HMAC with its own domain, size limits, only admitted human accounts each once; drop-in seats are added to the same manifest before the match ends, so their counters verify. |
| Lobby | Security | Admin panel (reviewed in the security review): scrypt, rate-limited sign-in, strict session cookie, CSRF, escaped output. Its sign-in from a real browser was fixed separately (`d1b8ec98`). |
| Client | Bugs | Every lobby screen and settings page in WebGPU and WebGL2: no exceptions, console errors or failed requests. |
| Client | Platform | With `navigator.gpu` removed, and with the adapter request returning nothing, the game boots on WebGL2 with no errors. |
| All | Bugs | Typecheck, 6,822 tests, Biome, build, simulation, physics, tick, fuzz (no NaN, deterministic) and `washoi_dm2` load all pass. |

### Firefox, one recording per gametype

Headless Firefox on hardware WebGL2 (ANGLE, Direct3D 11), driven over WebDriver
BiDi. Each recording played 40 s; frame times from `requestAnimationFrame`.
"Hitches" are frames over 80 ms, with their time from the end of the map load.

| --- | --- | ---: | ---: | --- | ---: | --- |
| Duel | washoi_dm14, 3:12 | – | 120 | 6.1 / 24.2 ms | 4 | 0.2 s 145 ms, 2.5 s 97 ms |
| Amphi | washoi_amphi2, 6:09 | 21.5 s | 94 | 6.1 / 54.5 ms | 38 | 0.1 s 101 ms, 0.3 s 139 ms, 1.4 s 133 ms, 11.4 s 85 ms |

| S&D | washoi_snd1, 0:34 | 29.8 s | 91 | 12.1 / 30.3 ms | 0 | none |

- S&D, with the bomb, had no frame over 50 ms: the bomb's material warm-up
  holds in Firefox.
- The hitches in the first 2–3 s follow the map load and are expected.
- FFA's at 6.2 s and 20.6 s and Amphi's at 11.4 s are mid-match, 85–170 ms:
  the size of a first-use shader link in Firefox (no
  `KHR_parallel_shader_compile`). Which effect each is was not profiled. Next
  step if they matter: a Firefox profile (`MOZ_PROFILER_STARTUP`) of the FFA
  recording, looking for `PWebGL::Msg_GetLinkResult` at those moments.
- The FFA recording is 29 s long, so its last 11 s of samples are the ended
  replay; its 63 fps includes that.
- Console warnings seen, all from content, none new in this cycle: glTF skins
  "Failed to find common root" (every mode), washoi_dm7's missing lightmap for
  `textures/lights/neonlamp_2500` and a water batch fallback, and "No look known
  for campaign mission" on two recordings that were campaign missions.

### Flaky tests

Three tests failed once each during the day while the machine was also running
probe browsers and servers, and passed when run alone:

- `CrosshairAmmo.test.ts` › defaults to 32, honors custom sizes…
- `DemosView.test.ts` › times out a missing reply, retries without reopening…
- `LobbyPanelRecovery.test.ts` › retries an outage, deduplicates in-flight attempts…

None reproduced in 8 further runs of the three files under load (a build and a
typecheck running alongside): 24 passing runs each. Their own timing is sound:
the recovery test's retry delay is always exactly 2 s (2 s ± 20 %, rounded).
The likely cause is real asynchronous work (module loading) racing the fake
timers when the machine is busy. Next time one fails, keep its assertion message
before rerunning; that is what was missing here.
