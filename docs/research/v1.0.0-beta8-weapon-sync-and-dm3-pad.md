# DM3 jumppad and Blade-only presentation investigation

Date: 2026-11-08. Scope: server-backed practice Duel on `washoi_dm3`, shared
jumppad extraction and read-only client diagnostics. No weapon rules, developer
gates, loadout grants or snapshot format were changed.

## Confirmed jumppad bug

The compiled BSP contains:

```text
target_push: origin "978 -320 192", targetname "j1_2"
trigger_push: target "j1_2", model "*3"
```

The destination allow-list omitted `target_push`, so extraction warned that
`j1_2` was unresolved and dropped that pad on both server and client. Accepting
the valid point class restores the existing ballistic target path. No movement
constants, trigger bounds or launch calculation change. The other pad already
uses an accepted destination class.

The regression fails before the fix (13 passing, one failing) and passes after
(14 passing). Indexed loading now extracts four triggers: two teleporters and
two pads. With actual DM3 collision, shared movement launched the reported pad
from Babylon position `(1068, -70, -320)` with velocity approximately
`(-124.33, 723.88, 0)`. The target converts to `(978, 192, -320)`.

## Weapon presentation failure: cause not reproduced

The reported session showed Blade in the HUD/model while slot 2 selected Plasma
and fired its projectiles. The session was closed before browser errors or
snapshot state could be captured. This may share the earlier rare Amphi client
state failure, but matching symptoms do not establish a shared cause.

`map` defaults to Duel and starts a real practice server. A fresh
`map washoi_dm3` connection joins and initializes Blade normally. An isolated
Duel server then grants Plasma through the normal `WeaponSystem.addWeapon`
path: snapshots, local inventory, HUD and displayed model all converge on
`plasmagun`. Thus the failure has not been reproduced in a fresh session.

The existing staging `loadout status` diagnostic is restored on this map feature
branch, with additional displayed-model, readiness and switch-state fields.
It reads the last received state without sending a request, choosing a kit,
joining, respawning or granting a weapon. It is available with `developer 0`.
It also reports local/host identity, spectator target and controller agreement.
A recurrence should be captured with `loadout status` before reloading, together
with any `weapon_state`/`GameEvents` browser errors.

The first synthetic keyboard probe did not own play input: neither selection
nor fire reached the server (unchanged authoritative weapon and fire tick).
That failed probe is not a reproduction of the reported bug. The follow-up with
explicit headless play capture passes: slot 1 yields Blade in authoritative state,
inventory, HUD and model; slot 2 yields Plasma in all four. A held fire reduces
Plasma's clip from 50 to 46 and advances the server fire tick. There are no failed
asset requests. This confirms a working control, not the missing original cause.
