# Console improvements — styling, action buttons, hover help

**Branch:** `0.9.24-console-improvements` in both repositories. The console
changes live in the outer repo; the fps submodule also removes the lobby rail's
decorative watermark after it was reported as a visual defect.
**Cycle:** a mini-branch picked up while `docs/research/SHAGGED.md` (the
SHAGGED editor spec) is being written by another agent.

## Why

The debug console (`~`) hasn't been touched since it was built: it uses its
own hand-picked colors (`UIStyles.consoleColors`, `debug-console.css`)
instead of the Washiki theme the rest of the UI (`GamePanel`, HUD, lobby)
has used since v0.9.17. Next to the main menu it looks like a different
product. It also has only one action button (`inspect`), and `help` output
lists commands as plain clickable text with no way to see a command's usage
without running `help <command>` separately.

## Current state (read before changing)

- `src/engine/debug/DebugConsole.ts` (1062 lines) — the whole console: DOM,
  history, autocomplete, logging, built-in commands (`help`, `clear`,
  `version`, `con_size`, `find`, `log_history`). `AGENTS.md` and
  `src/engine/README.md` call this `ConsoleSystem`, but no such class
  exists — `DebugConsole` and `CommandRegistry` are the real names. Not in
  scope here; noted for whoever next touches `docs/manual/guides/console-system.md`.
- `src/engine/debug/debug-console.css` (330 lines) — console-only styles,
  reading CSS vars (`--console-primary`, `--console-bg`, …) that
  `UIStyles.getConsoleStyles()` injects from a private `consoleColors`
  object (`src/engine/ui/UIStyles.ts:135`). That object is its own palette
  (teal `#2EC4B6`, SHAG-logo accent colors), unrelated to `--w-*`.
- The main UI's real theme is `WashikiTheme.css` (3878 lines): `--w-cyan`,
  `--w-magenta`, `--w-gold`, `--w-bg`/`--w-bg-panel`, `--w-border`,
  `--w-font-display` (Orbitron), `--w-font-body` (Rajdhani), the
  `--w-glow-*` box-shadows, and the `--w-shadow-print-*` offset-shadow
  "manga print slab" look used by `GamePanel.css` and `Button.css`.
- 74 command classes extend `Command` (`src/engine/console/commands/`); 66
  set `usage`, 29 set `subcommands`, 27 are `developer: true`-gated. Each
  has a `description` and most a `usage` string — enough to build a real
  tooltip from existing metadata, no new per-command authoring needed.
- `CommandRegistry.getHelp(name)` already renders the same text `help
  <command>` prints. `DebugConsole`'s `help` output already tags each name
  as `<span class="clickable-cmd" data-cmd="...">` (click re-runs or opens
  help) — the hook point for hover help already exists, it is just unstyled
  and has no hover behavior.
- Chat/log text that reaches the console is either escaped
  (`formatMessage`'s `escapeHtml`) or server-sanitized to printable ASCII,
  capped at 128 chars (`GameServer.handleChat`) before it is logged — so a
  hover-help feature reading `data-cmd` values (registry keys, never player
  text) has no injection surface to worry about.

## Bigger tasks (backlog, not done this branch)

- **`ConsoleSystem` naming**: `AGENTS.md` and `src/engine/README.md` both
  document `ConsoleSystem.getInstance().execute(...)`, which doesn't exist.
  Real API: `CommandRegistry.getInstance().execute(...)` plus `DebugConsole`
  for the UI. Fix belongs to whoever next reads `console-system.md` (see
  `docs/research/v0.9.24-QA.md` WO-1, already marked done — this slipped
  through).
- **Resizable by drag**, not just the `con_size` command/button cycle — a
  drag handle on the console's bottom edge.
- **Inline cvar controls**: `cvarlist`/`help <cvar>` output could render a
  small slider/toggle next to range or boolean cvars instead of only text.
- **Command palette overlay**: a fuzzy-search launcher (like a browser's
  command palette) separate from the history-driven single-line input, for
  discovering commands without knowing their name.
- **Scroll-to-bottom indicator** when the user has scrolled up in the
  output and new lines arrive.
- **Light/dark**: `UITheme` already supports light/dark; the console is
  always dark. Worth deciding once, not for this mini-branch.

## Testing note

`vitest.config.ts` sets `environment: "node"` globally; a handful of tests
opt into DOM per-file with a `// @vitest-environment jsdom` pragma
(`src/engine/console/__tests__/BindCommands.test.ts` is the existing
precedent for a console-adjacent DOM test). The new `DebugConsole` DOM test
follows that pattern rather than changing the global environment.
