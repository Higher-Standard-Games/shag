# Arc Blade model integration

Branch: `v0.9.31-arc-blade` in engine and FPS. The FPS repository has no changes;
the weapon definition currently lives in the engine's shared entity definitions.

Input: Desktop `neo-arc_blade__sci-fi_energy_sword.glb`, 2,271,388 bytes. Runtime
name/path: Arc Blade, `models/weapons/blade/arc_blade.glb` in `z_weapons.pk3`.
The source contains one mesh with 1,497 vertices, four embedded PNG textures,
and no animation clips. Its PBR material includes normal, metallic/roughness,
emission, and `KHR_materials_emissive_strength` with authored strength 10.
Author/license metadata identifies SURVIVED and CC BY 4.0; it is retained and
included in the package manifest with the source link and transformation note.

`scripts/import-arc-blade.mjs` adds an export-space parent instead of re-encoding
meshes or textures. It maps the source's long Z axis to the previous export's
X axis, aligns its broad face and centre, and rolls the cutting edge outward
around the long axis. Uniform scale is
0.1313852484276723. Both exports have length 2.002558370374091 model units,
approximately 60.08 at view-model scale 30. Width/thickness retain the new
model's proportions. World/pickup scale and first-person offset/rotation remain
the existing values. Combat values are unchanged.

The old blade-specific PBR-to-unlit-Standard conversion discarded normal and
metallic channels. The new first-person path preserves the supplied PBR
material and authored emission, with the existing safe weapon light cap.
The export is aligned to the established blade axes, so the existing carry
orientation and procedural swing/charge systems can be reused.

Media inputs and packages are Git-ignored and must be distributed separately.
Original source: `assets-source/weapons/arc-blade/arc_blade.glb`.
Normalized export: `assets-source/weapons/exports/blade/arc_blade.glb`.
The old export is retained as the normalization reference. A copy of the prior
runtime bank is at `.cache/media-backups/z_weapons-before-arc-blade.pk3`.

## Charge and lighting follow-up

The metallic blade was nearly black under hemispheric fill, which has no
specular contribution. A camera-relative directional light (intensity 3) is
restricted to the active Blade meshes. Its diffuse/specular colours use the
existing smoothed BSP lightgrid sample and visibility floor. It takes priority
over hemispheric fill within the existing material light budget; no extra world
lights or per-frame traces are introduced. Other weapons disable this light.
The imported metal/roughness, normal and cyan emission channels stay intact.
A 16-pixel mipmapped neutral cube supplies ambient metal reflections, tinted
through the material's reflection colour by the same BSP sample. This texture
belongs to the weapon view and is disposed with it; scene environment settings
are unchanged. NullEngine skips the GPU cube allocation.

The charge outline grows from 0.6 to 1.6 units (twice the previous width),
normalized by view scale, and pulses turquoise. The swing ribbon is light grey;
its peak alpha is 0.22 instead of 0.7, with a bilinear 64×32 opacity envelope
that fades all edges to transparent. Geometry and fade duration are unchanged.
Each trail owns and disposes its feather texture. Combat rules remain unchanged.
The charged projectile light, tail, cached Standard-material body, impact burst,
weapon release flash and pickup glow use teal. Blade flashes last 0.16 seconds
(up from 0.08); its view flash light decays at half its previous rate. Melee
swings also emit a smaller flash at the model's tip, jittered within four screen
pixels. The tip is found once on cold model import using the normalized blade's
long X axis, then stored as a cloned child socket. Projection follows weapon
and world camera FOV; charged projectile release keeps one central flash.

## Projectile mask and charge growth correction

The teal projectile tint originally added a constant emissive contribution to
an additive material, illuminating the entire underlying polygon. Both MD3
surfaces embed texture names; their original shaders use `blendFunc add`.
The orange-on-black images are now RGB opacity masks for the teal emissive
colour. The material has no unmasked emissive texture, uses additive alpha
blending and disables depth writes. Texture edges clamp to prevent repeated
glow when the original UV animation rotates. Material configuration waits for
the MD3 texture-load promises before moving the loaded image to the mask slot.

The charge outline starts at the same 0.6 units and grows linearly to 4.8 units,
three times the previous full-charge width of 1.6. At view scale 30 the final
mesh-space width is 0.16; both GPU backends reported this value.

## Forward-only step-in dash

The server queues the 48-unit step-in only when an accepted Blade primary
swing has forward input, no simultaneous back input, and horizontal velocity
projected along view yaw greater than 0.001 units/second. The tiny tolerance
rejects floating-point noise when movement is perpendicular to rotated views.
Forward diagonals qualify. Coasting without forward input, standing still,
sideways-only movement, backward motion and vertical-only movement do not.
Swing acceptance, damage timing, cooldown and collision-clamped dash execution
are unchanged. Eligibility is sampled at swing acceptance.

Assumptions: the rule applies both on the ground and in the air; view pitch and
vertical velocity do not determine forward movement. The existing server owns
the displacement; this introduces no predicted movement or protocol fields.
Live network feel has not been manually checked. Running game server processes
need the updated code to use the rule.
