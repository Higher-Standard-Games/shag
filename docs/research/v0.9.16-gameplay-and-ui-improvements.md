## WO-1 — Fall damage (`sv_falldamage`)

### Spec (confirmed with design)

Drop distance measured in **map units** (BSP units). Note: the engine renders BSP geometry 1:1 — world units ARE map units (movement constants like jumpVelocity 320 / player bounds −24..+32 are Q3-scale; `MapRenderer` swaps Y/Z axes but applies no scale). One acceptance step below verifies this with a trace.

| Drop distance | Effect |
|---|---|
| < 128u | No damage |
| 128u → 256u | Damage ramps linearly 0 → 100, applied **through the normal damage pipeline** (armor absorbs its usual share, like taking a 100-damage shot) |
| 256u → 384u | "Crush" band: player is left at **exactly 1 HP and 0 armor**, regardless of current HP/armor |
| ≥ 384u | Instant kill — a self-frag (obituary attributes the death to the faller) |

**Crouch-softened landing (confirmed by design):** holding CROUCH at the landing tick subtracts a soften margin from the effective drop before the band lookup: `effectiveDrop = drop − sv_falldamage_crouchsoften` (default **64u**). This makes it a skill mechanic across every band — a 300u crush-band fall crouch-lands as a ~236u ramp hit, and a 400u lethal fall crouch-lands in the crush band at 1 HP instead of dying. The input is already on the server (`InputButtons.CROUCH` on the landing tick's command); no client work needed.

Toggle: **`sv_falldamage`, default `1` (enabled)**. Optionally expose the thresholds as cvars (`sv_falldamage_min` 128, `sv_falldamage_full` 256, `sv_falldamage_fatal` 384, `sv_falldamage_crouchsoften` 64) — nice for tuning, not required for v1 except `crouchsoften` (needed to tune the new mechanic).

### Where it goes (verified against source)

- **Landing detection — server:** [FPSMovementSubsystem.ts](src/games/fps/server/systems/FPSMovementSubsystem.ts) already tracks airborne state per entity for diagnostics (`jumpStartTick`/`jumpStartY` maps, the "just went airborne / just landed" blocks after the sim step). Extend that block: while airborne track **peak Y** (not start Y — a jump that rises then falls should measure from apex); on the grounded transition compute `drop = peakY − landingY` and hand it to the damage path. This automatically does the right thing for ramps (a player sliding down a slope never goes airborne → no damage) and ledge grabs (grab teleports to ledge top; drop measured to the landing point is small).
- **Damage application:** [CombatSystem.ts](src/games/fps/server/systems/CombatSystem.ts) `queueDamage(DamageEvent)` → `processDamage` → `applyDamage(health, dmg, armorAbsorption)` ([HealthComponent.ts](src/shared/server/simulation/components/HealthComponent.ts): armor soaks `min(armor, damage × 0.66)`, rest hits HP). Add a `DamageType.FALLING` (check the existing `DamageType` enum) and emit with `attackerId = victimId` so the death pipeline registers a self-frag and the HUD/killfeed can say "X fell to their death".
- Band implementation notes:
  - **128–256:** `damage = 100 × (drop − 128) / 128`, `armorPiercing: 0` — plain pipeline, nothing special.
  - **256–384:** do NOT try to reverse-engineer a `damage` number through the 0.66 absorption math — it cannot express "exactly 1 HP + 0 armor" for all HP/armor combos (e.g. HP 5 / armor 200 kills the player). Handle `DamageType.FALLING_CRUSH` explicitly in `processDamage`: set `health.armor = 0; health.health = min(health.health, 1)` (never *heals* a player already at 1), still emitting the damage event with the actual HP+armor lost so HUD pain flash / stats stay truthful.
  - **≥384:** `damage = 9999, armorPiercing: 1` → guaranteed kill through the normal death path.
- **Cvar:** engine cvar table is [MovementVars.ts](src/engine/movement/MovementVars.ts) (outer repo — see `sv_slide*` block for the exact registration pattern). `sv_falldamage` default `1`. The subsystem reads it the same way `sv_slide` is read.
- **Client feel (already exists, verify only):** [LandingImpactEffect.ts](src/engine/viewport/effects/LandingImpactEffect.ts) gives the camera dip; damage/death arrive via the normal snapshot/event flow. No client prediction of fall damage in v1 (damage is server-authoritative; a 1-snapshot delay on the pain flash is acceptable).

### Watch out for

- **Respawn/teleport:** clear the airborne peak tracker on spawn/teleport events, or the first landing after a respawn-in-air measures a bogus drop. There is a `forceTeleportOnNextSnapshot` concept client-side; server-side, reset tracking where the respawn positions the entity.
- **Knockback + jump pads:** rocket-jump falls SHOULD deal fall damage (Warsow-like). No special case.
- **Determinism:** peak tracking must live in per-entity maps inside the subsystem (like `jumpStartY`), not module state — `server:tick`/`server:fuzz`/demo re-sim must stay green. Add a `FallDamage.test.ts` next to [FixedRatePhysics.test.ts](src/games/fps/server/__tests__/FixedRatePhysics.test.ts) using the same synthetic-sim harness: spawn airborne at controlled heights, tick to landing, assert the four bands (no damage / ramp value / 1HP+0armor / dead), and `sv_falldamage 0` disables all of it.

### Acceptance

1. Unit tests for all four bands + toggle + crouch-soften (same drop with/without CROUCH held lands one band softer) (headless, no map needed).
2. Trace check that 1 world unit == 1 BSP unit (drop a player from a known map height, log the measured drop, compare against the map editor value) — adjust thresholds by scale factor if this ever fails.
3. Browser: drop from a ledge >384u → death + self-frag obituary; 300u drop → 1 HP + 0 armor; small hops → nothing.

**Files:** fps submodule `server/systems/FPSMovementSubsystem.ts`, `server/systems/CombatSystem.ts`, new test; outer `src/engine/movement/MovementVars.ts` (cvar), possibly killfeed string in the fps HUD.
**Model:** Sonnet 5. Clean spec, existing patterns to copy, testable headlessly.

## WO-2 — GL ballistics ("grenades don't fly far, gravity too high")

### Evidence (this is another tick-fix leftover, as suspected)

- Server grenade ballistics live in [ProjectileSystem.ts](src/games/fps/server/systems/ProjectileSystem.ts): `velocity.y -= 800 × meta.gravity × dt`, `BOUNCE_FACTOR = 0.45`, dt plumbing verified correct (Simulation at 125 Hz passes dt = 0.008 every tick; the subsystem accumulator math is exact).
- The **tuning numbers are compensation artifacts**: [glauncher.ts](src/shared/entities/definitions/weapons/glauncher.ts) has `projectileSpeed: 1704` and `projectileGravity: 3` → **2400 u/s² gravity**. Git history: `projectileGravity: 3` was introduced while the server effectively ran ~62.5 Hz (commit `a83327e`, F6); commit `afebe02` ("post-timing-fix tuning", May 31) then multiplied speeds ×0.7 when the server was corrected to true 125 Hz — but **left gravity at 3×**. Ballistic range scales as v²/g: cutting v by 0.7 while keeping g tripled collapses the arc. Reference: Warsow GL (which these defs cite as their source) is speed ≈ 900, gravity ≈ 850 (≈ 1.06×800), timeout 1250 ms.
- **Server/client def divergence** (secondary bug, fix in the same WO): the server uses WeaponDef (`speed 1704, gravity 3, lifetime 2.0` hardcoded in [WeaponSystem.ts:1310](src/games/fps/server/systems/WeaponSystem.ts#L1310), bounce 0.45), while the client-side visual def [grenade.ts](src/shared/entities/definitions/projectiles/grenade.ts) says `speed 1000, gravity 1, lifetime 1.25`, and [ProjectileManager.ts](src/engine/weapon/ProjectileManager.ts) uses `bounceFactor 0.65`. Server-driven rendering hides most of it, but any client-side path (orientation, demo tools, future prediction) disagrees with the server.

### Plan

1. **Single source of truth:** move grenade ballistics (speed, gravity multiplier, lifetime, bounces, bounce factor) into the shared `ProjectileDef` (`grenade.ts`) and make the server (`WeaponSystem.fireProjectile` registration + `ProjectileSystem`) read from it. Delete the hardcoded `lifetime: 2.0` / `bounces: 3` in WeaponSystem and `bounceFactor` duplicates.
2. **Retune to Warsow baseline:** start at `speed 900–1000, gravity 1.05 (≈840 u/s²), lifetime 1.25–1.5 s, bounce 0.45`. User request: try **slightly slower speed** than the current effective feel — begin at 900 and iterate.
3. **Live tuning loop:** expose the values as cvars (`sv_gl_speed`, `sv_gl_gravity`, `sv_gl_lifetime`, `sv_gl_bounce`) or a `weapontune glauncher <field> <value>` console command so the feel pass doesn't require rebuilds. Keep the cvars dev-only if desired; the def values are the shipped defaults.
4. **Headless range measurement:** small CLI/test that spawns a synthetic sim, fires a grenade at 0° and 45° pitch, ticks to explosion, prints travel distance + bounce count. Lock the tuned numbers in as a regression test (range within ±10%).

### Acceptance

- 45° grenade travels ≈ v²/g ≈ 950–1100u before first bounce on flat ground (matches Warsow feel).
- Bounces look lively, not "sticky" (gravity no longer triple-crushing the rebound).
- Grenade explodes on timeout at the def's lifetime; server and client defs report identical numbers (one assertion test).
- Regression suite green (projectile system is server code).

**Files:** outer `src/shared/entities/definitions/weapons/glauncher.ts`, `.../projectiles/grenade.ts`; fps submodule `server/systems/WeaponSystem.ts`, `server/systems/ProjectileSystem.ts`; optional cvar wiring; new range test.
**Model:** Sonnet 5. Mechanically simple; flag clearly in the handoff that final numbers need a human browser feel-pass.

## WO-3 — Ghost pickup models (visible, floating, not pickable)

### How the system works today (verified)

- Map pickups are **server-authoritative via a full-state mask**: server [PickupSystem.ts](src/games/fps/server/systems/PickupSystem.ts) keeps `PickupItem[]` built from the shared table (`extractPickups`), and every snapshot carries `pickupActiveMask` (NOT PVS-filtered — [SnapshotBroadcaster.ts:133](src/games/fps/server/SnapshotBroadcaster.ts#L133)). Client applies it each snapshot: [GameEvents.ts:133](src/games/fps/client/GameEvents.ts#L133) → [FPSPickup.reconcileActiveSet](src/games/fps/world/FPSPickup.ts#L215) → `pickupById.get(id)?.setActiveState(mask[id])`. Design doc: SERVER_AUTHORITATIVE_PICKUPS.md.
- Client visuals are created by [EntityManager.spawnEntity](src/engine/entities/EntityManager.ts#L127) from BSP entity handlers, and matched to server ids **fuzzily**: `pickupTable.find(classname === def.classname && |ΔX| < 0.5 && |ΔZ| < 0.5)` → `pickupId` ([EntityManager.ts:170-178](src/engine/entities/EntityManager.ts#L170-L178)).
- Dropped weapons are a separate, entity-snapshot-driven renderer ([DroppedWeaponRenderer.ts](src/games/fps/client/DroppedWeaponRenderer.ts)) — lifecycle converges every snapshot and is a less likely ghost source.

### Ranked hypotheses (all silent today — that's the real problem)

1. **`pickupId === undefined` → permanent ghost.** If the fuzzy match fails, the FPSPickup is created WITHOUT an id, never lands in `pickupById`, and is **never reconciled** — it renders forever, and the server (which may not even track it) never grants the pickup. Zero warnings logged. Failure feeds:
   - classname present in `EntityRegistry` handlers but **not** in `PICKUP_CLASSNAMES`/`CLASSNAME_TO_WEAPON` ([PickupTable.ts](src/shared/bsp/PickupTable.ts)) → client spawns a visual for an entity the server-side table skipped entirely;
   - coordinate/rounding drift beyond the 0.5u window (suspended items, `origin` with decimals, duplicate items of the same class near each other picking the wrong entry);
   - anything spawned via `spawnEntityById` (console `spawnpickup`) — that path passes **no pickupId at all** and no `serverManagedRespawn` → intentionally client-local, but in a networked game it is a guaranteed ghost.
2. **Mask/registry index disagreement.** `reconcileActiveSet` iterates mask indices; client pickups with ids the mask doesn't cover (or vice versa) silently no-op. Any divergence between server `extractPickups(entities)` input and the client's (different BSP entity parse, gametype filtering applied on one side only) shifts or truncates the id space.
3. **State-toggle races around async loads and rAF deferral.** One race is already patched (model finishing load after `setActiveState(false)` — [Pickup.ts:232-238](src/engine/world/Pickup.ts#L232-L238)). But [onPickedUp](src/engine/world/Pickup.ts#L386) defers its visual disable to `requestAnimationFrame` — a reconcile flipping the state between call and callback leaves visuals contradicting `isActive` (that direction produces *invisible-but-pickable*, the mirror image; both are state-desync symptoms worth closing).
4. **Dropped-weapon edge:** `DroppedWeaponVisual.loadModel` is async with a disposal guard that looks correct; lower priority, but the soak test below covers it too.

### Plan — instrument first, then fix

1. **Instrumentation (do this before any fix):**
   - Console command `pickup_audit`: dump every client `FPSPickup` (name, classname, position, `pickupId`, `isActive`, mesh enabled?) alongside the latest received mask; flag any pickup with `pickupId === undefined`, any mask index with no client pickup, and any `isActive` ≠ mesh-enabled mismatch.
   - `console.warn` at creation time when the fuzzy id match fails (EntityManager) — this alone probably identifies the ghost on the next repro.
   - Optional: dev overlay billboard "NO-ID" above unmatched pickups (`developer 1` only).
2. **Structural fix (recommended direction):** stop re-deriving the pickup set client-side. The client should **iterate the shared `extractPickups` table directly** (it already computes it in the pre-render hook!) and spawn one FPSPickup per entry with the table's exact id — the BSP entity handler path then only covers non-tracked decorations/ammo. This makes an id mismatch structurally impossible instead of fuzzy-matched.
3. Make `reconcileActiveSet` defensive: count and (dev-mode) log unknown ids in the mask and registered pickups never covered by the mask.
4. Close the rAF race: `onPickedUp` visual changes should check `isActive` again inside the callback (or drop the rAF deferral for server-managed pickups — `setActiveState` already toggles instantly).
5. Decide the ammo-box story explicitly (they're client-local today — either server-track them or make the local pickup actually grant ammo in networked mode; currently they may be cosmetic ghosts by design).

### Acceptance

- `pickup_audit` clean (no undefined ids, no mask orphans, no visual/state mismatch) after: map load, 10 min bot soak with pickups+drops, a late join, and a gametype with item filtering.
- Scripted repro attempt: consume every pickup with a bot loop while a second client joins late — no floating unpickable models.
- Regression suite green + `PickupTable` determinism tests still pass.

**Model:** **Fable 5** (Opus 4.8 minimum). Intermittent, cross-layer (BSP parse → shared table → server mask → client registry → async visuals), and the fix requires judgment about restructuring vs patching. Instrumentation-first discipline matters more than raw speed here.
